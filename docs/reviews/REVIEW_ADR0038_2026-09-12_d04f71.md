## 总评

**Needs-revision**（方向成立，v0.2 需修订若干处事实与不完备处；D1/D2/D3/D7 的决策方向无需改动）

ADR 的核心判断——「用完的主机没有终态」是问题本质、`retired_at` 与存活正交、
删除与退役分家、不做带历史硬删——核对代码后成立且必要：DELETE 预检
（`backend/api/routes/hosts.py:465-554`）确为「非 ONLINE + 无活跃 Job + 无历史依赖」，
且心跳对缺失行会按 id/IP 重建（`backend/api/routes/agent_api.py:806-814`、
`backend/api/routes/heartbeat.py:196-221`），删除/退役分家不是过度设计。

需要修订的原因不是方向，而是三类可核验的偏差：

1. **D4/不变量 3 依赖的「现有告警去重惯例」在 host 级事件上不存在**（F3-01）：
   通知服务的去重身份对无 `run_id` 的上下文直接早退，SAQ 去重键也不含 `host_id`；
   「单次告警」按 v0.1 字面无法实现，也无法按 F7 要求测试。
2. **D5 的过滤面清单不完整**（F2-01）：ADR 列出的五面之外，另有扫描/归档扇出、
   预检 SSH 同步、批量热更新脚本、AI 助手工具、观测面（Prometheus/dashboard/
   file-server）、设备联动、控制命令与会话面（reload-config / 升级门禁 /
   Socket.IO 房间）、前端判定面八类真实面，均以 `ONLINE` 或全表扫描为判据；
   按 v0.1 字面实现会让不变量 1 在这些路径上失守（多数在「活体退役」场景可观测）。
3. **事实性错误**（F5-05）：§4 称 `api.hosts.remove`（`hosts.ts:25`）无 UI 调用点——
   该方法实际名为 `delete`，且 HostsPage 有单条与批量两个调用点；
   实现单若据此决定删除该方法会直接破坏现有 UI。

以上修订都是文本与落点级，不触及 D1/D2/D3/D7 的决策方向。建议 v0.2 收敛后转 Accepted。

## F1 语义完备性

### F1-01【建议】退役与 QUEUED PlanRun 的交互未定义，前置「无活跃 Job」覆盖不到排队中的计划

- 证据：ADR D2（`docs/adr/ADR-0038-host-retirement-semantics.md:62-66`）前置只有
  「非 ONLINE + 无活跃 Job」；活跃 Job 判据为 `PENDING/RUNNING/UNKNOWN`
  （`backend/services/host_upgrade_gate.py:44-48`）。而 ADR-0026 不变量①明确规定
  QUEUED 的 PlanRun **不得存在任何 JobInstance 行**（`docs/adr/ADR-0026-plan-execution-scaling.md:103-105`），
  目标设备清单固化为 `plan_run_target_device`。因此一台已被 QUEUED 计划引用的主机
  （其设备在目标清单里）可以在「无活跃 Job」的前提下被退役，退役时不会有任何提示。
- 后续行为：准入时 `backend/services/admission_pump.py:666-675` 只会把
  `host_offline` 归类为**可重试**（`DEVICE_BUSY`，回 QUEUED），
  即该 PlanRun 会一直排队等待一台永不回来的主机；ADR-0026 的不变量④
  （`docs/adr/ADR-0026-plan-execution-scaling.md:131-138`）没有覆盖「主机已退役」
  这一**运维决定型**不可用。
- 落点建议：D2 或新增 D8 明确二选一——(a) 退役前置增加「无 QUEUED PlanRun 引用」
  （与 DELETE 的 PlanRunHost 预检同族，`hosts.py:524-533`），或 (b) 明确允许退役，
  并在 D5 指定准入裁决为新 reason（如 `host_retired`）按不可重试处理、PlanRun 明确失败
  并给出可操作提示。二者都要写清，不能留给实现单。

### F1-02【建议】「退役要求先停 Agent」与实际判据不符，判据是代理条件

- 证据：ADR §4 运维代价写「退役要求先停 Agent（非 ONLINE 前置）」
  （`docs/adr/ADR-0038-host-retirement-semantics.md:118-119`），D2 的实际判据是
  `status != ONLINE`。`status` 的心跳超时归零由周期任务
  （`backend/tasks/session_watchdog.py:37-48`，`backend/scheduler/app_scheduler.py:32` 默认 15s
  周期）与读路径的 `_ensure_host_status_up_to_date`（`backend/api/routes/hosts.py:56-81`）
  维护，**非 ONLINE 只证明控制面近期没收到心跳**，不证明 Agent 进程已停：
  网络分区、Agent 假死、心跳超时窗口（默认 300s）内都会出现「进程还在、判据已满足」。
  这正是 D4「活体退役」场景的来源，ADR 已在 D4 承接，但 §4 的表述会让人误以为
  前置证明了 Agent 已停。
- 落点建议：§4 运维代价改为「退役前置是 stop-agent 的代理条件（status 非 ONLINE），
  不构成证明；活体退役由 D4 承接」，并把前置的时效性（15s watchdog + 300s 心跳超时）
  写进 D2 说明，便于实现单决定是否在 retire 路径内先刷新状态。

### F1-03【建议】unretire 对 `retired_by`/`retire_reason` 的写回语义未定义

- 证据：D2 只写「unretire 无前置」（`docs/adr/ADR-0038-host-retirement-semantics.md:62-66`），
  D1 三列为可空（`:58-61`），但没写 unretire 时是清空三列还是保留最后退役痕迹。
  两种语义对「谁最后把机器退掉、为什么」的现场可读性差别很大（审计在
  `AuditLog`，但读主机详情看不到）。
- 落点建议：D2 补一句明确写回（推荐：`retired_at` 清空、`retired_by`/`retire_reason`
  保留为最近一次退役痕迹，并在字段注释与 UI 上说明），或明确清空全部并指向审计。

### F1-04【观察】维护窗口/维护租约不在退役前置内

- 证据：热更新期间主机处于维护窗口 `host.maintenance_until`
  （`backend/services/host_maintenance.py:78-110`，模型 `backend/models/host.py:57-58`），
  设备侧还可能有 MAINTENANCE 类型租约；退役前置（`hosts.py:481-500` 同族判据）两者都不检查。
  影响有限：热更新要求 ONLINE（`hosts.py:614-618`），窗口通常随 `end_host_upgrade`
  释放；窗口残留时退役后派发已被排除，unretire 回来窗口多半已过期。
- 落点建议：不必新增前置，建议在 D2 显式写「维护窗口/维护租约不作为退役前置，
  原因：窗口是瞬时调度态且退役后派发面已收口」，避免后续评审反复提出。

## F2 过滤面穷尽性（D5 不变量）

### F2-01【建议】五面之外另有六类遗漏面（附 file:line）

D5 列了五面（派发快照 / claim / 统计容量 / 默认列表 / 控制面动作，
`docs/adr/ADR-0038-host-retirement-semantics.md:75-78`）。逐点核对后，遗漏如下：

1. **PlanRun 扫描/归档扇出**（`plan_run_scan_scope`）：`iter_plan_run_scan_hosts`
   （`backend/services/plan_run_scan_scope.py:113-122`）返回 `(host_id, status)`，
   五个调用点全部只判 `status == "ONLINE"`：
   `backend/api/routes/plan_runs.py:549-566`（archive_now + scan_now）、
   `backend/api/routes/dedup.py:464-471`、`backend/tasks/saq_tasks.py:313-324`、
   `backend/services/ai_assistant/plan_run_ops.py:391-406`（两处）、
   以及 `plan_run_ops.py:139-144` 的只读查询。退役但仍心跳（ONLINE）的主机会继续
   收到 scan_now/archive_now 下行命令。
2. **预检 SSH 同步**：`backend/services/precheck/runner.py:189`（`push_mismatched_scripts`）、
   `:216`（`sync_host_via_hot_update`）→ `backend/services/precheck/sync.py:68-105`/`:107+`，
   两函数只判 `host` 存在、有 IP、有 SSH 凭据，**无任何状态判据**；
   准入侧同样调用 `backend/services/admission_pump.py:497-557`。退役主机可能被 SSH
   推送/重启 Agent。同族的还有 `POST /agent/logs`（`backend/api/routes/logs.py:244-262`，
   agent-secret 鉴权，按 `host_id` 加载 Host 后 SSH `exec_command` 远程 tail 日志，
   同样无状态判据）。
3. **批量热更新脚本**：`backend/scripts/batch_hot_update.py:90-95` 直接
   `Host.status == "ONLINE"` 选目标，独立于 API 路由的
   `POST /hosts/{id}/hot-update`（`backend/api/routes/hosts.py:610-618`，同样只判 ONLINE）。
   ADR 的「批量刷新」若指该脚本，需要在 D5 点名；否则只改路由会漏。
4. **AI 助手**：`backend/services/ai_assistant/orchestrator.py:670-690`

### F2-02【建议】退役主机的派发裁决（fatal vs 可重试）未指定

- 证据：派发可用性分类的阶梯在 `backend/services/plan_dispatcher_sync.py:143-160`

  （`:68-69`）。准入侧对非 fatal 一律按可重试排队
  （`backend/services/admission_pump.py:666-675`：`_RetryableAdmission("DEVICE_BUSY")`）。
  退役主机若照 `host_offline` 处理，会排到永远；若照 fatal 处理，PlanRun 直接失败。
  D5 只说「不进入派发快照」，没有给出裁决。
- 落点建议：D5 增加一句裁决语义（建议：新增 reason `host_retired`，归入**不可重试**，
  并在准入失败详情里回带 host_id 与 unretire 指引），同时点名落点函数
  （`_classify_dispatch_devices_sync` + `_FATAL_DISPATCH_REASONS` + 准入侧），
  使 F1-01 的 (b) 方案可实施。热更新/升级一侧建议把判据放进
  `begin_host_upgrade`（`backend/services/host_upgrade_gate.py:229-231`）这一共享收口点，
  而不是逐个路由。

### F2-03【观察】`GET /hosts` 默认隐藏是既有端点语义变更，消费者面需说明

- 证据：`list_hosts`（`backend/api/routes/hosts.py:340-362`）当前返回全部主机，
  且无分页参数时返回裸数组（`:359-361` 兼容分支）。前端消费者包括
  `frontend/src/utils/api/hosts.ts:33-34`（`fetchHostList`）→ HostsPage、DevicesPage、

  设备页按主机分组时看不到退役主机（其设备行按 D6 保留），也会改变计划配置页的
  主机候选集。这两处大概是期望行为，但需要 ADR 明确，而不是留待实现单猜测。
- 落点建议：D5 或 §4 前端面补一句：默认隐藏的消费者面清单 + 设备页对
  「退役主机下的设备」的呈现口径（保留分组并打标 vs 归入历史）。

## F3 心跳策略（D4）

### F3-01【建议】「沿用现有告警去重惯例」不成立，需指定持久去重载体

- 证据：通知服务的通用去重在 **无 `run_id` 的上下文直接早退**
  （`backend/services/notification_service.py:342-344`；去重身份为
  `(event_type, run_id, task_id, device_serial)`，`:329-336`），
  SAQ 去重键同样只拼 `run_id`/`device_serial`（`:649-654`）——host 级事件
  （无 run_id）既不去重，还可能在同一 `notif:<event>:None:` 键上互相压制。
  `EventType` 目前只有四个值（`backend/models/notification.py:16-20`），
  新增事件类型需要模型枚举 + API `Literal`（`backend/api/schemas/notification.py`）+
  前端 union（`frontend/src/utils/api/types.ts`）与告警规则迁移端到端同步。
  ADR 不变量 3（`docs/adr/ADR-0038-host-retirement-semantics.md:114-115`）写
  「沿用现有告警去重惯例」，按现状无处可沿。
- 落点建议：D4/不变量 3 指定去重载体，推荐复用现有**先落盘后派发**的持久标记模式
  （`backend/services/plan_run_aggregation.py:98-147` 的
  `run_context.risk_high_notified` + 行锁 + commit 后再 dispatch），
  host 侧载体建议 `host.extra` 下一枚显式命名 flag（注意与 ADR-0025 占用的
  `extra['archive']` 区分，`agent_api.py:3159-3175`），并写明为何不新增列/表。

### F3-02【观察】「状态震荡」边沿未定义，决定 F7 的可测性

- 证据：不变量 3 写「只响一次，除非状态震荡——沿用现有告警去重惯例」
  （`docs/adr/ADR-0038-host-retirement-semantics.md:114-115`），但没定义
  「震荡」的判据（心跳中断后再恢复？`boot_id` 变化？Agent 版本变化？），
  也没定义告警与 UI 徽标的清除条件（unretire 时清？心跳停止时清？）。
- 落点建议：与 F3-01 一并给出边沿定义（建议：以「退役状态下首次出现心跳」为触发边沿，
  同一退役周期内只告警一次；`boot_id` 变化视为新周期、重新告警），
  并写明徽标显示条件（`retired_at IS NOT NULL ∧ status=ONLINE`）。

### F3-03【观察】不拒绝心跳的取舍成立；建议把中间选项记入备选

- 证据（支持 v0.1 取舍）：Agent 对心跳非 2xx 只记日志并返回 None
  （`backend/agent/heartbeat.py:83-91`），心跳响应同时承载
  `script_catalog_outdated`、`heartbeat_interval_seconds`、`backpressure.log_rate_limit`
  与版本门禁（`backend/agent/heartbeat_thread.py:345-390`）；
  若对退役主机回 409，会同时打断 backpressure 与版本门禁回路，
  且控制面失去 `last_heartbeat` 续期，反而看不清「活体退役」。D4 的取舍有据。
- 缺口：§3 只否决了 409（`docs/adr/ADR-0038-host-retirement-semantics.md:101-103`），
  没有讨论**响应内加 `retired: true` 标志**这一向后兼容的中间选项
  （Agent 可据此自收敛：停 watcher/patrol、停止本地扫描，但不制造失败模式）。
  当前 Agent 侧消费的响应字段是加法兼容的（`heartbeat_thread.py:361-390` 按 key 取值），
  改动成本低。
- 落点建议：§3 备选里补一条「退役标志随心跳响应下发（Agent 自收敛）」的取舍记录；
  若确定不做，写明理由（例如 Agent 侧无对应动作、退役主机本应已停）。

## F4 身份与换机（D6）

### F4-01【建议】「同 IP 换机 = 同一身份」的命中边界需写成契约

- 证据：`allocate_host_id` 在基础 id 被占用时追加 4 位后缀
  （`backend/core/host_identity.py:43-48`），超过 64 字符则回退
  `auto-<12hex>`（`:45-49`）；心跳侧匹配优先级为「按 `payload.host_id` 命中 →
  按 IP 兜底命中 → 新建」（`backend/api/routes/heartbeat.py:196-221`），
  而 `create_host` 一律走 `allocate_host_id`（`backend/api/routes/hosts.py:278-281`）。
  两个后果：
  1. 「同 IP = 同身份」只在**基础 id 未被占用**时成立。若原主机的
     `host.id`（IP 派生）仍存在但 IP 已改（`_sync_host_identity` 允许改 IP，
     `heartbeat.py:83-100`），新机器在同 IP 上线会拿到带后缀的**新身份**，
     而不是继承退役行——与 D6 的直觉相反，也不会触发 unretire。
  2. 反向：`_sync_host_identity` 遇到「目标 IP 已被其他 host 占用」时只告警、
     保留旧 IP（`heartbeat.py:87-97`），身份与 IP 长期分叉，
     退役行的 `ip` 可能指向别的机器。
- 落点建议：D6 把身份契约写成三句可测的优先级规则（id 命中 > IP 命中 > 分配新 id），
  并明确「IP 已被占用/身份分叉时，unretire 语义是什么、运维该看什么」（详情页展示
  `boot_id`/`agent_instance_id` 与 IP 变更警告），避免实现单各自发明。

### F4-02【建议】「`boot_id`/`agent_instance_id` 变化在详情与审计可见」无实现支撑

- 证据：两个字段在心跳与恢复上报时被**直接覆盖**
  （`backend/api/routes/heartbeat.py:243-247`、`backend/api/routes/agent_api.py:2903-2911`），
  全仓引用仅此与迁移/校验，无历史表、无变更审计事件；
  `agent_api.py:2904` 的 `previous_boot_id` 只用于当次恢复判定，不落盘。
  因此 D6（`docs/adr/ADR-0038-host-retirement-semantics.md:79-83`）承诺的
  「变化在详情与审计可见」当前**做不到**：详情只能看到最近一次值。
- 落点建议：二选一写清楚——(a) 降级表述为「详情可见当前值」，审计仅在
  retire/unretire 时记录当场快照；(b) 要求实现单在 unretire 与
  「退役后心跳」两条路径上写 `record_audit`
  （`backend/core/audit.py:35-45`）并携带 boot/instance 快照。
  推荐 (b)，成本小且与 D4 告警互补。

### F4-03【建议】ADR-0035 交互应明确「本 ADR 不做凭据动作」，并复核触发条件

- 证据：ADR-0035 当前状态为 Accepted v1.2，但**尚未实施**（全局共享
  `AGENT_SECRET` 仍是现状；升级触发条件四条全部依赖外部信号，
  `docs/adr/ADR-0035-agent-host-identity.md` §6/§6.1）。ADR-0038 只在 Revisit 2
  写「per-host 凭据落地后重审换机注册流程」
  （`docs/adr/ADR-0038-host-retirement-semantics.md:135-136`），
  没有说明**退役在凭据生命周期里的位置**：目标形态下，退役是最自然的
  「吊销/失效该主机凭据」时机；现状下则没有任何凭据可吊销。
- 落点建议：D6 补一句「本 ADR 在共享 secret 现状下不产生凭据动作；
  ADR-0035 §5 实施时，退役作为 host 凭据失效的触发点之一纳入其骨架」，
  并在 Revisit 2 回链 #906，避免两条线各自演进。

## F5 一致性与迁移

### F5-01【建议】迁移配套需点名门禁，避免首提交撞 schema 漂移

- 证据：仓库用 `alembic upgrade head` + `compare_metadata` 的基线白名单断言
  （`backend/scripts/check_schema_sync.py:120-129`，基线
  `backend/scripts/schema_sync_baseline.json`），CI 在 `pr-migrate-empty-db`
  跑「升级空库 → 断言 schema 与 ORM 一致」两步
  （`.github/workflows/ci.yml:305-315`）；单 head 由
  `tests/test_alembic_heads.py` 守护。ADR §4 迁移只写「三列 additive nullable，
  无回填；回滚 = drop 三列」（`docs/adr/ADR-0038-host-retirement-semantics.md:116-117`），
  没有点名这些门禁与「模型列与迁移逐字段一致（nullable/default/类型命名）」的要求。
- 落点建议：§4 迁移补一句配套清单：迁移文件 + 模型列（`DateTime(timezone=True)`
  对应 TIMESTAMPTZ、`String(n)`/`Text` 与迁移一致、避免
  Python default 与 server_default 漂移）+ `check_schema_sync` 保持绿 +
  `downgrade()` 实现（ADR-0008 要求可回滚）+ 单 head。这不是新决策，
  是把既有治理写进 ADR 的落点，防止实现单首提交即撞门禁。

### F5-02【观察】回滚「无状态依赖」需限定

- 证据：drop 三列确实不带新数据形态（审计仍在 `AuditLog`，
  `backend/core/audit.py:35-52`），但回滚会**静默撤销全部退役决定**：
  回滚后退役主机重新进入派发/统计面，且没有任何提示。
- 落点建议：§4 迁移把「无状态依赖」限定为「无新增数据形态；回滚的副作用是
  全部退役决定失效，需按运维变更流程执行」。

### F5-03【观察】术语冲突：script-versioning 已占用「退役」

- 证据：`docs/development/script-versioning.md:1,89-104` 已用「脚本退役」
  （`retirement_candidates` 亦见 `backend/scripts/check_unreferenced_script_versions.py:65`）。
  ADR-0038 的标题与标签直接使用「退役」（host retirement）。
- 落点建议：文档/UI 一律用限定词（「主机退役」/`retired_at`），
  在 ADR 术语处加一句与脚本版本退役的区分，避免运维工单与技能入口混淆。

### F5-04【观察】与其他 ADR 无方向冲突（逐条核对）

- ADR-0025：命名冲突已规避（`extra['archive']`，`agent_api.py:3159-3175`），
  历史保留原则一致（ADR-0025 管存储生命周期，本 ADR 明确不提供 purge）。
- ADR-0019：容量/租约以设备与 lease 为单位（`backend/services/plan_run_scan_scope.py`
  与 `lease_manager` 均不依赖 host.status 做容量），退役不需要改租约语义；
  唯一交互点是「在线容量统计」（F2-01 第 5 点）。
- ADR-0026：需要在裁决语义上对齐（F1-01/F2-02），无方向冲突。
- ADR-0034：执行登记簿领域（requirement 生命周期），与主机生命周期无关；
  仅「退役」一词在两个领域各自使用（F5-03）。
- ADR-0037：退役拒绝安装与提权边界无交互（安装脚本仍走 `install_agent.yml`，
  `hosts.py:793-880`）。

### F5-05【建议】§4 前端面事实错误：符号名与「无 UI 调用点」

- 证据：ADR §4 写「现状 `api.hosts.remove`（`frontend/src/utils/api/hosts.ts:25`）
  无 UI 调用点，随本 ADR 实现单决定保留或删除」
  （`docs/adr/ADR-0038-host-retirement-semantics.md:120-122`）。实际：
  `hosts.ts` 中无 `remove`，符号是 `delete`（`frontend/src/utils/api/hosts.ts:24-25`），
  且存在两个调用点——`frontend/src/pages/hosts/HostsPage.tsx:107`（单条删除
  mutation）与 `:308`（批量删除，含二次确认与失败汇总）。
- 影响：实现单若照字面「无 UI 调用点 → 可删」处理，会破坏现有主机删除 UI；
  反过来，D2 的删除/退役分家在前端是**既有删除入口旁新增退役入口**，
  不是「从零加交互」，工作量与回归面（`HostsPage.test.tsx`）也不同。
- 落点建议：§4 前端面改为「`api.hosts.delete` 已被 HostsPage 单条/批量删除使用；
  实现单需在删除入口旁增退役入口，并明确批量删除对退役主机的行为
  （建议：批量操作默认只作用于未退役主机）」。

## F6 安全面

### F6-01【建议】`retired_by` 语义与 `retire_reason` 强制性未定

- 证据：D1 定义为 `retired_by (String)`（`docs/adr/ADR-0038-host-retirement-semantics.md:58-61`），
  未说明存 user id 还是 username；仓库审计约定为两者并存
  （`record_audit(..., user_id, username)`，`backend/core/audit.py:35-45`）；
  `retire_reason` 是否必填、是否允许空串也未写。
- 落点建议：D1/D2 明确 `retired_by` 存 username（与 `AuditLog.username` 同名同义，
  便于详情页直出）、id 走审计字段；`retire_reason` 在 API 层必填（非空校验），
  理由：退役是低频、高影响的运维决定，理由缺失会让后续 unretire/追责无据。
  unretire 是否要求理由同 F1-03 一并定。

### F6-02【建议】控制面「拒绝」在路由层之外有旁路

- 证据：ADR D5 写「控制面动作（热更新/安装/批量刷新）对退役主机拒绝」
  （`docs/adr/ADR-0038-host-retirement-semantics.md:75-78`）。实际控制面动作分布在
  三个层次：API 路由（`hosts.py:585-618` hot-update、`:793-880` install）、
  预检 SSH 同步（`backend/services/precheck/runner.py:189,216` →
  `precheck/sync.py:68-105,107+`，无状态判据）、批量脚本
  （`backend/scripts/batch_hot_update.py:90-95`，自选 ONLINE）。
  只改路由层会留下两个旁路（F2-01 第 2、3 点）。另有三个更隐蔽的旁路：
  agent-secret 的升级门禁端点（`agent_api.py:3262-3307`，
  Ansible `update_agent.yml` 即走此路）、`POST /agent/logs` 远程 SSH
  （`logs.py:244-262`）、`POST /plan-runs/hosts/{host_id}/reload-config`
  （`dedup.py:495-514`，无 Host 读取）。
- 落点建议：D5 把「控制面动作」定义为**动作清单**（路由 + 预检同步 +
  批量脚本 + AI 控制类工具 + 远程日志/配置命令），并规定实现单在每个动作的**共享收口点**
  加统一判据（`begin_host_upgrade` 覆盖热更新/升级四入口；预检同步两函数；
  批量脚本；`emit_agent_control` 的调用点各自判据），而不是逐个路由打补丁。

### F6-03【观察】共享 `AGENT_SECRET` 下退役不新增绕过，也不能替代吊销

- 证据：Agent 鉴权是全局共享 secret（ADR-0035 现状，未实施 per-host 凭据），
  任何 Agent 可冒充任意 `host_id`（`agent_api.py` 的 `_verify_agent`；
  `agent_api.py:2917-2920` 注释亦承认「共享 AGENT_SECRET 认证进程而非 host/job 关系」）。
  退役只改变控制面策略（拒绝 claim/派发/控制动作），不改鉴权面：
  已持 secret 的主机仍能心跳、上报、读自身状态，冒充风险与退役前相同。
- 落点建议：§4 或 D6 补一句「退役不构成凭据吊销；在 ADR-0035 落地前，
  退役主机的 Agent 仍持有有效凭据，控制面以策略拒绝替代凭据拒绝」，
  避免运维把退役误当安全动作。
