## F1 语义完备性（D1/D2）

### F1-1【建议】「非 ONLINE」前置与 DEGRADED 语义需明示

- **证据**：`HostStatus` 仅三值（`backend/models/enums.py:25-28`），`host.status` 为 VARCHAR（`backend/models/host.py:33`）；控制面无任何 `status=DEGRADED` 写点，DEGRADED 只能由 Agent 上报（`backend/agent/capacity_reporter.py:134-161`）。两条超时路径都只收敛 `ONLINE`：watchdog（`backend/tasks/session_watchdog.py:42-48`，仅 `status == ONLINE`）、懒更新（`backend/api/routes/hosts.py:60-71`，`status != "ONLINE"` 直接返回）；设备读路径同理（`backend/api/routes/devices.py:33-56`）。
- **含义**：停机的 DEGRADED 主机将永远停留 DEGRADED。对退役入口这产生两面效果：①它是「非 ONLINE」，可直接退役（对卡死主机是必要的出口）；②它也放行「活体但降级」的主机——退役后不会出现任何状态收敛提示，只能靠 D4 的告警/徽标补救。
- **落点**：D2 明确写出「DEGRADED 允许退役」及其理由；验收场景覆盖「退役后仍以 DEGRADED 心跳」的形态。另注：watchdog 阈值默认 120s（`session_watchdog.py:34`）与 `hosts.py:53` 的 300s 不一致，退役判定与去重语义（F3-4）若绑定阈值需先统一或注明。

### F1-2【建议】retire 前置校验与 claim 存在竞态窗口

- **证据**：claim 对 host 行 `SELECT ... FOR UPDATE` 后判 ONLINE（`backend/api/routes/agent_api.py:396-403`）；D2 未要求 retire 入口对同一行加锁。两条心跳路径都可能把 status 写回 ONLINE（`backend/api/routes/heartbeat.py:236`、`agent_api.py:829`）。
- **影响**：校验（非 ONLINE）与提交之间的窗口内，心跳可复活主机并使一次 claim 穿过——退役后仍有作业在跑，与前置条件的目的冲突（窗口小、影响有限）。
- **落点**：D2 增加「retire/unretire 在同一事务内对 host 行 FOR UPDATE 复检」，与 claim 天然互斥（同一行锁）；验收补并发用例。`DELETE`（`hosts.py:465-554`）无锁属同族，但不属本 ADR 范围。

### F1-3【观察】「无活跃 Job」判据应复用既有常量，并明示不检查租约的理由

- **证据**：现有活跃定义 = `PENDING/RUNNING/UNKNOWN`（`backend/services/host_upgrade_gate.py:44-48`、`:117-126`；`plan_dispatcher_sync.py:56-60` 同值）。ADR 未写「活跃」的口径。
- **判断**：退役前置**不需要**追加「无 ACTIVE 租约」——retire 不删除、不改写任何行，租约由 `device_lease_reconciler` 按过期/终态回收，与 `DELETE` 预检（删除会级联租约）的动机不同。建议 ADR 明示该取舍，防止实现单过度收紧。
- **落点**：D2 引用 `host_upgrade_gate.ACTIVE_JOB_STATUSES` 并加一句「不做租约检查」的理由。

### F1-4【建议】退役与维护窗口的交互未定义

- **证据**：`maintenance_until/holder`（`backend/models/host.py:57-58`）与 `in_maintenance_window`（`backend/services/plan_dispatcher_sync.py:163`）是既有「瞬态占用」信号；热更新/准入脚本同步期间占用（`backend/services/host_upgrade_gate.py`、`backend/services/precheck/sync.py:68-104`）。
- **落点**：D2 择一并写明：允许退役（维护窗口不受影响，后续动作自然失败）或拒绝（409 提示先在途热更新完成）。推荐前者 + 告警，避免新死锁。

### F1-5【建议】换新流程的顺序需写入 ADR

- **证据**：D5 拟将「安装」列为退役主机拒绝动作，但换机（同 IP）在部署新 Agent 前必须先 `unretire`（否则安装/引导被拒）。设备物理搬移由心跳 re-home 处理（`backend/api/routes/heartbeat.py:364-403`，租约阻断 `:385-392`），与新机接入顺序无关。
- **落点**：D6 或「运维代价」节写明推荐序列：停旧 Agent → `retire` → 换硬件 → `unretire`（同 IP 同身份）→ 安装/引导新 Agent → 设备心跳 re-home 验证。不写清楚必然在实现后以 issue 形式返工。

## F2 过滤面穷尽性（D5 不变量）

> 结论：ADR 列的「五面」方向正确，但**枚举不完备**（至少 8 类）、且每一面「怎么判」未写（现状判据只认 `status`，而 D4 允许退役后 `status=ONLINE`）。这是 D4 决策论证链（「风险面已 fail-closed」）的直接缺口。

### F2-1【阻断】退役活体在派发/claim 双路放行——D4 的 fail-closed 论据不成立

- **证据**：派发分类器只查 `Host.status`（`backend/services/plan_dispatcher_sync.py:88-100`），唯一 host 判据是 `host_status == OFFLINE`（`:155`）；prepare 只拒致命原因（`:509-518`）；准入复检同源（`backend/services/admission_pump.py:666-675`）。claim 只判 `status != ONLINE`（`backend/api/routes/agent_api.py:401-403`）。而 D4 明确「退役后心跳照常更新 `status`」——两条心跳路径分别写 `payload.status`（`heartbeat.py:236`）与强制 ONLINE（`agent_api.py:829`）。
- **影响**：退役 + 活体心跳 = 主机 ONLINE 且未退役过滤 → 派发成功、claim 成功、作业照跑；D5 不变量在最常见的「忘了停 Agent」形态下失效，D4 的正确性依赖一个不存在的收口。
- **落点**：D5 每面改写为「判据 = `retired_at IS NULL` ∧ 原判据」，并声明 D4↔D5 的依赖；实现单在分类器（一处覆盖 prepare+admission）与 claim 各加过滤。

### F2-2【阻断】退役在准入队列的 reason/终态未裁定

- **证据**：`_FATAL_DISPATCH_REASONS = ("not_found", "no_host")`（`plan_dispatcher_sync.py:64-68`）；其余原因（`device_offline/host_offline/host_maintenance/active_lease/active_job`）按「可重试调度态」进队（`:64-66` 注释、`:516-518`）；准入侧非致命即 `_RetryableAdmission` → 每 30s 重排（`admission_pump.py:65`、`:673-676`、`:825-826`），致命走 `fail_plan_run_admission`（`:331-387`）。
- **影响**：若 `host_retired` 沿用 `host_offline` 形态 → 在队 Run 永久 QUEUED、零告警（与现存 offline 行为同构）；若归 fatal → prepare 400、在队 Run FAILED 并审计。两条路对「已完成 prepare 的 Run」影响完全不同，ADR 未裁定，实现单必然二选一后返工。
- **落点**：D5 增加一段「退役的派发语义」：建议归 **fatal**（退役是终态而非瞬态），写明 prepare 400 与在队 Run `FAILED`+审计+通知的预期；同时覆盖「同一 Run 部分主机退役」的行为（建议整个 Run 失败，全有全无，与准入队列 all-or-nothing 语义一致）。

### F2-3【建议】准入 Phase A 早于退役过滤：脚本同步可 SSH 触碰退役主机

- **证据**：准入任务 Phase A 取 `PlanRunHost.host_id`（`admission_pump.py:764-779`），先跑 `_verify_scripts_phase`（`:817`），**之后** Phase B 才做分类器复检（`:666-675`）；sha 不匹配会触发 `push_mismatched_scripts` → `sync_host_via_hot_update` → `execute_hot_update` + 维护窗口（`backend/services/precheck/sync.py:68-104`、`:107-133`）。
- **影响**：退役瞬间的活体主机可能在无过滤窗口被 SSH 热更新（占维护窗口、重启 Agent），与 D5「控制面动作拒绝」冲突；这是「在队 Run 退役」与「已 prepare」两类场景的公共路径。
- **落点**：D5 的动作清单纳入「准入队列脚本同步」，过滤点前移到 Phase A 之前（或 `_verify_scripts_phase` 内校验 `retired_at`）；F7 验收补「退役主机零 SSH 副作用」用例。

### F2-4【建议】统计面枚举遗漏

- **证据**：`stats.py:286-298` dashboard-summary 裸 SQL 全量 host（`host_total/online/offline/avg_*`、在线率分母）；`stats.py:264-272` file-server active hosts（ONLINE+fresh，退役活体会被算作活跃 Agent 参与挂载合规）；`stats.py:329-334` 设备计数不 JOIN host；`backend/api/routes/metrics.py:38-53` fleet gauge 按 status 分组；AI `backend/services/ai_assistant/tools.py:138`（platform health 计数）、`:374-389`（host 列表）。
- **落点**：D5「统计容量」具体化为「任何按 host 计数的读路径」并列出上述点；明确 `host_total` 是否含退役（建议：默认口径排除退役，`include_retired` 仅影响列表类接口）。

### F2-5【建议】控制面动作清单严重不完备

- **证据（均为现状，无退役过滤）**：
  - scan/archive fan-out：`backend/services/plan_run_scan_scope.py:113-122` 回传全部历史 host+status；消费方 `backend/api/routes/plan_runs.py:549-566`、`backend/api/routes/dedup.py:464-477`、`backend/tasks/saq_tasks.py:313-324`、`backend/services/ai_assistant/plan_run_ops.py:391-410` 均以 `status=="ONLINE"` 为准下发 `scan_now/archive_now`。
  - Socket.IO 直控：`backend/realtime/socketio_server.py:750-758`（`emit_agent_control`）、`:494-560`（`call_agent_rpc`）不看 host 状态；调用点含死信 RPC（`backend/api/routes/hosts.py:931`、`:972`）、`dedup.py:495` reload-config、AI reload_config（`backend/services/ai_assistant/orchestrator.py:670-691`，仅判 ONLINE）。
  - 升级门禁通道：`backend/api/routes/agent_api.py:3262-3307` + `host_upgrade_gate.py`（无状态检查）。
  - SSH 日志：`backend/api/routes/logs.py:244-282`（`verify_agent_secret` 而非 admin，无过滤）。
  - CLI：`backend/scripts/batch_hot_update.py:90-95`（直查 `status==ONLINE`）、API 模式 `:246-247`（经默认列表，D5 后间接收口）。
  - 既有 UI 通道：hot-update 仅拒非 ONLINE（`hosts.py:614-618`）、install 零检查（`:793-825`）、watcher-admin patch（`:557-582`）。
- **落点**：D5 由「三类动作」改为「动作清单（现有入口 file:line）+ 每动作裁决」；建议区分两类：执行/配置类（热更新、安装、reload_config、升级门禁、脚本同步 → 拒绝）与数据回收类（scan/archive_now、日志尾读 → 需要单独裁决，若一律拒绝会丢失退役前最后一批设备日志，建议允许但要求显式 admin 触发与审计）。二者任一选择都必须写进 ADR，否则实现单按字面拒绝会制造数据回收死角。

### F2-6【建议】设备选择面（列表/前端多选）

- **证据**：`backend/api/routes/devices.py:294-311` 设备列表不 JOIN host；前端 `frontend/src/components/schedule/DeviceMultiSelect.tsx:22-27` 全量拉设备、`PlanExecutePage.tsx:232`、`DevicesPage.tsx:57` 同源；preview 不校验可派发性（`backend/services/plan_dispatcher_core.py:472-482`）。

- **落点**：D5 增列「设备读路径/选择器」面：建议设备列表对退役主机设备做标注（而非硬过滤，保留历史可见性），派发侧按 F2-2 语义给出显式拒因。

## F3 心跳策略（D4）

### F3-1【阻断】「沿用现有告警去重惯例」不存在

- **证据**：`_delivery_identity = (event_type, run_id, task_id, device_serial)`（`backend/services/notification_service.py:329-336`）；`_load_prior_channel_delivery` 在 `run_id is None` 时直接返回 `(None, {})`——**无 run_id 不去重**（`:339-366`）。事件枚举仅 4 值（`backend/models/notification.py:16-20`），`AlertRule.event_type` 是 DB Enum（`:52`），新增主机级事件类型需迁移。`DEVICE_OFFLINE` 的「单次」实际靠状态护栏 `already_offline`（`backend/api/routes/heartbeat.py:142-148`），不是通用去重。另：`Host.extra` 不能承载去重戳——`heartbeat.py:249-282` 每次心跳重建 extra，仅白名单 6 个 `agent_*` 键保留，控制面写入键会被抹除。
- **影响**：按 ADR 文义实现，退役活体主机的心跳（周期下限 10s，`backend/agent/heartbeat_thread.py:68-69`；基础 `POLL_INTERVAL` 默认 5 被 clamp）会持续触发告警；「单次告警」与 F7 的验收均无从落地。
- **落点**：D4/不变量 3 指定去重事实源与「状态震荡」定义。两个可选（择一写入）：①新增列（如 `retire_alerted_at`，随 D1 三列同批迁移）；②状态跃迁语义——仅当此前 `last_heartbeat` 已过期（≥阈值）后再次收到心跳才告警一次，无需新列，震荡 = 再次超时后恢复。②更省存储但与阈值口径强绑定（见 F1-1）。

### F3-2【建议】「不做 409」的取舍成立，但应引用 Agent 端证据并把失败模式写入 Revisit

- **证据**：Agent 心跳客户端对非 2xx 抛异常并返回 `None`，无退避重试（`backend/agent/heartbeat.py:83-91`）；下游消费全部依赖响应非空：catalog 刷新跳过（`heartbeat_thread.py:361-365`）、心跳间隔/log_rate 背压跳过（`:367-404`）、设备重连恢复跳过（`:406-421`）。ADR §3 的顾虑有实证支撑。
- **落点**：把上述 file:line 补进 §3 该条；Revisit#1（升级 409）的触发条件补充「响应被丢弃导致背压/版本门禁失效」这一具体失败模式。

### F3-3【建议】心跳有两条端点，ADR 事实锚点不完整

- **证据**：真实 Agent 走 `POST /api/v1/heartbeat`（`backend/api/routes/heartbeat.py:164`；客户端 `backend/agent/heartbeat.py:84`），行为是取 `payload.status`（`:236`）并存 boot_id/agent_instance_id（`:244-247`）；ADR 1.2 只锚了 `agent_api.py:806-829`（`/api/v1/agent/heartbeat`，行为是缺行即建 + 强制 ONLINE）。仓库内未检出前者的调用方（疑似遗留/内部通道），但两路径都在运行态可达。
- **落点**：D4 实现要求覆盖两条路径，ADR 事实锚点补齐 `heartbeat.py:164-247`。

### F3-4【建议】告警震荡的定义要与阈值口径绑定

- 见 F3-1 落点②；无论选哪种机制，「第二次告警」的边界必须写成可测条件（如：last_heartbeat 距当前 ≥ `HOST_HEARTBEAT_TIMEOUT_SECONDS` 且退役中），否则 F7 的测试无法判定。

### F3-5【观察】单次告警与 D5 过滤是两组独立机制，互不替代

- 告警只解决「运维知情」，不解决「派发/claim 放行」（F2-1）。ADR 未把二者关系写死，建议在 D4 明示「告警是可见性，不承担收口职责」。

## F4 身份与换机（D6）

### F4-1【观察】「同 IP 换机 = 同一身份」结论成立，但归因应改为「ip 唯一约束 + 按 ip 复用」

- **证据**：`host.ip` 全局唯一（`backend/models/host.py:41`）；创建先做占用 409（`hosts.py:197-218`、`:221-233`）；心跳按 id 查、缺行先按 ip 复用（`backend/api/routes/heartbeat.py:196-205`）；`_sync_host_identity` 防 ip 被他人占用（`:76-100`）。「id IP 派生」（`backend/core/host_identity.py:10-25`）只是命名习惯，不构成身份约束。
- **落点**：修订 D6 行文并引用上述位置；`allocate_host_id` 的后缀逻辑（`:28-49`）在 ADR 中的角色应弱化（见 F4-2）。

### F4-2【建议】后缀路径的命中边界：id 与 ip 脱钩场景

- **证据**：正常换机流不可达（同 IP 先撞 409 或被按 ip 复用）；可达场景：`PUT /hosts/{id}` 改 ip 不改 id（`hosts.py:407-409`）、历史行 ip 为空。此时同 IP 新机可能得到 `198-51-100-6-xxxx` 后缀**新身份**，与 D6「同 IP = 同一主机身份」冲突。
- **落点**：D6 注明前提「仅当旧行 `ip` 仍等于该 IP」；实现单可加一致性检查（id 与 ip 派生态不符时告警/审计）。

### F4-3【建议】boot_id/agent_instance_id 的「审计可见」当前无落点

- **证据**：最新值原位覆盖、无审计（`heartbeat.py:244-247`、`agent_api.py:2903-2910`）；`job_instance` 无快照；唯一历史快照是 `device_lease.agent_instance_id`（`backend/models/device_lease.py:34`）。恢复路径会用 boot_id 判定 old instance 并 FINALIZE FAILED（`agent_api.py:2987-3012`）。
- **落点**：D6 的「变化在详情与审计可见」落到实现：unretire 审计 details 持久化当前 boot_id/agent_instance_id 快照，或新增身份变更审计事件；否则换机后历史归属不可考。

### F4-4【观察】与 ADR-0035 的交互：不加戏，但要说清边界

- **证据**：ADR-0035 当前状态 Accepted v1.2，§3 明示继续全局 `AGENT_SECRET`（per-host 凭据未实施）；claim/心跳等鉴权共用同一 secret。退役拒绝的强制力上限 = 客户端自报 `host_id`。
- **判断**：不引入新绕过（鉴权模型未变），也不解决冒充；D6 的 Revisit#2 措辞成立。建议补一句「退役过滤不构成身份防线」，避免读者误以为它提升了信任边界。

### F4-5【观察】换机需显式处理 SSH 主机密钥/凭据

- **证据**：`trust_host_key`/`replace_host_key` 机制（`hosts.py:322-333`、`:446-461`，#908）；新机 host key 变化会被拒绝静默覆盖。
- **落点**：F1-5 的换机序列里加入「必要时显式换钥/更新 SSH 凭据」，否则 unretire 后热更新/安装会撞主机密钥校验。

## F5 一致性与迁移

### F5-1【建议】三列 additive 的配套已明确，直接照做即可

- **证据**：additive 先例 `op.add_column` nullable（`backend/alembic/versions/bb22cc33dd44_add_suite_global_sha.py:23`）；对账 gate = 空库 `alembic upgrade head` + `backend.scripts.check_schema_sync`（`tools/dev/check_pr_migrate.py:116-129`、`scripts/run_gates.py:125-130`），diff 必须 ⊆ 基线（`backend/scripts/check_schema_sync.py:58-72`，索引/列按「表+名」比对）；单 head 由 `tests/test_alembic_heads.py` 保证。三列无索引，无需命名协商；**不得**把新增列预先写进 `schema_sync_baseline.json`。
- **落点**：ADR「迁移」段补一句「模型三列 + 单迁移配对，走既有对账门禁」，供实现单直接引用。

### F5-2【建议】回滚路径有隐含风险：drop 三列 = 静默全体 unretire

- **证据**：ADR「回滚 = drop 三列」；但退役本身是运维决定的状态，回滚后所有退役主机重新进入派发/claim 面且无提示。
- **落点**：downgrade 加 0 行守卫（先例：`backend/alembic/versions/w9x0y1z2a3b4_drop_plan_run_status_degraded.py:96-105` 的 count 断言），或在 ADR 明示「回滚即全体 unretire」并附运维告知。推荐前者。

### F5-3【观察】不变量 1 的 `⇔` 过强

- 派发/认领还受维护窗口（`plan_dispatcher_sync.py:163`）、设备状态/租约/活跃 Job（`:134-185`）、脚本校验等约束。`retired_at IS NULL ∧ status=ONLINE ⇔ 可被派发/认领` 应为 `⇒`（必要不充分）或显式写明「其余条件见既有路径」。
- **落点**：修订措辞，防止验收把「满足两条件但未派发」误判为缺陷。

### F5-4【观察】与 ADR-0025/0019/0026 无直接冲突

- 命名占用确认：`Host.extra['archive']` 属 ADR-0025 存储归档遥测（`agent_api.py:3160-3179`），与本 ADR 的 retire 不冲突；ADR-0019 租约语义不变（F1-3）；ADR-0026 的接口点在 F2-2 的 reason 归属。

## F6 安全面

### F6-1【建议】「必须审计」应改为列级强制 + 审计双写

- **证据**：`record_audit` 用 savepoint best-effort，`audit_logs` 表缺失时静默降级返回 `None`（`backend/core/audit.py:35-89`）；details 为 JSON 可承载 reason（无一级 reason 字段）。

## F7 验收可测性

### F7-1【建议】反例实证需给出可复核的操作口径

- **证据**：仓库无 mutation/变异测试工具（`tools/`、`tests/`、`scripts/` 零命中「mutation/反例实证」）。ADR 验收 2 的「临时移除任一过滤点 → 对应用例转红」是人工突变验证，没有留痕要求则无法复核。
- **落点**：验收改写为「每过滤点一条显式断言用例」+「在 Agent Note 记录变异实证的命令与结果」；Python 侧变异验证须清理 `__pycache__`（含 `test_*.pyc`），否则可能复用旧字节码导致假绿（仓库既往教训）。

### F7-2【建议】「单次告警」需先有语义再有判据

- 依赖 F3-1 的去重源与震荡定义；建议至少三例：首次心跳告警一次 / 持续心跳不再告警 / 超时后恢复再次告警；以及 unretire 后重新 retire 的计数重置。

### F7-3【建议】验收范围随 F2 清单扩容，并补两条集成用例

- 五面 → F2 清单（分类器+准入、claim、统计×5、列表/详情、动作清单、设备选择、前端多选）；新增：①在队 Run 目标退役后的终态（F2-2 语义）；②退役主机零 SSH 副作用（F2-3，含准入 Phase A）。

### F7-4【观察】测试接缝齐备

- 派发 `backend/tests/services/test_plan_dispatcher_device_validation.py:176-185`；claim 维护窗口先例 `backend/tests/api/test_agent_api_watcher.py:323-350`；主机删除 `backend/tests/api/test_hosts.py:552-627`；统计 `backend/tests/api/test_stats.py`、`backend/tests/api/test_metrics_fleet_gauges.py:22`；心跳 `backend/tests/api/test_heartbeat.py:286`。实现单可直接扩展，无需新框架。
