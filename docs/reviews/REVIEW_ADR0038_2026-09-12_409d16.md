## F1 语义完备性（D1/D2）

### F1-1（建议）「非 ONLINE」≠「Agent 已停」

**证据**：

- 退役前置拟复用 DELETE 瞬时两条：非 ONLINE + 无活跃 Job（ADR §2 D2；对照 `hosts.py:481-500`）。
- `HeartbeatIn.status` 允许 `DEGRADED`（`backend/api/schemas/host.py:104`），心跳原样写回 `host.status`（`heartbeat.py:236`）。
- `session_watchdog` 超时只扫 `Host.status == ONLINE`（`backend/tasks/session_watchdog.py:46`）——停跳的 **DEGRADED 主机永远不会被标 OFFLINE**。
- claim 已要求 ONLINE（`agent_api.py:401-403`），但派发快照只排除 `OFFLINE`（`plan_dispatcher_sync.py:155-160`）——**DEGRADED 仍可进入派发快照**，再在 claim 空转。

**问题**：活体 DEGRADED 主机满足「非 ONLINE」，可被 retire，与 §4「退役要求先停 Agent」运维叙述不一致；也放大「退役后仍心跳」成为常态路径，而非异常路径。

**落点建议（v0.2）**：

1. 明确退役前置语义二选一写死：
   - **严格停机**：要求 `status == OFFLINE`（或 `last_heartbeat` 超时），并修 watchdog 覆盖 DEGRADED；或
   - **Cordon**：允许 ONLINE/DEGRADED 在无活跃 Job（建议再加无 ACTIVE `DeviceLease`）时 retire，依赖 D5 封死新派发/claim，并把「活体退役」标为预期运维态。
2. 若保留「非 ONLINE」字面，须在正文承认 DEGRADED 活体可退役，并删掉「先停 Agent」的绝对表述。

### F1-2（观察）活跃租约未进退役前置

DELETE/退役拟检活跃 Job，不检 `DeviceLease` ACTIVE。热更新门禁同样以 Job 为准（`host_upgrade_gate.py`）。多数路径租约与 Job 同生灭，但 ADR 应用一句话说明「以 Job 为准、租约不另检」或补检，避免实现单自行发散。

### F1-3（建议）ONLINE 空闲机的运维摩擦

空闲 ONLINE 无法 retire，须先停 Agent 等 watchdog/`_ensure_host_status_up_to_date`（`hosts.py:56-80`）翻 OFFLINE。繁忙集群上「先停再退」窗口真实存在。属产品取舍，非逻辑漏洞；若选 Cordon（F1-1）可一并消掉。

## F2 过滤面穷尽性（D5）

ADR 列五面：派发快照 / claim / 统计容量 / 默认列表 / 控制面动作。核验后 **有遗漏面**，且与 ADR-0026 准入语义交叉处为阻断。

### F2-1（阻断）`host_retired` 必须进入致命拒因集

**证据**：`_FATAL_DISPATCH_REASONS = ("not_found", "no_host")`（`plan_dispatcher_sync.py:68`）。`host_offline` / `host_maintenance` 等为可重试，V2 准入队列下进 QUEUED 等待（同文件 L64-67、L155-168）。

**问题**：若实现把退役主机标成类似 `host_offline` 的可重试原因，则设备仍挂在退役 `host_id` 上的 PlanRun 会 **永久排队**（Agent 被 D5 封死，状态永不自愈）。

**落点建议**：ADR §2 D5 / 不变量 1 增补硬句：`host_retired`（或等价）∈ `_FATAL_DISPATCH_REASONS`（或 prepare 阶段 400），**禁止**仅当可重试 `queue_reason`。实现单回归必须覆盖「退役后原 host 设备被选进 Run → 立即失败/拒绝，不进无限 QUEUED」。

### F2-2（阻断/建议）遗漏的第六面（须写入 D5 清单）

| 面 | 证据 | 风险 |
|---|---|---|
| 设备默认列表 → 编排多选 | `devices.py:294-360` 无 host 生命周期过滤；`DeviceMultiSelect.tsx:22-24` 全量 `api.devices.list` | 退役主机设备仍可选进 Schedule/Plan，放大 F2-1 |
| 批量热更新脚本 | `batch_hot_update.py:92` 仅 `Host.status == "ONLINE"` | 活体退役（status 仍 ONLINE）会被扫入 |
| PlanRun 扫描下发 | `plan_run_scan_scope.py:113-122` 只带 `Host.status`；`saq_tasks.py` 对 ONLINE 下发 scan | 退役活体仍可能收 scan/control |
| AI 控制面 | `orchestrator.py:670-681` `reload_agent_config` 只验存在 + ONLINE | 与 D5「控制面动作拒绝」同族，须加 retired |
| 统计 / metrics | `stats.py:267-270`、`:298`；`metrics.py:44-50` 按 status 聚合 | 退役活体计入 ONLINE 容量/看板 |
| Socket.IO 接入 | `socketio_server.py:156-178` 全局 secret + `host_id` 入房，无生命周期门 | D4 允许心跳则 SIO 可保留；但 `emit_agent_control` / RPC 应拒绝退役目标（与热更新同级） |
| watcher 管理 | `hosts.py:557+` `watcher-admin-state` | 属控制面写路径，须列入拒绝集 |
| 默认主机列表 | `hosts.py:340-362` 当前无过滤 | D5 已覆盖；实现时补 `include_retired` |

**落点建议**：把上表收成 D5「过滤点清单」（含 file 锚点），验收「五面」改为「清单全覆盖 + 反例实证」。

## F3 心跳策略（D4）

### F3-1（观察→认可）不做心跳 409

**证据**：轻量心跳响应携带 `backpressure`、`agent_min_version`、建议间隔（`agent_api.py:843-867`；完整心跳同类）。拒绝心跳会制造 Agent 新失败模式，与 §3 否决理由一致。风险面由 D5 fail-closed 即可。**取舍成立**。

### F3-2（阻断）「沿用现有告警去重惯例」缺少可复用事实源

**证据**：`notification_service.py:343-345`——`run_id is None` 时 `_load_prior_channel_delivery` 直接 `(None, {})`，主机级上下文无法走该去重。SAQ 去重键同样绑定 `run_id`（`:649-653`）。

**问题**：不变量 3「按主机去重（只响一次……沿用现有告警去重惯例）」在现状代码下 **无可沿用惯例**。若实现只调 `dispatch_notification*` 而不另建事实源，活体退役主机按心跳周期重复告警。

**落点建议**：删除「沿用惯例」措辞；改为显式去重事实源，例如：

- `Host.extra['retirement']['alert_sent_at']`（注意勿与 ADR-0025 `extra['archive']` 冲突），或
- 独立审计/通知去重表以 `(event_type, host_id, retired_at)` 为键。

并定义震荡重置：`retired_at` 不变且持续退役 → 不重置；`unretire` 后再 retire → 新周期。

### F3-3（观察）UI 徽标与告警的职责切分

「已退役但仍在心跳」徽标可纯读 `retired_at IS NOT NULL ∧ last_heartbeat 新鲜`，不必依赖通知子系统——建议 ADR 把徽标判据与告警去重解耦书写，避免实现绑死。

## F4 身份与换机（D6）

### F4-1（阻断）同 IP 换机路径被 DB 唯一约束钉死，ADR 表述需诚实

**证据**：

- `Host.ip` 列 `unique=True`（`models/host.py:41`）。
- 创建/更新身份冲突显式 409（`hosts.py:221-224`、`:277`、`:400`）。
- 心跳按 IP 找已有行再 upsert（`heartbeat.py:200-205`）；缺失才 `allocate_host_id`（`:208`）。
- `allocate_host_id` 后缀路径处理的是 **id 已占用**（`host_identity.py:40-48`），不是「同 IP 第二台主机」。

**问题**：在现行约束下，同 IP 物理换机 **只能** 命中原行 → 运维语义确实是 unretire（D6 结论对），但「冲突后缀」对换机几乎不可达；若有人读 ADR 以为可注册 successor 新 id，会在 409 上撞墙。ADR-0035 per-host 凭据落地前，也不存在第二身份通道。

**落点建议**：D6 改为：「同 IP 换机在 `Host.ip` 唯一约束下物理上只能复用原行；unretire 为唯一恢复入口；`allocate_host_id` 后缀仅服务 id 碰撞/无 IP 回退，不构成换机分裂机制。」Revisit 与 ADR-0035 对齐保留。

### F4-2（建议）`boot_id` / `agent_instance_id` 不足以单独支撑换机审计

二者只活在 `Host` 行（`models/host.py:51-52`），`job_instance` **无**对应快照列。换机后心跳覆写（`heartbeat.py:243-247`）会抹掉旧机器身份；历史 Job 只留 `host_id`。

**落点建议**：unretire（及可选 retire）审计 `details` 强制写入变更前 `boot_id` / `last_agent_instance_id` / `agent_version` 快照；不要求本 ADR 改 Job 表。

## F5 一致性与迁移

### F5-1（观察）与 ADR-0025 / 0019 / 0034

- **0025**：`extra['archive']` 占用已在 ADR §1.2 正确规避；退役勿再占用 `archive` 键。
- **0019**：设备行保留 + re-home/租约阻断（`heartbeat.py:385-392`、`:403`）与 D6 一致。
- **0034**：执行契约层无冲突；本评审 Execution 仅写 `docs/reviews`。
- **0026**：见 F2-1——这是真正的交叉冲突点，不是无冲突。

### F5-2（建议）三列 additive 的配套

须同时落地：`models/host.py` ORM、Alembic revision、`HostOut`/retire API schema、`frontend/src/utils/api/types.ts`、以及 `check_schema_sync` 友好的**显式索引/约束名**（仓库已有命名对齐先例，如 `host.py:26` 注释）。回滚=drop 三列在「无新数据形态」意义上成立，但须注明：**回滚窗口内已退役主机会立即重新进入派发面**，需运维冻结或先 unretire 清单。

## F6 安全面

### F6-1（建议）全局 `AGENT_SECRET`（ADR-0035 现状）下的拒绝面

退役主机仍持共享 secret，可心跳与 SIO 连接（D4 有意允许）。安全边界依赖：

- claim 拒绝（D5）；
- 热更新 / 安装 / SSH 控制面动作拒绝（`hosts.py:586+`、`:794+`；`batch_hot_update.py`）；
- Agent RPC / `reload_config` 拒绝（F2-2）。

缺任一写路径，就会在「IP 可能已重新分配给新人」场景下误操作旧行凭据指向的机器。ADR 应把「SSH/安装/热更新/RPC」写成同一拒绝集合，而不是只举例「热更新/安装/批量刷新」。

### F6-2（建议）审计字段强制性

D1 列含 `retired_by` / `retire_reason`，但不变量 3 未写 `retire_reason` min_length。建议：retire/unretire 均强制非空 reason；`retired_by` 取自 admin 会话，禁止客户端伪造。

## F7 验收可测性

### F7-1（建议）反例实证可操作，但清单须扩展

§5「临时移除任一过滤点 → 对应用例转红」对五面成立；实现单应把 F2-2 清单纳入同一门禁，至少包含：

1. 退役主机不进派发快照；
2. claim 空结果；
3. `host_retired` 不进无限 QUEUED（F2-1）；
4. `GET /hosts` 默认隐藏 / `include_retired` 可见；
5. `GET /devices`（或选择器）默认不暴露退役主机设备；
6. hot-update / batch / install / reload_config → 4xx；
7. 统计/metrics 不含退役活体。

### F7-2（观察）单次告警如何测

在 F3-2 事实源落地后，可测判据建议：

- 同 `retired_at` 下连续 N 次心跳 → 通知记录恰好 1 条；
- `unretire` → 再 `retire` → 允许第 2 条；
- （可选）仅 status 震荡、`retired_at` 不变 → 仍为 1 条（与不变量 3「除非状态震荡」对齐前须先定义「震荡」指 lifecycle 还是 heartbeat status）。
