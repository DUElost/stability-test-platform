## 总评

**Needs-revision：4 项阻断、3 项建议、2 项观察。** “阻断”指不建议将 v0.1 原样转 Accepted，不代表发现了对应的生产事故。

支持以独立列表达退役、保留 FK/历史、保留干净主机硬删，以及不以心跳 409 实现退役。需要先明确：已排队执行如何收口、退役后哪些控制/证据路径可达、身份继承究竟按什么键，以及有退役事实后的发布和回滚边界。无需为此推翻单列生命周期真源或引入设备退役。

| 题目 | 结论与定位 |
|---|---|
| F1 语义完备性 | 删除/退役分家成立；`DEGRADED` 实际可退役，不能把“非 ONLINE”当作“Agent 已停”；无活跃 Job 不覆盖 QUEUED/PRECHECK。见 R01、R07。 |
| F2 过滤穷尽性 | 五类是分类，不是五个调用点；须覆盖准入前置副作用、异步/直连控制、设备派生库存，并区分历史集合与操作目标。见 R01、R02 及过滤矩阵。 |
| F3 心跳策略 | 不做 409 有源码依据；“沿用现有去重”不能直接保证按主机单次告警。见 R05、R08。 |
| F4 身份与换机 | “同 IP = 同一身份”不是当前实现的不变量；实例/boot 标识只能辅助诊断，不能证明硬件身份。见 R03、R06、R09。 |
| F5 一致性与迁移 | 正交状态设计兼容现有方向；队列、最终归档、schema 对账和回滚须补契约。见 R01、R02、R04 及配套清单。 |
| F6 安全面 | 退役是管理状态，不是共享 secret 的撤销；操作审计要强制落库，受信域退出要评估 ADR-0035 触发条件。见 R02、R06、R09。 |
| F7 验收可测性 | 可设计逐层反例，但不能让其他过滤器遮住被测过滤点；告警按退役周期而非 HTTP 调用计数。见验收矩阵。 |

## 发现与落点建议

### R01 · 阻断 · 已有准入快照与退役缺少串行化、终态策略

- **涉及**：F1/F2/F5/F7；设计风险。ADR D2/D5：`docs/adr/ADR-0038-host-retirement-semantics.md:62`、`docs/adr/ADR-0038-host-retirement-semantics.md:75`。
- **证据**：`docs/adr/ADR-0026-plan-execution-scaling.md:103` 明确 QUEUED 不创建 active Job；`backend/services/plan_dispatcher_sync.py:509` 只拒绝 `_FATAL_DISPATCH_REASONS`，其定义在 `backend/services/plan_dispatcher_sync.py:68`，仅含 `not_found/no_host`；`backend/services/plan_dispatcher_sync.py:750` 冻结设备及 host 快照。
- **反例**：主机 OFFLINE、已有 QUEUED/PRECHECK 快照而无 Job，按 D2 可退役。只过滤新 prepare 和 claim，不会定义这条旧执行的命运。准入任务在最终加锁前运行 verify；不匹配时还会 SSH/SFTP 推脚本（`backend/services/admission_pump.py:817`、`backend/services/admission_pump.py:551`）。因此“尚未产生 Job”不等于“尚无控制面副作用”。
- **现有防护不能省略**：最终物化已有 Host→Device 顺序锁及全目标复查（`backend/services/admission_pump.py:76`、`backend/services/admission_pump.py:663`），claim 也锁 Host（`backend/api/routes/agent_api.py:395`）。本发现不是声称当前完全没有并发保护，而是 retire 必须参与同一协议。
- **v0.1 落点**：D2/D5 补充新 prepare 与既有快照的不同策略。建议新目标中任一退役 host 即结构化拒绝；旧 QUEUED/PRECHECK 不删快照、不静默缩小目标集合，而以明确的 `HOST_RETIRED` 原因收敛执行。若选择等待 unretire，须明确恢复触发与等待边界，不能套用暂态 `host_offline`。
- retire 在同一 Host 行锁内检查状态、活跃 Job 并写退役事实；准入/claim 在锁内读退役事实。慢 precheck、安装/升级的在途与排队动作另明确“禁止新启动 / 已启动如何排空”的边界，不持长数据库事务跨 SSH。
- **实现易错点**：现有分类先检查 device OFFLINE/ERROR，再检查 host（`backend/services/plan_dispatcher_sync.py:143`）。永久退役判据不能被较早的暂态拒因遮住，否则即使新增 `host_retired`，离线设备仍可落入 QUEUED 快照。验收需覆盖此组合。

### R02 · 阻断 · 控制拒绝与历史证据收口不能共用一个“隐藏主机”过滤器

- **涉及**：F2/F5/F6/F7；设计风险。落点为 D5“控制面动作仅 unretire 除外”及 §4/§5。
- **证据**：`backend/services/plan_run_scan_scope.py:90` 从 Job、PlanRunHost、TargetDevice 三类历史/冻结关系取 host，而非设备当前归属；`backend/services/plan_run_scan_scope.py:119` 只读取存活状态。手动归档在 `backend/api/routes/plan_runs.py:549`、后台 scan 在 `backend/tasks/saq_tasks.py:314`，均以 ONLINE 为控制下发条件。`backend/realtime/socketio_server.py:749` 按 room 直接 emit，并非 Host 策略边界。
- **反例**：Job 已终态、最终 scan 尚未完成时允许退役；随后按 D4 仍在心跳、成为 ONLINE。沿用现有 fan-out 会向退役机发 `archive_now/scan_now`；反过来直接在历史 scope 查询过滤退役行，会把本应说明的缺失 host 从预期证据集合移除。二者都不能由“默认列表隐藏”解决。
- **旁路**：`backend/scripts/batch_hot_update.py:91` 的 `--direct` 查库选择 ONLINE host，`backend/scripts/batch_hot_update.py:139` 调共享升级门禁；安装服务 `backend/services/agent_installer.py:50` 直接取 host；`backend/api/routes/dedup.py:495` 的 reload-config 不经过 hosts 热更新路由。仅改 UI 或 `hosts.py` 两个端点不足。
- **v0.1 落点**：区分“历史归属集合”“可发新命令的目标”“只读查询”。沿用 D5 的最小方案是：保留历史 host，拒发新控制，并显式返回 `skipped_retired`/未完成证据，不能把它从预期集合删掉再报完整。若 ADR-0025 的终态收尾需要在退役后继续执行，必须在 D5 明列窄例外与鉴权条件，交人工裁决。
- Host 详情、安装状态、归档状态、审计和历史查询应保持可读；延迟历史上传保持既有 fencing 校验（`backend/api/routes/agent_api.py:2697`），不能因统一屏蔽 Agent namespace 而丢弃。安装/热更新/reload/watcher 管理写入须在实际执行边界复查，含排队后退役的任务。

### R03 · 阻断 · “同 IP 换机 = 同一身份”超出了分配器的保证

- **涉及**：F4/F6；事实边界错误。落点为 D6 及 §1.2 身份事实。
- **证据**：`backend/core/host_identity.py:28` 只是分配 ID：IPv4 首选映射，冲突追加后缀，非 IPv4/耗尽回落 `auto-*`。`backend/api/routes/hosts.py:407` 改 IP 不改主键。完整心跳先按显式 ID 查找，未找到或 sentinel 才按 IP 回查（`backend/api/routes/heartbeat.py:196`）；轻量心跳则仅按客户端 ID upsert（`backend/api/routes/agent_api.py:806`）。
- **可构造边界**：A 的原 IP 派生 ID 仍在，但 A 已换 IP；原 IP 可再分配给 B，B 得到后缀 ID。B 退役后，遗留/手填无后缀 `HOST_ID` 的同 IP 新机先命中 A。完整心跳发现 IP 已被 B 占用只保留 A 的旧 IP 并告警，仍按 A 的 host_id 继续处理（`backend/api/routes/heartbeat.py:83`），不会自动找回 B 的退役状态。
- 正确沿用服务端返回的 B.id 可以工作；这不是断言所有换机都会错，也不是要求新增 successor。现有碰撞用例 `backend/tests/test_host_identity.py:22` 已证明后缀路径不是理论死代码。
- **v0.1 落点**：把硬保证改为“同一 `host.id` 重连继承退役；IP 是分配/展示线索，不是身份等价关系”。换机必须显式确认要继承的记录与准确 HOST_ID，并使 HTTP、Socket.IO、安装配置一致；列出显式 ID、sentinel/IP 回查、后缀、IP 变更、非 IPv4 的恢复判据。不要在本 ADR 隐式引入按 IP 自动改写主键或身份归并。

### R04 · 阻断 · 三列可 additive，不代表启用后的回滚“无状态依赖”

- **涉及**：F5/F6；设计风险。`docs/adr/ADR-0038-host-retirement-semantics.md:116` 的“回滚 = drop 三列（无状态依赖）”应修订。
- **证据**：D1 在 `docs/adr/ADR-0038-host-retirement-semantics.md:58` 将该列定义为唯一生命周期真源；旧 claim 只看 ONLINE/维护窗口（`backend/api/routes/agent_api.py:401`），旧设备准入不认识退役（`backend/services/plan_dispatcher_sync.py:155`）。
- **反例**：退役主机按 D4 仍可 ONLINE。删列会不可逆丢失退役事实；仅回滚应用而保留列，旧 worker 也会忽略它，恢复派发/控制。schema 可降级与管理决定不被静默撤销是两回事。
- **v0.1 落点**：明确迁移→全部消费方支持退役→开放 retire 入口的发布顺序，覆盖 API、准入 worker、批量工具。存在退役行后禁止无条件删列/回滚到忽略退役的版本；必须先走显式、审计化的恢复/隔离方案，或选择保留兼容门禁的前滚修复。无退役事实时的降级与已启用后的恢复分开验收。
- 不应以维护窗口迁移也能 drop 列为理由照搬：维护窗口会到期，而退役不能靠时间自然解除（对照 `backend/alembic/versions/m8n9o0p1q2r3_host_maintenance_window.py:16`）。

### R05 · 建议 · 定义按退役周期的逻辑告警，而非沿用通用通知键

- **涉及**：F3/F7；设计与验收缺口。落点 D4、§4 不变量 3、§5“单次告警”。
- **证据**：`backend/services/notification_service.py:649` 的队列键只含 event_type/run_id/device_serial；投递身份 `backend/services/notification_service.py:329` 也无 host/退役周期；`backend/services/notification_service.py:343` 在无 run_id 时不查历史投递。不能直接作为 host 告警去重方案。
- **已执行纯函数反例**：从 AST 只提取上述两个函数，分别传入两台合成 host、以及同 host 的下一退役周期；两函数的结果均相同。该结果只证实现有键不适用，不声称已测试一个尚未存在的退役告警实现。
- **v0.1 落点**：建议逻辑事件键为 `(host.id, retired_at, event_type)`；同周期跨两条心跳、重试、多 worker、服务重启只建立一个事件，unretire 后再 retire 才产生新周期。若要因 ONLINE/OFFLINE 震荡再次提醒，须另外定义冷却和重置条件，不用“除非状态震荡”代替判据。
- 去重事实持久化并保证原子性，Redis 仅用于排队；复用现有通知投递渠道与结果记录，不把队列接受等同外部送达，不承诺外部通道 exactly-once。若用 Host.extra 存标记，要注意完整心跳在 `backend/api/routes/heartbeat.py:249` 重建 extra，只有特定键会保留。

### R06 · 建议 · 补齐操作幂等、强制审计及身份变化证据

- **涉及**：F1/F4/F6/F7；实现约束。落点 D1/D2/D6、§4 不变量 3。
- 列可空是为了存量/在用主机，不等于操作的 who/reason 可空。actor 从 admin 会话取，时间由服务端生成；retire/unretire 均要求非空、去空白并限长的理由。重复 retire 不重置周期、操作者和原因；重复 unretire 的 no-op/审计策略显式规定。
- **证据**：`backend/core/audit.py:35` 返回可空审计结果，缺审计表时在 `backend/core/audit.py:79` 告警后返回 None。若端点不验证此结果就提交退役，不能满足“必须审计”。建议本操作审计失败则事务失败，不顺手改动全站审计降级政策。
- 同事务记录前/后生命周期、actor ID/用户名、reason、host.id、相关身份观察值；unretire 清空当前标记后，仍能从审计重建退役历史。记录身份变化须在覆盖前保存旧值：完整心跳目前直接覆盖 `boot_id/last_agent_instance_id`（`backend/api/routes/heartbeat.py:243`），轻量心跳也不实现此变化审计。
- `backend/agent/identity.py:16` 的实例 ID 每进程重建，`backend/agent/identity.py:21` 的 boot ID 随 OS 重启变化，不能区别“原硬件重启”和“换了硬件”。它们是恢复/诊断信号，不是硬件凭据。HostOut 当前不含这些身份列（`backend/api/schemas/host.py:57`）；详情、审计及 `frontend/src/utils/api/types.ts:14` 须成套同步，不能仅在 UI 显示当前值便宣称有变化历史。

### R07 · 建议 · 将生命周期门槛与存活、可调度性、库存口径分开

- **涉及**：F1/F2/F7；语义和展示约束。落点 D2/D5、§4 不变量 1。
- **证据**：现有删除只拒 ONLINE（`backend/api/routes/hosts.py:481`）；HostStatus 包含 DEGRADED（`backend/models/enums.py:25`）。所以 D2 不会因 DEGRADED 而“过严”，反而允许仍在运行的 DEGRADED Agent 被退役；这可以成立，但与 §4“要求先停 Agent”的表述不等价。
- `retired_at IS NULL ∧ ONLINE ⇔ 可派发/认领` 也过强：维护窗口、设备状态、活跃租约和容量继续影响 claim（`backend/api/routes/agent_api.py:404`、`backend/api/routes/agent_api.py:429`），当前 prepare 还允许暂态不可用设备排队。建议写成“退役必不准入/claim；未退役还须满足原有各阶段条件”，单独裁决 DEGRADED 的准入策略，不顺带修改既有健康规则。
- 默认 hosts 过滤须在 count/pagination 前生效（`backend/api/routes/hosts.py:348`）。Dashboard 原始 SQL 同时查 host/device 全表（`backend/api/routes/stats.py:286`），metrics 对 Host/Device 分别 group by（`backend/api/routes/metrics.py:48`）；只过滤 host 计数，会留下退役机设备的“在线库存”。
- 设备主列表及选择器也要区分“可用库存”与“历史浏览”（`backend/api/routes/devices.py:294`），按所属 Host 生命周期派生 eligibility，而不是把如实上报的 ONLINE 强改 OFFLINE。详情可保留物理容量遥测，但不要将其当成可调度容量；历史统计不应因今天退役而追溯消失。

### R08 · 观察 · 不做心跳 409 的取舍有依据，但须覆盖两个实现

- **涉及**：F3。轻量入口 `backend/api/routes/agent_api.py:796` 与完整入口 `backend/api/routes/heartbeat.py:187` 的注册和状态更新并不相同，不能只修 issue 的一个导航锚点。
- 两者仍需返回版本门禁、目录版本和背压信息（`backend/api/routes/agent_api.py:843`、`backend/api/routes/heartbeat.py:507`）。Agent 对非 2xx 调用 raise_for_status 后返回 None（`backend/agent/heartbeat.py:83`），启动版本检查遇到 None 会跳过检查（`backend/agent/main.py:578`）。因此“拒绝心跳即可安全停止退役 Agent”并不成立。
- **v0.1 落点**：保留 D4、不做 409；§5 显式参数化测试两条心跳的 sticky retirement 与响应契约。claim 的独立版本门禁仍保留，不因心跳成功就授权执行（`backend/api/routes/agent_api.py:652`）。

### R09 · 观察 · 退役不是认证撤销；设备 re-home 是额外的输入副作用面

- **涉及**：F2/F4/F6。`docs/adr/ADR-0035-agent-host-identity.md:63` 明示接受共享 AGENT_SECRET；Socket.IO 接受共享 secret 和自报 host_id，并加入该 room（`backend/realtime/socketio_server.py:153`）。退役过滤只能约束选中的业务记录，不会撤销另一身份的认证能力，也不替代 SSH 凭据/机器上的 secret 清除。这是已接受的信任边界，不应误报为本 ADR 新引入的漏洞。
- 完整心跳还会新增设备、改 device.host_id；只有其他 host 的 ACTIVE lease 阻止 re-home（`backend/api/routes/heartbeat.py:373`、`backend/api/routes/heartbeat.py:385`、`backend/api/routes/heartbeat.py:403`）。所以 D4“如实记录心跳”不只是写 host 遥测，尤其要明确退役 host 还能否让无租约设备迁入其归属。迁离退役 host 与迁入退役 host 的政策不能靠一个列表过滤器推导；保留 lease 阻断，不擅自释放租约或改历史 Job 的 host。
- **v0.1 落点**：在 D4/D6 说明上述输入侧边界；至少将被归入退役 host 的设备排除出新执行库存，并测试迁出、迁入、ACTIVE/grace-held lease 各分支。是否限制迁入属于需要明确的政策，不将合法的物理迁移一概视为攻击。
- D6/Revisit 补充：物理下架后离开受信管理域、需主机级可归责审计时，**当时**评估 ADR-0035 的触发条件（`docs/adr/ADR-0035-agent-host-identity.md:176`），不能只等“per-host 凭据已经落地”。不要为了恢复退役机心跳而自动向其同步轮换后的全局 secret。
