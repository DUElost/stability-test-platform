## 3. 闭环模式核验

### IV-W01 机制并非口号（核验通过）

`tools/dev/ai_work.py` 已机械化的约束（契约 `execution-contract.md` §3.4/§3.5，v1.10）：

- `declare` 对**在窗同 issue** 默认 `[REFUSED]`，需 `--force` 显式放行并留痕；
- **决策类**（scope 落 `docs/adr/ADR-*` 具体文件）未带 `--issue` 时默认拒绝，`--force` 放行时输出 `[WARN]`；
- `effective_scope = declared ∪ derived(Git diff)`，声明不能覆盖 Git 事实——这是正确的认识论方向（不制造假锁）。

Registry 现状：158 条记录，`FINISHED×MERGED` 146（92.4%），`ABANDONED×NO_PR` 4，`FINISHED×PR_OPEN` 4，`CODING` 2–3；harness 分布 `zcode 53 / cursor 36 / codebuddy 32 / claude 19 / dsh 13 / opencode 3 / codex 2`。

**这同时是 CA-C02/CA-W03「双源记账」论点的一个活样本**：同一结论在四个载体里各写一遍，且相互之间没有自动一致性校验。综合轮应在汇聚时显式声明"以哪一份为准"，否则差异会被下一次漂移放大。

### IV-W03 台账正文与 issue state 是双源，且已漂移

台账正文是**发现索引**（无 state 列），事实状态只在 GitHub issue 上——这本身可接受，但已出现内容漂移实例：

- R02 台账 `#910`「设计与既有风险」仍列 `R02-R03 = #909`（`ENV=internal` 明文 HTTP 例外），标注"相关 #46"；而 `#909` **已 CLOSED**（其结论已由 ADR-0024 v1.1 收口）。
- 同因：`#891` 等台账正文中混入与本轮无关的历史编号（如 `#720`），读者无法从台账判断哪一项仍成立。

**影响**：审阅者必须回查 GitHub 才能判断台账条目是否仍然有效；而"回查"正是双源记账最容易漏掉的一步。

### IV-W04 单点审阅与合入

09-07 起 183 个 PR 全部由同一人类身份合入（09-09 起 100%）。配合 IV-Q04 的轻量 PR 路径，实际形态是：**编译期/静态类门禁自动，行为类验证依赖作者自证 + 夜间（当前为红）**。在"批量 PR"（如 `#1304` 一个 PR 收 5 个 P1）场景下，独立验证的深度进一步压缩。

## 5. 结论（摘要三问）

1. **覆盖**：R01–R15 分区与台账齐备，但「审查完成」目前只等于「发现已登记」。真实缺口是三类：**跨区收口未做**、**前一轮 44 条存量未消化**、**总纲 §5 自述与事实互相矛盾**。另有一批无主面（性能/负载、CVE/供应链、凭据生命周期、助手效果成本、数据保留与隐私、动态验证）。
2. **修复质量**：**准确=是**（105/105 关联合并 PR、0 reopen、原生秒级关单）；**有效=是**（机制化修复为主，抽样 21/25 带测试、25/25 带 Note）；**可持续=条件未满足**——唯一能独立证伪后端修复的自动网连续两晚为红且不阻断合入，过渡修复的 Revisit 无到期收割。
3. **闭环模式**：**方向准确、当前有效**。契约+门禁+Agent Note 是真实的复利资产（跨 harness 可迁移的记忆与可执行约束）；风险集中在三处：**验证权仍在"作者自证"**（IV-Q04）、**多人多稿无双源治理**（IV-W02/W03）、**单点合入**（IV-W04）。

## 9. 附：组合治理核验（临时止血 / 类级复发 / ADR 候选）

> 本节回答"已解决与未解决的 issue 中是否存在临时止血、是否有需要组合治理或新立 ADR 的情况"。
> 判据取第一性原理：**该修复是否降低了这一类问题的复发概率**——机制化修复降低，实例化修复不降低；
> 复利口径下，契约/门禁/Agent Note 是资产，重复点修是负债（每次都要重新理解同一根因、重写测试、重评审）。

### IV-B02 隐性过渡：同一根因的点修链（比显式止血更值得警惕）

三条链各自都"修好了当次现象"，但根因一直没被收口：

1. **迁移种子常量三连**：`#894`（入口改动）→ `#1171`（就地改迁移内 `content_sha256` 常量）→ `#1276`（新增回填迁移修旧库）。

**阈值规则建议（与 CA-D04 同源，本文给判据）**：同一类第 **2** 次出现即应升级为机制级修复
（门禁 / 契约 / 测试 harness）；第 **3** 次仍未升级即判定治理失效，须在综合轮显式记录理由。
按此规则，**seed 常量类（第 3 次）与静默吞类（第 27 次）均已越过阈值**。

**反例（证明机制化在本仓可行）**：`#1101`（改队列的共享原语 `GH_TOKEN`，一次修整类，见 IV-Q02）与
`#890`（leadership 分级 fail-closed，一条策略覆盖现在与未来任务）——这两例说明"改原语而非改调用点"
在本仓是被验证过的工作方式，缺的不是能力而是**默认把它用在每一类上**。
