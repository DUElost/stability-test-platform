## 1. 总评

**Needs-revision**（方向正确，Accepted 前需修 3 处阻断项）。

D1/D2 的「生命周期列与硬删分家」方向成立，`retired_at` 与存活正交、退役可解除、
历史不清空，与 #796/#937 决策自洽。但 v0.1 在**过滤面穷尽性（F2）、心跳告警去重
（F3）、身份/换机审计（F4）**三处存在与现有实现直接冲突的缺口，若按 v0.1 原文
实现会产生「退役主机上的 PlanRun 永久排队」「活体退役主机通知轰炸」「换机审计
证据覆写」三类真实缺陷。建议 v0.2 修订后再转 Accepted。

## 3. 发现

### F1 语义完备性 —— 建议

**F1.1 前置「非 ONLINE」未覆盖 DEGRADED 的活体歧义（设计风险）**

`session_watchdog.py:43-48` 只把 `Host.status == ONLINE` 且心跳超时的行置 OFFLINE。
`DEGRADED` 主机**永远不会**被 watchdog 置为 OFFLINE；其状态只能由下一次心跳
（`heartbeat.py:236` / `agent_api.py:829` 直接 `host.status = payload.status`）改写。
而 v0.1 D2 的退役前置写作「非 ONLINE + 无活跃 Job」（ADR §2 D2、§4 运维代价）。

- 触发：一台 `status=DEGRADED` 的活体主机（`capacity_reporter.py:161` 可产出
  DEGRADED health，Agent 心跳如实上报）满足「非 ONLINE」，且此刻无活跃 Job →
  **可直接被退役**，绕过「先停 Agent」意图。
- 影响：退役瞬间该机仍在运行，D4 仅告警不阻断，D5 只收口新派发——形成「活体
  退役 + 通知轰炸」的组合，正是 ADR 想避免的失败模式。
- 建议：前置改为**显式白名单**（`status == OFFLINE`）或「`status == OFFLINE`
  且 `last_heartbeat` 超时」，而非 `!= ONLINE`；v0.2 落点 ADR §2 D2。

**F1.2 无 cordon 语义，繁忙集群存在停机竞态（设计风险）**

前置要求「非 ONLINE」意味着运维必须**先停 Agent**，但在空闲 `ONLINE` 主机上，
停 Agent 与派发之间无原子保护（`plan_dispatcher_sync.py:155` 派发只排 OFFLINE），
新 PlanRun 可随时命中。ADR §4「运维代价」已承认此点，但未给出窗口。

- 建议：v0.2 增补「cordon（停止派发）先于物理停机」的过渡态，或明确接受该竞态
  为已知代价并写入运维 runbook。二者择一，不能留白。

### F2 过滤面穷尽性（D5 不变量）—— 阻断

v0.1 D5 列了五面（派发快照 / claim / 统计容量 / 默认列表 / 控制面动作）。实际
代码中存在**第六面及五面内部的致命遗漏**：

**F2.1 致命派发原因未纳入 `host_retired` → 永久排队死锁（阻断）**

`plan_dispatcher_sync.py:68` 定义 `_FATAL_DISPATCH_REASONS = ("not_found", "no_host")`；
`_classify_dispatch_devices_sync` 对**除这两者外**的所有不可用原因一律作为
`queue_blockers` 使 PlanRun 以 QUEUED 等待（`:516-518`、`:673-675`）。准入泵在
`admission_pump.py:666-675` 对非 fatal 的不可用同样 `_RetryableAdmission("DEVICE_BUSY")`
无限 requeue。

- 触发：退役主机的设备若被分类为 `host_offline`（`:155-160`，退役机停止心跳后必然
  如此）或新增 `host_retired` 原因但**未加入** `_FATAL_DISPATCH_REASONS` → 命中
  退役设备的 PlanRun 永久 QUEUED。
- 影响：用户看到 Run 卡在排队，无失败出口；与 ADR-0026 准入队列语义直接冲突。
- 建议：v0.2 D5 明确「退役是**不可重试配置语义**」：`_classify_dispatch_devices_sync`
  增加 `host_retired` 原因并把 `host_retired` 纳入 `_FATAL_DISPATCH_REASONS`；实现单
  必须覆盖 `admission_transaction` 的 fatal 分支。

**F2.2 遗漏面清单（均需 file:line 复核）**

| 面 | 位置 | 问题 |
|---|---|---|
| 设备列表 | `devices.py:294-377` | `list_devices` 无 host 退役过滤；退役机设备仍出现在全局设备列表，前端多选/项目页可误选 |
| 设备详情 | `devices.py:380-393` | 同上，单设备详情不标注退役归属 |
| 派发预备 | `plan_dispatcher_sync.py:509-518` | 见 F2.1；`device_host_map` 不携带 retired 标记 |
| 扫描目标 | `plan_run_scan_scope.py:113-122` | `iter_plan_run_scan_hosts` 只返回 `(host_id, status)`；退役机的**历史** PlanRun 扫描下发不检查退役（这是否正确需 v0.2 显式裁定：历史 PlanRun 补扫是否应触达退役机） |
| 批量热更新 | `batch_hot_update.py:90-95` | 直接模式按 `Host.status == "ONLINE"` 取主机，退役机若仍 ONLINE 会被热更新，与 D5「控制面动作拒绝」不符 |
| AI 控制面 | `ai_assistant/orchestrator.py:670-691` | `reload_agent_config` 只查 `host.status != "ONLINE"`，退役但 ONLINE 主机仍可被 AI 下发 |
| watcher 管理态 | `hosts.py:557-582` | `watcher-admin-state` PATCH 无退役拒绝 |
| Socket.IO 下行 | `socketio_server.py:822` (`room=agent:{host_id}`) | 退役主机若已重连 socket，`call_agent_control` 仍可送达；D5 需明确是否在 RPC 侧拦截 |
| 主机详情 | `hosts.py:365-372` | `get_host` 不标注退役态（D5 只约束「默认列表」，详情需返回 retired 字段供 UI） |

- 建议：v0.2 D5 从「五类」扩展为**收口矩阵**（读路径 / 写路径 / 下行 RPC），并
  指定每面的 owner 文件；实现单按矩阵逐点配反例实证。

### F3 心跳策略（D4）—— 阻断

**F3.1「沿用现有告警去重惯例」为不成立的事实断言（阻断）**

ADR §4 不变量 3 与 D4 称退役告警「按主机去重……沿用现有告警去重惯例」。核验
`notification_service.py:329-336`：`_delivery_identity` 的去重键是
`(event_type, run_id, task_id, device_serial)`，且 `_load_prior_channel_delivery:343-345`
在 `run_id is None` 时**直接返回空**（不去重）。主机级告警无 `run_id`，无法复用。

- 影响：若无新去重事实源，退役活体主机每心跳周期（默认 10s，`agent_api.py:844-849`
  动态建议）产生一次通知 → 通知轰炸。
- 建议：v0.2 给出具体事实源（推荐 `Host.extra['retired_alert_sent_at']` 或独立列），
  并定义**重置条件**（F7.2）；删除「沿用现有惯例」的错误事实句。

**F3.2「不做 409」取舍成立，但 backpressure/版本门禁影响需补一句（观察）**

`agent_api.py:821-849` 心跳响应承载 `scripts_outdated` 与 backpressure，拒绝心跳会
伤及二者——v0.1 §3 已正确保留为 Revisit。建议 v0.2 明确「退役主机心跳响应**仍
返回** backpressure/outdated，Agent 行为不变」，避免实现者误判。

### F4 身份与换机（D6）—— 阻断

**F4.1 同 IP 换机「= 同一身份」在现行唯一约束下是唯一物理可能，但冲突后缀路径
是死代码（事实纠偏）**

- `models/host.py:41`：`ip = Column(String(64), unique=True)`；`hosts.py:214-217`
  创建前显式 409。
- `heartbeat.py:83-97`：心跳发现 IP 被其他 host 占用时**保留旧 IP 并告警**，不
  新建行。
- `host_identity.py:43-48` 的 `allocate_host_id` 冲突后缀分支，在 `ip` 全局唯一且
  心跳按 id 复活的组合下不可达于「同 IP 换机」场景（仅 `host_id` 前缀冲突时可能）。
- 影响：D6 的「id 本就 IP 派生 → 同 IP = 同身份」描述与 `unique(ip)` 一致，结论
  成立；但 ADR §1.2「冲突追加短后缀」被读作换机路径会误导实现者。
- 建议：v0.2 在 §1.2 明确该分支的**实际可达边界**，并说明换机只能走 unretire。

**F4.2 `boot_id`/`agent_instance_id` 原地覆写导致审计证据丢失（阻断）**

`heartbeat.py:244-247` 单值覆盖 `host.boot_id` / `host.last_agent_instance_id`；
`job_instance` 无快照字段。同 IP 换机（unretire）后，旧机器的身份证据被新机器
覆写，历史执行归属不可回溯。

- 建议：v0.2 D6 要求 unretire（或首次换机心跳）**持久化原机器身份快照**至审计
  （`record_audit` details 或 `Host.extra` 历史段），并明确 `boot_id` 变化是否触发
  告警。与 ADR-0035 §4.2（host 表将增 `agent_secret_hash`/`credential_version`）
  的交互应写入 Revisit。

### F5 一致性与迁移 —— 建议

**F5.1 三列迁移的 schema-sync 配对（建议）**

仓库要求 model ↔ alembic ↔ create_all 对账（`AGENTS.md` 硬不变量 / #960 先例）。
D1 三列 additive nullable 需同时：`models/host.py`、alembic 迁移、Pydantic
`HostOut`（`api/schemas/host.py`）、前端 `types.ts`。若建索引须显式命名（`models/host.py:60-64`
的 `host_hostname_key` 先例），否则 `check_schema_sync` 漂移报警。

**F5.2 与 ADR-0019/0025/0026/0034 无结构冲突（观察）**

- ADR-0019（租约/容量）：退役不删设备行，与 D6 一致；`Device.host_id` FK
  `ondelete=CASCADE`（`models/host.py:72`）不因退役触发。
- ADR-0025（存储生命周期）：`Host.extra['archive']` 命名占用已在 §1.2 识别，
  ADR 用 retire 规避正确；但扫描/合并的 `PlanRun.run_context['archive']`
  （`dedup_scan.py:246`）与 `Host.extra['archive']`（`agent_api.py:3179`）是两套
  命名空间，v0.2 应确认退役不与之交互。
- ADR-0026：见 F2.1，**最大冲突点**。
- ADR-0034：评审/执行契约不受影响。

### F6 安全面 —— 建议

**F6.1 强校验与审计字段（建议）**

- `retire_reason` 建议 `min_length=1`（必填）；`unretire` 同样记录 reason（v0.1
  D2 称「unretire 无前置」，但未强制审计 reason，与 D1 的「全程审计」不完全一致）。
- 影响：在全局共享 `AGENT_SECRET`（ADR-0035 §3 现状）下，退役主机仍持有效 secret，
  `claim`/`hot-update`/SSH 的拒绝若只在 ONLINE 判定上做，存在 ONLINE 竞态绕过。
  建议 D5 的控制面拒绝以 `retired_at IS NOT NULL` 为**独立判据**，不依赖 status。

**F6.2 SSH/安装拒绝（建议）**

`hosts.py:585-618`（hot-update）、`hosts.py:793-885`（install）、
`ai_assistant/orchestrator.py:670-691` 均以 status 判定。退役主机若 status=ONLINE
仍可 SSH，与「IP 重分配防污染」目标冲突。建议 v0.2 显式要求三处加 retired 前置。

### F7 验收可测性 —— 观察

**F7.1 反例实证判据（观察）**

§5 验收 2 的「临时移除任一过滤点 → 用例转红」可操作，但需 v0.2 为**每个过滤点
指定唯一断言**（如 F2.1 的 fatal 判据断言 `queue_reason`/Run 终态为失败而非
QUEUED），否则实现单无法判定「对应用例」。

**F7.2 单次告警的测试语义（观察）**

需明确：退役主机**多次心跳只告警一次**；且 `OFFLINE → ONLINE` 震荡后是否重置
计数（v0.1 §4 不变量 3 括注「除非状态震荡」含糊）。建议 v0.2 定义
`retired_alert_sent_at` 的写入与重置条件，验收用例覆盖「连续 N 次心跳 → 1 条通知」
与「震荡 → 按定义重置/不重置」两个边界。
