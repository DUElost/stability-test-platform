## 2. 发现项分级清单（Findings）

### 2.1 阻断项（Blockers）

#### [A-01] 阻断：新表严禁挂「冲突时以本文为准」——新表仅拥有所有权路由权（Ownership Routing Authority）
- **证据位置**：`docs/design/2026-storage-roles-and-aliases.md:4`（「`目的：角色、别称、env、IP 一一对应；冲突时以本文 + 代码为准`」）、issue 正文候选方案 A 描述（「`沿用 storage-roles 形态与"冲突时以本文为准"条款`」）。
- **事实与风险**：
  `storage-roles-and-aliases.md` 能够声明「冲突时以本文 + 代码为准」，是因为它自身就是存储角色、路径和环境变量的**实质事实源（Substantive Source of Truth）**。
  然而，跨 ADR 语义所有权表（`2026-semantic-ownership.md`）的定位是**概念到 Canonical Owner ADR 的映射路由表**，它自身并不承载各子系统（如调度状态机、日志事件、版本管理）的深入设计细节与推理上下文。
  若新表被赋予「冲突时以本文为准」，它将蜕变为凌驾于所有 Accepted ADR 之上的第 5 份平行实质权威。一旦新表的一句话摘要与 Owner ADR 的正文出现微妙用词差异，将直接导致语义冲突升级。
- **落点与整改建议**：
  新表头部目的条款必须明确定位为**路由权威**，措辞调整为：
  > 「**本文是跨 ADR 概念所有权归属的唯一权威（Ownership Authority）；各概念的具体定义、生命周期行为与实现契约，以本文指向的 Canonical Owner ADR 及代码为准。**」

#### [A-02] 阻断：S15「复用 S2 验表内 file:line」在机读逻辑上不成立且假阳性极高
- **证据位置**：`tools/dev/check_governance_surface.py:147-164`（S2 `check_links` 源码实现）、issue 正文重点问题 F3。
- **事实与风险**：
  1. 经查 `check_governance_surface.py:148`，S2 的本职是 `markdown 相对链接目标存在。跳过 http(s)/mailto/# 锚点`。S2 仅做文件系统路径存在性校验，内部**根本没有解析或校验源码 `file:line` 行号的能力**，所谓「复用 S2 验 file:line」在代码层属于无源之水。
  2. 代码中的具体物理行号（`file:line`）是高度易变的目标（上游文件哪怕只插入一行 import、注释或类型标注，都会导致下方所有行号偏移）。若将源码物理行号作为 CI 硬门禁断言，会导致日常无关 PR 频繁因行号漂移而假红（Flaky CI），严重破坏研发节奏。
- **落点与整改建议**：
  S15 门禁的定位与校验方式应降维解耦：
  1. **代码真源定位**：校验目标文件在仓内存在（`os.path.exists`），锚点采用语义符号（函数名、类名、类型定义或 S11 式文本唯一 token），**物理行号绝不进入机读门禁断言**（行号仅可作为人类阅读的非约束性提示，或完全省去行号而仅保留文件名与符号名）；
  2. **ADR 锚点定位**：校验 ADR 文件存在，若带章节锚点则校验该 Markdown 标题锚点存在。

#### [A-03] 阻断：S15「同一概念 ≥2 owner → 红」若做跨 ADR 散文扫描，假阳性达 100%
- **证据位置**：`docs/adr/ADR-0028-device-log-event-and-continuous-upload.md:44`、`docs/adr/ADR-0018-infrastructure-layer-framework-adoption.md:315`、`docs/adr/ADR-0032-unisoc-mtk-parallel-dedup-pipelines.md:37`、`docs/adr/ADR-0025-phase4-architecture-alignment.md`。
- **事实与风险**：
  在复杂分布式系统中，一个核心业务对象必然存在**生命周期分层权威（Layered Authority）**。
  以 X2 日志域为例：`log_signal` 是跑测期 Agent 内存与 Outbox 的实时异常流权威；`device_log_event` 是终态落库后的归档事件权威记录；`ADR-0032` 是多厂商双轨并行 dedup/merge 的流水线行为权威；`ADR-0025` 是中心存储物理路径布局权威。
  这四者在自然语言中均会声明「XX 是唯一权威」，但它们各自约束的是不同切面，在架构上完全自洽（`#530` 与 `docs/design/2026-adr-0025-log-flow-sequence.md` §5 已正式确认此自洽性）。如果让 S15 用正则扫描 48 篇 ADR 中「同一概念」是否出现多个「权威」，X2 将被直接误判为重大冲突，造成 100% 假阳性。
- **落点与整改建议**：
  门禁判据必须从「扫描 ADR 全文散文」收敛为「**校验所有权表（`2026-semantic-ownership.md`）的数据结构**」：
  1. 表内**每行代表一个不可再分的细粒度概念切面**（例如 `日志 - 跑测期异常实时流` 与 `日志 - 终态持久化事件记录` 作为两行分开定义）；
  2. 表内每行有且仅有一个 Canonical Owner ADR；
  3. 表内概念标识不允许同名重复；
  4. 存量或增量 ADR 若在头部声明了 `归属域：semantic-ownership §N`，其章节号必须在表中有效存在。

## 5. 重点问题详细回答（F1–F7）

### F1：立项必要性与量化判据
- **必要性评估**：有明确的正收益。
- **量化判据**：
  当一个核心概念同时满足以下两项条件时，必须纳入跨域语义所有权表，而非仅靠就地（in-place）修补：
  1. **跨域度**：概念涉及 $\ge 2$ 个不同子系统域，且被 $\ge 3$ 篇 ADR 作为决策对象或核心前提引用；
  2. **漂移代价**：点对点声明需要维护 $O(k^2)$ 对相互声明（如 X1 涉及 0020/0021/0033，X3 涉及 0025/0027/0033），在敏捷迭代中极易发生漏改与断层。
  在集中路由表中维护仅需 $O(k)$ 复杂度。针对此类高阶概念，建立 Living 路由表收益确定。

### F2：平行权威边界划分（谁 supersede 谁）
- **职责划分**：
  - `AGENTS.md`：所有 AI Harness 的全局最小启动契约与硬不变量（基石）；
  - `DOC-MAP.md`：功能与业务需求的检索入口与导航索引；
  - `execution-contract.md`：AI 执行生命周期、并发与工作区协议；
  - `storage-roles-and-aliases.md`：物理/逻辑部署角色、存储挂载路径与环境变量映射；
  - `2026-semantic-ownership.md`：**概念权威归属的唯一索引源（Ownership Router）**。
- **表述权裁决**：
  新表仅拥有**所有权归属判定权（谁拥有定义权）**，绝不拥有**概念内容解释权**。当内容发生冲突时，以 Owner ADR 正文和代码为准，新表不得覆盖 Owner ADR 的实质决策。

### F3：S15 假阳性防范与机读判定
