## 3. Q3：修复模式是否准确、有效、可持续

### 3.1 骨架成立（第一性原理层面）

| 决策 | 为何成立 |
|---|---|
| 审查与修复分离（总纲禁止审查中改代码） | 避免审查者为自己刚写的代码背书 |
| Registry 是 visibility-only，非调度器 | 并行不伪造全局锁；`effective_scope = declared ∪ derived`（diff 为 ground truth） |
| issue 为工作单元 + 独立 worktree / branch | 可追溯、可并行、可回滚 |
| 同主题 ≥3 issue → 升格 ADR | R11 #1117/#1120/#1122 → ADR-0036：避免点对点补丁语义打架（**真复利**） |
| Agent Note 四段式 | 降低 harness 切换成本；**实测合规率 100%（09-07 后）** |

### 3.2 实测数据

**(d) FIFO 死锁机制（本稿通读 `scripts/ci/pr-automerge-queue.sh` 确认）**

- 队首 = `sort_by(.createdAt)` 最老的 open non-draft PR；

- 脚本已有 `cannot update pr branch due to conflicts` 的**冲突**解毒路径，
  **无「红 check」解毒路径**；
- #1246 建议的三条处置（逃生重试 / 显式告警 / 人工打破）**截至本稿均未实施**，#1246 仍 OPEN。

|---|---|---|
| 发现速度 ≤ 消化速度 | ⚠️ 改善但未达标 | 净欠 36；R13/R05 等仍积压 |
| 集成通道不自持停摆 | ❌ **未满足** | #1246 OPEN；09-09 实测 17.5h 中位延迟 |
| 修复有独立验证网 | ❌ **未满足** | `ci.yml` 中 `backend-test`/`frontend-check` 的 `if: github.event_name != 'pull_request'` → **PR 上恒 SKIPPED** |

**验证网证据（关键）**：实测 PR #1309 的 check 状态为
`backend-test: COMPLETED SKIPPED`、`frontend-check: COMPLETED SKIPPED`、`docker-build: COMPLETED SKIPPED`。
即 **「PR 全绿」≠「该 PR 通过了测试套件」**，全量缺陷发现窗口**最长 24 小时**
（夜间 `main-ci-backstop`，UTC 18:00）。这是刻意的注意力优先取舍（`ci.yml` 注释写明），
但代价必须记账。

## 5. 对 R01–R15 的总体定位

**已完成**：15 个分区的**静态只读**审查，产出 177 条发现（141 已关），
建立「台账 + 子项 issue」可追溯结构，并驱动一批高质量根因修复。**这是真实且显著的产出。**

**未完成**（故不构成「全面审查交付完成」）：

2. 逐维覆盖记录与逐轮区域报告——**零存在**，覆盖完整性不可审计；
3. 动态/运行验证——**15/15 轮均为静态**；
4. 存量 148 条 pre-R-era 缺陷池——**未被任何轮次纳入**；
5. 治理面自身一致性——**未被任何轮次纳入**。

**结论表述**：可宣称「R01–R15 分区静态审查已开展并产出有效发现」；
**不可宣称**「全面审查覆盖已完成」或「审查面已穷尽」。
