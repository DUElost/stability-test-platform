## 0. 总评

**Needs-revision**（6 阻断 / 14 建议 / 9 观察）。

先说成立的部分，避免修订时误伤。D1（独立 `retired_at` 列、不新增 `HostStatus`）、D2（retire/unretire 与 `DELETE` 分家）、D3（不提供带历史硬删）、D7（显式不做）方向正确，且与本仓既有实践同构——尤其 `watcher_admin_active`（`backend/models/host.py:34`：admin 独占写、心跳不触碰、逐消费点过滤）与 **#960 维护窗口**（`host.py:57-58` + `backend/services/host_maintenance.py:55` + `plan_dispatcher_sync.py:163` + `agent_api.py:406`：**同表可空时刻列、不改 status、同时收口派发与 claim、已生产验证**）。后者是本 ADR 最好的实现模板，v0.2 应显式引用，比现在引的 ADR-0026 更贴切（见 O7）。

不成立的集中在**「现状代码已经替我挡好了」这一类断言**，以及三处**事实核验遗漏**：

1. **D4 的心跳锚点挂在一条无调用方的路径上**（Z1）：ADR 引 `agent_api.py:806-829`，那是 `POST /api/v1/agent/heartbeat`；Agent 侧权威路径是 `POST /api/v1/heartbeat`（`backend/agent/heartbeat.py:84`；`backend/agent/heartbeat_thread.py:27` 自述 "SOLE authority"），而 `/api/v1/agent/heartbeat` 全仓**零调用方**。按 v0.1 文字实现，「保持退役 + 单次告警 + 异常徽标」在真实心跳上永不触发。
2. **D5 的"五面"不是穷尽面**（Z2）：D4 明许退役主机 `status` 照常变 ONLINE，于是**现存所有以 `status` 为唯一判据的路径对退役主机全部放行**（实测 19 处显式比较，非测试代码）。§1.2「退役只要同时被这两处识别即可落在真正的风险面上」在 D4 之下为**假**——claim 只比 ONLINE（`agent_api.py:401`）、派发只排 OFFLINE（`plan_dispatcher_sync.py:155`），二者都不看退役。 另有一条 D5 未答的必答题（Z6）：已在飞的 Run 遇 retire 是按冻结快照还是活读——仓内同构开关已选冻结快照，claim 却是活读。
3. **不变量 1 的 ⇔ 与现状不等价**（Z3）：DEGRADED 今天「可派发、不可认领」；按 ⇔ 字面实现会顺带把 DEGRADED 踢出派发＝未声明的容量行为变更。且退役必须是**致命**派发拒绝，否则撞 `_FATAL_DISPATCH_REASONS`（`plan_dispatcher_sync.py:68`）语义，PlanRun 永久 QUEUED。
4. **不变量 3 引用的「现有告警去重惯例」作为机制不存在**（Z4），且实现若把去重标志写进 `host.extra`，会被心跳整键重建抹除（`heartbeat.py:250-281`，仅 6 键保留）→ **每拍重响的告警风暴**。
5. **D6「boot_id / agent_instance_id 变化在详情与审计可见」零落点**（Z5）：`HostOut` 不含这两列、前端零命中、心跳路径完全不写审计、`previous_boot_id` 阅后即焚；且 `boot_id` 每次开机随机（`backend/agent/identity.py:21-42`）——**换机与重启在信号上不可分辨**。
6. 三处事实错位（不推翻结论，但 v0.2 必须改写）：`§1.1「跑过 Job ⇒ 永久 409」`受 `run_retention_cleanup`（`backend/scheduler/cron_scheduler.py:27` 默认 **3 天**、`:224-330` 删 StepTrace/DeviceLease/JobArtifact/JobInstance，注册于 `app_scheduler.py:244`）时间限制；`D3/§1.3/Revisit-3` 把 DB purge 交给 **ADR-0025**，而该文对 `retention|purge|保留期` **零命中**（它只管日志文件闭环）＝死引用；`§4 前端面`「`api.hosts.remove` 无 UI 调用点」为**双错**（方法名是 `delete`，`hosts.ts:24-25`；且**有**调用点 `HostsPage.tsx:107`、`:308`）。

D1–D3、D7 与「退役即终态」的定性我认可；阻断项集中在 D4/D5/D6 与不变量的**可实现性与事实基础**。§4 给出可直接抄进 v0.2 的最小修订集。

## 2. 逐项评审（F1–F7）

### F1 语义完备性 —— 判定：**建议**（流程覆盖成立，前置条件语义不精确）

退役/换新/下线/误操作恢复四类流程，D2+D6 组合可覆盖（换新＝retire+unretire，误操作＝unretire 无前置，下线＝retire）。三个缺口都在**判据层**：

1. **「非 ONLINE」不等价「Agent 已停」**。`host.status` 今天有 **4 个写手**：Agent 自报（`heartbeat.py:236`）、轻量心跳无条件 ONLINE（`agent_api.py:829`）、watchdog 超时（`session_watchdog.py:82`）、**读路径惰性改写并 commit**（`hosts.py:71`，被 `:354` 列表与 `:370` 详情调用；`devices.py:68` 在设备读路径里顺带把 host 打 OFFLINE）。同一条超时在不同模块取值不同：`session_watchdog.py:34` 默认 **120s**，`hosts.py:53`、`devices.py:30`、`precheck/reachability.py:40` 默认 **300s**（`settings.py:60` 向前端暴露的是 300 那个）。后果：Agent 刚停的 0–120s 内 status 可能仍是 ONLINE，retire 返回 409「请先停止 Agent 服务」而运维其实已经停了；§4「运维代价：退役要求先停 Agent」被写成一条**受竞态影响的人工步骤**。（→ S1）
2. **前置只查 Job，不查 ACTIVE 租约**。`hosts.py:488-499` 只看 `JobInstance`；租约侧 `lease_manager.py` 不引用 Host 状态（`grep Host|ONLINE|OFFLINE` 仅命中 `:37,:129` 的 `host_id`），且 `LeaseType.MAINTENANCE`（`models/enums.py:40-43`）**不要求 job_id**（`lease_manager.py:68-76`）→ 一台 OFFLINE、无 Job 的主机可带着 ACTIVE 租约被退役，此后其设备 re-home 会永久卡在 `heartbeat.py:385-392`。（→ S2）
3. **DEGRADED 不是"过严"，而是不变量方向反了**。DEGRADED ≠ ONLINE → 允许退役，不过严；真问题是 DEGRADED **今天可派发**（`plan_dispatcher_sync.py:155` 只排 OFFLINE）**却不可认领**（`agent_api.py:401` 要 ONLINE），且 DEGRADED 确有生产者（`schemas/host.py:104 Literal["ONLINE","OFFLINE","DEGRADED"]` + `heartbeat.py:236` 逐字写入）→ 不变量 1 的 ⇔ 与现状不等价（→ Z3）。

### F3 心跳策略（D4）—— 判定：**阻断**（取舍成立，两处支撑不实）

D4 的方向我认可，且理由比 ADR 给的更强：**status 的写权事实上在 Agent 手里**（`heartbeat.py:236` 逐字写上报值、`agent_api.py:829` 无条件 ONLINE），生命周期绝无可能寄生 status——连"OFFLINE"都只是服务端四个写手之一。但：

1. **Z1（阻断）告警/徽标锚在死路径**：见 §1 表第 3 行。权威路径还多两个轻量端点没有的行为：**按 IP 找回退役行**（`heartbeat.py:199-206`，换 `host_id` 的机器可凭 IP 悄悄复活退役行）与**设备 re-home**（`:403`）。D4 必须点名 `heartbeat.py`，并把"IP re-home 命中退役行"同样视为活体退役。
2. **Z4（阻断）「沿用现有告警去重惯例」——该惯例作为机制不存在**。通知栈只有三样：
   - SAQ 在飞去重键 `f"notif:{event_type}:{run_id}:{device_serial or ''}"`（`notification_service.py:649-654`，`dispatch_notification_async :657-681` 作 enqueue key）：**键形不含 host_id** → 主机级事件退化为 `notif:HOST_x:None:`，跨主机互吞；
   - 投递级幂等 `_delivery_identity :329-336` + `_load_prior_channel_delivery :339-362`（**`run_id is None` 直接短路 `:343-345`**），且 ADR-0036 D7 明写「**不承诺端到端去重**」（`ADR-0036-notification-delivery-semantics.md:79`）；`NotificationLog` 无任何 dedup/unique 约束（`models/notification.py:61-78`）；
   - 生产者侧**边沿触发**（`heartbeat.py:140-160` 的 `already_offline` 守卫；`session_watchdog.py:44-46` 只选 `status==ONLINE`）——是写法模式，不是机制；且 `EventType` 枚举**无主机级事件**（`models/notification.py:16-20`：仅 RUN_COMPLETED/RUN_FAILED/RISK_HIGH/DEVICE_OFFLINE）。
   - **风暴陷阱（确定缺陷）**：`host.extra` 每拍被整键重建，仅 6 键保留（`heartbeat.py:250-281`）。把"已告警"标志塞进 `extra` 的实现会在下一拍被抹除 → 每拍重响。
3. **代价被低估一处**：退役机继续心跳会被 `script_catalog_outdated` 驱动自动重拉脚本目录（`heartbeat.py:232-233` 计算、`:515` 下发 → Agent `heartbeat_thread.py:361-366` 回调 `_on_scripts_outdated`），而它不再被允许热更新 → `agent_code_sync_status` 长期判 drift（`schemas/host.py:87`）＝升级合规面上的永久红点。这不是失败模式，但 §4「运维代价」没写。（→ S9）
4. **双端点不对称**：轻量端点丢弃 `boot_id/agent_instance_id`（`agent_api.py:806-829` 不写）却无条件翻 ONLINE；权威端点写全。D4 只说"心跳"，实现极易只改一处，另一处成为"能翻 ONLINE 却不告警"的暗面。（→ O2）
5. **§3 否决 409 的论据可再核**：Agent 吞掉全部心跳异常仅记 error 日志（`backend/agent/heartbeat.py:89-91` `except Exception → return None`），409 不会让它崩；真实代价是存活事实失真＋每拍 error 日志。结论（不 409）我赞同，理由建议改写，并要求 Revisit-1 升级 409 前**先设计 Agent 侧处置协议**。（→ O3）

### F4 身份与换机（D6）—— 判定：**阻断**（裁定可接受，可见性承诺无落点）

**「同 IP 换机 = 同一身份」与代码一致，可接受**：`hostname/name/ip` 三列唯一（`models/host.py:28,40,41`）→ 同 IP 起不了第二行；心跳解析顺序 PK（`heartbeat.py:196`）→ **IP 找回**（`:199-206`）→ 建行（`:207-221`），两条命中路径都收敛到退役行。但四点必须写清：

1. **Z5：`boot_id`/`last_agent_instance_id` 的"详情与审计可见"零落点**。`HostOut`（`schemas/host.py:57-93`）**不含**这两列；前端 grep `boot_id` 零命中；`heartbeat.py` 全文件 `record_audit` **0 命中**（心跳不写任何审计）；唯一读者 `agent_api.py:2903-2904 previous_boot_id = host.boot_id` 是局部变量，用于 boot 不符时 CLEANUP（`:2995-3013`），**阅后即焚、无索引、无历史**（迁移 `t8u9v0w1x2y3_add_host_identity_columns.py` 仅 add_column）。更根本：`boot_id` 语义 = 每次开机的内核值（非 Linux 还是伪随机值），见 `backend/agent/identity.py:21-42` ⇒ **换机与重启在信号上不可分辨**。⇒ D6 承诺的审计与恢复证据基础不存在。
2. **身份实际"跟随 Agent 自报"，不严格跟随 IP**：`_sync_host_identity`（`heartbeat.py:76-112`）在 IP 被他行占用时保留旧 IP 并告警（`:83-97`），否则把 `ip/ip_address/name/hostname` 改写成新上报值（`:99-112`）。旧机搬到新网段继续跑 → 按 PK 命中同一行并把那行的 ip **拖走**。D6 应如实描述解析优先级。（→ S8）
3. **冲突后缀路径的边界**：后缀 `-<uuid4hex[:4]>`（≤8 次，超 64 字符放弃，回落 `auto-<12hex>`，`core/host_identity.py:41-49`）**只在旧哨兵 `host_id=0` 自动注册路径可达**（`heartbeat.py:63-65,208`）；正常自报 host_id 时走 `:208` 的 `str(payload.host_id)` **裸建、无冲突检查**。现实缺口：轻量端点自建的行不写 `ip/name`（`agent_api.py:807-814`）⇒ 该行 `ip` 为 NULL ⇒ 同 IP 的旧版 Agent 自动注册会拿到 `198-51-100-6-a1b2` **新行且不退役** → 同一物理 IP 双行、一退役一在用、容量与库存双身份。D6 未裁决这条。
4. **与 ADR-0035 的交互**：ADR-0035 §5:157-159 计划给 `Host` 增 `agent_secret_hash` + `credential_version`（并自述以 `boot_id/last_agent_instance_id` 为存储先例——恰好是本节证明**不可观测**的那两列）。退役＝"永久不再使用"，但 ADR-0038 全文不涉及凭据吊销；per-host 凭据落地后，退役主机凭据若仍可用即成新洞。⇒ 建议新增 D8 明确 `retire ≠ credential revoke`。（→ S8、S3）

### F5 一致性与迁移 —— 判定：**建议**（配套清单很短；回滚断言不成立；两处引用错位）

**配套清单（实测很短，对 ADR 有利）**：

1. `backend/models/host.py:58` 后追加三列——**沿用 `Column()` 旧式**（全 `backend/models/` 对 `Mapped[` 零命中，`declarative_base()` 在 `core/database.py`）；时间列一律 `DateTime(timezone=True)`（`host.py:31,35,50,57`）；**不要写裸 `String`**（models 内无长度 `Column(String,` 零命中，host 表现有列全带长度；`retired_by` 建议 `String(128)` 对齐 `models/audit.py:22`）；ADR 里的「TIMESTAMPTZ」是 PG DDL 词而非本仓声明写法（迁移侧 `postgresql.TIMESTAMP(` 全仓 0 命中）。
2. 一个 additive 迁移，`down_revision` 取当时唯一 head（实测现 head = **`cc33dd44ee55`**，由 `alembic heads` 确认；单头由 `tests/test_alembic_heads.py:12-30` 强制）。**同表模板**：`m8n9o0p1q2r3_host_maintenance_window.py`（两可空列 + 逆序 drop）。`p1q2r3s4t5u6_add_host_watcher_admin_active.py:18-36` 因 `nullable=False` 才需 server_default 两步，且 `:21-22` 注明 SQLite 不支持 `alter_column`——D1 的三列 nullable 可避开。
3. **不要动 `backend/scripts/schema_sync_baseline.json`**（现 7 条，零 host 项；`check_schema_sync.py:8-14` 语义＝「diff ⊆ 基线，基线外必拦」，成对项只豁免成对共现 #944）。⇒ 只改模型不改迁移、或反之，都会被 required check `pr-migrate-empty-db`（job `.github/workflows/ci.yml:286`，对账步骤 `:329`）拦，**"成对"由门禁自动保证，无需登记豁免**。附带脆弱点（O8）：`_diff_key`（`check_schema_sync.py:68-71`）对 `add_column/remove_column` 取 `d[2]|d[3]`，而 alembic 的该元组是 `('add_column', schema, table, Column)`（已安装 alembic 源码 `alembic/autogenerate/api.py:125-130`，非仓内文件）⇒ 列名位落的是 **Column repr**；叠加 `--rebaseline` 的覆盖语义（`:155-169`），一次误用会把 repr 形态条目写进共享基线。**实现单禁用 `--rebaseline`**。
4. 读模型同步：`schemas/host.py:57-93` + `frontend/src/utils/api/types.ts`（AGENTS.md 硬不变量；`pr-typecheck` 拦不住跨语言漂移）。
5. **本次不新增任何索引/约束**（含 `retired_at` 索引）：drop 列时 PG 会连带删索引，正是 `check_schema_sync.py:3-6` 记载的 #644 事故形态。

**回滚断言不成立（S6，确定缺陷）**：§4「回滚 = drop 三列（无状态依赖，退役期间不产生新数据形态）」——`retired_at` 就是 D1 自称的"单一真源"，drop 它＝**一次性、无审计、无前置地解除全 fleet 退役**，按 D5 定义这些主机立刻恢复可派发/可认领/计入统计。这与 §3 否决「心跳自动复活」的理由（运维决定被静默撤销）自相矛盾，且 D2 说 unretire 无前置 ⇒ 回滚成了唯一一条"批量 unretire"通道，比被否决的方案还宽松。另：CI 从不跑 `downgrade`（`.github/workflows/`、`run_gates.py`、`tools/` 三处 grep 零命中）⇒ 门禁绿不证明回滚安全；仓内对危险 downgrade 的处置是手写守卫测试（`backend/tests/migration/test_sentinel_downgrade_935.py:100` 形态）。**缓解恰好在现成机制里**：`record_audit`（`core/audit.py:35-97`）写独立表 `audit_logs`（`models/audit.py:8-31`），迁移回滚不动它 ⇒ 只要 retire/unretire 强制写审计，退役事实可从 `audit_logs` 重放。这条同时把 F6 的双真源问题变成回滚出口。

**跨 ADR**：无实质冲突，两处引用错位。① ADR-0026 正交先例**属实但引偏**——`:121`「三条正交信号」/`:119-129 不变量③`（三存活信号拆三列、三套超时判据）比 §1.3 隐含引用的 `:328`（那是 `plan_run_host` 上 status/phase 两列）更贴切；同表同形的最强模板是 #960 维护窗口（§0 已列）。（→ O7）② **ADR-0025 死引用**：该文标题即「Agent 侧日志闭环」，`retention|purge|保留期` 零命中 ⇒ D3/§1.3/Revisit-3 三处 deferral 无落点；现行 DB 历史清理是 `cron_scheduler.py:224-330 run_retention_cleanup`（默认 3 天，`app_scheduler.py:244` 注册为周期 job），本 ADR 不改动它即可，但必须改口径。（→ S3、S4）③ ADR-0019：`lease_manager.py` 不判 host 状态 ⇒ D6"不回收租约"与代码一致，但需显式化并补前置（S2）；「不计入在线容量」在 ADR-0019 语义下无对应物（容量来自 Agent 上报，控制面无 host 级额度可过滤）。④ ADR-0034/execution-contract：无冲突；但 D5 一张单装不下，建议新增「实施单拆分 + declare」小节（仿 ADR-0035 §5:149-150）。（→ S13）⑤ 登记面：`docs/adr/README.md:89` 已登记 Proposed；**`docs/DOC-MAP.md` 未登记 ADR-0037/0038**（grep 命中仅到 0036），属约定缺口（S12 门禁"不在场不约束"故不报红）。

### F6 安全面 —— 判定：**建议**（不构成新绕过；但"只在平台侧 fail-closed"要写明）

1. **更正一处易误判**：Agent 面**不是 fail-open**。`_verify_agent`（`agent_api.py:91-99`）在未配置 `AGENT_SECRET` 时经 `require_agent_secret`（`core/agent_secret.py:27-33`）**抛 503**，不放行；`heartbeat.py:168` 的 `verify_agent_secret` 同理。⇒ 退役不会引入新的认证绕过；v0.2 与后续讨论不应引用"AGENT_SECRET fail-open"。
2. **但退役在 Agent 侧完全不 fail-closed**：共享单一 secret 下，被退役主机的 Agent 仍可心跳（缺行即建 + 无条件 ONLINE）、re-home 设备、申请维护窗并 **abort 活跃 Job**（`agent_api.py:3262-3300`）、覆盖 boot_id、拉脚本目录（`routes/scripts.py:212,231,241`）。D5 的收口全部是平台侧读/派发面。这不是"新可用性坑"，而是既有共享凭据边界的自然延伸，真正解药是 ADR-0035 per-host 凭据（Revisit-2 已挂）。⇒ D5 需增"Agent 面退役写清单"，最低要求见 B4。（→ S11）
3. **审计双真源（S5）**：D1 的 `retired_by/retire_reason` 与既有 `audit_logs` 语义重叠，且**单行三列只能承载最后一次**退役——反复 retire→unretire→retire 会覆盖前次 actor/reason/时刻（连时间线都丢）。仓内 who-did-what 约定就是 `audit_logs`（append、多事件、带 IP；`delete_host` 已写 `hosts.py:535`，upgrade-gate 亦写 `agent_api.py:3293,3322`），而**实体行上挂 who 的先例为零**。建议：列 = 当前态判定投影（`retired_at` 必需），事件真源 = `record_audit(action="retire_host"/"unretire_host", details={reason})`；`retired_by` 取 `current_user` 而非 body（仿 `hosts.py:308-316`）。**`retire_reason` 建议强制非空**（unretire 同样），否则 Revisit-1「告警被证明无效」与 Revisit-3「高频清除需求」两条判据无数据可判。另注：`core/audit.py:61-88` 在 `audit_logs` 缺表时**降级吞掉** ⇒ admin 退役路径应 fail-closed（待验证项：生产表恒在性）。
4. 附带（非本 ADR 引入，待验证）：`core/csrf.py:78-82`：携带 `x-agent-secret` 头的请求**只判存在、不校验值**即豁免 CSRF（注释「非浏览器凭据一律放行」）。实际可利用性取决于 CORS 预检组合，建议独立核查（既有面，非本 ADR 引入）。

### F7 验收可测性 —— 判定：**建议**（可测性好，三处判据要收紧）

现成挂点充分：`backend/tests/api/test_hosts.py:545`（#937 预检回归＝验收 4 天然满足）、`test_metrics_fleet_gauges.py`、`test_stats.py`、`test_heartbeat.py` + `test_heartbeat_capacity.py` + `test_heartbeat_backpressure.py`、`test_session_watchdog.py`、`services/test_plan_dispatcher*.py`（4 个）、`test_plan_run_scan_scope.py`、`test_agent_api_watcher.py`、`test_precheck_reachability.py`、`api/test_upgrade_gate_api.py`、`tests/test_alembic_heads.py` + `test_alembic_upgrade.py`；夹具现成（`backend/tests/conftest.py:305 sample_host / :322 sample_offline_host / :339 sample_host_expired`）⇒ "每面一个退役用例"成本低。

三处判据需收紧：

1. **验收 2「移除过滤点→用例转红」在统计面不成立**：`metrics.py:44-53` 是泛型 `group_by(model.status)`，`stats.py:286-289` 是 raw SQL——删掉退役特例后仍会输出"看起来正常"的少一档数值。判据应改为「断言排除退役主机后的**具体计数值**」，不接受"HTTP 200／不含该 id"型弱断言。
2. **脚本面与平台外通道无 pytest 覆盖**：`batch_hot_update.py:89-95` 可仿 `tests/test_update_agent_playbook.py`（对脚本/playbook 做静态文本断言）的红绿形态；Ansible 手工 inventory 根本不在代码内（O5），只能靠 ADR 声明边界。
3. **「单次告警」的可测性取决于 F3 是否新建机制**。按建议实现为上升沿检测后，断言形状明确为四条：活体首拍恰 1 条 → 持续 N 拍仍 1 条 → 停 Agent（watchdog 翻 OFFLINE）后重启恰再 1 条 → unretire→retire 重新计轮。若沿用现栈则测不出来（去重键不含 host_id）。
4. 附带：退役的"反例"还需覆盖 **Z3 的 fatal/queue 分野**（构造 retired 主机 + 目标设备，断言 PlanRun 被**拒绝**而非永久 QUEUED）与 **F4 的双行边界**（`ip` 为 NULL 的退役行 + 旧哨兵自动注册 ⇒ 断言产生第二行，明确这是接受还是拦截）。
