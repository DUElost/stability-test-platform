## 1. 评审总评与核心结论

### 1.1 总评：Needs-revision

ADR-0038 v0.1 提出的「以 `retired_at` 三列 additive 字段为单一生命周期真源、硬删与退役分家、退役即终态保历史、生命周期与存活信号正交、调度与认领 fail-closed」的**核心技术方向完全正确**，切实解决了 [#796](https://github.com/DUElost/stability-test-platform/issues/796)/[#937](https://github.com/DUElost/stability-test-platform/issues/937) 之后「历史主机无法删除亦无法终态」的技术债死路。

然而，在对代码库真实实现进行静态对账核验后，发现 v0.1 存在 **3 项阻断级缺陷（Blocking Findings）** 和 **4 项建议级缺口（Suggestions）**。这些问题若不在 ADR 决策层面完成闭环并直接进入实现单，将导致：
1. **调度器进入死循环死锁**（退役主机设备未纳入 fatal 原因集，在准入队列中无限排队等待无法释放）；
2. **同 IP 换机直接触发 DB 唯一性约束崩溃**（`Host.ip` 全局唯一，ADR 声称的后缀分支实为死代码）；
3. **心跳风暴淹没通知系统**（ADR 声称的「沿用现有去重惯例」在代码库中实际不存在，退役主机活体每 10s 产生一条新通知）。

因此，总评判定为 **Needs-revision**，建议 ADR-0038 修订为 v0.2 并吸收本报告裁决后转 **Accepted**。

## 3. F1–F7 逐项详细评审与事实证据

### F1 语义完备性：D1/D2 与前置条件判定

#### 1. 结论分级：建议（Suggestion）

#### 2. 事实证据（file:line）
- `backend/api/routes/hosts.py:481-485`：硬删现有预检代码直接判断 `if host.status == "ONLINE": raise HTTPException(409, "主机当前 ONLINE，请先停止 Agent 服务再删除")`。
- `backend/models/enums.py:25-29`：`HostStatus` 定义包含 `ONLINE`、`OFFLINE`、`DEGRADED` 三种状态。
- `backend/agent/capacity_reporter.py:161`：当 Agent 出现多 ADB Server 冲突等健康度警告时，如实上报 `status = "DEGRADED"`。
- `backend/tasks/session_watchdog.py:43-48`：心跳超时巡检仅检查 `Host.status == HostStatus.ONLINE.value`，**完全不扫描 `DEGRADED` 状态**！

#### 3. 深度分析
1. **前置「非 ONLINE」在调度场景下存在运维竞态（过严）**：
   - 在活跃的测试集群中，一台空闲但处于 `ONLINE` 状态的主机，随时可能在下一秒被新派发的 `PlanRun` 选中使用。
   - 如果退役的前置条件强制要求「先停 Agent → 变为非 ONLINE → 才能调用 retire」，运维人员必须面临两难：
     - 如果直接登录机器 `systemctl stop agent`，正好处于该主机刚接单或即将接单的瞬间，会导致 Job 被非预期打断或超时沦为 `UNKNOWN`；
     - 停掉 Agent 后，控制面通常需要等待最长 `_HOST_HEARTBEAT_TIMEOUT`（300 秒）由 `session_watchdog` 判定为 `OFFLINE`，操作延迟极大。
   - **正确语义应为 Cordon（排空/隔离）**：退役的核心诉求是「控制面立即停止向该机派发新工作」。只要满足 `active_jobs == 0`，即使主机当前仍为 `ONLINE`，也应允许直接调用 `POST /hosts/{id}/retire`！一旦写入 `retired_at`，D5 的五面过滤立刻 fail-closed 封死新派发与 claim，随后运维人员可以从容登录机器停机下架。
2. **`DEGRADED` 主机的双向漏洞**：
   - 若前置条件字面执行为 `status != "ONLINE"`：一台 Agent 正常运行但健康状态为 `DEGRADED` 的活体主机，居然可以直接被退役，绕过了停止 Agent 的限制；
   - 反之，若运维停止了一台处于 `DEGRADED` 的 Agent，由于 `session_watchdog.py:46` 只处理 `ONLINE` 主机，该机器的 DB 状态将**永远停留在 `DEGRADED`，永远不会自然变为 `OFFLINE`**！
3. **活跃依赖检查不完备（不足）**：
   - `hosts.py:488-495` 仅检查了 `JobInstance` 的活跃状态，未检查 ADR-0019 的设备租约（`DeviceLease`）。
   - 若某设备正持有 `LeaseType.SCRIPT` 或 `LeaseType.MAINTENANCE` 租约，`active_jobs` 计数为 0，但设备实际处于独占租约中。若此时强行退役，会导致租约孤立或状态失步。

#### 4. 落点建议
- 修订 ADR-0038 D2：
  - 放宽前置条件：将「非 ONLINE + 无活跃 Job」调整为**「无活跃 Job（含 PENDING/RUNNING/UNKNOWN）且无活跃 DeviceLease」**，取消强制「非 ONLINE」前置；
  - 允许在线空闲主机直接退役（即 Cordon 语义），退役后依靠 D4 的心跳告警提示运维关停进程；
  - 若保留状态门禁，必须显式定义为 `status in ("OFFLINE",)`，并同步修复 `session_watchdog.py` 对 `DEGRADED` 超时的处理缺口。

### F2 过滤面穷尽性：D5 不变量与遗漏的第六面

#### 1. 结论分级：阻断（Blocking）

#### 2. 事实证据（file:line）
- `backend/services/plan_dispatcher_sync.py:68`：`_FATAL_DISPATCH_REASONS = ("not_found", "no_host")`。
- `backend/services/plan_dispatcher_sync.py:98-160`：`_validate_dispatch_devices_sync` 查询 `Device` outerjoin `Host`，只校验了 `snap.host_status == HostStatus.OFFLINE.value`，**未校验 `Host.retired_at`**。
- `backend/api/routes/devices.py:340-377`：`GET /api/v1/devices` 列表查询完全没有关联 `Host.retired_at`。
- `frontend/src/components/schedule/DeviceMultiSelect.tsx:24`：前端派发用例弹窗直接从 `api.devices.list` 获取设备。
- `backend/scripts/batch_hot_update.py:92`：`db.query(Host).filter(Host.status == "ONLINE")`，未过滤退役主机。
- `backend/services/ai_assistant/orchestrator.py:670-683`：`reload_agent_config` 工具只判断 `host.status != "ONLINE"`，未过滤退役主机。
- `backend/services/plan_run_scan_scope.py:113-123` 与 `backend/tasks/saq_tasks.py:314-324`：扫描任务向所有 `ONLINE` 主机下发 `scan_now`。

#### 3. 深度分析
1. **[阻断] 调度准入死锁（Admission Queue Deadlock）**：
   - ADR-0026 实现了准入队列。在 `plan_dispatcher_sync.py:510-520` 中，派发设备校验分为两类：
     - 命中 `_FATAL_DISPATCH_REASONS`：直接判为不可恢复失败，PlanRun 终态终止；
     - 未命中 fatal（如 `host_offline`, `host_maintenance`）：判为瞬时阻塞，PlanRun 保持 `QUEUED` 等待 admission pump 周期轮询重试。
   - 如果 D5 在派发侧将退役主机识别为 `host_retired`，但**没有将 `host_retired` 加入 `_FATAL_DISPATCH_REASONS`**：
     该 PlanRun 将被永久放入准入队列，持续占用队列重试预算，永远无法自动出队！这是 P1 级别的派发死锁！
2. **设备选择面穿透（Device Selection Surface）**：
   - 虽然 ADR D7 明确不做「设备退役」，但退役主机上的设备在物理上已随主机离线或待清退。
   - 现状下 `GET /api/v1/devices` 与 `_ensure_host_online_for_device`（`devices.py:33-81`）仅根据 host 的 `ONLINE/OFFLINE` 更新设备。如果退役主机 Agent 未停（`status=ONLINE`），其设备在接口中依然显示为 `status=ONLINE`！
   - 用户在 `DeviceMultiSelect.tsx` 页面可以正常勾选这些设备提交 PlanRun，提交后立即在派发层被驳回，造成极差的交互体验。
3. **控制面遗漏动作**：
   - `batch_hot_update.py` 会向所有 `ONLINE` 的退役主机分发并执行更新脚本；
   - AI 助手 `reload_agent_config` 可被触发向退役主机推送配置刷新；
   - `hosts.py:557`（`PATCH /watcher-admin-state`）、`hosts.py:972`（`POST /log-signal-dead-letters/{row_id}/replay`）均未防守退役状态。
4. **后处理扫描下发（ADR-0025 SAQ scan_now）的语义未裁决**：
   - `saq_tasks.py:314` 在 PlanRun 结束时向各主机下发 `scan_now` 提取测试日志。若参与过该 Run 的主机在此期间被退役，且此时 Agent 仍在心跳：
     - 若下发：由于机器可能已被物理拆除或擦盘，会导致超时；
     - 若跳过：该 Run 在该机上的残留日志可能无法被 merge。ADR 必须对后处理扫描是否豁免退役做出明确裁决。

#### 4. 落点建议
- 修订 ADR-0038 D5：
  - 补充说明调度器准入致命原因契约：**`host_retired` 必须显式加入 `_FATAL_DISPATCH_REASONS`**；
  - 扩充第六面「设备展示与选择面」：`GET /api/v1/devices` 应支持关联 `Host` 过滤退役主机的设备，或在 `DeviceOut` schema 中增加 `host_retired: bool` 标识，前端联动置灰；
  - 补充控制面拦截清单：明确覆盖 `batch_hot_update`、AI 助手工具、`watcher-admin-state`、`replay` 等端点；
  - 显式定义 ADR-0025 扫描下发策略：历史 Run 扫描以 `PlanRunHost` 存在性为准，若主机退役且在线允许最后一次采集，若已离线直接标记跳过。

### F3 心跳策略：D4 的权衡、去重机制与 Agent 影响

#### 1. 结论分级：阻断（Blocking）

#### 2. 事实证据（file:line）
- `docs/adr/ADR-0038-host-retirement-semantics.md:114-115`（不变量 3）：“退役主机心跳告警按主机去重（只响一次，除非状态震荡——**沿用现有告警去重惯例**）”。
- `backend/services/notification_service.py:343-345`：
  ```python
  def _load_prior_channel_delivery(db, event_type: str, context: Dict[str, Any]):
      run_id = context.get("run_id")
      if run_id is None:
          return None, {}
  ```
- `backend/services/notification_service.py:329-336`：`_delivery_identity` 仅提取 `(event_type, run_id, task_id, device_serial)`，**完全没有 `host_id` 维度**。
- `backend/agent/heartbeat.py:84-91`：Agent 收到非 2xx HTTP 状态码时，`resp.raise_for_status()` 抛出异常并返回 `None`，并在下一个 `poll_interval`（10s）无休止重试。

#### 3. 深度分析
1. **「不做 409、心跳如实记录」的取舍完全成立**：
   - 经静态核对 `backend/agent/heartbeat_thread.py:345-385`，心跳返回值承载了 `heartbeat_interval_seconds`（背压频率调整）、`log_rate_limit`（日志限速）、`script_catalog_outdated`（脚本更新通知）。
   - 一旦控制面返回 HTTP 409，Agent 的 `requests.post` 将抛出异常，整个心跳响应处理流程被截断，Agent 既不会退出，也无法接收到任何控制面下发参数，只会以 10s 一次的高频不断在本地打 error 日志，恶化网络与 I/O 环境。
   - 因此，D4 决定「心跳如实更新 last_heartbeat 与 status，不做 409，在调度/认领侧 fail-closed」的技术权衡十分精当。
2. **[阻断] 虚假的告警去重机制（Phantom Deduplication）**：
   - ADR-0038 不变量 3 宣称「沿用现有告警去重惯例」。
   - 但经代码实测，控制面目前的 `notification_service.py` 的投递去重是**专为测试执行（Run/Task）设计的**！其第一行就是 `if run_id is None: return None, {}`。
   - 系统中**根本不存在**现成的主机级别（`host_id`）告警去重机制！
   - 如果实现人员按照 ADR 的指示「沿用现有惯例」调用 `dispatch_notification`，每 10 秒一次的心跳每次都会被判定为无先前记录（`prior_log_id is None`），导致控制面每 10 秒向所有管理员通道（钉钉/邮件/Webhook）发送一封「退役主机仍在线」的报警，系统将在几分钟内发生告警雪崩！
3. **退役主机的背压建议**：
   - 既然 Agent 还在心跳，控制面在 D4 响应体中可以通过 `backpressure.heartbeat_interval_seconds` 返回最大间隔（如 300 秒），Agent 侧 `heartbeat_thread.py:377` 会自动采纳并放缓心跳频率，显著减轻控制面压力。

#### 4. 落点建议
- 修订 ADR-0038 D4 与不变量 3：
  - **纠正事实引用**：删除「沿用现有告警去重惯例」的表述，明确定义主机级告警去重机制；
  - **给出具体的去重方案**：
    - 方案 1（推荐，零外部依赖）：在 `Host.extra` 中存储 `retired_heartbeat_alert_sent_at` 时间戳；或者在 `Host` 表增加 `retired_alerted_at` 列。当且仅当该字段为空，或当 host 经历过一次 `OFFLINE`（状态震荡）后再次收到心跳时，才触发一次告警并更新时间戳；
    - 方案 2：在心跳响应中注入背压提示，建议心跳周期退避至 300s；
  - 在 `HeartbeatResponse`（`agent_api.py:311`）中增加 `is_retired: bool` 字段，供新版本 Agent 识别自身已退役并主动进入静默休眠。

### F4 身份与换机：D6 裁定、冲突后缀与审计连续性

#### 1. 结论分级：阻断（Blocking）

#### 2. 事实证据（file:line）
- `backend/models/host.py:41`：`ip = Column(String(64), nullable=True, unique=True)`，**数据库层有 IP 唯一性约束**！
- `backend/api/routes/hosts.py:214-217, 275-277`：`create_host` 显式调用 `_find_host_identity_conflict`，若 IP 重复直接返回 `409 HOST_IDENTITY_CONFLICT`。
- `backend/core/host_identity.py:28-49`：`allocate_host_id` 包含生成 `198-51-100-6-a1b2` 后缀的逻辑。
- `backend/models/host.py:51-52`：`boot_id` 与 `last_agent_instance_id` 是 `Host` 表上的直接可变列；而 `JobInstance`（`job.py`）与 `PlanRunHost`（`plan_run.py`）均未持久化这两个字段。

#### 3. 深度分析
1. **[阻断] `allocate_host_id` 后缀分支是死代码，同 IP 无法新建主机**：
   - ADR-0038 D6 提及了 `allocate_host_id` 的冲突后缀机制。但实际上，无论在 REST API（`hosts.py:275`）还是在底层 DB 约束（`host.ip unique=True`），只要一台退役主机占据了该 IP，任何试图以该 IP 创建新主机的操作都会在进入 `allocate_host_id` 之前就被 409 阻断；即便绕过预检，也会在 `db.flush()` 处触发数据库 `IntegrityError`！
   - 因此，「同 IP 换机 = 同一主机身份」不是一种可选策略，而是**当前数据库模型下的绝对物理限制**——只要退役主机不被物理硬删，该 IP 就绝不可能再分配给另一条 `Host` 记录！
2. **审计断链风险（Audit Traceability Gap）**：
   - ADR D6 认为：「同 IP 换机无需 successor 分裂，`boot_id` / `agent_instance_id` 的变化在详情与审计可见」。
   - 但代码静态事实表明：`boot_id` 与 `agent_instance_id` 在 `job_instance` 中**没有任何快照备份**！
   - 一旦新机器开机并执行 `unretire`，新机器的第一次心跳就会直接原地覆写 `Host.boot_id` 和 `Host.last_agent_instance_id`。
   - 此时，历史测试报告（如三周前由老机器执行的 PlanRun）在关联 `Host` 查询时，看到的将是新机器的硬件与实例标识，导致「历史到底在哪台机器上跑的」发生混淆与篡改。
3. **与 ADR-0035 per-host 凭据体系的深度冲突**：
   - 在 ADR-0035 落地后，主机凭据将是 per-host 独立哈希。
   - 若同 IP 换机沿用旧 `Host` 记录，旧物理机可能已报废或挪作他用，如果它持有的凭据依然有效，将破坏「设备报废即吊销」的安全原则；
   - 若在退役时吊销凭据，则换上的新机器将无法通信，必须在 `unretire` 流程中配套设计「凭据重新签发/重置」流。

#### 4. 落点建议
- 修订 ADR-0038 D6：
  - 承认当前物理限制：明确指出受限于 `Host.ip` 的唯一性约束，当前架构下同 IP 换机**只能**复用原 `Host` 记录走 `unretire`，删除关于后缀分裂的误导性描述；
  - 弥补审计断链：要求在 `unretire` 动作的 `record_audit` 中，将换机前的 `old_boot_id`、`old_agent_instance_id` 作为审计快照固化在 `AuditLog.details` 中；
  - 补全 ADR-0035 联动说明：在 Revisit 中明确，ADR-0035 实施时，`POST /hosts/{id}/retire` 必须将该主机的凭据标记为 `REVOKED`，而 `unretire` 必须提供重新生成凭据的 enrollment token。

### F5 一致性与迁移：与既有 ADR 的契合度及迁移门禁

#### 1. 结论分级：建议（Suggestion）

#### 2. 事实证据（file:line）
- `backend/scripts/check_schema_sync.py:47-75`：基于 `alembic.autogenerate.compare_metadata`，任何未在基线中的模型/迁移差异均会阻断门禁。
- `tools/dev/check_pr_migrate.py:4-18`：本地与 CI 的 `pr-migrate-empty-db` 门禁执行真容器空库迁移比对。
- `backend/models/host.py:26, 105`：已有迁移注释明确指出唯一约束与索引必须在 ORM 与 Alembic 严格显式命名，防 schema 漂移。

#### 3. 深度分析
1. **既有 ADR 兼容性矩阵**：
   - **ADR-0025（存储归档）**：ADR-0038 放弃 `archive` 命名改用 `retire`，成功避开了 `Host.extra['archive']` 的命名占用，兼容良好；
   - **ADR-0019（设备租约）**：兼容良好，但需在退役前置检查中补充对活动租约（`DeviceLease`）的检查；
   - **ADR-0026（执行扩容与准入队列）**：存在严重衔接点！如 F2 所述，派发器的新增错误码 `host_retired` 必须同步注册到 `plan_dispatcher_sync.py:_FATAL_DISPATCH_REASONS`，否则与准入队列的重试状态机冲突；
   - **ADR-0034（多 Harness 执行契约）**：纯流程文档，无语义冲突。
2. **三列 Additive 迁移的 schema-sync 刚性约束**：
   - 仓库推行严格的 `pr-migrate-empty-db` 与 `schema-sync` 守卫（#644/#825）；
   - 在 `host` 表新增 `retired_at` (TIMESTAMPTZ), `retired_by` (String), `retire_reason` (Text) 时：
     - 若为了加速查询对 `retired_at` 建立了索引（如 `ix_host_retired_at`），该索引必须**同时显式声明在 `backend/models/host.py:Host.__table_args__` 中**！
     - 否则，ORM `Base.metadata` 与 Alembic autogenerate 比对会立刻检出 `add_index|host|ix_host_retired_at`，直接将 CI 门禁染红；
3. **回滚路径可行性**：
   - 三列均为 nullable，存量数据无需回填，回滚仅需 `op.drop_column`，无数据破坏性风险，回滚路径安全清晰。

#### 4. 落点建议
- 在 ADR-0038 §4 迁移小节增加**「门禁与对账规范」**说明：
  - 指明实现单在新增 Alembic 迁移脚本的同时，必须在 `backend/models/host.py`、`backend/api/schemas/host.py:HostOut`、`frontend/src/utils/api/types.ts:Host` 同步更新；
  - 若包含索引，必须显式对齐命名并通过 `python tools/dev/check_pr_migrate.py` 自测。

### F6 安全面：共享密钥现状下的越权与审计完整性

#### 1. 结论分级：建议（Suggestion）

#### 2. 事实证据（file:line）
- `backend/realtime/socketio_server.py:153-183`：Socket.IO `/agent` 命名空间连接只比对全局 `AGENT_SECRET`，并直接把 `sid` 绑定到客户端声明的 `agent:{host_id}` 房间。
- `backend/api/routes/hosts.py:585-888`：热更新与安装路由通过 SSH 执行远端命令。
- `backend/core/audit.py:35-65`：`record_audit` 记录操作人、IP、详情。

#### 3. 深度分析
1. **退役主机控制面 SSH 动作的阻断是关键安全防线**：
   - 现实中，退役的主机往往会被关机、拔网线，甚至其静态 IP 会在数日或数月后被网络管理员重新分配给打印机、监控探头或其他业务服务器。
   - 控制面的 `POST /hosts/{id}/hot-update` 与 `POST /hosts/{id}/install` 会读取历史存储在 DB 中的 SSH 凭据，直接向 `host.ip` 发起 SSH 连接并执行 `rm -rf` / `rsync` / `systemctl restart` 等高危 root 操作！
   - 如果 D5 不对退役主机绝对拦截 SSH 动作，一旦管理员在 UI 误点，控制面将对局域网内重用该 IP 的无关物理设备造成毁灭性破坏！因此，D5 拒绝控制面动作具有极高的安全防御价值。
2. **Socket.IO 房间驻留问题**：
   - 退役主机的 Agent 若未关停，凭借全局 `AGENT_SECRET` 依然可以接入 Socket.IO 并加入 `agent:{host_id}` 房间。
   - 只要控制面坚持 D5 的 fail-closed 原则（不向该房间发送 `scan_now` 或控制 RPC），该连接仅作为僵尸信道存在，不产生数据越权，但在监控面板上会造成混乱。
3. **审计字段的强制性（Audit Strictness）**：
   - ADR D1 定义 `retire_reason` 为 Text，但在 API 层面未说明是否必须填写。
   - 在生产环境，下线或退役物理节点是重大基础设施变更。若允许留空，极易退化为无从溯源的人为误操作。因此，API 层面必须要求 `retire_reason` 至少包含非空白字符（`min_length=1`）；
   - 同时，`POST /hosts/{id}/unretire` 同样需要传入 `reason`，并在 `AuditLog` 中记下解除退役的缘由。

#### 4. 落点建议
- 修订 ADR-0038 D2 与安全考量：
  - 明确 API 规范：`POST /hosts/{id}/retire` 的入参 Payload 必须强校验 `reason` 必填（如 `min_length=3`）；
  - `POST /hosts/{id}/unretire` 同样增加可选或必填的 `reason` 参数并落入审计日志；
  - 强化 D5 的安全定性：将「控制面动作拒绝」明确列为防范「向重分配 IP 执行高危 SSH 操作」的硬安全防线。

### F7 验收可测性：五面过滤反例实证与告警去重判据

#### 1. 结论分级：观察（Observation）

#### 2. 深度分析与判据设计
ADR-0038 §5 给出的验收要求方向明确，但缺乏可直接指导测试用例落地的**操作判据**。为确保实现单交付时具备严格的**反例实证（Counter-example Falsifiability）**，建议将验收标准细化为以下判据：

1. **派发面反例实证（Dispatch Snapshot）**：
   - **前置**：构造 Host A（`retired_at != None`, `status = "ONLINE"`），设备 D 归属于 Host A；
   - **正例**：提交包含设备 D 的 PlanRun 派发请求，断言校验失败，错误原因必须为 `host_retired`，且进入 `_FATAL_DISPATCH_REASONS` 立即终止，不进准入等待队列；
   - **反例**：临时注释掉 `_validate_dispatch_devices_sync` 中的 `retired_at` 检查，用例必须转红（因 `status == "ONLINE"` 导致派发通过）。
2. **认领面反例实证（Agent Claim）**：
   - **前置**：Host A（`retired_at != None`, `status = "ONLINE"`），Job J 处于 `PENDING` 并指定 Host A；
   - **正例**：以 Host A 身份调用 `POST /agent/jobs/claim`，断言返回 `jobs = []`，Job J 保持 `PENDING`；
   - **反例**：临时注释掉 `claim_jobs` 中的 `retired_at` 检查，用例必须转红（Job J 被成功认领）。
3. **容量与监控反例实证（Stats & Metrics）**：
   - **前置**：打桩 1 台正常在线机、1 台退役但在心跳的机（`status=ONLINE`）、1 台退役且离线的机（`status=OFFLINE`）；
   - **正例**：调用 `GET /api/v1/stats/dashboard-summary` 与 `/metrics`，断言在线主机计数恒为 1，离线主机计数恒为 0；
   - **反例**：临时移除 SQL `WHERE retired_at IS NULL`，断言在线计数变为 2 转红。
4. **单次告警与震荡边界判定（Single Alert & Oscillation）**：
   - **去重测试**：退役主机连续发送 5 次心跳，断言通知中心/渠道仅记录 1 条告警事件；
   - **震荡重置测试**：
     - Step 1：退役主机心跳 → 产生第 1 次告警；
     - Step 2：停止心跳超过超时时间 → 触发看门狗将该机置为 `OFFLINE`；
     - Step 3：退役主机再次启动心跳（状态由 `OFFLINE` 震荡为 `ONLINE`）→ 断言触发第 2 次告警（合理通知管理员“已报废机器再次复活”）；
     - Step 4：主机被调用 `unretire` → 断言告警去重状态彻底清除。

## 4. ADR-0038 v0.1 → v0.2 修订落点清单（Action Items）

在人工裁决并决定将 ADR-0038 转为 Accepted 之前，建议在 v0.2 中完成以下文字与条款修订：

1. **§2. D2 修订**：
   - 将退役前置条件修改为「无活跃 Job（PENDING/RUNNING/UNKNOWN）且无活跃 DeviceLease」；允许 `ONLINE` 空闲主机直接执行退役（Cordon 语义）；
   - 规定 `POST /hosts/{id}/retire` 的 `reason` 字段为必填校验项，`unretire` 支持可选 `reason` 并记录审计。
2. **§2. D4 修订**：
   - 纠正事实依赖：删除「沿用现有告警去重惯例」的描述；
   - 明确定义退役告警去重事实源（建议写入 `Host.extra` 或新增去重时间戳），明确状态由 `OFFLINE` 翻转为 `ONLINE` 时允许告警再次触发一次；
   - 明确心跳响应中可通过调整 `heartbeat_interval_seconds` 对退役活体机器施加背压。
3. **§2. D5 修订**：
   - 明确派发器将 `host_retired` 纳入 `_FATAL_DISPATCH_REASONS`，防止准入队列永久死锁；
   - 补全遗漏的过滤面：`GET /api/v1/devices` 设备查询关联主机状态、`batch_hot_update` 批量更新过滤、AI 助手工具过滤、后处理日志扫描策略。
4. **§2. D6 修订**：
   - 澄清 `Host.ip` 的全局唯一性硬约束，删除「allocate_host_id 冲突后缀」对同 IP 换机的误导描述，明确指出同 IP 换机即为就地 `unretire`；
   - 增加审计快照要求：在换机与 `unretire` 发生时，将前任机器的 `boot_id` / `agent_instance_id` 快照归档在审计详情中，防止历史执行证据丢失。
5. **§4. 不变量与门禁修订**：
   - 补充三列 additive 迁移在 ORM、Alembic、Pydantic v2 与前端 API 类型库中的对账要求，提醒索引显式命名以规避 `check_schema_sync` 门禁阻断。
