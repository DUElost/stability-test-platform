# 稳定性测试平台：第一性原理与长期复利审计

> 审查日期：2026-09-23（Asia/Shanghai）
> 取证基线：`main@8bc6bc1e`
> 性质：只读静态审计与容量验收设计；不是生产容量认证、ADR 或实施授权。
> 输入目标：最多 150 台 host 同时运行；按每台 host 理论挂测 25 台计算，最多 3750 台 device 同时运行。

旧文档中的 host/device 数字与本次输入不一致是预期中的需求修订，**不作为缺陷**。本文把
150/3750 作为目标边界；在线、可租用、正在执行、进行瞬时操作的设备数须分开计量。
没有读取生产凭据、生产数据库或实际主机清单，没有调用生产接口、操作设备或运行压测。
代码默认值和模型推导不等于生产实测值。

## 1. 从产品目的推导架构约束

平台真正交付的不是“同时显示 3750 台设备”，而是将这些设备的运行时间转化为可信的
可靠性结论：知道哪台设备、哪个构建版本、哪个专项在有效运行多久后发生了什么故障；
证据能被归档、去重、追溯并形成可复现的问题；控制面与 Agent 的故障不能默默改变事实。
单人长期维护意味着重复性的发布、灰度、恢复和对账必须可由机器和文档复现。

因此，新增专项、Shell/Python/APK/Jar/PowerShell/JUnit 插桩 APK、客户刷机工具时，最有
价值的复用边界是 **Plan/Step 的意图、设备租约、宿主能力、不可变工具包、运行产物与
外部副作用**。每接入一种工具都改调度状态机，或复制一套上传、去重、Jira 链路，会让
第 N 个专项的成本随存量增长；把工具差异约束在相应宿主的适配器中，成本才可能递减。
这与 [ADR-0033](../adr/ADR-0033-tool-kit-ecosystem-integration.md) 的 Platform/Host/Device
工具分类、Tool Contract，以及 [ADR-0051](../adr/ADR-0051-release-unit-and-content-addressing.md)
的发布单元方向一致。

## 2. 当前具备的复利资产

1. **执行事实与资源边界。** Plan、Step、Job、PlanRun、设备租约和终态处理已有独立模型；
   ADR-0026 的准入、批量续租、fencing 和 Agent 操作 permit 使高并发设备运行不必等同于
   同时启动高负载操作。它们是容量测试的基础，尚非容量通过的证据。
2. **发布单元已从版本目录转向内容寻址包。** 当前 `main` 的 [ADR-0051](../adr/ADR-0051-release-unit-and-content-addressing.md)
   v1.2 及 [脚本版本约定](../development/script-versioning.md)表明 Phase 3 已合入：210 个
   版本目录已删除，每族保留可演进源码树，manifest 和站点包承载不可变版本。
   `script_catalog.py` 从 manifest 与包注册，`tool_cache.py` 校验整包摘要。
   ADR 所记“fleet 48/48 strict”属于该文档的运维记录，本轮没有独立复核运行态。
3. **现有专项机制有可复用核心。** Suite 绑定、按 Job 摄入的 `test_case_result`、
   DeviceLogEvent、scan/upload/merge 和 Jira 后处理已经分别成形。新增专项可以复用
   编排和证据链，前提是其专属协议不渗入通用状态机。
4. **机械门禁优于人工台账。** manifest 与包摘要、迁移、测试和发布检查为长期演进提供
   可执行约束。应优先保留能阻止错误发布的门禁，按实际故障复盘减少重复登记工作。

## 3. 发现：先处理不可恢复的失败，再讨论吞吐

### F1｜连接预算缺少全局上界：扩容前的高优先级风险

[`backend/core/database.py`](../../backend/core/database.py) 的同步和异步引擎分别使用
`pool_size=30`、`max_overflow=60` 默认值，单控制面进程的**配置允许峰值**是
`2 × (30 + 60) = 180`；[`deploy/postgres/docker-compose.yml`](../../deploy/postgres/docker-compose.yml)
设置 `max_connections=100`。这并不表示当前实际打开 180 条连接，但说明应用可在自身
池达到上限前耗尽数据库连接。增加控制面实例还会将两份池按实例数放大。
[ADR-0047](../adr/ADR-0047-db-pool-and-connection-capacity.md) 仍为 Proposed。

**最小出口：**在该 ADR 中定下所有实例合计的连接预算、数据库管理/备份预留、显式
排队超时和对外过载语义；以现有连接池指标取得分布，再决定是否需要多实例或代理。
单纯调大池或先加 worker 会扩大这一风险。生产 `.env` 是否覆盖默认值，本轮未核实。

### F2｜证据可丢失但中心不一定看得见：正确性风险

[`backend/agent/artifact_uploader.py`](../../backend/agent/artifact_uploader.py) 的产物队列
默认上限 256；`submit()` 在队列满时非阻塞丢弃，并增加本地 `submits_dropped`。
DeviceLogEvent/EventUploader 有另一套持久状态与重试路径，不能把它们的保证自动套给
JobArtifact。并发故障恰是审计最需要证据的时刻，因此该计数必须成为中心可观测的
完整率信号，而不只是 Agent 退出日志。

**最小出口：**隔离环境注入已知数量的产物和慢存储，核对发现、提交、归档、失败及丢弃
总数；把丢弃与积压指标接入告警。是否需要持久 outbox，由实测峰值与可接受丢失目标决定。

### F3｜恢复能力需要脱离当前宿主验证：存续风险

[`scripts/pg_backup.sh`](../../scripts/pg_backup.sh) 默认写入工作区的 `backups/`，保留 7 天；
它是逻辑备份脚本，不证明实际部署已做异地/离机保存或能恢复。单人项目尤其需要在
控制面、数据库宿主或中心存储不可用时，由另一人按记录恢复到可核对的状态。

**最小出口：**明确业务可接受的 RPO/RTO；核对实际备份目的地、新鲜度和告警通道；
在隔离环境定期从备份重建并对拍关键表、包清单和证据目录。实际备份拓扑、Alertmanager
接收链与磁盘容量本轮未验证，不据此宣称生产目前“无备份”或“即将满盘”。

### F4｜150/3750 仍是目标，没有完整的验收证据

[ADR-0026/0027 灰度步骤](../operations/adr-0026-admission-and-scale-gray-rollout.md)
已提出 44→60→100 host 的阶梯；当前没有从本轮证据证明 150 host、3750 device 的
长跑、断线恢复和证据完整率。按每台 25 个健康设备，服务器心跳建议间隔为
`20 + 25//10 = 22s`（[`agent_host_heartbeat.py`](../../backend/services/agent_host_heartbeat.py)）。
在“整轮耗时可忽略、全部同时在线”的条件下，心跳请求约 `150/22 ≈ 6.8/s`，设备
快照约 `3750/22 ≈ 170/s`；实际轮次还包含探测、网络与处理时间。**快照数不能直接
等同 SQL UPDATE 数，更不能据此推断可承载量。**

**最小出口：**先定义每专项活跃比例、产物体积、故障频度、准入延迟、运行/终态正确率和
恢复时间；按第 5 节做隔离压测。把数据库连接、WAL/磁盘、p95/p99 延迟、锁等待、
租约续期、产物完整率和单 host 的 USB/ADB 供电瓶颈一起记录。

### F5｜工具包已统一，直接执行器仍只认识 Python/Shell

[`pipeline_engine.py`](../../backend/agent/pipeline_engine.py) 的 `runners` 只有
`python`、`shell`；[`script_catalog.py`](../../backend/services/script_catalog.py)
的直接入口后缀只有 `.py`、`.sh`。包模型解决版本身份与分发，不自动解决 APK、Jar、
PowerShell、Windows 专属刷机工具的宿主、环境与能力匹配。把每个文件后缀都做成顶层
`script_type` 会把工具差异扩散到调度器。

**最小出口：**沿 ADR-0033 的 Platform/Host/Device 层次，为新载体定义薄适配器，统一
输入、退出码、环境检查、产物和超时；在 host 能力声明与派发门禁中表达 OS、架构、
ADB/USB、驱动及客户工具前置条件。先用一类真实非 Python/Shell 工具完成端到端
试点，再推广；不把“理论上可由 Shell 调起”算作已支持。

### F6｜短期证据保留与长期可靠性结论需要分层

[`scheduler.py`](../../backend/core/settings/scheduler.py) 中 PlanRun 默认保留 3 天；
[`cron_scheduler.py`](../../backend/scheduler/cron_scheduler.py) 的保留清理按终态选择并删除
关联事实。已有的 [`TestCaseResult`](../../backend/models/case_result.py) 将结果关联到
PlanRun，外键为级联删除。因此不能说平台“没有逐用例结果”，但也不能凭逐用例表
推断它已经拥有跨 Run 的 MTBF 历史、构建版本回归或故障签名资产。

**最小出口：**先定义原始日志、可复核摘要、长期统计的不同保留期和再计算能力；长期层
至少要能关联 device、构建版本、专项/用例、有效运行小时数、故障签名、证据 URI 与
Jira key。保留策略必须有存储预算和删除审计，避免无限堆积。生产实际保留设置未核实。

### F7｜部分读路径的成本随规模增长，应以测量决定改造

[`GET /devices`](../../backend/api/routes/devices.py) 分页后逐项校正 host/device 状态，
必要时在读请求里 `commit()`；[`/results/summary`](../../backend/api/routes/results.py)
对 `JobInstance` 按状态聚合，所示查询没有时间窗。前者会让查看频率影响写入，后者在
历史 Job 增长时需要确认索引、过滤与缓存策略。这是代码形状风险；本轮没有执行计划
或用户并发测量，不能给出实际延迟或 SQL 条数。

**最小出口：**在目标数据量下测设备页和结果页的 p95、查询次数、扫描行数与写入量；
只处理超过 SLO 的路径。正确性和可追溯性优先于提前引入复杂缓存。

## 4. 可证伪的 150/3750 验收路径

1. **固定负载定义。** 明确 150 台 host 的在线/运行比例、每台设备的作业长度与专项组合、
   每小时日志和产物体积、同时终态/同时重连的波次。约定准入、终态、证据完整率与恢复
   时间的 SLO；容量数字必须同时带这些条件。
2. **合成控制面阶梯。** 在隔离数据库与存储中逐档构造 60、100、150 host 和最多
   3750 device 的心跳、claim、续租、终态和断线恢复；测连接池、PG 活动会话、锁等待、
   WAL、CPU/内存、队列积压和 p95/p99。`fake_agent.py` 是可用夹具入口，但须补足可编排
   负载和校验，不能把现有功能夹具直接称为容量测试。
3. **真机物理阶梯。** 先验单 host×25 device 的 USB 树、ADB、供电、日志采集、刷机与
   脚本并发；再按实际 host/device 数分档长跑。合成设备不能证明物理端的稳定性。
4. **跨域故障注入。** 复测控制面重启、PG 拒连接、批量 Agent 重连、ADB 假死、包校验
   失败、中心存储变慢/写满及 Jira 重试；逐项对拍租约、终态、设备时长、产物和外部
   副作用，明确可重试与人工介入边界。
5. **接入成本验收。** 选一项新测试专项、一种非 Python/Shell 工具和一种客户刷机工具，
   记录新增文件、核心模块改动、发布步骤、灰度/回滚时间与首轮故障。长期目标是新增
   实例主要增加适配器和声明，不重复实现执行、证据与提交链。

## 5. 建议的实施顺序与复审触发

- **先守事实：**裁决 ADR-0047 的连接总预算；建立产物丢弃的中心对账；完成可验证的
  备份与恢复闭环。这些是扩容前高后果风险，不依赖 3750 真机到位。
- **再取得容量证据：**执行第 5 节的隔离阶梯，按实际瓶颈调整单实例、多实例、查询、
  归档与存储设计。不得仅凭静态公式宣布扩容通过。
- **随后扩展工具生态：**按宿主和能力声明接入真实 APK/Jar/PowerShell/刷机样板；沿
  ADR-0051 发布不可变包，沿 ADR-0033 收敛输入输出契约。
- **持续积累数据资产：**将长期可靠性指标的分母、签名和构建版本归属形成独立设计，
  与短期原始证据保留分离；以能否复算和追溯缺陷为验收条件。

本报告只提出审计判断与可证伪标准，不改生产配置、不开工单、不修改状态机。上述任一
关键项完成，或首次取得 150/3750 的运行分布后，应按新的代码和测量结果重审对应结论。
