## 0. 总评

**Needs-revision**（需修订后转 Accepted）

ADR-0038 的问题定性（§1.1「不是删除要不要挡，而是用完的主机没有终态」）与 D1/D2/D3 的主体方向**成立且必要**：#937 的保历史预检确实造出运维死路，`retired_at` 作为与 `status` 正交的生命周期真源是本议题的正确形态，D3「退役即终态、不做带历史硬删」与 #796/#937 决策一致，§3 对 `status=RETIRED`、`deleted_at`、FK SET NULL 的否决理由均站得住。**主干可接受。**

但 v0.1 的**收口面与事实核验不完整**，存在 2 条阻断、5 条建议、2 条观察。阻断项的共同形态是：ADR 把「过滤」当成了「识别」，而 `status` 与生命周期正交这个前提恰恰意味着**任何依赖 `status` 的既有闸门都不会自动保护退役主机**。具体而言：

- **F2-1（阻断）**：`retired_at` 若不被派发准入路径识别为**致命**原因，退役主机的 PlanRun 会在 ADR-0026 准入队列中**永久排队**——不是瞬时抖动，而是无上界的活锁。ADR D5 的五面清单未覆盖 `_FATAL_DISPATCH_REASONS`，§5 验收也没有对应判据。
- **F3-1（阻断）**：ADR §4 不变量 3 声称退役心跳告警「沿用现有告警去重惯例」——**该惯例不存在**。现有去重是 SAQ job key（`notif:<event>:<run_id>:<serial>`，`notification_service.py:649-654`）与投递级 channel_delivery（`:326-356`），二者都以 `run_id` 为锚；主机维度无锚点。更关键的是，ADR 若要落 `Host.extra['retired_alert_sent_at']`，**该键会被下一次心跳直接抹掉**（`heartbeat.py:250-281` 白名单重建 `host.extra`）。

这两条是「按 v0.1 实现单直接落地即产生线上故障」的量级，必须在 ADR 转 Accepted 前修订。

## 2. 逐项评审（F1–F7）

### F1 语义完备性 —— 判定：**建议**

**F1-1（建议）退役前置「非 ONLINE」在真实运维流程下过严，且与 D4 的告警设计自相矛盾。**

D4 承认「退役后又启动/重启 → 保持退役 + 告警」是**预期场景**，D2 却要求退役前置必须「非 ONLINE」。二者叠加的后果是：运维必须**先停 Agent、等状态落到 OFFLINE、再退役**——而 `_ensure_host_status_up_to_date`（`hosts.py:56-79`）与 `session_watchdog._check_host_heartbeat_timeouts`（`backend/tasks/session_watchdog.py:41-49`）把 OFFLINE 的判定挂在**心跳超时**上，默认 `HOST_HEARTBEAT_TIMEOUT_SECONDS`（`hosts.py:53` 默认 300；`session_watchdog.py:32` 默认 120——**两处默认值不一致**，见 F5-3）。即：停 Agent 后运维需空等一整个超时窗口才能退役。这与 §4「运维代价」写的「退役要求先停 Agent（非 ONLINE 前置）」是同一件事，但 ADR 未评估该等待成本，也未提供跳过手段。

建议：采纳 **Cordon 语义**——`active_jobs == 0` 且无活跃 `DeviceLease` 即可退役，`status` 不参与前置；活体退役由 D4 告警承接。这样 D2 与 D4 不再互斥，且退役不再要求「先停机」。

**F1-2（建议）「误操作恢复」路径被 D6 收窄为「同 IP = 同身份」，覆盖不了换新机场景。**

D6 裁定「同 IP 换机 = 同一主机身份 → 运维语义为 unretire」。但受 `Host.ip` 唯一约束（`host.py:41`）与创建时 409（`hosts.py:221-233`）约束，**新机沿用旧 IP 时无法新建 host 行**——运维只能 unretire 旧行。这意味着「换新」与「误操作恢复」在数据上是**同一个动作**，审计上不可区分。ADR §5 未要求 unretire 记录「这是换机还是误操作」。

建议：`unretire` 同样强制 `reason`（与 F6-2 同源），并在审计中要求区分 `replacement` / `mistake`；或在 Revisit 中显式声明「换新与恢复不可区分是接受的代价」。

**F1-3（观察）`DEGRADED` 是可达状态，且不会被任何看门狗降级为 OFFLINE。**

`HostStatus` 含 `DEGRADED`（`backend/models/enums.py:26-29`），Agent 自报 `status`（`backend/api/schemas/host.py:104` 的 `Literal["ONLINE","OFFLINE","DEGRADED"]`），控制面**如实落库**（`heartbeat.py:236` `host.status = payload.status`）。但 `session_watchdog` 只扫 `status == ONLINE`（`session_watchdog.py:46`），`hosts.py:60` 与 `devices.py:42` 亦只处理 `ONLINE`。→ **一台停机前上报过 DEGRADED 的主机，永远不会被自动改为 OFFLINE**，会永久停留在 DEGRADED。

对 ADR 的影响：前置「非 ONLINE」对此类主机**放行**（DEGRADED ≠ ONLINE），故不会误伤；但 §1.1 的语义陈述「OFFLINE 只表示当前不可达」未覆盖 DEGRADED 这个既非在线也非超时的第三态，§1.2「`status` 是存活信号（ONLINE/OFFLINE/DEGRADED）」一句把三态并列而未说明 DEGRADED 的 owner 与退出路径。建议在 §1.1/§1.2 补一句 DEGRADED 的语义与它不参与退役前置的理由。

### F2 过滤面穷尽性（D5 不变量）—— 判定：**阻断**

D5 列的「五面」是：派发快照 / claim / 统计容量 / 默认列表 / 控制面动作（ADR:75-78）。逐面核对后，**第 1 面与第 5 面各有一个实质缺口**，另有多处需要补入。

**F2-1（阻断）派发面遗漏 `_FATAL_DISPATCH_REASONS`：退役主机会在准入队列中永久排队。**

这是本轮最严重的一条。派发面的真实收口**不在** `plan_dispatcher_sync.py:155` 的 `host_offline` 判定，而在 ADR-0026 的准入队列分流：

- `_FATAL_DISPATCH_REASONS = ("not_found", "no_host")`（`backend/services/plan_dispatcher_sync.py:68`）；
- 非致命原因**不拒绝**，而是转为 `queue_blockers` 让 PlanRun 以 `QUEUED` 等待（同文件 `:510-519`；注释 `:65-67` 明说「其余（offline/error/host_offline/active_lease/active_job）是**可重试的调度状态**——V2 准入队列下不拒绝，只作为 queue_reason 让 PlanRun 以 QUEUED 等待（不变量④）」）；
- 准入阶段同一分流：`admission_pump.py:667-673`，非致命 → `_RetryableAdmission("DEVICE_BUSY", unavailable)`；
- 可重试路径**不回退尝试计数**（`requeue_plan_run` 显式说明「Clean competition requeues do NOT consume admission_requeue_attempts」，`admission_pump.py:290-294`），只按 `ADMISSION_RETRY_BACKOFF_SECONDS` 无限重排 `next_admission_at`（`:313-316`）。

→ 若实现单只加「退役 → `host_offline` 同类原因」，则命中退役主机的 PlanRun **永远在 QUEUED 与 PRECHECK 之间循环**，既不 FAILED 也不前进。ADR-0026 不变量④把「可重试」限定为**调度竞争**（设备被别的 PlanRun 占用），退役是**配置事实**、重试永不收敛——语义上属于 `_FATAL_DISPATCH_REASONS` 同族（`plan_dispatcher_sync.py:65-67` 把致命原因定义为「配置错误，prepare 直接 400」）。

要求：D5 第 1 面必须显式写明「`host_retired` 纳入 `_FATAL_DISPATCH_REASONS`」，并说明已 QUEUED 的在窗 PlanRun 如何收口（否则退役瞬间的在窗运行会停在队列里需要人工处置）。§5 验收需增一条对应判据。

**F2-2（阻断）控制面动作遗漏 upgrade-gate 与全部 Agent 写入面。**

D5 第 5 面写作「控制面动作（热更新/安装/批量刷新）对退役主机拒绝」。实际盘点：

| 面 | 现状是否有 `status` 闸门 | 证据 |
|---|---|---|
| 热更新 | **有** | `hosts.py:614-618`（非 ONLINE → 409） |
| 批量热更新（API 路径） | **有**（客户端过滤） | `backend/scripts/batch_hot_update.py:247` |
| 批量热更新（`--direct`） | **有**（SQL 过滤） | `batch_hot_update.py:90-95`（`.filter(Host.status == "ONLINE")`） |
| **Agent 安装** | **无** | `hosts.py:793-825` 只校验 404 与 `host.ip` 存在；**无 status 检查** |
| watcher-admin-state | **无** | `hosts.py:557-583` 只校验 404 |
| **upgrade-gate（两条）** | **无** | `agent_api.py:3262-3267`、`:3310-3315`；服务层 `host_upgrade_gate.py:212-233` 只查存在性 + 活跃 Job + 维护窗口 |
| Socket.IO `agent:{host_id}` 下行 | **无** | `socketio_server.py:178`（enter_room）、`:749-760`（`emit_agent_control` 按 room 路由） |

即 D5 第 5 面**至少漏了 upgrade-gate**（未在 ADR 任何位置出现）。更根本的是：**退役主机若仍在心跳（D4 明确允许），它的 Agent 在除 claim 外的所有 agent 端点上仍是合法写入方**——claim 是唯一检查 `status` 的（`agent_api.py:401`）。结果上报（`/jobs/{id}/complete`）、日志信号（`/log-signals`、`/device-log-events`）、续租（`/leases/extend-batch`）、`/recovery/sync` 均无 host 维度校验（`_verify_agent` 只校验全局共享 `AGENT_SECRET`，且**不接收 `host_id`**，`agent_api.py:91-99`）。

需要说明的是：这**不**意味着退役主机的活体会「偷跑作业」——派发与 claim 已封死，活体 Agent 无新作业可跑。真实风险是**状态污染与可用性坑**，尤其 `/recovery/sync`（`agent_api.py:2887-2908`）会**无生命周期校验地覆写 `host.boot_id` 与 `last_agent_instance_id`**——这正好击穿 D6 声称的「`boot_id` 变化在详情与审计可见」的审计链（见 F4-2）。

要求：D5 第 5 面补 upgrade-gate；并就「退役主机仍心跳时 Agent 是否有权写状态」给出明确取舍——要么承认写面开放（则须在 §3/§4 写明残差），要么把 `retired_at` 纳入 `_verify_agent` 同级的 host 维度校验。

**F2-3（建议）统计面与列表面需要精确化「哪些口径排除、哪些口径保留」。**

- 统计：`stats.py:267`（`/file-server` 按 `status == ONLINE` 且心跳新鲜）自动排除退役主机（因为 D4 不改 `status`——但活体退役主机仍是 ONLINE，**会被计入**，这是 D4 的直接后果，ADR 未提）；`stats.py:296-298`（`/dashboard-summary`）按 `status` 分桶并**取全表 `host_total`**（`:290-292`），退役主机会计入 `total` 与 `online`。`metrics.py:36-51`（`_refresh_fleet_gauges`）按 `status` group_by 全表，同样计入。
- 列表：`list_hosts`（`hosts.py:340-363`）当前无任何过滤，D5 要求新增 `include_retired`——但需同时决定 `total` 的口径（`hosts.py:349` 的 `query.count()` 与分页），否则前端分页会与实际条数不符。前端 `fetchHostList` 固定 `limit=200`（`frontend/src/utils/api/hosts.ts:32-33`），退役主机增多后会静默截断。

**F2-4（观察）以下面经核验「无需改动」，建议在 D5 中显式列入以封闭反例。**

下列面都通过 `status == "ONLINE"` 间接排除退役主机（在 D4 不改 `status` 的前提下**不足以保证**——活体退役主机仍是 ONLINE）：

- `plan_run_scan_scope.iter_plan_run_scan_hosts`（`backend/services/plan_run_scan_scope.py:113-122`）→ 调用方 `saq_tasks.py:314-321`、`plan_runs.py:556-561`、`dedup.py:471-475`、`ai_assistant/plan_run_ops.py:398-404` **四处**均判 `host_status == "ONLINE"`。
- 资源预检：`precheck/reachability.py:100-110`（`host_status` 仅入诊断 dict，**不参与判定**——`:144` 之后只读 `conflict`）。
- watcher 目标选择：`precheck/watcher.py:13-47`（按 `watcher_admin_active`，**与 status 无关**）。
- AI 助手 host 查询：`ai_assistant/tools.py:374-389`（`_q_hosts` 无 status 过滤）、`:138-145`（`_q_platform_health` 全表 group_by）。
- `reload_agent_config`（`ai_assistant/orchestrator.py:679-681`）**有** ONLINE 闸门。
- 导出/报告：`plan_run_export.py:153`（仅表头）、`report_service.py:162`（按 job 取 host）——历史面，**应当保留**，符合 D3。

**结论**：D5 的「五面」在**计数**上尚可（把上述归入「列表/统计」），但在**判据**上漏了 F2-1 与 F2-2 两个实质点。建议 D5 改为按「读面 / 写面」二分，逐条点名文件与 reason 常量。

### F3 心跳策略（D4）—— 判定：**阻断**（取舍成立，事实依据不成立）

**F3-1（阻断）「沿用现有告警去重惯例」是不存在的事实。**

ADR §4 不变量 3 原文：「退役主机心跳告警按主机去重（只响一次，除非状态震荡——**沿用现有告警去重惯例**）」。核验：

- 现网去重有**两处**，都以 `run_id` 为锚，**主机维度均不适用**：
  1. SAQ 入队键 `_notification_job_key` = `f"notif:{event_type}:{context.get('run_id')}:{context.get('device_serial') or ''}"`（`backend/services/notification_service.py:649-654`）。无 `run_id` 的主机事件会退化成 `notif:HOST_X:None:` —— **全主机共用同一键**，语义错误。
  2. 投递级幂等 `_load_prior_channel_delivery`：`run_id = context.get("run_id"); if run_id is None: return None, {}`（同文件 `:343-346`）——**无 `run_id` 直接放弃去重**。
- `EventType` 枚举只有 4 值 `RUN_COMPLETED / RUN_FAILED / RISK_HIGH / DEVICE_OFFLINE`（`backend/models/notification.py:16-20`），**无任何 host 生命周期事件**。
- 全仓唯一的「进程内一次性集合」先例是 `recycler._defer_cutoff_alerted`（`backend/scheduler/recycler.py:726`、`:759-765`）——**内存态、进程重启即失效、无持久化**，不构成可复用的「惯例」。

**更关键的实现陷阱**：若实现单照 ADR 精神把去重键放进 `Host.extra`（如 `retired_alert_sent_at`），**该键会在下一次心跳被抹掉**——`heartbeat.py:249-281` 每跳都用白名单**重建** `host_extra`（只保留 `agent_version` / `agent_installed` / `agent_installed_at` / `agent_code_revision` / `agent_code_deployed` / `agent_code_deployed_at` 六个键），然后 `host.extra = host_extra`。退役主机正好是每 10s 心跳的那台，于是**每跳都重置去重状态 → 每跳都告警**，恰好产生 ADR 想避免的告警轰炸。

要求：§3/§4 删除「沿用现有告警去重惯例」的表述，改为**指定去重事实源**。可选且需 ADR 明确的形态：`host` 表新增持久列（与 D1 的三列同批迁移，成本最低）／复用 `AuditLog`（`backend/models/audit.py:26` 的 `details` JSON）／独立小表。无论哪种，**不得使用 `Host.extra`**。同时 §5 验收第 3 条需补「重复心跳不重复告警」的确定性判据与「OFFLINE↔ONLINE 震荡后是否重置」的边界定义。

**F3-2（建议）不做 409 的取舍本身成立，但 D4 的「风险面已 fail-closed」论证不成立。**

ADR §3 否决心跳 409 的理由（「心跳还承载 backpressure / 版本门禁等响应，拒绝会给 Agent 制造新的失败模式」）核验**成立**：`agent_heartbeat` 确实返回 `backpressure` 与 `script_catalog_outdated`（`agent_api.py:797-799` docstring；`:818-823` 计算 `scripts_outdated`），Agent 侧据此调节（`backend/agent/heartbeat.py:25` 等）。保留该否决。

但 D4 括号内「风险面（派发/认领）已 fail-closed（D5）」的论证有一个隐含前提：**claim 与 dispatcher 检的是 `status`，不是 `retired_at`**（`agent_api.py:401`、`plan_dispatcher_sync.py:155`）。由于 D4 明确让心跳**继续把 `status` 写成 ONLINE**（`agent_api.py:829` / `heartbeat.py:236` 的行为不变），这两道闸门**对退役主机完全不生效**。真正的 fail-closed 必须由 `retired_at` 自己提供（即 F2-1/F2-2 要求的显式过滤），不能引用 `status` 闸门。建议 D4 改写这句论证，否则实现单可能误以为「已有闸门可复用」。

### F4 身份与换机（D6）—— 判定：**建议**

**F4-1（建议）「同 IP 换机 = 同一身份」的裁定成立，但 ADR 给出的机制描述与实际约束不符。**

ADR D6 写「（id 本就 IP 派生）」，暗示换机时新机可能拿到**带冲突后缀**的新 id。实际：

- `Host.ip` 有**全局唯一约束**（`backend/models/host.py:41`）且创建时显式 409（`hosts.py:221-233`）。→ 新机用旧 IP 无法建新行。
- 心跳按 `host_id` 主键查（`heartbeat.py:196`），仅在**遗留自动注册哨兵**路径才按 IP 兜底查找 + `allocate_host_id` 冲突后缀（`heartbeat.py:192` `_is_auto_register_sentinel`、`:196` `host = None if is_auto_register else db.get(...)`、`:202-208`）。
- 因此 `allocate_host_id` 的冲突后缀分支（`host_identity.py:28-47`）在**正常换机路径上是死代码**。

即 D6 的**结论正确，理由需修正**：同 IP 换机只能复用旧行，不是「因为 id 派生所以同身份」，而是「因为 `ip` 唯一约束禁止建第二行」。建议把该句改为引用 `host.py:41` 与 `hosts.py:221-233`。

**F4-2（建议）`boot_id` 变化「在详情与审计可见」缺历史锚点，且会被 `/recovery/sync` 静默覆写。**

- `boot_id` 仅存于 `host` 表（`backend/models/host.py:51`），**无任何快照/历史表**；心跳原位覆写（`heartbeat.py:238-239`：`if payload.boot_id: host.boot_id = payload.boot_id`）。
- `agent_instance_id` 情况较好：`device_lease.agent_instance_id`（`backend/models/device_lease.py:34`）按租约留痕，可支撑「哪个 Agent 实例跑的哪个 job」的审计。
- 但 `/recovery/sync`（`agent_api.py:2887-2908`）在**无生命周期校验**下同样覆写两者，且它记录 `previous_boot_id` 变量（`:2903-2904`）后**仅用于本地逻辑，未落审计**。

→ D6「`boot_id` / `agent_instance_id` 变化在详情与审计可见」对 `boot_id` **不成立**：详情只能看到当前值，审计看不到变更事件。建议：D6 明确『`agent_instance_id` 经 `device_lease` 留痕可审计；`boot_id` 仅现值，换机审计须由 `unretire` 的 audit `details` 显式快照原机器标识』，并把「unretire 时快照 `boot_id` / `last_agent_instance_id`」写成 D2/D6 的硬要求。

**F4-3（观察）与 ADR-0035 的交互已由 Revisit 2 承接，但触发条件可能长期不满足。**

ADR-0035 现状：共享全局 `AGENT_SECRET`（`docs/adr/ADR-0035-agent-host-identity.md:63-68`），per-host 凭据为**目标形态、未实施**（`:137-143`、`:151-152`），触发条件四项（`:178-185`）。D6 的 Revisit 2 把换机流程重审挂在「ADR-0035 落地后」。由于 ADR-0035 的触发条件（泄露事件/不受信网段/审查 P0/合规要求）**可能长期不满足**，该 Revisit 实际上无确定时间点。建议 D6 或 Revisit 2 补一个**时间上界或替代触发**（例如「退役功能上线满 N 个月且出现首例换机」），否则该重审会无限期悬置。

### F5 一致性与迁移 —— 判定：**建议**（风险低于 ADR 自身预估）

**F5-1（建议）三列 additive 迁移有近乎同形的直接先例，配套要求可精确枚举。**

`backend/alembic/versions/m8n9o0p1q2r3_host_maintenance_window.py` 就是 D1 的同形先例（同表、同形态、可空列、`downgrade` drop、2026-09-08 落地）：

```python
def upgrade() -> None:
    op.add_column("host", sa.Column("maintenance_until", sa.DateTime(timezone=True), nullable=True))
    op.add_column("host", sa.Column("maintenance_holder", sa.String(128), nullable=True, default=""))
def downgrade() -> None:
    op.drop_column("host", "maintenance_holder")
    op.drop_column("host", "maintenance_until")
```

配套要求（实测）：

1. **ORM ↔ Alembic ↔ Pydantic ↔ 前端 TS 四端**：ORM `backend/models/host.py`；Pydantic `backend/api/schemas/host.py:104`（`HostOut` 同族）；前端 `frontend/src/utils/api/types.ts:20`。ADR §4「前端面」已提 HostsPage，但未提 `types.ts` 同步——按 AGENTS.md 硬不变量「前端 API 类型以 `types.ts` 为入口，并与后端 schema 同步」，须显式列入实现单。
2. **schema-sync 门禁**：`pr-migrate-empty-db` 分两步——空库 `alembic upgrade head`（`.github/workflows/ci.yml:320-322`）+ `python -m backend.scripts.check_schema_sync`（`:323-329`）；本地等价物 `scripts/run_gates.py:129-130` → `tools/dev/check_pr_migrate.py:117-125`（**docker 缺失时 SKIP 并退出 0**，`:85-94`——即本地可能静默跳过该门禁）。该脚本用 `alembic.autogenerate.compare_metadata` 对比迁移结果与 ORM，**基线白名单**模式，基线外漂移必拦（`backend/scripts/check_schema_sync.py:129`、`:175-178`）。diff 家族含 `modify_nullable` / `modify_type` / `modify_default` / `add_column` / `remove_column`，键形态 `kind|table|column`（`:68-72`）。当前基线**仅 5 项且无 `host` 条目**（`backend/scripts/schema_sync_baseline.json`）→ 新列任何漂移**直接红**，无基线掩盖可能。
   - 注意：`check_schema_sync.py:128` 的 `MigrationContext.configure(conn)` **未配置 `compare_type` / `compare_server_default`**（全仓 grep 零命中），故**类型与 server_default 漂移实际可能漏检**；`modify_nullable` 是 Alembic 默认开启项，会被捕获。→ 这意味着 ADR 写「`retired_at` TIMESTAMPTZ」时若迁移用 `sa.DateTime()`（无 `timezone=True`）而模型用 `sa.DateTime(timezone=True)`，**可能静默通过 CI** 却在 `create_all()` 与生产库之间产生真实差异。建议 ADR 明确拼写 `sa.DateTime(timezone=True)`（同表先例 `m8n9o0p1q2r3:34`、`host.py:31`）。
3. **ORM 同步是硬前置，ADR 未提**：`backend/tests/conftest.py:147` 用 `Base.metadata.create_all()` 建测试库，**不跑迁移**。故新列必须在 `backend/models/host.py` 同步声明，否则 `backend/tests/` 全部看不到该列；反之若漏写迁移，`backend/tests/` **仍会全绿**，只有 `pr-migrate-empty-db` 能拦。ADR §4「迁移」段只写了「三列 additive nullable，无回填；回滚 = drop 三列」，**未提 `models/host.py` 同步与 schema-sync 门禁**——这是 v0.1 的实际缺口（`docs/adr/ADR-0038-host-retirement-semantics.md:116`）。
4. **类型拼写与长度需钉死**：`retired_at` 用 `sa.DateTime(timezone=True)`；`retired_by` / `retire_reason` ADR 只给了 `String` / `Text` 未给长度。同表先例为 `String(64)` / `String(128)` / `String(1024)`（`host.py:25,29,40,46`），且 `sa.Text` 在 `host.py` **无先例**。迁移与模型长度不一致即漂移键。
5. **索引命名（若建）**：本仓**无全局 `naming_convention`**（`backend/alembic/env.py`、`backend/core/database.py` grep 零命中），故自动命名索引会与模型侧名字不符被拦。约定 `idx_host_<purpose>` / `uq_host_<cols>`，先例 `Index("idx_host_last_heartbeat", "last_heartbeat")`（`backend/models/host.py:63`；迁移侧 `a1b2c3d4e5f6:68`）。**ADR 未提索引是安全选择**；若 D5 过滤需要索引，须在**迁移与模型两处**显式命名，且 partial index 属已知脆弱区（`check_schema_sync.py:9-10` 把「partial index 比较 bug」列为既有噪音）。
6. **单 head 约束**：`tests/test_alembic_heads.py:12-30` 断言 `alembic heads` 恰一个 → 新迁移 `down_revision` 须直接指向现 head。本 worktree（`ea621988`）实测 125 个 revision、单一 head = **`cc33dd44ee55`**（`backend/alembic/versions/cc33dd44ee55_add_notification_delivery.py`）；实现单须以届时 `alembic heads` 实读为准（主工作区存在未跟踪的 seed 迁移，head 可能前移——本稿不以主工作区未提交状态为准），不得开分支。
7. **回滚**：约定统一（每个 additive host 列迁移都带 `downgrade()` 逆序 drop，`m8n9o0p1q2r3:42-44`、`t8u9v0w1x2y3:38-40`），且 ADR-0008 `:26`「所有结构变更通过 Alembic 脚本管理并可回滚」为强制要求。但**无任何测试覆盖 host 列的 downgrade**：`tests/test_alembic_upgrade.py:33-53` **只跑 upgrade**（`:46` 回放到 `l2m3n4o5p6q7`、`:51` 升 head），`tests/test_alembic_heads.py` 只数 head；仅有的 downgrade 用例在别的表（`backend/tests/migration/test_sentinel_downgrade_935.py:100-120` 等）。ADR「回滚 = drop 三列」在机制上成立但与 `m8n9o0p1q2r3` 同形，**无自动验证**——建议实现单补一条往返用例，或 ADR 明说「靠同形先例」。
8. **不存在「迁移 ↔ seed 配对」规则**：ADR 若引用此类要求属虚构。`docs/development/dependencies-and-quality.md` 与 `repository-workflow.md` 对迁移零着墨；ADR-0008 只管 schema 演进（`:24-27`）。唯一的「配对」概念是 `check_schema_sync` 内部的 **#944 成对基线键**（`check_schema_sync.py:78-106`），与 seed 无关。

**F5-2（建议）与 ADR-0025 / 0019 / 0026 / 0034 无实质冲突，但有一处措辞需对齐。**

- ADR-0025 主体是**日志归档闭环**（`docs/adr/ADR-0025-*` §D2–D4，`:66-278`），其唯一「不变量」在 watcher 章节（`:295`），与主机生命周期无关。ADR-0038 §1.2 只借用了「`extra['archive']` 命名占用」这一**事实**，核验**准确**（生产者 `backend/agent/heartbeat_thread.py:255`，消费者 `agent_api.py:3179`、`plan_runs.py:2571`）。**无冲突。**
- ADR-0026：见 F2-1——不是冲突，而是 D5 漏了它的分流常量。ADR §1.3 引用的「ADR-0026 status/phase 正交先例」需注意：该正交性陈述的实际对象是 **`plan_run`** 表（`docs/adr/ADR-0026-plan-execution-scaling.md:328` 的 `status` 列说明），**不是 `host`**——作为**类比**恰当，但不构成 host 表的既有限制。ADR-0019/0025/0026/0034 中**均无** host 生命周期相关的不变量（零命中）。
- ADR-0019：`boot_id` / `last_agent_instance_id` 是 ADR-0019 Phase 3a 产物（`t8u9v0w1x2y3_add_host_identity_columns.py`），本 ADR 不改其语义。**无冲突。**
- ADR-0034 / 执行契约：ADR-0038 属**决策类产物**，其实现应为独立 Requirement；§5「实现单另开，ADR Accepted ≠ 实施启动」的措辞与 ADR-0035 `:21` 的同款表述一致。**符合契约 §3.5。**

**F5-3（观察）ADR 引用的超时常量存在两套默认值不一致，且已在别处被识别为待收口问题。**

`hosts.py:53` 定义 `HOST_HEARTBEAT_TIMEOUT_SECONDS = int(os.getenv(..., "300"))`，`session_watchdog.py:32` 定义 `_HOST_HEARTBEAT_TIMEOUT = int(os.getenv(..., "120"))`。二者**读同一 env 但默认值不同**（300 vs 120）。本仓已有 OPEN PR #1593（`fix/1518-heartbeat-timeout-single-source`，「统一 HOST_HEARTBEAT_TIMEOUT_SECONDS 单一来源」）在收口此问题。ADR §1.2/§4 未引用该常量，故不构成 ADR 缺陷；但**F1-1 的「停 Agent 后需等多久」直接取决于它**，建议 ADR 在评估运维代价时引用单值来源，并在 #1593 合入后复核。

### F6 安全面 —— 判定：**建议**

**F6-1（建议）退役**不**产生新的认证绕过；但 D5 的拒绝清单若照抄，会首次给 install/upgrade-gate 装上闸门，须说明这是「新增」而非「对齐」。**

- ADR-0035 现状核验：全局共享 `AGENT_SECRET`，`_verify_agent` **不接收 `host_id`**（`agent_api.py:91-99`），Socket.IO `/agent` 握手同样只校验全局 `auth["agent_secret"]` + 客户端自报 `host_id`（`socketio_server.py:153-183`）。**ADR-0038 未声称有 per-host 凭据，故无虚假前提。**
- 退役**不**放宽任何现有校验：退役只是新增一个拒绝条件。`claim` 已要求 ONLINE（`agent_api.py:401`），退役不会让它更弱。
- 但 F2-2 已指出：install（`hosts.py:793-825`）与 upgrade-gate（`host_upgrade_gate.py:212-233`）**当前完全没有 status 闸门**，连 OFFLINE 主机都能装。D5 若把「安装」列入拒绝面，实现单需意识到这是**补第一道闸门**，其影响面（例如合法地在 OFFILINE 主机上重装 Agent 的运维流程会被打破）超出退役本身。建议 D5 对这两个面单列理由，或显式声明「仅新增 `retired_at` 判定、不改变 `status` 语义」。
- IP 复用风险：`resolve_host_ssh_credentials` 在无显式凭据时**按 IP** 回落查 inventory（`backend/core/ssh_security.py:78-80`）。由于 D6 让退役行继续持有 `host.ip`，且推荐流程是 `unretire`（`retired_at` 复归 NULL），**D5 的拒绝拦不住「unretire 之后把热更新打到换了物理机的新机」**。这是**既存**风险（未退役主机同样存在），ADR 既未引入也未关闭，Revisit 2 已条件性承接。建议在 §4 或 Revisit 2 补一句「本 ADR 不解决 IP 复用导致的 SSH 目标错配；归 ADR-0035 per-host 凭据」，避免读者误以为 D5 提供了该保护。

**F6-2（建议）`retired_by` / `retire_reason` 两列与 `AuditLog` 冗余；`reason` 应强制必填。**

- `record_audit` 签名（`backend/core/audit.py:35-45`）：必填 `action` / `resource_type`，可选 `resource_id` / `details`(JSON) / `user_id` / `username` / `request`。→ **who 由 `user_id`+`username` 天然捕获，when 由 `AuditLog.timestamp` 服务端默认捕获**（`backend/models/audit.py:20-33`），reason 可入 `details`（先例：`hosts.py:266` 的 `details={"ip":..., "change": reason}`）。
- 故 D1 的 `retired_by` / `retire_reason` **在溯源上冗余**。唯一不可替代的是 `retired_at`——它是**过滤真源**（D5 所有判定靠它），必须在 `host` 行上。`retired_by` 的边际价值仅剩「不经 audit 表 join 就能在主机列表显示谁退的」。
- 建议：保留 `retired_at`（必须）；`retired_by` / `retire_reason` 二选一——要么删除并声明「溯源一律走 audit 表」，要么保留但在 D1 写明保留理由（如列表展示需求）。**不建议三列全留而不说明**（AGENTS.md 总原则：只改当前 Requirement 必需内容）。
- 另：`retire_reason` 应**强制必填**（建议 `min_length=1`）。现状 `AuditLog` 写入失败是**跳过 + warning 而非致命**（`audit.py:66-89`），若再依赖 audit 存 reason，则「无 reason 的退役」可能静默产生。`unretire` 同样需强制 reason（呼应 F1-2）。

### F7 验收可测性 —— 判定：**观察**

**F7-1（观察）§5 验收第 2 条的「反例实证」缺可操作判据。**

原文：「D5 五类过滤点各有回归测试，且**反例实证**成立（临时移除任一过滤点 → 对应用例转红）」。问题：五类里多类**没有可「移除」的单一过滤点**——例如「统计容量」是 `stats.py:296-298` 的两个 `sum(...)`，「默认列表」是 `list_hosts`（`hosts.py:340-363`）里**尚不存在**的新参数。判据应改为「每个过滤点有一个命名断言（如 `assert retired_id not in payload.host_ids`）」，而不是依赖「移除代码看是否变红」这种不可自动化的操作。

另：F2-1 要求的新增判据（`host_retired ∈ _FATAL_DISPATCH_REASONS`）与 F2-2 的 upgrade-gate 面应补入 §5。

**F7-2（观察）§5 验收第 3 条的「单次告警」缺去重语义与震荡边界定义。**

在 F3-1 未解决前，该条**不可测**——「单次」的去重键、存储位置、进程重启后是否仍生效、以及「OFFLINE→ONLINE 震荡后是否重置」（ADR §4 不变量 3 括号内提到「除非状态震荡」但未定义）都未定。建议 §5 补三条判据：①连续 N 次心跳仅 1 次告警；②进程重启后不重发；③震荡定义（如「离开退役态后再进入」才重置，或「永不重置」）。
