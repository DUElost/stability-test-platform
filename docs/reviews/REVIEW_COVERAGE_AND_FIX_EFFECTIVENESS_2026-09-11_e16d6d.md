## 3. Q2：已关闭 Issue 的修复质量

### 3.1 方法与边界

本会话不重做全量抽样（他源已有 17 项分层抽样），而是把注意力放在**验证他源提出的
两个反例在当前基线是否仍然成立**——这是最能证伪"已关闭即已修复"的证据类型。
结论：两个反例均**独立复现成立**，且 `origin/main` 未做任何相关改动。

### 3.2 F01：#901 并发 refresh 仍可重复签发（已关闭，验收未兑现）

`backend/services/token_blacklist.py` 的 `revoke()` **已经**实现了正确的原子消费
语义：PG 路径使用 `ON CONFLICT DO NOTHING ... RETURNING jti`，并以
`result.first() is not None` 返回"本次是否为首次插入"（第 51–61 行）。注释明确说明
不用 rowcount 是因为其在 `DO NOTHING` 下依赖驱动实现。

问题在调用点 `backend/api/routes/auth.py:435`：

```python
expires_at = datetime.fromtimestamp(payload_data["exp"], tz=timezone.utc)
revoke(db, jti=jti, expires_at=expires_at, reason="rotation")
```

返回值被直接丢弃。可达交错：

1. A、B 两个并发请求同时通过第 396 行的 `is_revoked()` 预检查；
2. A 插入成功（`revoke` 返回 `True`），B 冲突（返回 `False`）；
3. 两者都继续执行，都签发新会话。

`#901` 的验收包含"重放/并发刷新回归通过"。判定：**已关闭，但并发验收未兑现。**
最小出口：仅允许 `revoke()` 返回 `True` 的请求签发，其余走 `_refresh_unauthorized`；
补并发 refresh、refresh/logout 竞争的回归测试。

### 3.3 F02：#1123 取消时提前释放互斥（已关闭，直接违反自身验收）

`backend/tasks/saq_tasks.py:98-126`：

```python
    try:
        return await asyncio_to_thread(fn, *args, **fn_kwargs)
    finally:
        _SYNC_OVERLAP_GUARDS.end(key)
```

SAQ 超时取消外层协程时，`CancelledError` 在 `await` 点抛出、`finally` 立即执行、
guard 被释放；但 Python 无法终止已经运行的同步线程。于是互斥已放开、旧线程仍在
执行（merge 的工具子进程与汇总写盘、extract 的 NFS 拷贝），重试可以进入同一个 key。

这恰好是该 Issue 声明要防住的场景，且 docstring 第 108–109 行把这条路径写成了安全的
（"本轮在协程侧等待（不占线程池、可被 SAQ 正常取消）"）——被取消的是**等待方**时
成立，被取消的是**持有方**时不成立。现有测试覆盖手工占位、等待、正常结束和函数
异常，未覆盖"线程已启动后取消持有者"的交错。

判定：**已关闭，但直接违反自身验收；单进程即可发生，不需要多 worker。**
最小出口：把 guard 生命周期绑定到实际同步工作完成（例如由工作线程自身在结束时
释放，或改用可跨取消存活的持有登记），并覆盖取消、提交失败与 worker 异常出口。

### 3.4 两个反例是同一根因

按第一性原理，这不是两次孤立疏忽：

> **把分布式/异步不变量交给进程内机制或时序假设保证，而不是交给能原子判定胜者的那一层。**

- `#901`：原子判据已经存在（`RETURNING`），但决策没有使用它；
- `#1123`：用进程内 guard 约束一个生命周期不受协程控制的线程。

同根因在不同模块连续复发，说明该原理**尚未被制度化**——它散落在个别 Note 里，
没有成为可检查的门禁或复核清单项。

### 3.5 可持续与不可持续修复的分界

样本中形成复利的修复有共同形态：

| Issue | 可持续原因 |
|---|---|
| #1215 | 带 expected status 的条件 UPDATE，以 `rowcount == 1` 作唯一胜者，不用进程内锁冒充分布式权威 |
| #1214 | 数据进入日志/LLM/回执前经统一结构化脱敏入口，替代散落字符串补丁 |
| #890 | leader election 数据库异常 fail-closed 并同步 ADR，策略覆盖一族后续任务 |
| #1074 | 中心存储已配置时发布失败显式失败，不回退本机伪报成功 |
| #1203 | 清理与执行所有权绑定，迟到旧执行者不能删除继任者占位 |
| #1042 | 本地持久 outbox + 稳定事件身份 + 控制面幂等，符合「瞬时通信不承载业务事实」 |

共同点：**恢复单一事实源、显式错误语义或所有权不变量，并由契约级回归锁住。**
反面形态：进程内锁、客户端 Web Lock、时序退避——它们会在下一个并发场景里以新
Issue 形式重新出现。

### 3.6 关于百分比

在没有稳定抽样框、分母、评分规则与复核记录之前，"准确性约 85%""有效性约 90%"
这类项目级数字不应作为质量结论。可替代的可测指标：

- closed 后被重开或产生同根因 follow-up 的比例；
- 高风险 Issue 验收条件的兑现率（#901、#1123 在本指标上为 0/2）；
- 同类缺陷 30 天复发率；
- main 全量逃逸率与恢复时长；
- 过渡止血按期删除 / 升格 / 显式延期的比例；
- 生产类 Issue 关闭时附带版本与运行证据的完整率。

## 4. Q3：多 Harness 修复模式

### 4.1 应保留的骨架

Issue 溯源与可失败验收、独立 worktree/branch、Registry 查重与 scope、
strict branch protection、FIFO 串行集成、Agent Note / ADR。这些解决的是
**「多个 Agent 并行改同一仓库会互相污染」**这个真问题。

但必须明确：**它们全部作用于 Git 协调层，没有一项证明产品语义正确。**

### 4.2 W1：合入即结束，验收条件无人兑现

现行链路末端「合入 main → 需求结束」把 Git 集成成功等同于语义正确。#901 与
#1123 是直接反证：验收条款写在 Issue 里，两个 PR 都绿、都合入、Issue 都关闭，
验收条件一个都没被检查；Harness 在合入瞬间退出，责任链早于深度验证结束。

结束条件应按交付类型分层：

| 类型 | 结束条件 |
|---|---|
| 代码缺陷 | 合入 + 定向回归 + 适用的 main checkpoint + Issue/Registry 核销 |
| 生产/部署缺陷 | 上述 + 对应版本与环境的运行证据 |
| 真机/硬件问题 | 上述 + 设备矩阵或 signoff |
| 风险接受 | 决策者、残余风险、检测来源、升级触发、复议日期 |
| 临时止血 | 伤害已受控 + 根因承载项 + owner + `review_by` + 可测删除条件 |

### 4.3 W2：PR 绿不等于验证过，且无强制独立复核

required checks 为 `lint`、`CodeQL`、`pr-typecheck`、`pr-compileall`、
`pr-agent-tests`、`pr-migrate-empty-db`，全部为轻量门禁；完整 `backend/tests/`、
Vitest、Docker build 由夜间 main backstop 承担。在 3 天合入 150 个 PR 的吞吐下，
深度失败的发现时延可达一天且归因困难。

同时经 API 确认 `required_approving_review_count = 0`、
`require_code_owner_reviews = false`。这不等于作者没有自审，但可以确认
**系统层面不存在强制的第二双眼睛**——恰好覆盖了 #901（鉴权）与 #1123（并发）
这两类最需要独立复核的变更。

建议：鉴权、授权、事务、状态机、迁移、执行协议、部署与 CI 权限变更一律独立复核；
普通低风险 PR 保留快速路径 + 随机抽检；密集合入期增加 coalesced main checkpoint，
把深度失败发现时延压到约一小时，而不是固定等到夜间。不建议给所有 PR 强塞全量检查。

### 4.4 W3：自由认领优化关单数而非风险下降

88 个 open bug 中简单 P2 占多数，主链组合问题天然更难、更易被跳过。认领应受人类
维护的全局优先级约束：安全、数据正确性、主链不可完成优先；P0 必须稀缺；设计风险
先确认触发前提再转实现单；未定义共同语义时先做组合设计。

### 4.5 W4：FIFO 红队首无解毒出口（#1246 仍 OPEN）

本会话确认 #1246 仍为 OPEN（最后更新 2026-09-10T18:43Z），#1205 已于
2026-09-10T07:33Z 合入即当次阻塞已解除，但**机制缺口未修复**：队列脚本只处理队首，
队首非 SUCCESS 即退出，无告警、无隔离、无恢复顺序。

严格 FIFO 本身不是错误，错误是红队首时只有静默停摆。自动跳过同样不可直接采用
（改变顺序语义）。最小方案：持续失败 10–15 分钟告警 → 人工确认后转 draft 或加
受审计的 quarantine 标签 → 后续 PR 前进 → 原 PR 修复后按明确规则重新入队；
不绕过 required checks，不手工 merge。若要改变 FIFO 方向语义，先修订 ADR-0034 /
工作流契约。

### 4.6 建议终态流程

```text
Finding
→ 去重、反证与问题确认
→ 严重度、交付类型、共同不变量、可失败验收
→ Issue 或组合治理主题
→ 开发者选择 Harness + declare
→ 独立 worktree 修根因（不变量必须下沉到可原子判定的层）
→ 定向回归 + 风险分层 CI + 高风险面强制独立复核
→ strict FIFO 集成；红队首可见且有人工隔离出口
→ main 批次全量 checkpoint
→ 按交付类型做环境验收
→ Issue/Registry 核销（验收条款逐条对账）
→ 14/30 天复发与 Revisit 收割
```

与现行流程的差异集中在最后四步：**验收对账、环境验收、复发收割目前均不存在。**

## 5. Q4：止血、治标不治本与组合治理

### 5.1 止血的真实形态：危险的那部分没有被标注

`AGENTS.md` 要求「临时止血必须标注为过渡并写明终态出口」。本会话在
`backend/**/*.py` 全量检索 `止血|过渡|临时方案|workaround|stopgap`，生产代码命中
**极少且多为无关语义**（dpkg `libglib2.0-0` 过渡包、SUW 合法过渡态、
`file_server_monitor.py` 的同机过渡期）。

这不能推出"项目没有止血"。正确结论是：

> **止血以「对同型缺陷的逐条 path-level 修复」形态存在，从未被识别为止血，
> 因此没有 owner、没有 `review_by`、没有可测的删除条件。**

对比来看，[#1273](https://github.com/DUElost/stability-test-platform/issues/1273)
（TRUNCATE `DeadlockDetected` 退避重试）反而是**健康**的止血：边界清晰、Note 里
写明未定位泄漏会话、性质自陈为过渡。真正沉淀技术债的是下面三个簇——它们每一条
单独看都是"根因修复"，合起来看是同一个未被表达的缺失契约。

### 5.2 簇 A：假成功 / 成功语义不统一（最大簇，跨 R04/R07/R08/R10/R13/R14）

**证据规模**：以「假成功 / 仍返回成功 / 报成功」检索命中约 26 个同型 Issue。

- 已关闭：#1274（手动 scan 入队异常被吞仍回 200 "enqueued"）、#1027（monkey_setup
  不检查 adb 退出码）、#1074（中心存储发布失败仍回退本地报成功）、#1005（outbox
  入队失败终态静默丢失）、#1255（不完整恢复报 PASSED）、#1077。
- 仍开放：#812（clean_env / push_resources / fill_storage 三处 rc 全吞）、#809
  （monkey 看门狗链 3 处）、#816（设备脚本杂项 6 处）、#807（teardown 离线假全绿）、
  #805、#810、#828（LogPuller 残缺现场伪成功上送）、#746、#755、#757、#951、
  #949（热更新 is-active 失败仅 WARN，控制面仍 ok）、#1253（R14-F07 同型）、
  #759（archive 假成功仍报已触发）、#752、#797。

**第一性原理**：系统没有「操作结果语义」的统一契约。三种本质不同的状态被压成同一个
`200 OK`：

```text
已受理（enqueued）  ≠  已生效（applied）  ≠  已验证（verified）
```

在 Agent 脚本层它表现为子进程 `rc` 未检查，在控制面表现为触发类端点返回裸 `ok`，
在运维工具层表现为 WARN 冒充成功。

**为什么逐条修是治标**：#1027 关闭后，#812 / #809 / #816 又是完全同型的新实例；
#949 与 #1253 是同一缺陷在 R04 与 R14 的两次独立登记。每修一处只堵一个调用点，
下一个新脚本、新端点继续生产同型缺陷——**修复速度与产生速度同阶，净复利为零**。

**组合治理建议**：

1. 定义三态契约：触发类端点必须返回可查询的 handle（job/action id）而非裸 `ok`；
   「已受理」不得与「已生效」共用状态码与文案。
2. Agent 脚本层做**机械化门禁**：子进程调用必须消费 `rc`，可参照
   [ADR-0021](../adr/ADR-0021-script-content-alignment-gate.md) 的内容对齐门禁形态。
   门禁只对**新发布版本**生效（冻结版本不可原地改，见 5.4）。
3. 运维工具：WARN 不得作为成功出口，健康检查区分 liveness 与 readiness。

**是否需要新 ADR：需要。** 判据满足「存在互斥的长期语义选择」（同步确认 vs 异步
handle）与「跨模块边界」（控制面 API / Agent 脚本 / 运维工具三层）。范围应严格限定为
**操作结果语义契约**，不夹带具体端点重构。

### 5.3 簇 B：进程内状态冒充跨进程权威（与 §3.4 同根因）

**成员**：

| Issue | 表现 |
|---|---|
| [#91](https://github.com/DUElost/stability-test-platform/issues/91) | 限流器 `OrderedDict` 为模块级进程内状态，多 worker 下实际限额 = 配置值 × 副本数 |
| #1123 | 进程内 guard 约束生命周期不受协程控制的线程（§3.3） |
| #901 | 服务端不变量依赖客户端 Web Lock 兜底（§3.2） |
| [#1121](https://github.com/DUElost/stability-test-platform/issues/1121) | ADR-0027 声明「无需 sticky」，但 Agent 未强制 transport，room 跨进程 ≠ Engine.IO 会话跨进程 |
| #517 | sync `get_db` 与 async session 并存 |

**#91 的 body 精确说明了这个簇的危险形态**：

> 生产是 systemd 单进程 uvicorn，所以**现在是准确的**。一旦为了吞吐加 worker，
> 限流就会静默放宽 N 倍——没有任何告警提示这件事。

**第一性原理**：**部署形态是这些不变量的隐含前提，而前提没有被代码或门禁固定住。**
单进程下全部正确，横向扩展的瞬间集体失效，且不产生任何信号。这是比普通缺陷更差的
性质——它把"当前正确"和"设计正确"混为一谈。

**是否需要新 ADR：不需要，应做 ADR-0027 修订。**
[ADR-0027](../adr/ADR-0027-control-plane-horizontal-scaling.md) 正是做出"可横向扩展 /
无需 sticky"声明的那份文档，而 #1121 已证明该声明超出已验证范围。新建 ADR 会造成
两份关于同一横向扩展语义的权威文档。

**最小出口**：ADR-0027 增补「多副本安全性清单」，逐项登记仍为进程内权威的组件；
启动时检测 `workers > 1` 且存在未迁移组件则 fail-closed 或强制告警——把隐含前提
变成可执行断言。

### 5.4 簇 C：脚本冻结版本 × 静默吞咽 × 退役门禁崩溃（自我加强的腐化闭环）

这是本会话最重要的发现，因为它**不是静态债务，而是一个正反馈回路**。

**本会话独立实测数据**（AST 精确统计，`except` handler 体恰为 `pass`，排除测试）：

| 归属 | 处数 | 占比 |
|---|---:|---:|
| `backend/agent/scripts/` 已发布冻结版本 | **371** | **77.6%** |
| Agent 非脚本代码 | 68 | 14.2% |
| 控制面及其他 | 39 | 8.2% |
| 合计 | 478 | 100% |

脚本目录规模（`git ls-files`，不含工作区未跟踪的新版本）：**32 类脚本 / 116 个版本
目录 / 211 个 `.py` / 71,730 行**。
[#735](https://github.com/DUElost/stability-test-platform/issues/735) 立项时记录为
**100 个版本 / 180 文件 / 59,406 行**。即该治理 Issue 开放期间，脚本资产增长了
**+16 个版本目录、+31 个文件、+12,324 行（+20.7%）**。

> 计数口径说明：#739 记录的「431 处静默异常吞咽」含裸捕获，与本会话「体恰为 `pass`」
> 的口径不同，两者不可直接相减，不能据此断言增长；但 478 这一当前值本身成立，
> 且脚本行数的 +20.7% 增长是同口径可比的。

**闭环机制**：

```text
脚本层缺 rc 检查（簇 A）
  → 已发布版本不可原地修改（硬不变量）
  → 修复只能通过发布新版本
  → 版本目录膨胀（#735）
  → 退役诊断工具 check_unreferenced_script_versions 崩溃（MissingGreenlet）
  → 生产 64.3% 零引用版本、47 个仍 is_active，从不下线
  → 冻结存量持续增长
  → 簇 A 存量中 77.6% 永久不可达
  → 回到起点，且分母更大
```

**长期主义判据下的结论**：在这个回路被打断之前，**对簇 A 的逐条修复是负复利**——
每修一条脚本缺陷就新增一个冻结版本，使回路分母增大。这正是"治标不治本"的教科书
形态，而且它已经在数据上显形（+20.7%）。

**最小出口（顺序不可颠倒）**：

1. 先修 `check_unreferenced_script_versions` 的 `MissingGreenlet` 崩溃——这是整个
   回路上**唯一非侵入的切入点**，且不触碰任何冻结版本；
2. 下线 47 个零引用 `is_active` 版本，恢复退役闭环；
3. 在退役闭环可用后，再让簇 A 的 rc 门禁对新版本生效，否则门禁会直接放大膨胀。

**是否需要新 ADR：不需要，需要的是裁决。**
[`SCRIPT_VERSION_BLOAT_ENDGAME_FEASIBILITY_2026-09-10.md`](./SCRIPT_VERSION_BLOAT_ENDGAME_FEASIBILITY_2026-09-10.md)
已完成可行性研究但**未裁决**；ADR-0020 / ADR-0021 / ADR-0029 已覆盖不可变与对齐语义。
再开 ADR 只会增加概念数量，而缺的是一次"做或不做"的决定。

把这些与簇 A–C 混为一谈会稀释注意力预算。**deferred 且有触发条件 ≠ 止血。**

### 5.8 对 Q3 流程的回推

Q4 的发现修正了 Q3 的一个判断：现行模式的缺口不只是"终点定义错误"，还有
**入口缺少同型归并**。当前流程中 Finding 直接变成独立 Issue，Harness 自行认领
单条修复；没有任何环节会问"这是第几次遇到同型缺陷"。簇 A 的 26 个 Issue、簇 C 的
+20.7% 增长，都是在每一步都合规的情况下累积出来的。

因此建议在 §4.6 终态流程的「去重、反证与问题确认」之后增加一个**归并判据**：

> 同型缺陷计数 ≥3 时，禁止继续开独立实现单；必须先产出共同不变量与组合验收，
> 再分解为有依赖顺序的小 PR 链。

注意这条判据的约束对象是**实现单**，不是 Issue 登记——继续登记症状是必要的可见性，
但不应继续独立开工。同时重申：同型计数达标只触发**统一设计审查**，是否升格为 ADR
仍需满足 §4 的 ADR 判据（互斥长期选择 / 跨边界 / 现有 ADR 无法承载）。

## 7. 建议优先顺序

顺序依据：先打断自我加强的负反馈，再修确定缺陷，最后补流程。

1. **修 `check_unreferenced_script_versions` 崩溃并下线 47 个零引用版本（#735）**——
   簇 C 闭环上唯一非侵入切入点，不打断它则后续所有脚本层修复继续放大膨胀；
2. 重开 #901、#1123，按 3.2 / 3.3 的最小出口修复，并补并发与取消交错回归；
3. 将"不变量必须下沉到可原子判定层"写入高风险变更复核清单（避免第三次复发）；
4. 为簇 A 建立操作结果语义契约的设计裁决（仿 ADR-0036 形态），冻结同型缺陷的
