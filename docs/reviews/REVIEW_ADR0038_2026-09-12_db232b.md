## 结论概览

**总评：Needs-revision**（方向可接受，需修订后转 Accepted；实现单仍应在裁决后另开）

ADR 的四条主干判断我独立核验后**认可**，不构成修订理由：

1. `retired_at` 作为单一生命周期真源、且**不复用 `status`**——核验成立：`status` 有 4 处写入者，
   其中 2 处是**读路径懒更新**（`hosts.py:56-81`、`devices.py:57-76`），任何以 `status` 承载运维
   决定的设计都会被下一次心跳/列表请求改写；
2. 删除与退役分家、退役不触发任何删除——与 #937 预检（`hosts.py:477-553`）方向一致；
3. 退役可解除、全程审计——必要且缺失度最低的一部分；
4. 「不做 409」的心跳取舍——`/api/v1/heartbeat` 还承载 backpressure 与版本门禁响应
  （`agent_api.py:852-867`），拒绝会新增 Agent 侧失败模式，本轮不做成立。

**必须修订的 3 项（阻断）**：

| ID | 一句话 |
|---|---|
| F2-A | 派发面的 `host_retired` 归位缺失，且两种归位方式的后果都没写：归 retryable ＝ 永久 QUEUED 静默停摆（正常排队不消耗重试计数），归 fatal ＝ prepare 400；不写死即无法实现 D5 |
| F3-A | 「沿用现有告警去重惯例」不成立：仓库**没有任何 host 级告警与 host 级去重**，现有去重身份强制依赖 `run_id`，缺失即短路；无 `run_id` 的主机告警每次心跳都会新建通知日志并下发 |
| F6-B | D4「心跳如实记录 `status`」使现有 ONLINE 门**不再等价于「在用」**，而 D5 第五面（控制面动作）依赖的正是这些 ONLINE 门——必须显式新增 `retired_at IS NULL` 判据，ADR 未给出这一点 |

**建议 12 项 / 观察 5 项**，集中在：心跳与重连写路径（第六面）、统计面的 filter-or-count 语义、
`Host.extra` 会在心跳被重建这一实现陷阱、身份判据的单向性、审计证据的持久化面、迁移配套
（schema-sync / 单 head / 显式命名索引）、与维护窗口先例的关系；以及两处 ADR 事实性更正。

按 ADR 自身结构统计：F1 语义完备性（3 建议 + 1 观察）、F2 过滤面穷尽性（2 阻断 + 3 建议 +
2 观察）、F3 心跳策略（2 阻断 + 1 建议 + 1 观察）、F4 身份与换机（3 建议 + 1 观察）、
F5 一致性与迁移（2 建议 + 1 观察）、F6 安全面（1 阻断 + 1 建议 + 1 观察）、F7 验收可测性（2 建议）。

## F1 语义完备性（D1/D2 的入口设计与前置）

### F1-A（建议）「非 ONLINE」前置的判据在不同调用顺序下会漂移，建议改为显式 stale 谓词

- **位置**：`backend/api/routes/hosts.py:53,56-81`；`backend/api/routes/devices.py:30,33-80`；
  `backend/tasks/session_watchdog.py:34,42-50`
- **事实**：`host.status` 的 OFFLINE 化有 3 条路径，判据名称相同
  （`HOST_HEARTBEAT_TIMEOUT_SECONDS`）但**默认值不一致**：watchdog 默认 120s
  （`session_watchdog.py:34`），`hosts.py:53` 与 `devices.py:30` 默认 300s；且列表/详情**读路径**
  会顺带写状态（`hosts.py:353-357`、`:371-372`）。
- **影响**：退役前置里的「非 ONLINE」实际含义取决于「谁最近读过这台主机 / watchdog 是否跑过」。
  运维刚停掉 Agent 就点退役，在 watchdog 未跑、列表未刷新时会拿到「主机当前 ONLINE，请先停止
  Agent」的 409——而此时 Agent 已经停了。属于 fail-closed（可重试、不产生错误状态），但会浪费
  一次运维交互并误导判断。
- **落点建议**：D2 前置把「非 ONLINE」写成「非 ONLINE **或** `last_heartbeat` 已过期」，或抽取
  单一 stale 谓词供 watchdog / 读路径 / 退役前置共用；同时顺带记录三处默认值不一致（是否收口
  为同一常量由实现单决定，不与本 ADR 耦合）。

### F1-B（建议）DEGRADED 必须显式给出处置，因为它既满足「非 ONLINE」又不被派发侧拦截

- **位置**：`backend/models/enums.py:25-28`；`backend/services/plan_dispatcher_sync.py:155-160`；
  `backend/api/routes/agent_api.py:401-403`
- **事实**：派发侧只拦 `HostStatus.OFFLINE`（`plan_dispatcher_sync.py:155`），claim 侧要求 ONLINE
  （`agent_api.py:401`）。因此 DEGRADED 主机今天就会「派发通过、认领被拒」——作业静默挂住。
  另外核实到 **DEGRADED 当前无任何写入者**：Agent 心跳不传 `status`
  （`backend/agent/heartbeat_thread.py:345-360` 未传，`backend/agent/heartbeat.py:25` 默认
  `"ONLINE"`），`agent_api.py:811,829` 恒写 ONLINE，watchdog 只处理 ONLINE（`session_watchdog.py:47`）。
  `capacity_reporter.py:161` 的 DEGRADED 是 `health.status` 子对象，不是主机状态。
- **影响**：ADR 说前置是「非 ONLINE」，于是「活的 DEGRADED 主机」在语义上可被直接退役；同时
  「无活跃 Job」这条在当前代码下恰好会拦住 DEGRADED 主机上已挂住的 PENDING 作业——即前置会把
  退出路径堵成两条互斥的 409。今天是 latent（无写入者），一旦 Agent 版本开始上报 DEGRADED 就会
  变成真问题。
- **落点建议**：D2/D4 用一句写明 DEGRADED 的定位（「存活但降级，等同在用，不可退役」或
  「等同不可用，可退役」二选一），并在 §1.2 事实核验里补一行「DEGRADED 现无写入者（latent）」，
  避免实现单按不存在的状态写用例。

### F1-C（建议）D2 的「无活跃 Job」是瞬时快照，未说明与已派发未认领作业的关系

- **位置**：`backend/api/routes/hosts.py:488-500`（`_ACTIVE_JOB_STATUSES` 预检）；
  `backend/services/plan_dispatcher_sync.py:736-745`（PlanRunHost 快照）；`agent_api.py:401`
- **事实**：退役前置只查「此刻有没有活跃 Job」。但作业可以在「预检通过 → 写入退役」之间被派发
  （派发侧只看主机状态，不看退役——见 F2-A）。一旦发生：作业已物化、退役已写入、claim 被
  D5 拦 → 该 PlanRun 停在 PENDING/QUEUED。
- **影响**：与 F2-A 同因，但即使 F2-A 修好（派发侧拦住退役主机），**已经派发出去的存量作业**
  仍需一句处置口径（等待完成 / 由运维 abort / 允许退役但作业继续到终态）。ADR 未提及。
- **落点建议**：D2 补一句「退役不改变已存在的 Job 状态；退役前置只保证发起时刻无活跃 Job，
  并发派发由 D5 过滤面兜底」，并交给实现单决定是否需要反向「退役前 re-check」。

### F1-D（观察）误操作恢复与入口分家未覆盖「换新」的一半流程

- **位置**：ADR D2/D6；`backend/api/routes/hosts.py:197-218`（name/ip 唯一冲突预检）
- **事实**：「退役→换新机器上线」这条真实流程里，新机器若沿用原 IP/name，会先撞
  `_find_host_identity_conflict`（`hosts.py:275-277` 直接 409），必须先 `unretire` 才能注册；
  若新机器换 IP，则会新建一行，旧行仍占 `name`/`ip` 唯一位。
- **影响**：ADR 的 D6 只说「同 IP 换机 = 同身份 → unretire」，没有说「换 IP 的换新」怎么走
  （新建行？那旧行是否要退役？）。这属于 ADR 声称覆盖的「硬件退役/换新/下线」里的「换新」分支。
- **落点建议**：D6 或 §4 运维代价里补一行换 IP 换新的口径（建议显式：换 IP 视为新主机，
  旧行走退役），避免实现单自行发明。

## F2 过滤面穷尽性（D5 不变量）

### F2-A（阻断）派发面缺 `host_retired` 归位：不写死后果就是永久 QUEUED 静默停摆

- **位置**：`backend/services/plan_dispatcher_sync.py:68,88-100,155-168,509-519,827`；
  `backend/services/admission_pump.py:292-293,666-671`
- **事实链**（全部逐行核验）：
  1. 派发侧对「主机状态」只有一条拒绝理由：`host_offline`（`plan_dispatcher_sync.py:155-160`），
     快照只取 `Host.status` 与 `Host.maintenance_until`（`:88-100`）——**没有退役概念**；
  2. V2 准入队列只把 `_FATAL_DISPATCH_REASONS = ("not_found", "no_host")` 判为拒单
     （`:68`、`:509-519`），其余一律作为 `queue_blockers` 建 QUEUED 单；
  3. 退役主机在 D4 下 `status` 可如实为 ONLINE（`heartbeat.py:236`）→ **通过 host 检查** →
     PlanRun 建单、PlanRunHost 与 jobs 物化（`:736-760`、`:1034`）；
  4. 认领侧被 D5 拦（`agent_api.py:401` 需新增退役判据）→ 作业永不执行；
  5. 关键：**正常排队不消耗重试计数**——代码注释明写「Clean competition requeues do NOT consume
     `admission_requeue_attempts`」（`admission_pump.py:292-293`），`MAX_ADMISSION_REQUEUE_ATTEMPTS`
     只约束「worker 已死的 stale PRECHECK」（`precheck_reaper.py:287,367`）。
- **影响**：若 `host_retired` 归入 retryable（与 `host_offline`/`host_maintenance` 同类），该 PlanRun
  **无上限、无 dead-letter、无告警地永久排队**；对比先例：`host_offline` 会因心跳恢复而自愈、
  `host_maintenance` 有 TTL 会过期（`host_maintenance.py:32-33`）——**退役永不自愈**，同类处置在这里
  语义不成立。若归入 fatal（prepare 400），则与 ADR 原话「退役主机不进入派发快照」并不等价，
  且需说明「排到一半被退役」的存量单怎么处置（F1-C）。
- **落点建议**：D5 第一条改写为可实现的判据并二选一定死：
  ① 「退役视同 `no_host` 级 fatal（prepare 400，明确错误码如 `host_retired`）」——推荐，语义最干净，
  与「不在用」一致；或 ② 「退役为 retryable 但必须同时给出停止条件」（例如超过 N 分钟/由运维
  abort），并说明为何可接受永久排队。
  实现落点建议复用**单一分类点**：`_classify_dispatch_devices_sync` 已被 prepare、TOCTOU 复检
  （`plan_dispatcher_sync.py:827`）与准入泵（`admission_pump.py:666-671`）三处共用，加在此处即三面
  同时覆盖（同 F5-B）。

### F2-B（阻断→建议）第六面「控制命令下行」：多个面向退役主机的下行通道不查退役（部分连 ONLINE 都不查）

- **位置**（逐条核验）：
  - `backend/api/routes/plan_runs.py:553-567`：scan/archive 扇出按 `host_status == "ONLINE"` 挑选并
    `emit_agent_control(..., "archive_now"/"scan_now")`；主机集合来自
    `backend/services/plan_run_scan_scope.py:90-122`（union job/PlanRunHost/host_id_snapshot，只看状态）。
  - `backend/api/routes/dedup.py:510-513`：`POST /plan-runs/hosts/{host_id}/reload-config` **完全没有
    host 查询**，直接 `emit_agent_control(host_id, "reload_config")`。
  - `backend/services/ai_assistant/orchestrator.py:677-680`：AI 工具 `reload_agent_config` 只校验
    `host.status != "ONLINE"`。
  - `backend/realtime/socketio_server.py:154-186`：Agent 连接仅校验全局 `AGENT_SECRET` 与非空
    `host_id`，注册 `_host_to_sid[host_id]` 并进入 `agent:{host_id}` 房间，**不查主机是否存在、更不查退役**。
  - `backend/scripts/batch_hot_update.py:89-95`：按 `Host.status == "ONLINE"` 全量热更新。
- **影响**：D5 第五面写的是「热更新/安装/批量刷新」，实测这些之外还有**扫描/归档扇出、reload-config、
  AI 工具、Socket.IO 房间注册**四条下行通道。退役主机只要 Agent 还活着（D4 明确允许心跳），
  这些通道会继续对它下命令；其中 scan/archive 还会把该主机重新写进结果集与去重产物口径
  （`backend/services/dedup_scan.py` 按触发的 host_ids 登记产物）。
- **落点建议**：D5 第五面扩写为「控制面与下行命令（热更新/安装/批量刷新/扫描归档扇出/
  reload-config/AI 工具/Socket.IO 房间）」并为每类给出 file:line 落点；`Socket.IO` 一条建议单独
  决策：**连接是否拒绝**（推荐只做下行拦截、不拒绝连接，理由同 D4 不做 409——拒绝连接会牵动
  Agent 重连策略）。另建议记录 `dedup.py:510` 这条「零校验」现状：它今天对不存在的主机也不报错。

### F2-C（建议）心跳/重连写路径不在五面内，且 D4 的「如实记录」范围没界定

- **位置**：`backend/api/routes/heartbeat.py:236,244-247,249-262,281,76-113,403`；
  `backend/api/routes/agent_api.py:806-814,829`
- **事实**（逐条核验）：
  - `heartbeat.py:236` `host.status = payload.status`（Agent 恒上报 ONLINE）、`:238` `last_heartbeat`、
    `:244-247` `boot_id` / `last_agent_instance_id`、`:250-281` **重建 `host.extra`**、
    `:76-113` `_sync_host_identity` 改写 `ip/ip_address/name/hostname`；
  - `heartbeat.py:403` `device.host_id = host.id` **无条件**重挂设备，唯一拦截是「该设备存在
    指向别的主机的 ACTIVE 租约」（`:385-392`）→ **退役主机一旦重连，可把设备从现属主机抢回**；
  - `agent_api.py:806-814` 找不到即**新建**主机行、`:829` 强制 ONLINE（第二条心跳实现）。
- **影响**：D4 只承诺「保持退役、不改写 status 的**退役位**」，但上面这些写入会改写 `status`、
  设备归属、`extra`、身份字段。设备抢占是其中最具破坏性的一条：D6 说「设备物理搬移由现有
  re-home 处理」，但没说退役行重连时 re-home 是否仍应生效。
- **落点建议**：D4 增一段「心跳可写 / 不可写字段边界」：建议 `status`/`last_heartbeat`/遥测 `extra`
  照写（如实），**身份与归属字段（`ip`/`name`/`boot_id`/`agent_instance_id`、设备 re-home）**
  明确是否照写；若照写，需说明「退役不冻结身份」对审计（F4-C）的影响。这条与 F3-B 的
  `extra` 重建是两个不同的坑，不要合并。

### F2-D（建议）统计面比 ADR 描述的更宽，需要逐点定「排除」还是「保留」

- **位置**：`backend/api/routes/stats.py:264-272,286-298,304-327,338-347,451-459`；
  `backend/api/routes/metrics.py:39-53`；`backend/services/ai_assistant/tools.py:136-149,374-389`；
  `backend/services/file_server_monitor.py`（经 stats.py:264 传入的 host 列表）
- **事实**：`dashboard-summary` 的 `host_total`/`host_online`/`online_rate`/资源均值来自
  `SELECT status, extra, ip FROM host` **全量行**（`stats.py:286-347`）；Prometheus `host_online`
  gauge 按 status 分组全量计数（`metrics.py:44-53`）；AI 平台健康同样按全量 host 分组
  （`tools.py:136-149`）；`GET /hosts` 无任何过滤（`hosts.py:340-362`）。
- **影响**：D5 写「不计入在线容量与库存统计」。但「库存」边界不明：`host-failure-rate` 这类
  **历史 KPI**（`stats.py:451-459`）按退役行分组恰恰是历史保留决策要的（D3 不删历史）；
  dashboard「主机总数」则更像在线容量。不区分会导致实现单要么过度排除（历史 KPI 消失）、
  要么排除不足（退役机稀释在线率）。
- **落点建议**：D5 把统计面拆成两类并各给一句口径：**「在线容量/资源水位类」排除退役**
  （`stats.py:264-272`、`metrics.py:44-53`）、**「历史 KPI/趋势类」保留退役**（`stats.py:451-459`、
  报告与导出）；`HostOut` 需新增 `retired_at` 字段（`backend/api/schemas/host.py:57-99` 现无）供前端
  与筛选使用。

### F2-E（观察）设备侧入口未收口：可继续在退役主机上建设备/选设备

- **位置**：`backend/api/routes/devices.py:98`（创建设备只校验 host 存在）、`:294-377`（列表不按主机
  退役过滤）、`frontend/src/pages/devices/components/AddDeviceModal.tsx`（host_id 自由输入）
- **影响**：退役主机仍可作为设备归属被写入；设备列表与执行准备页会把退役主机的设备呈现为候选
  （`frontend/src/utils/planExecuteReadiness.ts` 只依据 `host.status !== 'ONLINE'` 判断）。
- **落点建议**：D7「显式不做」里目前写了「设备退役独立议题」；建议补一句**设备归属写入**的边界
  （是否允许 `POST /devices` 指向退役主机），否则实现单会默认允许。属观察级：不产生新失败模式，
  只是收口不完全。

## F3 心跳策略（D4）

### F3-A（阻断）「沿用现有告警去重惯例」不成立：不存在 host 级告警，也不存在 host 级去重

- **位置**：`backend/services/notification_service.py:329-345,442-500,549-560,649-655`；
  `backend/api/routes/heartbeat.py:142-160`；`backend/models/notification.py:16-20,122-126`
- **事实**（逐条核验）：
  1. `EventType` 只有 `RUN_COMPLETED / RUN_FAILED / RISK_HIGH / DEVICE_OFFLINE`
     （`notification.py:16-20`）——**没有任何 host 级事件类型**；全仓也没有 host 离线/降级/心跳超时告警
     （host 状态变化只有日志与 metric，无 `dispatch_notification*` 调用）。
  2. 去重身份是 `(event_type, run_id, task_id, device_serial)`
     （`notification_service.py:329-336`），**不含 host_id**；且
     `:343-345` `if run_id is None: return None, {}` —— **无 run_id 时彻底短路**。
  3. 短路后果：`:469-479` 判定 `prior_log_id is None` → `:483-500` **每次都新建 `NotificationLog`**
     并置 `emit_new=True` → 站内通知与通道投递都会重复；per-channel 幂等
     （`:549-560` + `notification_delivery` 唯一约束）只对**同一 log** 生效，救不了新 log。
  4. SAQ 去重键 `notif:{event_type}:{run_id}:{device_serial or ''}`（`:649-655`）在无 run_id 时退化为
     **常量键**，而 SAQ 去重只覆盖「仍在队列中」的同键作业——作业完成后键释放，下次心跳照常入队。
  5. 仓库内真正可复用的惯例是**发射点的状态跃迁门**：`heartbeat.py:142-148` 的
     `already_offline` 早退，使 `DEVICE_OFFLINE`（同样**无 run_id**，`heartbeat.py:154-160`）只在
     状态真正变化时发一次。
- **影响**：D4 要求的「单次告警（去重）」当前**没有事实源**。若实现单按字面「沿用惯例」调用
  `dispatch_notification_async("HOST_RETIRED_HEARTBEAT", {...})`，退役活体主机将以心跳间隔
  （Agent 侧自适应建议间隔，`agent_api.py:852-867`）持续产生**通知日志行 + 站内通知 + 渠道消息**，
  即告警轰炸（用户痛点）。
- **落点建议**：D4 与不变量 3 改写为「复用发射点状态跃迁门（先例 `heartbeat.py:142-148`）」，
  并**指定去重状态的事实源**（列 or `extra` 白名单键——见 F3-B）、**重置条件**（非退役态/心跳恢复？
  还是只在 unretire 后重置）与**告警事件类型**（若新建 `EventType`，需按 ADR-0036 的投递语义
  给出键形态；注意其去重身份无 host_id，需要扩展或改用设备序列号位）。

### F3-B（建议）去重状态不能放 `Host.extra` 的裸键：心跳会重建 extra 并只保留 6 个白名单键

- **位置**：`backend/api/routes/heartbeat.py:249-262,281`；对照 `agent_api.py:3167`（ADR-0025 已占
  `extra['archive']`）
- **事实**：`host_extra = {}` 起步，仅从 `prev_extra` 拷贝
  `agent_version / agent_installed / agent_installed_at / agent_code_revision / agent_code_deployed /
  agent_code_deployed_at` 六个键（`:253-262`），再叠加 `payload.extra` 与若干固定键，最后
  `host.extra = host_extra`（`:281`）**整体替换**。
- **影响**：任何自建键（如 `retired_alert_sent_at`）会在**下一次心跳被静默抹掉**——去重退化为
  「永不生效」，且因为不报错，只有线上告警轰炸才能暴露。这是本 ADR 最容易踩的实现陷阱
  （ADR §1.2 只提了 `archive` 命名冲突，没提「extra 不是持久状态容器」）。
- **落点建议**：D4 明确去重状态载体：① 新增列（与退役三列同批迁移，代价最小、语义最清晰）
  或 ② `extra` 白名单加键（须在 `heartbeat.py:253-262` 同步登记）；推荐 ①。同时在 §1.2 补一行
  「`Host.extra` 每次心跳重建，非持久事实源」的结论。

### F3-C（建议）D4「如实记录」需与 ADR-0035 的归属审计要求对齐

- **位置**：`docs/adr/ADR-0035-agent-host-identity.md:176-199`（§6 触发条件与 §6.1 检测来源）；
  `backend/api/routes/heartbeat.py:196-205`
- **事实**：当前全局 `AGENT_SECRET` 下，心跳按 `host_id` 取行，取不到则**按 IP 认领**
  （`heartbeat.py:199-205`）。ADR-0035 触发条件 4 是「主机级审计归属成为合规/定责要求」。
- **影响**：退役位（`retired_at`）本身不会被心跳清除（D1 独立列，fail-closed，方向正确）；但
  谁能心跳、心跳改写了哪些字段（F2-C）在共享 secret 下都不可归因。今天不构成绕过，
  但一旦触发条件 4 命中，退役审计（谁退役/谁又让它心跳）需要同一套主机级归属能力。
- **落点建议**：D6 的「ADR-0035 per-host 凭据落地后重审换机注册流程」扩为
  「重审换机注册**与退役审计归属**」，并在 §6 触发条件映射（ADR-0035 §6.1）里留一个回链。

### F3-D（观察）不做 409 的取舍成立

- **位置**：`backend/api/routes/agent_api.py:852-867`（心跳响应含 backpressure 与版本门禁）
- **结论**：核验通过，Revisit 1 保留合理；仅提示若将来升级为 409，需同步评估
  `HeartbeatResponse` 契约与 Agent 侧重试/退避（`backend/agent/heartbeat_thread.py`）。

## F4 身份与换机（D6）

### F4-A（建议）「id 本就 IP 派生」只在创建时成立，判据应写成「按行认机器、ip 是可变属性」

- **位置**：`backend/core/host_identity.py:10-25,28-49`；`backend/api/routes/heartbeat.py:76-113`；
  `backend/api/routes/hosts.py:197-218,275-281`；`backend/models/host.py:40-41,61`
- **事实**：`ip_to_host_id` 只在**创建行**时把 ip 映射为 id（`hosts.py:278`、`heartbeat.py:208`）；
  行建立之后 `_sync_host_identity`（`heartbeat.py:76-113`）只改 `ip/ip_address/name/hostname`，
  **不改 id**。因此 DHCP 迁移一次后，行的 `id` 与 `ip` 即脱钩。
- **影响**：D6 的「同 IP 换机 = 同一主机身份」在**IP 复用**场景成立（心跳按 ip 认领旧行，
  `heartbeat.py:199-205`），但反向不成立：**同一身份不必然同 IP**。ADR 用它作为 D6 的唯一论据，
  措辞会误导实现单写出「按 ip 匹配」的判据（例如给 retire 加入 ip 重校验），从而在 DHCP 迁移过
  的主机上出错。
- **落点建议**：D6 改述为「生命周期按**主机行 id** 判定；`ip` 是可变属性，仅在注册时参与 id 派生；
  同 IP 换机因此复用原行（复用是**结果**而非判据）」。

### F4-B（建议）`allocate_host_id` 冲突后缀路径不是死代码，D6 需要给出预期

- **位置**：`backend/core/host_identity.py:39-49`；`backend/api/routes/heartbeat.py:207-208,199-205`；
  `backend/api/routes/hosts.py:275-281`
- **事实**：手工建主机路径在冲突前就 409（`hosts.py:275-277`），所以该路径不经过后缀分支；
  但**自动注册路径**（`heartbeat.py:207-208`）先按 ip 找行、找不到才分配，因此当「旧行 ip 已漂移
  走（F4-A）而旧 ip 被新机复用」时，`exists(base)` 为真 → 追加后缀生成 `198-51-100-6-a1b2` 形态的
  **新行**，而不是复用旧行。
- **影响**：这正是 D6 问的「冲突后缀路径下的命中边界」——答案是**可达**，且与「同 IP 换机=同身份」
  的裁定**方向相反**（该场景下同一物理 IP 会分裂出两行）。ADR 未说明该场景是 bug、是接受、
  还是需要显式按 ip 复用。
- **落点建议**：D6 补一句该边界的期望（推荐：明确「id 已被占用但 ip 相同 → 仍复用旧行」，
  即在自动注册里把「按 ip 命中」置于「按 id 分配」之前；现状 `heartbeat.py:199-208` 已是这个
  顺序，只需确认并写成不变量），并配一条回归用例（F7-A）。

### F4-C（建议）boot_id / agent_instance_id 不足以支撑审计与恢复，需要新的持久化面

- **位置**：`backend/models/host.py:51-52`；`backend/api/routes/heartbeat.py:244-247`；
  `backend/models/job.py:25`（JobInstance 只有 host_id）；`backend/models/device_lease.py:34`
  （agent_instance_id **唯一**的历史载体是租约）
- **事实**：`boot_id` 与 `last_agent_instance_id` 只存在于 host 行的**当前值**，每次心跳原地覆写；
  `job_instance` **没有任何** agent 身份/机器快照字段（全仓仅 `device_lease.agent_instance_id`）。
- **影响**：换机（同 IP 或同 id）后，「这条历史 Job 是哪台物理机跑的」不可回答；D6 说
  「`boot_id`/`agent_instance_id` 变化在详情与审计可见」——**当前没有可承载「变化」的面**
  （详情只显示当前值，心跳不写审计）。
- **落点建议**：D6 明确该可见性的事实源：建议在 `unretire` 与「检测到身份变化」时写审计
  （含前后 `boot_id`/`agent_instance_id`/`ip` 快照），复用 `record_audit`
  （`hosts.py:261-270` 有 `host_key_replaced` 先例）；是否新增列由实现单决定，但 ADR 必须承认
  「现无持久化面」这一事实，否则验收无从谈起。

### F4-D（观察）退役主机在共享 secret 下的冒名写面

- **位置**：`backend/api/routes/heartbeat.py:196-205`；`docs/adr/ADR-0035-agent-host-identity.md:176-199`
- **结论**：退役位不会被冒名心跳解除（D1 独立列，方向正确）；但冒名者可写 `status`/`extra`/身份字段
  （F2-C），形成「退役主机的遥测可被任意持有全局 secret 者污染」。今天无额外绕过，
  与 ADR-0035 §3 风险接受一致；记入 ADR-0035 触发条件 4 命中时的复核面（同 F3-C）。

## F5 一致性与迁移

### F5-A（建议）三列 additive 迁移的配套没写：schema-sync 比对、单 head、显式命名索引

- **位置**：`.github/workflows/ci.yml:329`（`python -m backend.scripts.check_schema_sync`）；
  `backend/tests/test_schema_sync_guard.py`；`backend/models/host.py:25-27,60-64`（显式命名先例）
- **事实**：空库建库路径与 ORM 的一致性由 `check_schema_sync` 在 CI 强制（ci.yml:329），
  其回归守卫明确「索引单边漂移必须拦截」（`test_schema_sync_guard.py:11-19,35-48`）；
  `Host` 现有唯一约束/索引都显式命名以避免自动命名漂移（`host.py:26-27,61-64`）。
- **影响**：ADR 只说「三列 additive nullable，无回填」。实现单若给 `retired_at` 加索引
  （`GET /hosts` 默认列表要过滤，见 F2-D），漏写显式名或漏改迁移即被 CI 拦；ADR 未提这条门禁，
  也没有说是否要索引。
- **落点建议**：§4 迁移补一行实现前置：ORM 与 alembic 成对修改 + `check_schema_sync` 必须绿 +
  `alembic heads` 保持单 head + 新增索引（如 `idx_host_retired_at`）显式命名。是否建索引交由
  实现单按 `GET /hosts` 查询形态决定。

### F5-B（建议）与 #960 维护窗口的关系未定义：同形互斥面，建议复用同一分类点

- **位置**：`backend/services/host_upgrade_gate.py:6`（自述「`host.maintenance_until` 是唯一能同时
  挡住派发与 claim 的互斥面」）；`backend/services/host_maintenance.py:55-66`；
  `plan_dispatcher_sync.py:163-168`；`agent_api.py:406-409`；下行命令面见 F2-B
- **事实**：现有先例把「主机级生命周期门」实现为**一个判据 + 两个消费点**（派发分类器与 claim），
  并由 `_classify_dispatch_devices_sync` 单点覆盖三处派发入口（`plan_dispatcher_sync.py:509,827`、
  `admission_pump.py:666`）。退役门需要覆盖同样的两个消费点（D5 前两条），但 ADR 未提这个先例，
  也未说明两者优先级（维护窗口内退役？退役主机的升级门？——后者现状只查存在性，
  `host_upgrade_gate.py:229-231`）。
- **影响**：两套生命周期门各自实现会出现「分类器里两个 reason 谁先命中」「claim 里两个检查顺序」
  等未定义行为；`host_upgrade_gate.py:6` 那句「唯一互斥面」在退役落地后**变成不准确的文档**，
  需要同步修订。
- **落点建议**：D5 写明实现落点＝复用 `_classify_dispatch_devices_sync`（新增 `host_retired` reason）
  与 `_claim_jobs_for_host`（`agent_api.py:396-409`，与 `in_maintenance_window` 并列）；并在
  §4 影响里点名 `host_upgrade_gate.py:6` 的措辞需随实现更新。

### F5-C（观察）回滚会丢失退役事实

- **位置**：ADR §4 迁移（drop 三列）
- **结论**：与「退役不产生新数据形态」一致，回滚后历史行无依赖（D3），可接受；建议迁移注释明写
  「drop 会丢失退役状态与审计三列，属不可逆的运维状态丢失」，避免被当成无损回滚。

## F6 安全面

### F6-A（阻断）D4 使现有 ONLINE 门不再等价于「在用」，D5 第五面必须显式加退役判据

- **位置**（逐条核验，均无退役判据）：
  - `backend/api/routes/hosts.py:611-615`：hot-update 仅 `host.status != "ONLINE"` 拒绝；
  - `backend/api/routes/hosts.py:821-825`：install 仅校验存在 + 有 IP（**连 ONLINE 都不查**）；
  - `backend/services/host_upgrade_gate.py:229-231`：`begin_host_upgrade` 仅校验存在
    （外部 Ansible 升级入口 `agent_api.py:3262-3307` 也走这里）；
  - `backend/api/routes/dedup.py:510-513`：reload-config 零校验；
  - `backend/services/ai_assistant/orchestrator.py:677-680`：AI reload 仅查 ONLINE。
- **影响**：D5 写「控制面动作（热更新/安装/批量刷新）对退役主机拒绝」——但**退役主机的 `status`
  在 D4 下就是 ONLINE**（心跳如实写），这些 ONLINE 门**全部放行**。也就是说 D5 第五面若按
  「现有门已覆盖」理解，则完全未生效；这是一个 D4 与 D5 的直接冲突面，必须在 ADR 里说清。
- **落点建议**：D5 第五面明确写出「现有 ONLINE 门不足以判定在用（因 D4），每个控制面动作需新增
  `retired_at IS NULL`/统一 `host_is_active()` 判据」并列出上表落点；`install` 与 `upgrade gate`
  两条尤其要写（前者今日无状态门，后者连 ONLINE 都不查）。

### F6-B（建议）`retire_reason` 与 `unretire` 的审计字段应强制

- **位置**：ADR D1/D2；`backend/api/routes/hosts.py:261-270`（审计先例）；`base/api/schemas/host.py`
- **事实**：D1 把 `retired_by`/`retire_reason` 定义为可空列，D2 只说「admin + 审计」，
  未说 `reason` 是否必填；unretire 无前置也未要求原因。
- **影响**：退役是「从在用转为终态」的运维决定，理由为空会让事后定责（含 ADR-0035 触发条件 4）
  失去依据；unretire 无原因则误操作与有意复活不可区分。
- **落点建议**：请求 schema 对 `reason` 强制 `min_length=1`（列本身可仍为 nullable 以兼容
  未来系统发起的退役），unretire 同样记录原因；审计 details 里带上 IP/`boot_id` 快照（配合 F4-C）。

### F6-C（观察）无 DB 校验的 host 定向 RPC 需要一份清单

- **位置**：`backend/api/routes/hosts.py:931-1030`（dead-letter 列表/重放，直接对 host_id 走 Agent RPC）、
  `backend/api/routes/logs.py:247-275`（`POST /agent/logs` 开 SSH）、`socketio_server.py:749-760,794-835`
  （`emit_agent_control` / `call_agent_control`）
- **结论**：这些路径不读 host 行，D5 的过滤面天然覆盖不到；是否要拦取决于「退役是否代表禁止
  控制面继续操作该机」。属观察级（不构成新绕过：仍需 admin 或 agent secret），建议实现单里
  枚举成清单并逐条决策，避免遗漏成事实上的后门。

## F7 验收可测性

### F7-A（建议）「反例实证」判据可操作且有先例，但五面需要扩成六类并给出用例落点

- **位置（先例）**：`docs/notes/bug-fix/2026-09-11-host-delete-history-guard-796.md:35`
  （「临时禁用三处预检（mutation）→ 两用例均转红」）、
  `docs/notes/bug-fix/2026-09-11-hard-delete-dependency-guards-937.md:40`（同型）
- **事实（现成回归入口）**：`backend/tests/services/test_plan_dispatcher_device_validation.py:176-185`
  （`host_offline` reason）、`backend/tests/services/test_admission_queue_step3.py:226`
  （准入队列按状态 requeue）、`backend/tests/api/test_metrics_fleet_gauges.py`（fleet gauge）、
  `backend/tests/api/test_hosts.py`（host 路由）、`backend/tests/api/test_devices.py:134-190`
  （设备状态随主机）。
- **落点建议**：验收 2 的五面扩为「五面 + 下行命令类（F2-B）」并逐点指定可复用测试文件；
  「反例实证」沿用仓库既有 mutation 写法（临时移除该过滤点 → 对应用例转红），这条 ADR 现有表述
  已足够可操作，只需补「临时移除」的粒度（每个过滤点一条）。

### F7-B（建议）「单次告警」缺可测定义

- **位置**：ADR 不变量 3 与验收 3；F3-A/F3-B 的证据面
- **事实**：去重语义当前无事实源（F3-A），`Host.extra` 不可作为状态载体（F3-B），因此
  「只响一次」既无法实现也无法断言。
- **落点建议**：ADR 写明三件事后用例才可写：**状态源**（列/白名单键）、**重置条件**
  （OFFLINE→ONLINE 震荡回来是否重置；unretire 后是否重置——D4 现在只说「除非状态震荡」，
  没定义「震荡」）、**断言形式**（同一主机连续 N 次心跳 → `NotificationLog` 恰好 1 行；
  重置条件触发后 → 恰好 2 行）。建议配一条反例实证（去掉状态门 → 用例转红）。
