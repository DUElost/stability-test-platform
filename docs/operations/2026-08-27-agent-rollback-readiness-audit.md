### 2.2 控制面侧

- 回滚目标版本可得性：`2108a41` / `0f9d8cc` 均在 git 历史 ✓（git 历史恒可回退）
- 打包机制（`backend/services/host_updater.py:400-405,449`）：`_build_tarball()` 打包 `_AGENT_SOURCE_DIR` **当前 HEAD**，热更新下发 `agent/VERSION` 记录该 revision

## 3. 机制判定：回滚 = 两步人工操作

| 步骤 | 操作 | 性质 |
|------|------|------|
| ① 控制面 agent 源码树切到旧 revision（`git checkout <rev>` 或 worktree） | 控制面写操作 | 需人工执行，无一键入口 |
| ② 对目标 host 重发 hot-update → 重启服务 | 已有运维路径（runbook §2/§3） | 成熟 |

**发现的机制缺口**：无「一键回滚到指定 revision」入口；热更新永远打包当前 HEAD，回滚依赖人工先切换源码树。此步骤不在任何演练记录中——正是「回滚须是演练最多的路径」原则下最薄弱的一环。

**部分隐式演练的实证**：双版本在役本身说明「从 2108a41 回退到 0f9d8cc 的路径」被 10 台未升级 host 长期运行着——回滚目标版本的行为被真实环境持续验证（尽管是无意为之）。
