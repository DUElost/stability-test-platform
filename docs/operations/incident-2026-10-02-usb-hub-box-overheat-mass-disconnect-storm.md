# 2026-10-02 USB hub 箱过热失效与断电型断连风暴复盘（NX2 批次 · 双宿主共用箱拓扑）

> **状态**：失效箱已复电并验箱通过（2026-10-02 17:01，空载枚举干净、浸泡零事件，见 §4）；NX2 批次改为「部分直插宿主根口 + 箱载压到 ≤16 台」的降载布局继续运行（§5）。
> **影响范围**：一台 32 口 hub 箱（两宿主共用，箱内 Realtek RTS5411 两级级联）及其挂载的 30 台 NX2 设备（H-A×16 + H-B×14）中断约 1 小时； Monkey run 701 的 30 个作业失去硬件后挂 RUNNING，随设备直插回树自动续跑 26 台。前一晚的 X6728 批次终止（run 683）为**有意拆除**，与本次失效无关但共用同一拓扑事实。
> **关联**：[7-29 xHCI 主控死亡事故](./incident-2026-07-29-host-8-87-xhci-death-and-adb-outage.md)（**H-A 即同宿主**，彼时是宿主侧主控层、本次是箱侧供电层，判据不同）；监控缺口 issue [#3592](https://github.com/DUElost/stability-test-platform/issues/3592)（断电型风暴检测面缺失，方案待 Planner）；[四层判别文档](./host-device-visibility-triage.md)（本族故障落在其 L0–L4 覆盖之外）。
> **化名**：按 ops 惯例宿主 IP 用 RFC5737 化名且尾段不保真——H-A=`192.0.2.87`（沿用 7-29 案）、H-B=`192.0.2.71`、H-C=`192.0.2.72`、H-D=`192.0.2.73`；真身钉法=DMI+心跳指纹。文中「现场口述」指由在场运维确认、无法远程复核的事实。

## 2. 根因判定

结论：**共享供电箱的热/功率余量被 NX2 档载荷击穿**。箱是崩溃点，设备是热源，两者都不是「故障方」——手机零电气异常、箱空载完全稳定。NX2 机型的 USB 供电取流档位**明显高于** X6728（同箱对照直接钉死）。

### 2.1 判据矩阵（载荷-时长-结果）

| 载荷形态 | 持续时间 | 内核 USB 事件 | 结果 |
|----------|----------|----------------|------|
| 箱空载（X6728 拆除后） | ~20h | **0**（hub 全程保持枚举） | 稳定 |
| 31 台 X6728 满载 | 3.5h | 0（仅人为拆除时断开） | 稳定 |
| **30 台 NX2 满载** | **45min**（含 25min Monkey） | 前兆抖动（H-B 15:25）→ 人工断电风暴 | **热失效** |
| 23 台 NX2（箱 2：H-C+H-D） | 2h+ | 0（**现场口述：箱体温热，低于死箱**） | 稳定但贴近余量 |
| 箱空载（复电后） | 10min+ | 0 | 稳定 |

### 2.2 风暴标记构成（与慢性链路劣化完全不同）

| 标记 | H-A（15:55–15:59） | H-B | 词表覆盖 |
|------|------|------|----------|
| `USB disconnect` | 197 | 201 | **否** |
| `attempt power cycle` | 60 | 57 | **否** |
| 半箱根 hub 重枚举循环（~4s 周期） | 有 | 有 | **否** |
| `error -71/-110`（LINK_ERROR） | **6** | **3** | 是（阈值 20/1h ⇒ 不触发） |
| over-current / `HC died` / `cable is bad` | 0 | 0 | — |

供电塌陷型死亡的设备是「干净消失」而非「错误退出」：几乎不产生链路错误码，电气保护未跳（零 over-current）、宿主控制器健康（零 `HC died`）。**箱侧失效与宿主侧失效的铁证判据**：H-B 的 3 台幸存设备全部直插宿主根口（不经任何 hub）。

### 2.3 排除清单

- **非手机电气故障**：零 over-current、零设备侧错误码；震动是 Monkey 设计内行为（随机事件流触发电机振动），本次不做设备侧归因。
- **非空载自败 / 非 hub 固有缺陷**：空载 20h 零事件（§2.1 第一行）；复电验箱通过。
- **非宿主 xHCI 主控问题**：零 `HC died`；7-29 案（同宿主 H-A）是主控层死亡，本次主控全程健康——同宿主两次事故在**不同层**。
- **非单口/线缆**：两半箱（两宿主侧）同时失效；`cable is bad` 零命中。
- **非 L0 意图混淆**：本次断电是止损动作，前兆（15:25）在断电之前已存在。

## 4. 复电验箱判据（本次人工流程，未 SOP 化）

1. 上行线接好后，两宿主各自干净**顺序**枚举半箱：各 10 颗 RTS5411（5×`0bda:5411` USB2 面 + 5×`0bda:0411` USB3 面），树形 1+4 两级、无重枚举循环；
2. 空载浸泡 ≥5 分钟：零 `USB disconnect`、零 `error -71/-110`、零 `attempt power cycle`；
3. 通过后分批挂设备（每批摸温），带载后继续盯 §3 配方 2 的计数。

## 6. 复盘要点

- **「两宿主 USB 同刻异常＝先查共用箱」**：同箱两半同刻失效是必然不是巧合；10-01 排查时该拓扑事实缺位，曾被引向「共用电源排」假设。箱在平台与内核中无实体（#3592 缺口 3）。
- **mass-disconnect 风暴 ≠ 链路错误风暴**：现役 `usb_link_degraded` 词表覆盖后者；断电/热塌型风暴 `-71` 仅个位数，恒不触发（#3592 缺口 1）。
- **部分损失是健康面的盲区**：`usb_tree_empty` 只覆盖整树死亡；根口有零星幸存者时徽章恒 HEALTHY（#3592 缺口 2）。
- **1h 滑动窗的窗尾效应**：风暴后 `usb_link_degraded` 会多响约 1 小时（H-C 第二段 16:09–16:26 即晨风暴窗尾）——判「仍在抖」必须回查 dmesg，不能只看告警时序。
- **告警日志量与严重度不成正比**：1300+ 行里 95% 是人工断电瞬间的 flap 记录；真正的负载前兆只有 H-B 的 4 次断连。按日志量定严重度会误判。
- **设备挂点必须 sysfs 证实**：凭 adb 计数/BUSY 反推「设备挂回了箱上」本次实测误判一次（实为根口直插、箱上 0 台）。
- **L0 先于人**：同刻整批掉线先问现场（人为/有意操作），再排硬件——本次 X6728 拆除（10-01）与箱断电（10-02）两起「整批消失」最终都是有意动作或其直接后果。
