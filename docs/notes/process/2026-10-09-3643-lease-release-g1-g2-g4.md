# #3643：设备租约紧急释放 SOP 补 G1、G2、G4；G3 出实施方案

Status: implemented
Class: process

## Decision

按 Owner 在 #3643 的裁决补齐 `docs/operations/device-lease-emergency-release.md` 的三个缺口，G3 只出方案：

- **G2（在途判据）**：只允许释放 job 已终态（`COMPLETED`、`FAILED`、`ABORTED`）的租约；`PENDING`、
  `RUNNING`、`UNKNOWN` 属在途。`lease_type` 不是 `JOB` 时停止并报告：当前代码只有
  `backend/services/agent_claim.py` 创建租约，且只创建 `JOB` 租约。
- **G1（回收器不可用）**：两个条件同时成立。①`job_instance.ended_at` 距今超过 5 分钟（Owner 选定阈值，
  约 20 轮回收）；②控制面 Prometheus 中
  `stability_reconciler_runs_total{check="terminal_job_active_lease",outcome="success"}` 5 分钟增量为 0
  （有采样、无一次成功）。增量大于 0 表示回收器在运行，按回收器缺陷上报，不手工绕过；
  查询无结果视为无法判定，停止并上报。
- **G4（释放后仍占用）**：主机每次心跳按 ACTIVE 租约重算设备状态（`backend/api/routes/heartbeat.py`）。
  仍为 `BUSY` 时，先查是否有新的租约（正常占用），再查主机 `last_heartbeat` 是否超过
  `HOST_HEARTBEAT_TIMEOUT_SECONDS`。
- **G3（写库身份）**：Owner 要求规划者出方案、由实施者认领，见 #3646（管理端 API 替代手工 SQL）。
  SOP 中 G3 仍标缺口，并链接 #3646。
- `diagnose-device-stall`：按 Owner「WSL 情况统一不考虑，当前只在 Linux 端运行」删除 WSL / 5039 内容；
  第 5 步的在途判据改为指向 SOP 第 6–7 步。

## Alternatives

- G1 只用调度器计数 `stability_apscheduler_job_runs_total{job_name="device_lease_reconciler"}`：不选。
  `_with_leadership`（`backend/scheduler/app_scheduler.py:72`）在非主节点上跳过执行，却仍记 `success`，
  该计数不能证明回收器在干活；`stability_reconciler_runs_total` 只在主节点真正执行时增长。
- G1 第 ② 条原写作「总增量为 0，或 `outcome="error"` 增量大于 0」（#3651 首版）：被复核 R1 否决。
  窗口内一次历史报错加上随后恢复的成功运行，会被误判为「不可用」，与「回收器在运行时不得手工绕过」冲突；
  首版还把「无结果」在其他指标有值时按 0 处理，会把「无法判定」当成「已停转」。改为只看成功增量，
  无结果即停止。这一判据由实施者设计，Owner 只裁决了 5 分钟阈值；收紧方向为 fail-closed。
- G1 阈值取 1 小时（与 `production-diagnostics.md` 核对表第 ④ 项一致）或 15 分钟：Owner 选 5 分钟。
- G2 允许「超过宽限期的 UNKNOWN」：Owner 选只允许终态。
- `diagnose-device-stall` 第 9 步 L2 重启前的空闲判据（沿用 L1 原文的 `active_jobs=0`）：Owner 的回复只裁决了
  WSL 一项，该判据保持不变，在 PR 中提请确认。

## Verification

- 用 ORM 元数据的列名在内存 SQLite 中建表（`device`、`device_leases`、`job_instance`、`plan_run`、`host`），
  执行 SOP 中的全部 5 条 SQL：全部成功。只校验表名和列名，不校验 PostgreSQL 方言与数据；未连接任何数据库。
- PromQL 中的指标名与标签值逐项对照 `backend/core/metrics.py:371` 与
  `backend/scheduler/device_lease_reconciler.py:954`；未在生产 Prometheus 上实际执行。
- G1 判据离线验证（复核 R1 要求）：用 CI 同版本、同摘要 pin 的 promtool 3.13.3，以 `promql_expr_test`
  在模拟时间线上求值（`eval_time=10m`、窗口 `[5m]`），`promtool test rules` 退出码 0：
  - 持续无运行（计数不增长）→ 0 → 不可用；
  - 持续报错（成功不增长、error 增长）→ 0 → 不可用；
  - 先报错后恢复成功 → 1 → 回收器在运行，停止（同一时间线上原判据的 error 分支为 1，即误放行，复现了 R1 反例）；
  - 指标从未出现 → 无结果 → 停止；
  - 采集中断（该序列 t=3m 后无样本，其他指标在线）→ 无结果 → 停止；
  - 全程成功 → 1 → 停止，按回收器缺陷上报。
  反证：把「先报错后恢复」的期望改为 0、把「从未出现」的期望改为有值，promtool 两处均报 FAILED，断言有效。
  场景文件只放在本地临时目录，内容贴在 PR 评论中，未入库。
- `./scripts/project_python.sh scripts/run_gates.py check:quick`：退出码 0；16 个成员中 15 项通过，
  `schema-at-head` 因未设置 `DATABASE_URL` 按门禁设计跳过（本容器的隔离 `.venv`，未连接任何数据库）。
