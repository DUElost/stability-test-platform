# Agent Note: 审计单「事实层」的验证方法（4 判据 + 2 测量纪律）

Status: implemented
Class: process
Issue: 无对应 issue（方法类记录。来源：本会话认领 15 单的过程中，反复出现「issue 声明与代码不符」）

## Decision

对本仓「审计/审查派生」的 issue，**动手前一律先验证其声明的事实层**，并采用以下四条判据。
动机是同会话内 **6 单的 issue 声明与代码不符**（详见 §Verification）——其中两单若不验证就会造成实质损害。

### 判据 1：声称「某配置从未被读取」时，**不要用裸 `getenv` 计数**

**反例（`#737`）**：13 个"幽灵配置"里，`CORS_ORIGINS` / `CORS_ALLOW_METHODS` / `CORS_ALLOW_HEADERS` /
`UNKNOWN_GRACE_SECONDS` **都在用**，只是不裸调 `os.getenv`：

```bash
grep -nE "_parse_csv_env|_int_env" backend/core/*.py
# cors.py:15-17            _parse_csv_env("CORS_ORIGINS", …)   ← 同文件 :20/:23 还有强制校验（RuntimeError）
# job_timeout_config.py:92 UNKNOWN_GRACE_SECONDS = _int_env(…)
```

**正确做法**：按「键名在代码中的**全部出现**」分三档，而不是按某一种调用形态计数：

```bash
git grep -nE "KEY_NAME" -- "*.py" "*.ts" "*.tsx" "*.sh" "*.yml" "*.mdc" | head -20
# 读法：① 真读取（任意形态：getenv / helper / 常量赋值 / import 后使用）
#       ② 提及（注释、docstring、告警文案）
#       ③ 同前缀它键（例：HEARTBEAT_TIMEOUT_SECONDS 的命中其实是 HOST_/COORDINATOR_ 前缀版）
```

### 判据 2：判断「已修未关」用**已合入 PR 交叉引用**，并**必须读代码复核**

引用计数是**脏信号**——实测 open issue 里 `#462` 有 **116 次**引用，全部是脚本 docstring 里的
「功能来源」标注，与"是否已修"无关。高信号判据：

```
open issue → timeline 找「已合入 PR 的 cross-reference」
           → 剔除台账/总表（每个 PR 都会引用它们 → 天然假阳性）
           → 要求引用 PR 的**标题或正文**把它当「被修对象」（本仓惯例：fix(agent): …（#775））
           → **逐项读代码复核**，不要只看标题
```

实测收敛路径：**30 → 剔台账 6 → 5（标题指名）→ 真正「已修未关」2 个**。

> 最重要的一条反例：`#1591` 的引用 PR 标题写着「修复 #1591」，但正文自带
> 「**未覆盖（后续）**」三条（判定粒度 / abort 后 USB 锁 / 现场 11 台恢复）
> —— **只看标题就会把仍有残余的单误关**。故：#775 留证关闭、#1591 保持 OPEN。

### 判据 3：「幽灵功能」的形态＝**端点恒返回空值 + 前端有完整消费链路**

`#734` 的 DeviceMetrics：表早已被迁移删除 → 端点退化为恒返回 `points: []`（docstring 自述 deprecated），
而前端保留弹窗 + 图表 + api 方法 + 类型 + **两处入口** → 用户点进去永远空白。

扫法：先找"恒空/恒定"的端点返回，再找其前端消费链：

```bash
grep -rn "returns empty\|deprecated; returns\|return .*= \[\])" backend/api/routes/*.py | head
```

### 判据 4：多条目批次单在关单前**逐项复核**

`#788`（9 项）里 5 项已陈旧；`#737`（13 项）里 4 项不实。**审计时点为真的条目，几天后可能已被别处
修掉，也可能本就不实**。批次单的关单应以**逐项复核表**为前提，而不是以"有人做过"为前提。

### 测量纪律 1：「全部为零」的结果，先怀疑测量本身

本会话踩过一次：`git grep -n -- "*.py" …` **漏写 pattern**，于是 `*.py` 被当成搜索串 →
13 个键全部返回 **0 命中**。若把这个零结果当证据，会得出**与 issue 相同的错误结论**（"13 个全是幽灵"）。

纪律：结果过于干净（全零 / 全命中）时，先用一个**已知为正**的对照项验一下测量本身。

### 测量纪律 2：新写的回归断言**必须真的跑过**

`#749` 新增的"查询次数恒定"用例首跑就红——不是断言不成立，而是我给测试设备编了个**不存在的
`host_id`** 触发外键约束。断言的价值来自"它真的被执行过"；只写不跑等于没有证据。

## Alternatives

- **直接信任 issue 声明动手**：不选。`#826` 的前提若照做会给安全网**加 `:(glob)`**（只命中浅层，
  削弱守卫）；`#737` 的第 1 项若照做会**删掉 4 个真实生效的配置**。两例都是"做比不做更糟"。
- **用「issue 引用计数」判断是否已修**：不选。`#462` 的 116 次引用全是功能来源标注，零信息量。
- **用「引用 PR 的标题」判断是否已修**：不选。`#1591` 的标题正是「修复 #1591」，却仍有 3 项自述未覆盖。
- **把本方法固化成工具/定时任务**：本轮不做。属流程/工具面决策（与 `#1569` required checks、
  `#1585` memory-lint 等工具面在窗项相邻），应由 owner 立项。
- **默认"审计单不可信"**：不选。本会话 9 单成功交付的事实说明：验证成本（每单 2–4 次检索）
  远小于做错成本；本方法主张的是**先验证**，不是**不信**。

## Revisit

- 判据 2 有**天然盲区**：修复若**未在任何 PR / 注释 / 文档里引用 issue 号**，该方法查不到。
- 若将来把四条判据固化成工具或例行扫描，应先解决两个前提：① 台账/总表类 issue 的自动识别
  （当前靠人工剔除）；② "同前缀它键"的自动归属（当前靠人工判读）。这两点都属工具面决策。
- 判据 1/3 的适用面会随仓库演进变化（例如 `pydantic-settings` 收敛落地后，`getenv` 形态会整体减少，
  判据 1 的检索方式应随之调整）。
