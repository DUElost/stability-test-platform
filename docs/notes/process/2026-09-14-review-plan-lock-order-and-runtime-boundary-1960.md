# 审查总纲补「共享行加锁全序」与「运行期断言登记」两项检查要求（#1960）

Status: implemented
Class: process

## Decision

在 [`docs/reviews/PROJECT_REVIEW_PLAN.md`](../../reviews/PROJECT_REVIEW_PLAN.md)（全面
只读审查总纲）补三处，**只改检查要求，不动 R01–R15 分区编号与既有分工**：

1. **§3 第 2 条（并发与恢复）** 增一句：并发这一项必须额外产出「共享行加锁表」，
   理由写在同一处——只按本区路径自查只能证明每条路径内部自洽。
2. **§3 新增第 7 条（共享行加锁全序）**：以**共享行 / 资源**为单位（本平台最小集
   `job_instance`、`device_leases`、`plan_run`、`plan_run_host`、`host`）穷尽列出全部
   加锁点及其获取顺序，断言全局存在一致全序；相反顺序即判 P1。明确指出**枚举单位
   必须是共享行，不是业务路径**，并注明共享行数量有限、无需穷举并发交错。
3. **§3 新增第 8 条（方法能力边界）**：静态只读审查必须登记「运行期方可成立的断言」
   清单（锁序环、活锁、连接池耗尽、超时收敛、真实并发交错、真机 / NFS 行为等），
   标注本方法不可覆盖，并写明应由哪类运行证据填补。该项不得留空、不得以「未发现
   问题」结案。
4. **§4.2 发现分类**增一行「确定缺陷 · 锁序相反」：给出相反顺序的两处 `path:line` 与
   共同触碰的共享行即可判定为确定缺陷（相对顺序是静态事实），但须注明「是否成环取决
   于并发交错」；并显式禁止把它就近并入「性能 / 队首阻塞」。
5. **§5 当前登记**补一行台账载体：2026-09 轮次 R01–R15 台账在 GitHub issue
   #891…#1302，并写明**仓库内没有区域报告文件**，故事后无法在本仓库内核对「某区是否
   为某维度登记过覆盖或不适用理由」。

### 为什么改这三处（归因，不是泛泛的「维度不够」）

2026-09-13/14 复发的 `job_instance` / `device_leases` 锁序死锁（#1959）在 R01–R15
全面审查与跨区收口链 A 中**都没有被发现**，且该家族的**另一半**其实被 R06 发现了
（R06-F07 → #992）。归因如下，逐条对应上面的改动：

- **检查单位错位**：原六维里「并发与恢复」列举的是重入、幂等、竞态、超时、取消、
  崩溃恢复、资源释放——都是**一条路径内的时间序正确性**。锁序是反过来的：同一批行
  被 N 条路径以不同顺序触碰。分区审查因此必然看不到环，且**这不是跨区问题**：冲突
  双方都在 R06 自己的范围内（总纲 R06 的范围本就含租约 / fencing、claim / 续租 /
  complete、超时回收）。→ 改动 1、2。
- **能力边界未登记**：总纲 §1 已写明「静态审查不等于运行验证」，但没有要求把
  「哪些断言只能靠运行期成立」写成清单。于是静态审查的「没发现」被当成了结论。
  唯一证据来源（PostgreSQL 服务端日志）本就在审查授权面之外。→ 改动 3。
- **分类决定了能看见什么**：`PLATFORM_AUDIT_2026-09-11.md` 其实**读过**出问题的那个
  函数（「租约对账去掉 `break` 全循环」），但归类为「性能 / 队首阻塞」，相反顺序就在
  同一函数相邻几十行处被滑过。→ 改动 4。
- **覆盖记录没有落地载体**：总纲 §4.1 要求每区记录六维的检查证据或不适用理由，但
  §5 仍写「R01–R15 全部未开始」「区域报告尚未建立」，仓库内没有区域报告文件，
  事后无法查证 R06 是否登记过锁序维度。→ 改动 5（只补载体指针，不改状态——状态需与
  GitHub 台账逐条核对，不在本次范围）。

### 未做（显式记录）

- **没有改 §5 的完成状态**。「R01–R15 全部未开始」与 GitHub 台账不一致（
  `REVIEW_COVERAGE_AND_FIX_EFFECTIVENESS_2026-09-11_85d793.md` 已记录该漂移），但
  逐区状态需要与 15 个台账逐条核对，属独立工作；本次只补台账载体指针，避免用一个
  猜测的状态覆盖另一个。
- **没有新增 R16–R20 分区**。覆盖报告 §2 已判定「无需因本轮结束而机械增加
  R16–R20；需要把现有分区上的横向验证补齐」；本 PR 走的是同一方向——把「横向」
  从「端到端链路」补成「共享资源不变量」，而不是增加分区数量。

## Alternatives

- **只改 §3 第 2 条、不新增第 7/8 条**：放弃。把要求塞进一句话里无法被当成可交付物
  检查（原来六维的写法就是证据：写得都对，但没有可执行单位）。
- **新增独立文档《锁序契约》**：放弃。共享行是小集合、随代码演进，写成独立权威会与
  `_cas_renew_leases` 这类既有调用契约注释分叉；放进总纲的检查维度更贴职责。
- **同时修正 §5 的完成状态**：放弃（见「未做」）。状态核对需要台账数据，不属只读
  方法层改动。
- **顺手把锁序检查做成门禁脚本**：放弃。静态扫「加锁点全集」会高度依赖启发式，误报
  成本高；先让人审按共享行列表检查，等出现第二次同类问题再考虑机制化（与
  `repository-workflow.md` 的「同类夜间红灯 ≥2 次再前移」同精神）。

## Revisit

  成本高于收益（例如共享行频繁变动导致每次都要重列），应在本文件记录并改为「仅对
  新增 / 变更的加锁点增量核对」。
- **§5 状态核对**：需要有人拿 15 个台账 issue 逐条核对本轮完成度，再回写 §5；在此之前
  §5 的「全部未开始」不应被当作事实依据引用。
- **若同类漏检再发生一次**（新的「两条路径相反顺序」被事后发现），按 Alternatives 的
  判断把第 7 条升级为门禁或 CI 检查，而不是再加一条审查建议。
