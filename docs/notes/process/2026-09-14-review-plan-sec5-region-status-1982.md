## Decision

在 [`docs/reviews/PROJECT_REVIEW_PLAN.md`](../../reviews/PROJECT_REVIEW_PLAN.md) §5
落地三件事，**不改分区编号、不改完成定义、不动 `docs/DOC-MAP.md` 与 `AGENTS.md`**：

1. **`| R01–R15 | 全部未开始 |` 改为实情**：逐区静态只读审查已交付；14 区口径为
   「待验证」，R02 台账未收口（进行中）。
2. **首轮基线与日期行改写**：「pending，首次开展时记录」→
   `2026-09-07 → 2026-09-11（逐区基线不同，见 §5.1；不构成单一快照）`。
3. **新增 §5.1 逐区状态表**：区域 / 台账链接 / 状态 / 审查日期 / 审查基线 / 备注，
   外加口径说明与「未建立载体」说明。

### 实查依据（`gh issue view`，2026-09-14）

15 个台账中 **14 个 CLOSED（09-12 / 09-13 关闭）、1 个 OPEN（R02 #910）**；
15 个台账正文逐区记录了审查基线（`c9230c08` … `0d523265`，互不相同）与
「状态口径：待验证」。R01/R02/R14/R15 的表述形态与其余不同，已逐条读正文确认。

### 为什么统一记「待验证」而不是「已完成」

§4.1 明确「已完成只表示约定范围的审查交付完成，不表示无缺陷、修复完成或生产验收通过」。
本轮的 15 个台账**没有一区做过动态验证**（各自自述未跑 pytest / 隔离 PG / 真机 /
浏览器 / 部署 / 故障注入），按 §4.1「影响主要结论的关键证据不足时应保持待验证」，
状态列只能记「待验证」。

把「静态交付完成」也折进「已完成」会让下一轮元审查高估覆盖质量——
`REVIEW_COVERAGE_AND_FIX_EFFECTIVENESS_2026-09-11_85d793.md` §2 已就这类分母失真做过更正，
本单是把它固化进总纲的状态列，而不是再写一份说明。

### 登记的两处纪律缺口（本轮不新建载体）

- **本轮总记录从未建立**：本轮实际以 15 个台账 issue 为载体逐区推进，没有
  `PROJECT_REVIEW_<date>_<sha>.md`。本单只登记该缺口与「下一轮先建总记录」的要求，
  不补建一份事后拼凑的总记录——那会把逐区不同基线包装成同一快照，与 §4.1 的
  「基线变化须补审或明确保留限制」相悖。
- **仓库内没有区域报告文件**：本仓库内无法核对某区的六维覆盖记录，须查 GitHub 台账。

## Alternatives

- **只把「全部未开始」改成「已完成」**：放弃。会把「静态交付」读成「已验证」，正是
  覆盖报告已指出并更正的失真。
- **按四态分别标注「部分区域已完成、部分待验证」**：放弃。15 区在方法上是同一形态
  （静态只读 + 未跑动态验证），人为细分只会制造没有证据支撑的差异；R02 的差异
  （台账未关）是**载体状态**而非审查完成度，故单独成行并写明区别。
- **补建本轮总记录文件**：放弃（理由见上）。若强行补建，基线只能取某一个 SHA，
  而逐区基线横跨 `c9230c08`…`0d523265`，等于制造假快照。
- **同时修正 §4.1 的完成定义**：放弃。定义本身没有问题，问题在于从未被用于回写状态；
  本次只回写状态。

  从推荐改为强制（本单暂不强制，避免立刻制造 15 个空文件）。
