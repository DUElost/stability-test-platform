# ADR-0035 §6 触发条件检测来源（#906）

Status: implemented
Class: process

## Decision

**问题**：ADR-0035 §6 的四条「升级为主机级凭据」触发条件全部依赖**外部信号**
（泄露事件 / 受信域假设失效 / R06·R08·R11 的 P0 结论 / 合规定责要求），但 ADR 只
写了「满足任一即实施」，**没写信号从哪里来、谁看、命中后第一步做什么**。结果是
「触发条件已命中」只能靠人想起——等价于没有触发条件；ADR 转 Accepted 后风险
被记为「已挂触发条件」，实际处于无人监视状态。

**裁决（最小方案，不动 ADR-0034、不新建监视机制）**：ADR-0035 新增 §6.1，把每条
触发条件钉到来源场景：

| # | 信号来源（读什么） | 检出方 | 命中后第一步 |
|---|---|---|---|
| 1 | 泄露/异常响应：R02 台账（#910）、审计日志与安全告警、设备运维事件 | R02 负责人 / 值班 | 评估「全量轮换前旧值窗口内的冒充读接口」是否有实际损害 |
| 2 | 架构变更：ADR-0027 多实例推进（Epic #720）、新网段/多云/多租户方案评审、ADR-0024 v1.1 受信域假设复议 | 架构组（评审入口） | 判定受信管理域假设是否失效 |
| 3 | 安全审查结论：R06 / R08 / R11 批次的 P0 行 | 各批次审查负责人 | 判定是否构成「主机冒充导致不可接受后果」 |
| 4 | 合规/定责要求：外部审计、等保/客户审计清单、事故定责需求 | 平台负责人 | 确认主机级审计归属是否成为硬要求 |

并写明：命中后按 §5 骨架拆实施单、#906 作为实施/触发器载体保持 OPEN；
**不新建定时任务或监视服务**；若某条「检出方」长期不可归因，应在下次 R02 台账
复核时提级为流程缺口，而不是把本 ADR 当作已闭环。

ADR-0035 v1.1 → v1.2；adr/README 与 DOC-MAP 索引同步（S12）。

## Alternatives

- **加定时任务/监视服务自动判触发条件**：四条判据三条是人类语义判定（「是否造成
  实际损害」「是否构成不可接受后果」「是否成为硬要求」），没有可机械化的信号源；
  建一个只能报警「请人工看看」的定时任务是纯负担，且与 ADR-0034「Registry 非
  调度器」的取向相悖。
- **把触发条件搬进契约/Registry 作为可见性维度**：契约管 Execution 协同，
  不是架构决策的触发器载体；且 #1238 正在做契约分层收紧预算，此时增维度方向相反。
- **只在 #906 issue 里加一节、不动 ADR**：**已一并做**（issue 正文同步），但只放
  issue 不够——ADR 是权威件，读者从 §6 出发时必须能直接看到检测来源，否则
  「触发条件」在权威件里仍是无主条目。
- **直接拆实施单开工（不等触发条件）**：与 §3 当前状态决策（接受共享
  `AGENT_SECRET`、明示 deferred 验收②）相冲突，且泄露事件未发生、受信域假设
  仍成立；本次不重开该裁决。
