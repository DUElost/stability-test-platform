# ADR-0033 v1.7：D0 可拦对象的计数口径（#3014 案 3A）

Status: implemented
Class: architecture

## Decision

owner 按 #3014 案 3 推荐裁决。本单把「D0 分级准入是否首次有真实对象 / §5.4 条件 1 是否成立」的
**计数口径**定死，并修正一处被沿用的错误归因。**D0–D4 决策与 §5.4 三条触发条件文本一律不动**。

1. **§5.1 归因修正**：原文把「新族门禁零触发」解释为"本期 10 个新版本目录全部落在既有族"。
   实测更根本的原因：**分母选错**。D0 管的是「外部工具**源码**全量复制入仓」，而
   `backend/agent/scripts/` 现 35 族里 **0 族含第三方源码**（无 LICENSE / 版权头命中），
   展锐三族实际位于中心存储 `tools/`（§5.4 过渡形态）。该目录的族数 / 版本目录数**从来不是**
   D0 的可拦对象计数。脚本膨胀账（族数、版本目录、行数、env 读键）本身仍然有效，
   但归属 **ADR-0039 与 #735**，不得再用作 D0 的触发证据。
2. **§5.6 新增「D0 可拦对象口径」**：计数 = **带外部资产的族**（厂商二进制 / 第三方源码套件 /
   需独立分发的大体积 APK）。首次基线：35 族 → **16 带外部资产**（`flash_firmware`、`flash_preflight`
   = SP Flash Tool；`gpu_setup`/`gpu_check`/`gpu_finish` = Antutu APK；`monkey_*` 五族 +
   `powercycle_*`/`sleep_*`/`mtbf_setup` = APK 资源）/ **19 纯 adb-python 平台自研**。
   并落三个归类判定：`clear_recents`（09-20，第 35 族）、`unisoc_probe`、`unisoc_signal_trigger`（09-14）
   = **非 D0 对象** → 不需 Tool Contract 准入、**不触发 §5.4 条件 1**。#2827 的「未触发」结论由此获得依据。
3. 版本 v1.6 → **v1.7**；S12 派生面同步：`adr/README.md` 主表行 + M7 看板 + `DOC-MAP.md` 行。

## Alternatives

| 选项 | 否决理由 |
|---|---|
| 按 #3014 案 3 原表述「改写 §5.4 三条触发器」 | 实施时复核发现三条**已按形态限定**（需要版本化分发+防篡改 / 中心存储源码目录+env 扩散 / Phase 3 启动），错的不是条件而是 §5.1 的对账度量 → 收口点从 §5.4 移到 §5.1 + §5.6，**这是对已裁事项的实施性收窄，已在此显式登记** |
| 把 `clear_recents` 当 D0 对象要求它先做 Tool Contract | 它是平台自研设备端能力脚本，无外部资产；强套 = 给非 D0 对象加准入成本，且把 D0 撑成"一切脚本的准入" |
| 只在 issue 里记结论、不改 ADR | D0 的账目还要被下一次对账复用；错口径留在权威文档里会再次误导（本次就是被 §5.1 带偏后写进 #2546 F-4） |
| 现在就删 §5.1 的膨胀账 | 那是 ADR-0039/#735 的一手核验记录，删了丢历史；改为标注归属与用途边界 |
