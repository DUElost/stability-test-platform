# 脚本版本不可变收窄（ADR-0039）与 P1 立项所需只读统计（#735 §2）

Status: implemented
Class: architecture

## Decision

#735 §2「长效机制」的 P1 路径此前**无 ADR 承接**，且其启动前置（两项只读统计）登记为
「待验证」。本单完成前置统计并把 P1 立为方向级 ADR。

**1）完成两项只读统计（生产库，仅 SELECT）**：

| 指标 | 值 |
|---|---|
| `script` 版本行 | 136（引用 45 / 零引用 91） |
| 零引用且 `is_active=true`（#735 退役候选） | **60**（21 族） |
| 零引用且已退役 | 31 |
| 版本目录 `.py` 总行数（148 目录） | **89,517** |
| 其中零引用目录（90 个） | **56,394（63.0%）** |
| 其中「零引用且活跃」 | 26,295（29.4%） |
| 被引用目录（必须保留） | 26,878（30.0%） |

**2）回答了 P1 的本质判据**（「历史版本还需不需要被重新执行」，可行性研究 §4 当时两侧均
无证据）：`plan_step` 共 152 行、仅覆盖 **45** 个 distinct 版本；**零引用版本出现在
`plan_step` 中的数量为 0**——即零引用 = **不在任何 Plan 定义中**（无论该 Plan 是否运行
过），而不是「存在于某个尚未运行的 Plan 里」。`plan_step` 对 `script` 的引用完全闭合
（0 条指向表外版本）。故「重新执行」只剩「人工把该版本重新编辑回某个 Plan」一条路径，
判据由未知变为已知且有界。

**3）立 [`ADR-0039`](../../adr/ADR-0039-script-version-immutability-narrowing.md)（Proposed）**：
不可变契约收窄为两段式——`refs>0` 绝对不可变（强度不变）；`refs=0` 且已退役允许物理删除。
并收紧删除的前置与权限：D2 删除权不下放自动流程（仅人工 PR + 附只读证据）；D3 退役与
删除间设冷却期、粒度**按版本非按族**（实测同族内零引用与在用版本并存是常态，按族删会
误删）；D4 删除后不可重新派发是显式代价、**不设**代码级逃生；D5 重跑需求走发新版本；
D7 门禁判据与 DB 引用**解耦**（门禁不得连生产库）。

**范围限定**：本单**只出 ADR + 只读统计**。不改 `AGENTS.md` 硬不变量、不改
`check-script-version-immutability.py`——按 ADR §4.3，那必须与 ADR 裁决**同一 PR**进行，
且须在 #735 本体（含退役动作）之后。

## Alternatives

- **直接改 `AGENTS.md` + 门禁，不做 ADR**：弃——`AGENTS.md` 明文「改变现行执行语义前
  必须先由 ADR 正式裁决」，且该不变量是 2026-07-31 派发中断事故的防线，改它必须留裁决
  记录；
- **跳过退役动作直接删零引用版本**：弃——会把「从可选面移除」与「从仓库删除」压成一步，
  失去冷却期与无成本回退（退役可逆、删除不可逆）；ADR 已把它写成 D1 前置条件；
- **按工具族整体删除**：弃——`monkey_setup` 12 个零引用版本与在用版本并存，按族删会误删；
- **门禁内连库查引用数自动判定**：弃——违反生产库边界，且使 CI 门禁依赖环境可用性；
  改为「门禁静态判定 + 人工 PR 附只读证据」；
- **把统计写成「引用数是 0 是否等于永不重启」的推论**：弃——本轮给出了更强的实测结论
  （零引用 = 不在任何 Plan 定义中），不做弱化表述。

## Verification

- **只读纪律**：全部统计经 `check_unreferenced_script_versions`（修复后）与 `plan`/
  `plan_step`/`plan_run` 的 `LEFT JOIN`/`COUNT` 只读 SELECT 完成；**无任何写库操作**，
  未跑迁移，未在生产库试跑测试；
- 统计口径交叉核验：`plan_step` 行数 152 与 distinct `(script_name, script_version)`
  45 一致；`plan_step` 指向 `script` 表外版本数 0（引用闭合）；两处独立 JOIN 得出的
  零引用版本集合一致；
- 行数口径与 DB 版本号归一化已核对：`script.version` 存 `1.0.0` 而目录名为 `v1.0.0`，
  归一化后 148 个目录中 135 个匹配到 DB 行（13 个无 DB 行：新增未扫描等，已单列 7.0%）；
  **首轮因未归一化得到 0% 的假结果，已修正并复算**；
- `python scripts/run_gates.py check:quick` → 结果见提交时输出；
- ADR 编号 0039 经 `ls docs/adr/` 确认未被占用；`docs/adr/README.md`、`docs/DOC-MAP.md`、
  可行性研究 §5 三处引用已同步。

## Revisit

- **ADR-0039 最脆弱的假设**：`refs = 0` ⟺「不在任何 Plan 中」依赖「Plan 引用只由
  `plan_step` 表达」。若将来引入 Plan 模板引用 / 动态脚本解析 / 跨环境 Plan 导入等机制，
  该等价关系失效，ADR §6 已把此列为复议触发条件；
- **未做面（明确留给后续）**：① `AGENTS.md` 硬不变量与门禁判据的修订（须与 ADR 裁决同
  PR）；② #735 退役动作本身（60 个零引用活跃版本，**对生产库的写操作**，须单独走生产
  变更流程）；③ 门禁红绿双向验证（删 `refs>0` 目录 → 红 / 删 `refs=0` 已退役 → 绿）；
- **13 个无 DB 行的目录**（6,245 行，7.0%）经逐个核验**全部是该族比 DB 最新行更新的版本**
  （新增待扫描，非历史遗留，如 `gpu_check@1.0.8` vs DB 最新 `1.0.6`）——它们**不在删除候选
  面内**，ADR-0039 D1 的 `refs=0` 判据对它们不适用（无 DB 行即无引用计数可言）；反向的
  `gpu_setup@1.0.3` 有 DB 行但仓内无目录，属既有状态，非本单引入；
- 若删除放量后出现**派发中断事故**，按 ADR §6 立即停止放量并回退至绝对不可变。
