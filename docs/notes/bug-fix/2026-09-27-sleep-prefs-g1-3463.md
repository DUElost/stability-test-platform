# sleep 三族 prefs 收紧（#3463 G1-sleep）：读空不再是整写/删除证据，adb 解码宽容化

Status: implemented
Class: bug-fix

## Decision

按 #3463 §3 G1 行、§4 G1 验收实施（批次 B1「高阶模型规划 + 实施者按方案执行」，本单为
{G1-sleep} 单元；powercycle 三族由姊妹单交付）：`sleep_setup` / `sleep_check` /
`sleep_finish` 三族 `_lib.py` 逐字同构 port 两类修复。

1. **F1（prefs「读空＝不存在」）**：参照实现 = `powercycle_setup/_lib.py` 的
   `_root_read_prefs()` + 收紧后的 `repair_prefs_ownership()`（#2846/#2979 判据）。
   旧 sleep 形态更糟：`get_prefs_xml()` 只走 run-as，而 AutoTestTool 是 platform 签名
   shared-uid 系统 app，AOSP 对其恒拒 run-as ⇒ 读**恒**空 ⇒
   - `repair_prefs_ownership` 每轮部署 `rm -f` 健康 prefs（续跑 current_count 归零）；
   - `set_stop_flags` 把「恒空」当文件不存在，每轮 finish 整写最小 map，压掉
     test_times/current_count/auto_resume 全量字段。
   收紧后判据：root 走 `_root_read_prefs` 单调用同源证据（ok/empty/absent/denied/
   transient）；非 root 的 run-as 读取归入同一 kind 集（`_run_as_read_prefs`，被拒
   显式化为 `denied`）。`set_stop_flags` **仅 `absent` 整写最小 map**；
   `transient`/`denied`（含无 root 时无法删除的 `empty`）保留文件、不写任何字节，
   抛「可重试失败」——引擎侧步骤重跑由 plan step 的 `retry` 承载，脚本侧不发明新通道。
   `get_prefs_xml()` 语义与参照一致（root 优先，`ok` 才返回文本；空串仅表示
   「此刻读不到」）。`repair_prefs_ownership` 只认「存在 + 读取成功 + 内容为空」
   这一种确定性损坏形态才 `rm -f`。
   新版本登记（§A 流程）：`sleep_setup@1.0.4`、`sleep_check@1.0.5`、`sleep_finish@1.0.5`
   （均 = 当前 head + 1，无占位顺延）。`backend/schemas/pipeline_templates/sleep.json`
   三个 pin 同批追平磁盘 head（#2865/#2998 守卫；首轮漏钉致 `pr-agent-tests` 红，
   按 #3463 v1.1 修订返修——方案 v1 的 §4 门禁不含根目录 `tests/`，该红不计入实施返修）。
2. **F2（严格解码）**：`adb()` 从 `text=True` 改为显式收字节 + `decode_device_output()`
   （宽容 UTF-8，port `gpu_setup` #3069 形态），一个坏字节不再可能以
   `UnicodeDecodeError` 炸掉调用点。

## Alternatives

- **只修 `repair_prefs_ownership`、`set_stop_flags` 沿用「读空整写」**：被否——恒拒的
  run-as 读取下「读空」恰恰是常态，整写最小 map 与误删同形态、同数据损失（#3463 §1 F1 判据）。
- **让 `set_stop_flags` 在 transient/denied 时静默跳过写入继续 stop 流程**：被否——
  静默跳过会恢复「假成功」形态（running=true 残留 → boot 自启叠加，#894 已花过代价）；
  方案 §3 明确要求「向步骤暴露可重试失败」。
- **非 root 路径不分类、维持旧行为**：被否——本实况里非 root + run-as 恒拒正是主触发
  路径，不分类就没有 absent/denied 的证据来源，判据无法成立。
