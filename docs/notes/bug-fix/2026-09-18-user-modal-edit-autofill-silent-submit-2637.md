# 编辑用户弹窗：密码管理器直写后提交静默失败（渲染条件与校验口径同源，#2637）

Status: implemented
Class: bug-fix

- 日期：2026-09-18
- 关联：`#2637`（本单）、`#2497`（引入该回归的改动：字段改非受控 + 提交改读 FormData）、
  `#2453`/`#2456`（同族：受控组件只认 state 把已填表单判成空）、`#2406`/`#2435`（同弹窗其它静默失败面）

## Decision

**这是我 #2497 那次改动引入的回归**（issue 已定性）：把「能提交但不改密」换成了「不能提交且不报错」。
本单按 issue 的建议收口成两条，不再扩大面。

### 失败链（issue 复现，代码逐行核对）

1. 密码管理器**直写** `#user-password` 的 `.value`（事件不冒泡，React 收不到）→
   `passwordPresent`（编辑态确认框的可见性判据）恒为 `false`；
2. `{(passwordPresent || !isEditMode) && (…)}` ⇒ 确认框**不在 DOM 里**，`FormData` 取不到
   `confirmPassword`（回落到 state 的 `''`）；
3. 校验判「两次不一致」→ `handleSubmit` 提前 return ⇒ **请求不发**；
4. 而错误文案 `<p>{errors.confirmPassword}</p>` 正写在**那个不渲染的块内部** ⇒ **界面毫无反应**。

### 修法（两条，都只动渲染/文案）

1. **渲染条件与校验口径同源**：`{(passwordPresent || !isEditMode || !!errors.confirmPassword) && (…)}`
   —— 只要存在确认密码错误就**强制渲染**该块，错误因此一定可见；
2. **错误文案区分两种形态**：只填了密码（确认框此前没渲染）时给「请再次输入密码以确认修改」，
   两次都填了才说「两次输入的密码不一致」——「不一致」在只有一个输入框的情况下会让人找不到北。

用户可见行为：管理器直写后点保存 → **看得到原因、确认框就地出现** → 补填确认密码 → 提交发出。

## Alternatives

- **把确认框改成编辑态恒显示**：能绕开本缺陷，但改的是**语义**（「留空表示不修改」的编辑态约定
  会让每次都要求确认），不是修缺陷。否。
- **提交前按 DOM 同步状态（`syncPasswordPresence(form)`）**：**实现过又删掉了**——反向验证显示
  它与「错误非空即渲染」的组合里**不可判别**（去掉它用例仍全绿），即它是冗余守卫，不是判据。
  最小方案的纪律：不可判别的守卫不留（详见 Verification 的变异表）。
- **表单级 `onInput` 统一同步（替代字段的 `onChange`）**：同样被反向验证证明是**装饰性重构**
  （还原成原 `onChange` 行为等价）——已回退，本单最终不引入 `formRef`。
- **给字段块加 `key`**：一度以为是「无 key 兄弟按位置复用导致非受控输入串位」，实测**变异不掉**
  （条件分支在 children 数组里占位稳定），且当初观察到的「用户名被清空」是我测试自己没模拟
  「先关后开」转场导致的（见下）。已删除该 key 与那条错误归因的注释。
- **只改文案不改渲染条件**：错误依然落在不渲染的块里 ⇒ 静默照旧。否。

## Verification

- `npx vitest run src/pages/users/components/UserModal.test.tsx` → **19 passed**（新增 3 条：
  两步流修复路径、「只填密码 → 不静默」、「人工键入 → 确认框立刻出现」）；
- **2 处定向变异逐条回退即红**（跑完还原）：渲染条件退回 `(passwordPresent || !isEditMode)` →
  **2 failed**；错误文案退回单一「不一致」→ **2 failed**；
- 前端全量 `npx vitest run --maxWorkers=3` → **1029 passed / 128 files**；
  `python scripts/run_gates.py check:quick` → **12 gates 绿**；
- **写用例时踩到的两件事（都值得留给下一个人）**：
  1. **编辑态的测试必须先关后开**：表单重置发生在 `prevOpen !== isOpen` 的 render 期转场里，
     直接 `render(<UserModal isOpen editUser={…}/>)` 不会触发它 —— 表单是**空**的，于是提交报
     「请输入用户名」。我一度把它归因成 React 的 key 复用（错），变异证明后才定位到测试写法；
  2. **模拟键入要用 `fireEvent.input`**：`fireEvent.change` 不触发 React 的 `onChange`
     （React 文本输入映射的是原生 `input`），用它写的「键入 → 确认框出现」用例会假红。

## Revisit

- **同族扫描未做**：本弹窗之外还有别的**编辑态**表单（`HostModal`/`AddHostModal` 等）用同样的
  「密码非空才显示确认」形态；#2456 扫过一次「受控组件只认 state」，但**「编辑态 + 管理器直写」
  这一组合**没有系统性判据。若再现同类静默，考虑抽一条共用规则：*任何「条件渲染的校验错误」
  都必须保证错误可见*（渲染条件包含 `!!errors.x`）。
- **`passwordPresent` 仍是「手工维护的派生量」**：它其实等价于「DOM 里密码框非空」，理想形态是
  在读 FormData 的同一处派生（提交时）而非并行维护一份 state。本轮为最小改动没有动结构；
  若将来再出现可见性判据与校验不一致，就该把它并进 `readFormValues` 的返回值。
- **浏览器侧未实测**：触发前提（密码管理器直写 `.value` 且事件不冒泡）来自 #2453 的 nginx
  零请求证据，本轮沿用同一模拟手法，未在真实浏览器里复现本弹窗。
