Status: implemented
Class: bug-fix

## Decision

2026-09-21 只读审计（24h 代码审计轮）登记的「门禁/断言看着在守、实际够不到目标」四条一并收口。

### #2974 锁序守卫看不见 helper 内取锁与 UPDATE-CAS

**判据扩面**（`tests/test_lock_order_collection_total_order.py`）：

- **同模块 helper 内的锁**——传递解析调用图（`seen` 防环）。原判据只认循环**直接** body 里的 `with_for_update` 属性调用，于是「循环体里只调一个 `_lock_and_recheck(...)`」整段被跳过：`device_lease_reconciler` 的候选项逐个调 `_abort_reaper_recheck_job`，锁在那里面；
- **逐行 `update(Model).where(等值)` CAS**——UPDATE 同样取行锁，`recycler` 的 patrol-stall 批正是用它。判定时取链式表达式的**根**（`update(X)` 自身的源文段只覆盖到 `update(X)`，`.where(...)` 在父节点上），批量 `…where(Model.id.in_(ids))` **不算**：一条语句的锁集合由执行器决定，不是「程序按某个顺序逐把取」；
- 就地排序 `rows.sort(key=…)` 与 `sorted()` 同义，同样算「内存里定序」。

扩面后仓库面立刻由 0 命中变 4 命中，四处逐一处置：

| 位置 | 事实 | 处置 |
|---|---|---|
| `device_lease_reconciler.py:_reconcile_aborted_running_jobs` | 候选项逐个在 helper 里 `with_for_update`，而 `begin_nested()` 是 SAVEPOINT、不释放 PG 行锁 ⇒ 一个 tick 提交前持整批 job 行锁，取锁序 = PG join 返回序；查询**没有** `order_by` | 查询补 `.order_by(JobInstance.id)`，消费点再显式 `reap_rows.sort(key=…)` |
| `recycler.py:recycle_once` patrol-stall 批 | 逐行 `update(JobInstance)`（`_mark_patrol_stall`）同事务持有到末尾 commit，取锁序 = 迭代序，而批次**选择**按 `overdue DESC` | 选择口径不动，取锁处 `sorted(_collect_patrol_stall_candidates(...), key=lambda item: item[0].id)` |
| `device_log_event.py`（**本单新暴露**） | 循环逐行 `update(DeviceLogEvent).where(id == …)` 同事务持有到 commit，而集合查询无 `order_by` | 查询补 `.order_by(DeviceLogEvent.id)` |
| `plan_run_abort.py`（**本单新暴露**） | 循环按 `Counter` 插入序逐 host `update(PlanRunHost)` 取行锁，同事务持有到提交 | 改为 `for hid in sorted(host_counts)` |
| `admission_pump.py:claimed`（**本单新暴露，裁定无风险**） | 循环体调用的 `requeue_plan_run` 只锁 1 行且**当场 commit** | 登记进判据内的 `_ADJUDICATED_SAFE`（新增登记面，每条必须写裁定理由；键含迭代对象源文段 ⇒ 形状一变登记即失配、判据重新变红），并补 `test_adjudicated_safe_entries_are_not_stale` |

两处实修各补一条具名回归（`test_abort_reaper_locks_candidates_in_job_id_order` / `test_patrol_stall_locks_batch_in_job_id_order`），除通用判据外还钉住「候选查询带 `order_by`」「批次选择仍按 overdue DESC」这两件通用判据看不见的事。

**未主张**：没有做 PostgreSQL 阻塞法实测（构造阻塞需写库），本 PR 主张的是「代码事实 + 取锁序与对侧一致」，不是「曾发生过死锁」。

### #2986 sticky 表头守卫的取值窗口够不到目标

原判据用同一个 8 行窗口既**识别** sticky 表头又**取**透明度值；`DeviceOverview.tsx` 的表头元素跨 25 行、透明度在第 11 行 ⇒ 该文件贡献 0 个被测值却计入反空转下限，把 `/95` 改回 `/50` 全绿。改为：

- **识别**仍用 8 行窗口，**取值**改走整个元素块（同名标签配对，上限 60 行，配不上时退化为「起始 + 上限行」，宁可多取不取空）；
- 反空转下界改建在**取出过值**的文件集合上（原为「被识别成表头」的集合）；
- 四条参数化用例各加一条「该文件必须至少取到一个值」，否则用例恒真。

### #2987 `#2848` 的断言挂在不可能失败的纯函数上

`buildFailedDeviceRows` 是 `.map`，结构上不可能违反「不重排、不截断」，四条用例因此对**调用点**（组件 `useMemo`）的回归零判别力。新增 `describe('#2848 不变量钉在调用点（#2987）')`：桩掉 recharts 渲染层与 `StableResponsiveContainer` 的尺寸就绪门（jsdom 里 `offsetHeight` 恒 0、`ResizeObserver` 是 no-op，不桩则断言退化为空转），从 `BarChart` 收到 `data` 处断言 24 条整份进图与次序原样透传。

### #2964 harness 探针对照行的期望值过期

`claude-subdir-plain` 的 `expected.q1=False` 取自 2026-09-06/07；2026-09-08 的 #857 仓库侧绕过把根 `CLAUDE.md` 换成指向 `AGENTS.md` 的 symlink 后，`@import` 通道从仓库消失、子目录裸跑经 ancestor 加载拿到完整根契约 ⇒ `q1=是` 是**新常态**，上游是否修复已不再相关。期望值改为 `True`，行语义从「上游修复监测行」改为**根契约送达的回归哨兵**（变否则是送达通道失效）；同步该行的 `desc`/`note`、`claude-with-root` 的 note（wrapper 已降级为后备、退役另按 #857 note 的 Revisit 判）、模块 docstring 与自测标签里的 #857 例子，并更新设计 note `docs/notes/feature/2026-09-07-harness-ingest-probe.md` 的三处旧措辞与其 Revisit 条。

## Alternatives

- **锁序守卫只扩 helper 解析、不做 `update()` CAS 检测**：放弃。`recycler` 的实修点正是 UPDATE-CAS，判据若仍看不见它，本单的「家族已闭合」会第二次立不住（这也正是 #2974 的立单理由）。
- **给 `admission_pump.py` 硬加一次冗余排序**：放弃。它的问题不是顺序而是「单行事务不成环」，为消红而排序会把「已裁定无风险」伪装成「有风险已修」，反而误导后来者；用带理由的裁定登记更诚实。
- **sticky 守卫把 `_WINDOW_LINES` 从 8 调到 12**：放弃。窗口大小是魔数，元素再长一点就再次失效；按元素块取值才是与「值可能出现在块内任意深度」匹配的形态。
- **`#2987` 改加一条源码静态守卫（扫调用点有没有 `sort(`/`slice(`）**：放弃。静态守卫断的是文本形态，组件换个写法（例如在 `useMemo` 里先赋值再传）就漏；桩掉图表层从 props 处断言是**行为**断言，且与仓内 `FileServerPage.test.tsx` 的 recharts 桩法同源。
- **`#2964` 保留 `q1=False` 并把该行标成「已知恒 DRIFT」**：放弃。恒红的行会训练读者忽略整张矩阵，判别力归零——这正是本单要修的。
- **把被在飞 PR 覆盖的文档批（#2989/#2992/#3001/#3003）也塞进本 PR**：放弃，理由与同日文档批一致（PR #3005 / #3012 触及同文件与同语义面）。

## Revisit

- **锁序判据的已知射程**（写进模块 docstring）：跨模块 helper 与对象方法不解析（只做同模块模块级函数名）、批量 `in_(...)` UPDATE 不算、无显式锁的隐式取锁（`INSERT … ON CONFLICT`、外键检查）不在内。真出现一类漏判就补一类，别把调用图一次做大。
- `_ADJUDICATED_SAFE` 的 `admission_pump.py:claimed` 条目：`requeue_plan_run` 一旦改成「锁多行后提交」，裁定立即失效，必须重裁（判据只保证形状变化会变红，不保证理由仍成立）。
