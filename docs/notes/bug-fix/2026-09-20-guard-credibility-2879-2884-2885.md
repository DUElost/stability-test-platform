# 守卫可信性批：不可判定不得读成通过（#2879 / #2884 / #2885）

Status: implemented
Class: bug-fix

## Decision

三条守卫共一个失败形态：**「看不见」被当成「看过且干净」**。本批把三处判据面收成
fail-closed，并给守卫本身补上可证伪的自检。

### #2879 · 审计 `resource_type` AST 守卫三处静默放行

`backend/tests/test_audit_resource_type_guard.py` 原先在三处「不可判定即放行」：
`except SyntaxError: continue`（整份文件免检）、调用名只认 `func.id`/`.attr`
（`as` 改名 / `getattr` 取用即从扫描面消失）、`_literal_str(...) is None →
continue`（非字面量 `resource_type` 不被判定）。改后：

1. 扫描逐份源码走 `_scan_source()`（守卫与自检同一实现），`SyntaxError` 收集后
   **断言为空**（语法面另有 `pr-compileall` 兜底，守卫不再自留免检口）；
2. `as` 改名导入**被识别**（`_imported_record_aliases`）；`getattr(x, "record_audit")`
   无法解析调用点 ⇒ 记入 `dynamic_refs` 并**断言为空**；
3. 非字面量与 `**kwargs` 展开一律计入违规（判据是「写侧合规」，不是「字面量合规」）；
4. 新增调用点下限 `_CALL_SITES_BASELINE = 117`（全量实测值）：**扫描面缩小即红**——
   这是对未知绕过形态（wrapper、importlib…）的兜底判据。

判据与扫描面事实同源：`_scan_backend_audit_calls()` 返回 `(calls, report)`，
数量断言与违规断言读的是同一次扫描，不会各看一套。

### #2884 · `script_guard_probe.summarize` 的 `guard` 块判据只覆盖 rc=1

#2797 用「payload 是否带 `guard` 块」区分真判定与进程早死，但只兑现于 `rc != 0`：
`rc=0` 且 payload 形状漂移时直接落成 `GUARD OK: 无到期项`；`rc=2`（argparse 用法错误
与 `GUARD_UNKNOWN` **同码**）被归因成「执行事实不可得」。现在「带不带 `guard` 块」
是 `rc ∈ {0,1,2}` 的**首判**：不带 ⇒ broken（写指标、任务 exit 1）。同时收掉两个崩溃
面：`guard` 非 dict、`violations` 非数字 ⇒ broken，不再抛 AttributeError/ValueError
——巡检崩掉时指标停在旧值，消费方读到的正是「守卫说干净」。

### #2885 · 列宽守卫读模型常量而非库实际宽度

#2792 的派生宽度取自 `JobLogSignal.__table__.columns`：模型与迁移是两份可独立漂移的
事实，库落后于迁移时守卫按 32 放行而 DB 仍是 16，单条超宽照样 abort 整批 INSERT。
新增 `deployed_column_widths(db)`：摄取时从 `information_schema.columns`
（`table_schema = current_schema()`）实采一次，`log_signal_column_overflow(row, widths)`
以之为判据；探针失败（权限/连接/非 PG）退回模型宽度并留 warning——写侧主职是写入，
探针坏降级为旧行为而不是拦停。

## Alternatives

- **#2879 只补第 3 点**（issue 建议「最该改」）：非字面量确实是最常命中面，但改名导入与
  `getattr` 会让「扫描面」本身不可证——绿灯意味着「没看见」而非「看过干净」。故一并做。
- **#2879 做全量数据流分析**（跟踪 wrapper 的参数来源）：超出静态守卫射程，且 wrapper 内层
  调用点仍在扫描面内、其 `resource_type` 非字面量时已被 fail-closed 拦住。用下限断言兜底。
- **#2879 用 `==` 基线**（对齐 `check_inner_imports` 的硬等值）：合法新增调用点会恒红，
  摩擦大于收益；改 `>=` 下限，只拦「扫描面缩小」这一危险方向。
- **#2884 只改 rc=0**：rc=2 的 argparse 误归因与两个崩溃面同源（都是「进程没走到输出」），
  一并收；码表语义未变（带 `guard` 块的 rc=2 仍是 unknown）。
- **#2885 改成与 DB 无关的硬上限**（issue 建议方向②）：会拒掉库其实装得下的值
  （模型与库都是 32 时 20 字符本可入库），属误伤；**启动期采样一次再缓存**：DDL 之后
  缓存会陈旧，而每批一次的 catalog 查询相对摄取已有的逐条 `db.get` 可忽略，故按批采样。

## Verification

**反例优先（先证伪再采信）**——三处生产改动退回 `HEAD` 后新用例全红：

- #2879：变异 A（非字面量/kwargs 回到静默跳过）、B（不识别 `as` 别名）、C（不采集
  `dynamic_refs`）→ `test_guard_self_test_bypass_forms` 三次均 FAILED；恢复后绿。
  自检本身含**正向断言**（改名导入的调用点必须被识别到），不会因「扫描器返回空」而假绿。
- #2884：`HEAD` 版模块跑新用例输入——`summarize(0, {"_stdout_tail": "garbage"})` →
  `(due=0, broken=0)` 读成干净；`summarize(2, argparse 用法错误)` → `unknown=1` 归因错；
  `guard` 非 dict → `AttributeError`、`violations="abc"` → `ValueError`（巡检直接崩，
  指标停在旧值）。新实现四种输入全部 broken + 指标照写。
- #2885 **实弹复现**（临时用例 `ALTER TABLE job_log_signal ALTER COLUMN source TYPE
  varchar(16) ...`，跑完即删、DDL 已还原）：旧代码 ——
  `StringDataRightTruncationError: value too long for type character varying(16)`
  （整批 INSERT 被 PG abort，正是 #2792 的原始 P1）；新代码 ——
  `{'inserted': 0, 'total': 1, 'rejected': [{'job_id': 1, 'seq_no': 1,
  'reason': "log_signal field exceeds column width: ['source']"}]}`。

## Revisit

- `_CALL_SITES_BASELINE` 是手工维护常量：合法新增调用点不受影响（`>=`），**删除**调用点时
  需人工确认后下调。若这成为常态摩擦，可改成按目录分布的下限。
- #2879 未覆盖跨函数 wrapper 的**参数来源**（`def my_audit(rt): record_audit(resource_type=rt)`
  的 `rt` 从哪来不追）；非字面量已 fail-closed，故此类调用仍会被拦，但归因只到「非字面量」。
- #2885 每批一次 `information_schema` 查询：若将来出现跨 schema 的同名表，`current_schema()`
  过滤需复核；若摄取 QPS 显著上升，再考虑带 TTL 的缓存（须保证 DDL 后不长期陈旧）。
- #2884 的 rc=2 语义仍与 argparse 同码，靠 `guard` 块区分；若判据侧将来给 2 换语义，
  需同步本文件与码表注释。
