# 设备页「全选」语义：只修 main 上仍成立的那一条（#2600）

Status: implemented
Class: bug-fix

- 日期：2026-09-17（立案日；实现于 09-18）
- 关联：`#2600`（`/devices` 全选语义可发现性）、`#2599`/`#2601`（同批观察自 dev 栈的另两单）、
  `#496`（列表基础设施：分页 + 虚拟滚动 + 轮询策略——本单按 issue 明确不动分页实现）

## Decision

**issue 正文的两条主要指控在 main 上不成立**（观察来自陈旧前端构建产物），本单只修仍成立的第三条。

### 复验（基线 `c851d1c8`，2026-09-18）

| issue 指控 | main 实况 | 判据 |
|---|---|---|
| 「表头复选框没有任何 `title`/`aria-label` 说明『当前页』」 | **不成立**：`aria-label="选择当前页设备"` 已在 | `ExpandableDeviceTable.tsx`（改动前 `aria-label="选择当前页设备"`） |
| 「没有『选择全部 N 条筛选结果』的入口」 | **不成立**：按钮与 `onSelectAllFiltered` 自 **2026-07-15**（`0b8bc4ce`）即在 main | `DeviceBulkActionBar.tsx`、`DevicesPage.tsx:212-218` |
| 「『已选择 N 台设备』文案不区分页与全量」 | **成立**（残留） | `DeviceBulkActionBar.tsx` 主行只报分子 |

**为什么观察会偏**：issue 的现场来自 dev 隔离栈，而它的**前端是构建产物**（`stp-dev-frontend-1`
容器跑的是镜像里烤好的 `dist-prod`，不随仓库挂载热更）。实测该 bundle（`assets/index-CS9KZPMF.js`）
对「选择全部筛选结果」**0 命中** ⇒ 那个界面比 main 早，看不到 7 月就有的入口。
（同批的 #2599/#2601 已在各自 PR 里逐条复验过，那两单的指控在 main 上成立。）

### 本单实际改动（两条，都是「让规模差可见」）

1. **批量条计数带分母**：`已选择 50 台设备` → `已选择 50 / 546 台设备`——页选与全量不再同形；
   已有的「选择全部筛选结果 (546)」按钮作为补齐入口原地保留（`selectedFilteredCount < filteredCount`
   时才显示）。
2. **表头复选框可访问名与 tooltip 带页大小与作用域**：`选择当前页设备（本页 50 台）` +
   `title="全选当前页 50 台；其他页保持原选择"`。

## Alternatives

- **只回复「已实现」并关单、不改代码**：残留（计数不暴露规模差）是 issue 第 2 条的核心，
  且它随规模线性放大（546 台时是 50 vs 546，1000 台时同形依旧）。否。
- **把表头复选框改成「全选筛选结果」**：改的是**语义**而不是可发现性——页选在 1000 台规模下是
  有意义的原子操作（翻页核对后整页打标），issue 也只要求「加标注 + 提供全量入口」。否。
- **新增页选/全量切换控件**：入口已存在（同一个按钮），再加一个只是重复。否。
- **顺手把分页改成服务端分页/虚拟滚动**：属 #496，issue 明确排除。否。

## Revisit

- **若 #496 把分页改成服务端分页**：「选择全部筛选结果」的语义要从「客户端 Set 并集（当前实现
  依赖全量已加载）」换成服务端 selection-all（否则分母有了、补齐入口却只能覆盖已加载页）。
  本单的判据（分母 + 入口）到那时仍适用，只是实现面要改。
- **同类陈旧现场**：凡是「界面行为」类 issue，复验时先确认**前端是构建产物还是热更源码**
  （`docker inspect` 看 nginx 容器的挂载 + `grep` bundle 里的文案），否则会把旧版本的行为当现状
  ——本单是第二次踩到（#2599/#2601 的宿主 dev 后端则是源码挂载，所以那两单的复验成立）。
