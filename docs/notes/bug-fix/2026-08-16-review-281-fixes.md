# #281 评审结论逐项修复（P0/P1/P2）

Status: implemented
Class: bug-fix

对 #281（feat/multiworker-b1-b4）评审结论的逐项修复。评审全文与复现见
PR #281 的审查结论；本 note 记录修复决定、放弃的备选与验证方式。

## Decision

- **P0 生产护栏统一**：新增 `security.is_production_like_env()`，把
  `ENV=internal` 与 `ENV=production` 同等视为生产类环境。`validate_production_auth_cookie_settings`
  （main.py lifespan 调用）、`is_public_register_allowed` 默认策略、
  `STP_SKIP_INFRA_CHECK` 豁免均改用它。此前护栏只认 `production`，而生产
  部署 `.env.backend` 是 `ENV=internal`，安全 Cookie/CSRF/注册策略全部旁路。
- **P0 SocketIO 匿名接入**：`/dashboard` 命名空间改为**除 `TESTING=1` 外
  始终要求有效认证**（token 或 HttpOnly cookie 或显式配置的 `WS_TOKEN`），
  不再依赖 ENV 判定。动态复现确认：`ENV=internal` 下无 token 握手可连接。
  **二轮硬化**：`WS_TOKEN` 源码默认值 `dev-token-12345` 不算「已配置」，
  未显式设置时静态口令旁路不生效（否则任何部署都有一把公开万能口令）。
- **P1 密码长度回归**：`backend/tests/api/test_users.py` 的 6 位 `pass123`
  改为 8+ 位，并新增 6 位密码 422 断言测试。
- **P1 登录锁定原子化**：`LoginLockout.guarded_attempt(key, verify)` 在单把
  互斥锁内完成「检查锁定→密码验证→失败计数/成功清零」，路由不再三段式
  调用；并发请求无法同时越过锁定检查越阈值试密（原 auth.py:94/102/104
  TOCTOU）。
- **P1 锁定淘汰保护**：`_evict_if_needed` 只淘汰未锁定条目；全部在锁定中
  时**不再插入新键**（二轮 P2：原实现 `setdefault` 会让容量上限形同虚设，
  表被锁满后继续灌新用户名字典无限增长），并返回是否可淘汰。
- **P1 锁定剩余秒数**：`_remaining_seconds` 用 `math.ceil` 向上取整（二轮
  发现：`int()` 截断会让剩余 <1s 的锁定误报 0，看起来已解锁）。
- **三轮 CR Major（09:44 复评）**：
  - **用户名枚举时序通道**：用户不存在时对固定 dummy 哈希执行一次 bcrypt
    （`_TIMING_DUMMY_HASH`），两条路径计算量一致；
  - **unknown 键空间填表**：未注册用户名一律归入共享 `UNKNOWN_ACCOUNT_KEY`
    桶——按 `unknown:<用户名>` 逐名跟踪的键空间由攻击者控制，可占满
    跟踪表让真实账户失去锁定保护；
  - **全局锁串行化所有登录**：`guarded_attempt` 改用固定 64 片分片锁
    （内存有界），同账户仍原子，不同分片可并行 bcrypt；
  - **>72 字节密码静默截断**：`security.PasswordStr`（8–128 字符且 ≤72
    UTF-8 字节，Pydantic AfterValidator）应用于 register/用户 CRUD/改密
    全部入口，哈希前 422 拒绝；
  - 另修：429 锁定命中补审计（`login_locked`/`token_locked`）；生产类环境
    拒绝无效 `AUTH_COOKIE_SAMESITE` 显式值；`backend/tests/conftest.py`
    增加 autouse fixture 清空模块级锁定默认实例（共享桶后跨测试污染）。
- **四轮 CR Major/Minor（10:04 复评）**：
  - **审计 IP 伪造**：`record_audit`/`record_audit_async` 不再直接解析
    `X-Forwarded-For` 链首（客户端可伪造前置值污染审计来源），改经
    `limiter.resolve_client_ip` 可信代理解析（对端不可信完全忽略 XFF；
    可信则从右往左取第一个非可信条目，与限流同源）；
  - **失败计数时间戳**：`guarded_attempt` 在密码验证后用新时间戳重新
    `_prune` 再计数——验证跨过失败窗口边界时过期失败不参与计数、不误锁。
- **P1 锁定身份键**：锁定键由路由提供——已注册账户用数据库 `user.id`，
  未知用户名用 `unknown:<原样用户名>`；模块不再 `lower()`。`users.username`
  是大小写敏感的普通 String，Alice/alice 是两个账户，不再共享锁定桶。
- **P1 失败/拒绝审计持久化**：`login_failed`、`token_failed`、
  `refresh_rejected`（jti 黑名单 + 无 jti 两条路径）、`change_password_failed`
  写审计后显式 `db.commit()` 再抛/返回。get_db 不自动提交，失败路径此前
  随会话关闭整体回滚（PG 容器实验：审计行数为 0）。
- **P1 Plan 链尾原子追加**：新增 `POST /api/v1/plans/{plan_id}/append-chain-tail`
  ——单事务内 FOR UPDATE 锁定链尾、校验 `expected_updated_at`（可省略，
  超窗时客户端无法提供）、创建新 Plan、更新 `next_plan_id`；409 时整体
  回滚，不再产生孤立 Plan。前端 `createChainTailPlan` 改走该接口，链尾
  在最近 200 条窗口内时携带版本令牌，超窗则省略（服务端行锁兜底）。
  **二轮审查 P1（锁后重读）**：追加改为 `_lock_chain_tail`——从锚点起
  每个节点先 `FOR UPDATE` 再 `db.refresh()`，锁内重新确认是否仍是链尾；
  `next_plan_id` 非空则继续走到新尾并加锁。不能信任加锁前读到的
  updated_at（后到者持同一旧令牌会误判乐观锁通过，把先到者刚连上的
  新 Plan 覆盖成孤立）。PostgreSQL 并发测试覆盖带令牌（一 201 一 409）
  与无令牌（双 201 按序连接）两条路径，均无孤立 Plan。
- **P2 密码审计字段**：`user_updated` 的 `changed` 恢复包含 `password`
  字段名（仍不记值）——仅改密时审计不再为空数组。
- **P2 删除乐观锁**：`DELETE /plans/{plan_id}?expected_updated_at=...`
  携带且不匹配时 409；令牌可省略（兼容旧客户端）。
- **P2 PR 门禁**：ci.yml 新增 `pr-backend-test`（PG service 跑
  `backend/tests/`），**信息性、非阻塞**——不进入 required checks，合入
  路径 ~2 分钟注意力预算不变（见 `2026-08-14-merge-path-attention-budget.md`
  补充节）；被否决的是「backend-test 前置为 PR 必查项」，信息性信号不在
  否决范围内。
- **P2 文档**：AGENTS.md「每 15 分钟」改为「每天（UTC 18:00）」并补充
  pr-backend-test；`DEVICE_LOG_FLOW_REVIEW_2026-08-09.md` 的
  `backend/agent/event_dirs.py` 链接改为 `backend/agent/aee/event_dirs.py`；
  archive 下 17 条失效相对链接全部修正（唯一目标存在性校验后机械替换）。
- **P2 bcrypt 警告**：`security.py` 改直连 `bcrypt`（hashpw/checkpw，72 字节
  截断语义与旧 passlib `truncate_error=False` 一致，存量 `$2b$` 哈希可直接
  校验），消除 passlib 1.7.4 读 `bcrypt.__about__` 的警告。`requirements.txt`
  **未改动**（lock 一致性门禁 `requirements_digest.py --check` 要求 py3.11
  重建 lock，本机无 py3.11）；passlib 固定版本暂留作未使用依赖，待 py3.11
  下重建 lock 时清理。

## Alternatives

- 锁定原子化选进程内全局锁（锁内做 bcrypt 校验）：放弃每账户细粒度锁
  （生命周期清理复杂、存在锁对象竞态窗口）与 Redis/DB 锁（多 worker 部署
  才需要，见 #91 既有局限声明）。
- SocketIO 认证选「TESTING=1 外一律要求认证」而非「internal 也按生产
  判定」：前者对任何未来新增环境都 fail-closed，不依赖 ENV 枚举。
- 生产 Cookie 护栏：`ENV=internal` 纳入生产类后，本机部署（HTTP-only
  nginx 模板）曾面临 `AUTH_COOKIE_SECURE=0` 拒启。**部署决策（操作者
  选定，方案 B）**：纯 HTTP 内网部署，无需域名/公网/证书——`ENV=internal`
  语义定为「无 TLS 内网部署」，`AUTH_COOKIE_SECURE=1` 强制仅限
  `ENV=production`；internal 保留其余全部生产级护栏（CSRF 强制、SameSite
  取值校验与 none 拒绝、SocketIO 强制认证、注册默认关闭、
  `STP_SKIP_INFRA_CHECK` 禁用）。理由：Secure cookie 在纯 HTTP 下被浏览器
  拒绝（不发送），强制它=必然拒启且无安全收益；被否决的备选是显式逃生阀
  `STP_ALLOW_INSECURE_COOKIES=1`（默认 fail-closed，.env.backend 需加新
  变量）与强制 TLS（无证书供给条件）。`deploy/control-plane/nginx/` 的
  HTTPS 模板（stability-platform-https.conf）仍保留，上 TLS 后置
  `AUTH_COOKIE_SECURE=1` 并考虑收紧。
- 链尾接口的 `expected_updated_at` 做成可省略：客户端超窗找不到链尾时，
  旧行为是静默跳过连接（断链 bug），新行为是省略令牌交给服务端行锁原子
  追加——比强制必填更正确。

## Revisit

- 部署按 internal 语义启动（`AUTH_COOKIE_SECURE=0` 合法）后，冒烟：登录 /
  SocketIO（无 token 必须被拒）/ 链尾追加。若未来上 TLS：置
  `AUTH_COOKIE_SECURE=1` 并重议是否把 internal 的 secure-cookie 例外收紧。
- 多 worker 部署落地时，锁定与 IP 限流一起迁 Redis（#91 同批）。
- py3.11 可用时重建 requirements.lock 并移除 passlib；同时把本地 venv
  （当前 3.13）与 CI/镜像（3.11）对齐为统一运行基线。
- HEAD 时间戳（author/committer 2026-08-17 00:27 +08:00）与 push/CI 派发
  时刻自洽，无时钟异常证据；后续评审注意审查基准日与提交时序的表述即可。
