# API 应用层超时上界与长请求豁免（#1199，R12-R01）

Status: implemented
Class: bug-fix

## Decision

现状：`apiClient` 实例与 refresh / 会话探活均无应用层 timeout。风险核心是
**401 恢复共享路径**——`_refreshInFlight` 防抖 Promise + 跨标签 Web Lock 在
refresh 挂起时被无限占住，后续所有 401 恢复排队等待；普通请求挂起则 UI 无限
pending（依赖浏览器/代理超时，行为不可预期）。

修正（A 最小闭环 + B 纵深，常量集中在 `utils/api/timeouts.ts`）：

- **A**：`auth.ts` refresh 加 `AUTH_REFRESH_TIMEOUT_MS = 10s`；`client.ts` 会话
  探活加 `SESSION_PROBE_TIMEOUT_MS = 8s`。释放机制本已具备
  （`_refreshInFlight.finally` + Web Lock 随回调 settle 释放），超时触发失败
  路径即释放，后续 401 可立即重试。
- **B**：`apiClient` 实例默认 `API_TIMEOUT_MS = 30s`；六处长请求显式豁免
  `NO_TIMEOUT = 0`（由浏览器/代理兜底）——assistant 连接测试 / 消息发送
  （LLM）、报表导出、套件导出 ×2、JIRA xls 上传。
- `toApiError` 把 axios 超时（`ECONNABORTED`/`ETIMEDOUT`/message 含 timeout）
  映射为「请求超时，请重试」+ code `TIMEOUT`，不再暴露
  `timeout of 30000ms exceeded` 技术串。

## Alternatives

- 只做 A：不解决普通请求无限 pending；改动最小，已并入 B。
- 全局 30s 不豁免：会误伤 LLM（常态 30-120s+）与文件上传/下载（验收 3 明确禁止）。
- 长请求用 120s 而非 0：LLM 长工具循环耗时不可预估，120s 仍可能截断合法请求；
  0 交由浏览器/代理兜底更安全（豁免点均为用户前台动作，不占共享恢复机制）。
- AbortController 手写计时器：与 axios 原生 timeout 等价，徒增代码。

## Revisit

- 新增长端点（或后端接入 SSE/流式，axios 不适用）时需同步维护豁免清单；
- refresh 超时在极慢网络下会走失败路径（与今日网络错误同类）；若出现误登出
  反馈，可评估提高阈值或改为有界重试。
