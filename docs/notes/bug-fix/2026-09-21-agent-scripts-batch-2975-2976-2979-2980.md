# Agent 脚本修复批：假绿与误删的三条判据收紧（#2975 #2976 #2979 #2980）

Status: implemented
Class: bug-fix

## Decision

09-20 变更审计立出的四个脚本缺陷，同属「错误被吸收成绿色/健康文件被当成损坏」
这一族，按脚本版本不可变契约各发新版本（#2980 一次改三族同形）：

- **#2976 clear_recents v1.0.3**：`_dump_ui` 丢弃 `uiautomator dump` 与 `cat`
  两处 rc ⇒ 读失败=空串=0 卡=「本来就没有任务卡」提前成功，还写从未测量的
  `tasks_after: 0`。现返回 `(xml, reason)`，dump rc≠0 / cat rc≠0 / 空输出 /
  非 XML 四态一律转红并带 `metrics.ui_read_failed`；`require_tasks` 的判定
  从不可达的「尝试耗尽后」挪到首个成功读取之后。
- **#2979 powercycle_setup v1.2.3**：#2846 的修复把「读空」与「文件不存在」
  分开核验，但 `get_prefs_xml`（cat）与 `_prefs_file_state`（test -f）仍是
  **两次独立 adb 调用**——cat 撞瞬时失败（rc=-1）+ test -f 成功回 present ⇒
  照删健康 prefs。现合并为**同源单探测** `_root_read_prefs()`（ok/empty/absent/
  denied/transient 五态），删除只认「存在+读成功+内容为空」这一种确定性损坏；
  其余形态保留文件等下轮。
- **#2980 gpu_finish v1.0.7 / powercycle_finish v1.0.6 / sleep_finish v1.0.4**：
  #2834 把临时目录回收挂 `main()` 的 `finally`，但引擎墙钟到点是给进程组发
  SIGTERM（CPython 不转异常 ⇒ finally 不执行，锚点实测 rc=-15）。现 main()
  开头装 SIGTERM 处理器转 `SystemExit(143)`（引擎 SIGTERM→SIGKILL 有 ~2s
  grace，本地 rmtree 充裕），并加启动兜底清扫 **≥24h** 的同族前缀孤儿目录
  （SIGKILL 漏网的回收出口；24h ≫ 合法墙钟 600s，不误删并行兄弟）。
- **#2975 monkey_setup v2.3.10**：#2862 的「结构化出口」把 att 降级结论落在
  **步骤字典**，而引擎只读顶层 `payload["metrics"]` ⇒ 恒 `{}`、零消费者。
  现 `main()` 成功/失败两出口都把步骤 metrics 聚合进顶层；v2.3.9 docstring
  的错误主张就地勘正（不留"修了但没人读"的注释化石）。

模板 pin：五族新版本均未注册（scan 是运维写、不进 PR），按 #2998 的
EXCEPTIONS 机制登记滞后（pin 保持已注册 head，防 `_validate_script_refs`
422），删除条件逐条写明；`--pending-activation` 视图追平后删条目并追 pin。

## Alternatives

- #2979 曾考虑「删除前把两次调用都成功才放行」——被否：两次成功的交错窗口
  依旧存在，只是更窄；同源单探测从根上消除交错面。
- #2980 曾考虑引擎侧「超时前先给脚本 grace 信号」——引擎已有 grace（2s），
  问题在脚本侧没人接 SIGTERM，改引擎影响所有脚本族，超出本单必要面。
- #2975 曾考虑改引擎读 `steps.*.metrics`——被否：顶层 `metrics` 是本仓既有
  约定（gpu_finish 即此形状），改读取面牵动所有步骤消费者。
- #2976 的读失败曾考虑重试后降级——被否：读不到就是测不到，测不到不配
  拿到任何计数值。
