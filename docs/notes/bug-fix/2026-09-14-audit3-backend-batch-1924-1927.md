# audit-20260913-3 backend 收尾批：abort merge 覆盖 / 通知扫描窗口 / 扇出容错 / 指标基数（#1924 #1925 #1926 #1927）

## Decision

1. **#1924 `plan_run_abort.py` requested_job_ids 第二段写**：#703 放锁窗口里
   并发 host 级 abort 按 "merged, not replaced" 契约并入的条目，会被重取锁
   后的整写快照覆盖（host 分支用的 `existing_requested` 也是放锁前旧读）。
   两分支统一改为与**锁内现值** merge（re-lock 后 `run_ctx` 是新鲜读，merge
   只增不删，语义安全）。
2. **#1925 `notification_service._load_prior_channel_delivery`**：先例查找加
   `_PRIOR_DELIVERY_SCAN_WINDOW`（5000 条 id）有界窗口——表无
   event_type/context 索引也无保留任务，无界全表倒序扫在每次首投递（必然
   无匹配）都整表逐行 JSON 提取。窗口内查不到即视为「无先例」，与 #1826
   前的「最近 30 条」口径同族（仅放大）。表达式索引留 Revisit。
3. **#1926 `socketio_server.schedule_agent_control_fanout`**：`_fanout` 循环体
   per-item try/except——单 emit 失败（Redis adapter publish 异常等）不再
   终止整个扇出协程（剩余 host 永远收不到 abort control）；失败的 future 加
   done-callback 记录协程级异常（原样丢弃 = "never retrieved" 噪音）。
4. **#1927 漂移指标 label 收敛**：`stability_plan_run_counter_drift_total`
   去掉 `plan_run_id` label（单调无界，client 子序列永不回收，系统性漂移
   时基数恰好在最需要时爆炸），只保留白名单 `mode`；run 维度改记日志；
   告警表达式 `sum by (mode)` 归并（防逐 series 告警风暴）；promtool 场景
   与解析器同步（聚合前缀剥离）。

## Alternatives

- #1924 只修 else 分支——否：host 分支的 stale `existing_requested` 有同样
  窗口，两分支统一现值 merge 才闭环。
- #1925 加表达式索引——更优终态但要迁移；有界窗口零 schema 风险先止血，
  索引在 Revisit（若通知量级增长再立）。
- #1926 失败项二次补偿队列——否：abort control 已有 reaper 宽限兜底，
  补偿队列超出本单最小面；per-item 隔离 + 日志已消除静默丢失。
- #1927 用 Top-N 有界 label——否：mode 已足够回答「哪类计数器在漂移」，
  run 维度对告警无用（是日志/审计的事）。
