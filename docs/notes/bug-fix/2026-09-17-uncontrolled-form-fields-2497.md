# 建号表单改非受控字段：消除 React 回写密码管理器所填值导致的页面卡死（#2497）

Status: implemented
Class: bug-fix

- 日期：2026-09-17
- 相关：`#2453`（提交改读 DOM 值）、`#2456`（其余表单扫尾）、`#2435`/`#2406`（同表单的判据对齐）
  ——本单是同一现场暴露的**第四条、也是唯一一条「页面卡死」**

## Decision

**把 `UserModal` 的四个字段由受控改为非受控**（`defaultValue` + 提交时读 DOM）：

- `username` / `password` / `confirmPassword` / `role` 全部 `value=` → `defaultValue=`；
- 键入不再逐字符写 state（少了每键一次重渲染）；
- **编辑态「密码非空才显示确认框」**的可见性判据改由 `onChange` 维护的 `passwordPresent`；
- 重开归零不再依赖受控重置：弹窗关闭时 `if (!isOpen) return null` 已让整棵子树卸载，
  重开自然拿到新的 `defaultValue`（用例钉住）。

### 为什么必须「不回写」而不是继续加固提交侧

`#2453` 已把**提交取值**改成读 DOM（那一层是对的，本单保留）。但受控组件的另一半行为没变：
**React 会在重渲染时把 DOM 值回写成 `value` prop**（即 state）——管理器直写 `.value` 后
state 仍是空串，于是下一次重渲染把它**清回空**；管理器（或浏览器）发现值被清掉**再写**，
React 再清……这条往返足以占满主线程，表现为**浏览器级「页面无响应」**。

现场证据链（把「不是我们的判据/取值问题」排除干净）：

| 观察 | 结论 |
|---|---|
| 事发时浏览器加载的是**新构建**（`UsersPage-CsSGA20g.js`，11:19 重建） | 不是「修复没生效」 |
| `GET /api/v1/auth/me`、`GET /api/v1/users` 均 200 | 会话与页面加载正常 |
| 全程**零 `POST /api/v1/users`** | 卡死发生在事件处理之前——提交侧修复无从生效 |
| **Safari（系统自带填充）同一套步骤正常** | 页面不是根本坏掉；差异在「填充方」 |

## Alternatives

- **在 `onChange` 之外加 `onInput`/`onBlur` 同步 state**：要不要触发事件、事件是否冒泡，
  都由管理器决定——用「猜对方行为」去修「对方行为导致的循环」。否。
- **保持受控，只靠 `#2453` 的提交读 DOM**：提交侧确实修好了，但**回写循环仍在**（页面照样卡死，
  事件处理根本轮不到）。否——这正是本单要补的另一半。
- **把字段全部改成只读 + 自定义输入层**：改动面远超本单，且会拿走浏览器的自动填充能力。否。
- **只反馈给扩展厂商、仓内不改**：卡死的是我们的页面，用户不关心是谁的锅；且非受控本身
  就少一层「React 与管理器抢同一个 DOM 值」的耦合。否。

## Revisit

- **同样的改造按需推广**：`#2456` 已把 6 个表单的**提交取值**统一（其中 4 个已改、2 个留出口）；
  若在其它表单上也观察到「填值后卡顿/无响应」，同样按本单改非受控（判据：卡顿发生在
  **请求发出之前**、且只在第三方管理器填充时出现）。
- **编辑态确认框**：管理器若在编辑态直写密码且不派发任何事件，`passwordPresent` 不会更新 →
  确认框不出现。人工键入不受影响；若真出现，改用容器级 `MutationObserver` 或总是显示确认框。
- **扩展侧**：Chrome + Yandex 密码管理器这条组合建议另行反馈给扩展厂商（本仓无法修它）。
- **回归网**：本题的两条用例（回写/重开）是这一层的唯一自动化护栏——**任何把字段改回受控的
  改动都会立刻红**，不要为了「写起来顺手」改回去。
