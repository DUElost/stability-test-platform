# 后端与运维审计批（#2056 / #2058 / #2059）

Status: implemented
Class: bug-fix

## Decision

**#2056 console 注册表在事件循环上做同步 Redis 调用**
`_dashboard_room_exists("console", …)` 在 `async on_subscribe` 路径上直接调
`RunConsole.instance().status(ident)`，而注册表用的是**同步** redis 客户端
（`console_registry._SOCKET_TIMEOUT_SECONDS = 2.0`）→ Redis 抖动时每次订阅校验最多冻住
整个 ASGI 2s，而重连客户端会密集打这条路径（#703 同族的「事件循环被打满」）。
**改**：`await asyncio.to_thread(RunConsole.instance().status, ident)`——把同步读挪出循环；
同步客户端保持原样，供 ticker/线程路径复用。

**#2058 硬 ExecStartPre 无 start-limit → 无界重启环**
两个 unit 都把 schema 守卫放在**硬** `ExecStartPre`（无减号），同时 `Restart=always` +
`RestartSec=5`，且都没有 `StartLimit*`：守卫一红就每 5s 重跑「alembic upgrade + 守卫」
无限循环，把真实原因埋在 activating/auto-restart 里。这与
`docs/notes/process/2026-08-30-deploy-source-guard-and-required-env.md` 的既有决策
（「无 `StartLimit*` 不得硬失败」）直接冲突。
**改**：两个 unit 的 `[Unit]` 段加 `StartLimitIntervalSec=300` + `StartLimitBurst=3`
（写在 `[Unit]`，放 `[Service]` 会被 systemd 忽略——测试对此也做了断言）。

**#2059 准入泵 push-fatal 恒记 script_sync_config_error**
`admission_pump` 的 Phase A 对 push 阶段 fatal 一律抛
`_FatalAdmission("script_sync_config_error", …)`，而 `#1920` 已把退役早退码
`host_retired` 收入 fatal 子串 → 退役主机的终态 reason / `last_error` / 审计都记成
「脚本配置错误」，同一 PR 精心安排的 Phase B `HOST_RETIRED` 分支在这条路径上不可达。
**改**：抽出纯函数 `_fatal_admission_for_push_failures()`：命中退役的条目 `reason` 就地
归一为 `host_retired`，整体归因 `HOST_RETIRED`；非退役 fatal 行为不变。

## Alternatives

- **#2056 把注册表整块换成 async redis**：改动面覆盖 ticker/线程路径（那里同步更自然），
  且要重做连接生命周期——用 `to_thread` 是只影响目标路径的最小面。
- **#2058 去掉硬 `ExecStartPre`**（回到 08-30 的软失败）：会丢掉 #1882 想要的
  「代码超前库时拒绝启动」保护；加 start-limit 保留保护又消除重启环。
- **#2059 在四个 fatal 分支各写一次映射**：重复且易漏；抽成纯函数后可离线单测
  （不需要 DB/pump 全链路）。

## Revisit

- **#2058 的 300s/3 次是需要按运维节奏核实的取值**：schema 守卫失败属于「必须人工介入」
  的类别，3 次重试只为吸收「刚 pull 但迁移还没跑完」的瞬时窗口；若现场需要更长窗口，
  调 `StartLimitIntervalSec` 即可（单点）。
- **#2056 的同类面**：`socketio_server` 里还有别的同步 I/O 触点在 async 路径上
  （如落库查询走 `asyncio.to_thread` 与否）——本批只修已确认会阻塞订阅校验的注册表读；
  全面盘点属独立任务。
