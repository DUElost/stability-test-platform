# 后端五单修复：#1550 / #1552 / #1555 / #1559 / #1560

Status: implemented
Class: bug-fix

## Decision

同属 `audit-2026-09-12` 批次的后端侧五单，一个 PR 交付（同批另见 #1547-#1549 的
CI 三单与 agent 侧 PR）。

1. **#1550 DLE 迁移表缺 PULL_FAILED 出边**：`UPLOAD_PENDING` / `UPLOADING` 两态
   没有 `PULL_FAILED` 出边，而 Agent 在本地目录缺失时**无条件**打 `PULL_FAILED`
   （`event_uploader._upload_one` 的 missing-local 分支，即 #380 要求的终态收敛），
   驱动它到达那里的恢复循环恰好只轮询这两个状态 → 补丁吃 409 → 行永远停在在途态，
   每 30s/600s 重新入队再撞 409。
   修法：把 `PULL_FAILED` 从字面表里**移出**，改由 `_TRANSITIONS_LITERAL` 对所有
   非终态**统一派生**（终态 = `_EXTRACTABLE_STATES`，不得降级，与 #1174 同口径）。
   逐条手写已经漏过一次，派生式让将来新增状态无法重演。
2. **#1552 `run_context` 过期时机错位**：`_patch_run_context` 走原生 `text()`
   UPDATE，SQLAlchemy 不同步 identity map；而 `run_ctx` 只是 `dict(pr.run_context)`
   的副本。`db.expire(pr, ["run_context"])` 原先排在聚合读取（第 385 行）**之后**，
   注释声称的「让同 session 后续读者读到库端值」落空 → `_abort_requested` 读到写入
   前的 dict → abort 覆盖不生效 → 卡在 RUNNING、job 已全终态的 run 被收敛成
   **SUCCESS** 并发成功通知。
   修法：新增 `_reload_run_context(db, pr)`，在两处分段写之后、任何聚合读取之前调用。
3. **#1555 通知降级池不可达**：`dispatch_notification_async` 调 `enqueue_sync` 未传
   `required`（默认 False）→ fire-and-forget 在**触碰 Redis 之前**就返回 True，
   Redis 故障被 `_do_enqueue_best_effort` 吞掉 → `if enqueued: return` 直接返回，
   文档承诺的「Redis/队列故障 → 降级线程池」永不触发。
   修法：给 `enqueue_sync` 增加 `on_async_failure` 回调（仅 fire-and-forget 路径
   生效），通知路径把降级动作交给它。
4. **#1559 reaper 单候选故障中断整轮**：`_recover_stale_precheck_run` 里的
   `get_saq_job_state_sync` / `is_worker_alive_sync` 是裸 `future.result(timeout=3.0)`，
   Redis 抖动会抛；该异常穿透 `for` 循环，本 tick 其余 stale PRECHECK 全部得不到
   恢复——而 reaper 是它们唯一的恢复通道。
   修法：逐候选 try/except + `db.rollback()` + `continue`，并在 tick 日志里增列
   `errored`。
   顺带修正 `_read_from_loop` 的 docstring：它声称「超时后调用者拿到 None」，与实现
   不符——正是这段注释让人以为候选循环不需要 try/except。
5. **#1560 Global 基线门禁的现场定位**：#973 的 `exported_global_sha256` 只加可空
   列、迁移不回填，于是本版本发布后**所有**此前导出过的套件都落进 `not_exported`，
   而文案一口咬定 "has never been exported"。
   修法：`step` 码保持 `not_exported`（既有契约与 `result_summary` 消费方不变），
   补 `missing`（逐项列出缺哪个基线/文件）与 `ever_exported`，并按后者切换
   message；同时在 `docs/operations/mtbf-api.md` 写明「升级后必须对全部 bound
   suite 重导一次」。

## Alternatives

- **#1550 只补两条边**：与派生式等价但下次新增状态仍会漏；否决。
- **#1550 把 PULL_FAILED 也放进 REMOTE/ARCHIVED/PRUNED**：会让已权威的
  remote_path/checksum 被降级清空（#1174 要堵的正是这个）；否决。
- **#1552 让聚合直接吃 `run_ctx` 局部变量**：`apply_plan_run_*` 是 add/abort/
  aggregator 三方共用入口，改签名面更大；`expire` 一行即可；否决。
- **#1555 改 `required=True`**：它在**主事件循环线程**上调用会抛
  EnqueueSyncError 防死锁，而本函数存在从循环内调用的路径，直接换会让循环内调用
  全部退化成同步等待；否决。
- **#1555 让 `enqueue_sync` 在 fire-and-forget 下改返回 Future**：改变返回值语义、
  影响全部既有调用方；回调是增量且向后兼容；否决。
- **#1560 新增 step 码（如 baseline_missing）**：`step` 会写入
  `pr.result_summary["step"]` 且被多处测试断言，改码是契约变更；`detail` 增字段
  已足以自助定位；否决。
- **#1560 加一次性回填脚本**：把「磁盘上的 Global 文件」当基线回填，等于信任
  可能已被改动的文件——而那正是 #973 要检测的场景；本轮不做，留给运维按 runbook
  重导（重导会用渲染结果重建文件与基线）。

## Revisit

- **#1560 的终态**：本轮只做「可定位 + runbook」。若实际重导成本过高（bound suite
  数量大），再考虑一次性回填脚本，但必须先裁定「磁盘文件可否作为基线」。
- **#1555 的观测面**：降级池触达目前只有一行 warning。若后续要按 SLO 观测
  「通知降级率」，需要加计数器——本轮未加（该模块目前无任何 metrics）。
- **#1559 的 `errored` 只在日志**：未进返回值（返回值形态被多处测试与调用方依赖）。
  若需要按 tick 告警 reaper 恢复失败率，应另开计数器而非改返回结构。
- **`enqueue_sync` 的其余调用点**：本轮只修了通知路径。#1216（助手路径）此前已修；
  其余 fire-and-forget 调用点若有「必须知道是否真入队」的语义，应逐个评估是否
  接入 `on_async_failure`。
