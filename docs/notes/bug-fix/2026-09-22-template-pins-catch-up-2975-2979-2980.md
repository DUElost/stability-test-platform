# 模板 pin 追平到已修版本：五个「合入但不生效」的脚本修复收口（#2975 #2979 #2980）

Status: implemented
Class: bug-fix

## Decision

`#2975`（monkey_setup v2.3.10：步骤 metrics 聚合进顶层出口）、`#2979`（powercycle_setup
v1.2.3/1.2.4：prefs 删除判据改同源单探测）、`#2980`（gpu_finish v1.0.7 / powercycle_finish
v1.0.6 / sleep_finish v1.0.4：SIGTERM 处理器 + 孤儿启动清扫）三单已在 09-21 关单，但**它们的
修复没在生产路径上**：脚本目录已合入、`script` 表也已注册激活，唯独种子模板仍钉旧版本 ——
而模板是新建 Plan 的唯一来源，所以生产一直在跑带缺陷的旧版本。

**做两件事，不做第三件：**

1. 把 6 处 pin 追平到磁盘 head（即各修复版本）：

   | 模板 | 步骤 | 旧 pin | 新 pin |
   |---|---|---|---|
   | `monkey.json` / `monkey_watcher_patrol.json` | `script:monkey_setup` | 2.3.9 | **2.3.10** |
   | `powercycle.json` | `script:powercycle_setup` | 1.2.2 | **1.2.4** |
   | `powercycle.json` | `script:powercycle_finish` | 1.0.5 | **1.0.6** |
   | `gpu.json` | `script:gpu_finish` | 1.0.6 | **1.0.7** |
   | `sleep.json` | `script:sleep_finish` | 1.0.3 | **1.0.4** |

2. 清空 `tests/test_pipeline_template_script_pins_2865.py` 的 `EXCEPTIONS`（5 条全删）。
   这不是顺手清理：`test_pinned_template_scripts_track_latest_on_disk` 取
   `expected = EXCEPTIONS[action][0]`，**只追 pin 不删例外**会让该用例红；而
   `_exception_lag_reason` 又拒绝「豁免版本 == 磁盘 head」，所以把例外改成新版本同样不成立
   —— 清空是唯一自洽的收口。

**为什么是现在**：这 5 条例外自述的删除条件是「部署 scan 注册激活 vX 后 pin 追平并移除本条」，
而该条件的机器判据是本文件 docstring 指定的 `--pending-activation` 视图（#2931）：

```
$ python -m backend.scripts.check_unreferenced_script_versions --pending-activation
pending-activation: 全部脚本族磁盘 head 版本均已在库且 active（无待激活项）
```

视图清空 = 磁盘 head 已在库且 active = 例外没有存续理由。这也是 #2975 正文里那句
「`--pending-activation` 不能当生效判据」的正面用途：它判的不是「修复是否生效」，而是
「例外该不该留」。

## Alternatives

- **只追 pin、保留例外并改写成新版本**：不成立。见上 —— 守卫取例外值当期望，且
  `_exception_lag_reason` 明确把「豁免版本 == head」判为失效例外（"滞后已消除，删例外并追 pin"）。
- **继续留旧 pin，等 `#3030` 的 plan_step 重指一起做**：否决。旧 pin 会让**之后新建的每个
  Plan** 继续带缺陷版本，把待办越种越多；先追模板是 #3030 评论里认同的顺序（先堵住源头）。
- **把守卫基线从「磁盘 head」改成「`script` 表已激活版」**：这是正确的方向，但属
  `#3109①`（基线方向与豁免面）的射程，本 PR 不夹带 —— 混进来的话，本 PR 的验证会被
  「守卫判据本身变了」污染，而那是另一件需要独立裁决的事（改动方向 = 从「磁盘事实」
  改为「库事实」，会改变谁在什么时机变红）。
- **同批把 `ensure_root` 的 60s 抬到 180s**：不在本 PR。那是 `#3087` 的射程，理由与本次
  完全不同（那条是「超时 < 脚本预算」，不是「pin 滞后」），且它要求把 timeout 守卫扩面到
  全部脚本族，属另一个可独立复核的改动。

## Verification

- `PYTHONDONTWRITEBYTECODE=1 python -m pytest -p no:cacheprovider -q
  tests/test_pipeline_template_script_pins_2865.py tests/test_check_device_template_timeout_2981.py`
  → **7 passed**（含 `test_exceptions_are_real_lags_with_reasons` 的空清单路径与
  `test_exception_shape_predicate_has_teeth` 的变异自证，二者在本改动下正是「稳态」形态）。
- 5 个模板 JSON 逐份 `json.loads` 通过；改动面仅 6 行版本值 + 例外表，`git diff --stat` 6 文件。
- 生效前置已独立核实：`--pending-activation` 空（上引），且只读查库
  `select name, version, is_active from script` 显示 5 个目标版本全 `is_active=true`。
  ⇒ pin 的目标值同时满足「磁盘存在 ∧ 已注册激活」，不会触发
  `_validate_script_refs` 的 422。
- **未覆盖（明确记录）**：本改动只影响**新建** Plan。在飞 `plan_step` 已固化版本号，
  实测仍有 14 个步骤钉旧版本（`gpu_finish 1.0.6` 5 / `powercycle_finish 1.0.5` 3 /
  `monkey_setup 2.3.9` 2 / `powercycle_setup 1.2.2` 2 / `sleep_finish 1.0.3` 2），
  需要走 `#3030` 的重指路径，不在本 PR 内声明为已解决。

## Revisit

- 例外表转为长期空表是稳态，但**判据仍是「磁盘 head」**：若有人在未 scan 的窗口内同时
  新增版本目录并 bump pin（守卫会放行），该模板新建 Plan 会全 422 直到部署 scan —— 这一
  反向风险归 `#3109①`，本 PR 只保证「当前这一刻三态重合」。
- 前端计划编辑器是同一 pin 的另一个生产者，本守卫两个都看不见（`EMPTY_LIFECYCLE` 仍钉
  `check_device 1.0.0`）：归 `#3109②`。
- 在飞 Plan 的版本追平（14 个 plan_step）归 `#3030`；追平完成前，这批计划仍会复现旧缺陷。
