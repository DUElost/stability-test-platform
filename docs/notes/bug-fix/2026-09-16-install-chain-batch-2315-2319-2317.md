# 安装/升级链批：导出不静默拆除 + wrapper 能力前置判据 + 时区无 bus 回退（#2315 / #2319 / #2317）

Status: implemented
Class: bug-fix

## Decision

**#2315 声明为空不再拆除既有 NFS 导出（取 issue 方案 A）。**
`render_exports(config)` 在无声明 Agent 时返回 `""`，而 S2 无条件写文件 + `exportfs -ra`
→ 既有导出被撤下（客户端挂载点还在但写不进、`mount_status.ok=false`），报告却是
`PASS export_deferred`。改为：**渲染为空且既有文件确实声明过客户端** → 不写不重载，
报 `export_kept` 并给出两条出路（带清单重跑 / 要撤除就手工删文件 + `exportfs -ra`）。

- 为什么取 A 而不是 B（对照 DB 的 `agent_installed=true` Host）：站点安装器是**本机
  工具**，不查业务库；把判定挂到 DB 会给安装链引入新的跨界依赖，且 B 仍是「报错」而非
  「不破坏」。
- 为什么不是 C（onboarding 回写 site.yaml）：那是更大的声明态设计变更（谁是权威、
  多来源冲突怎么办），超出本单。
- **终态出口**：`export_kept` 是过渡语义（issue 的「defer ≠ teardown」）。要真正撤除导出
  须显式动作（删文件 + reload），本单把这条写进检查消息与 Note。

**#2319 wrapper 能力前置判据（取 issue 方案 2：能力声明）。**
`#2180` 把逐能力探针换成脚本头 `selftest`，但 `selftest` 只断言 wrapper **自洽**
（属主/权限 + parser↔本机契约表），对「本机 wrapper 是否具备脚本将要调用的子命令」零
判别力——缺一子命令但自洽的旧 wrapper 同样 `exit 0`，脚本在第一次调用处被 argparse
拒绝，**此时 apply-code/restart 已执行**（#1942 修掉的半态）。

- wrapper 新增 `capabilities` 子命令（逐行打印 `_SUBCOMMAND_CONTRACT` 的键）；
- 远端脚本头改**双前置判据**：`selftest` + `capabilities` 与
  `host_updater._REQUIRED_PRIV_SUBCOMMANDS` 比对（清单逐行 → 脚本内 `tr '\n' ' '` 归一
  后按词匹配），缺任一项即 fail-closed 并带 `update_agent.yml` 指引；
- **守卫**：`test_required_priv_subcommands_cover_every_call_in_the_script` 钉「渲染脚本
  里每个 `$PRIV <sub>` 调用 ⊆ 期望集合」——否则将来加了新调用却忘同步集合，判据又会变成
  自指的；
- **ADR 对齐**：ADR-0037 §2 D2 升 **v0.5** 勘误（原文写「selftest（含子命令契约校验）
  fail-closed」，与实现不符），索引三面（README 主表 / DOC-MAP / M7）同步——由 S12 门禁
  逐面校验（本单实测过一次：漏 DOC-MAP 即红，补后绿）。

**#2317 无 system bus 目标的时区对齐（文件级回退）。**
`timedatectl set-timezone` 需要 system D-Bus；容器 / 精简镜像上连不上总线（
`Failed to connect to system scope bus via local transport`）→ 任务非零、Play 终止、
容器 Host 无法重装。改为 `block/rescue`：rescue 打印 rc + stderr 摘要（可读失败），
再走**文件级对齐**（`ln -sfn /usr/share/zoneinfo/<tz> /etc/localtime` + 写
`/etc/timezone`），随后仍走同一条断言（不以降级换「看起来对了」）。
另加 `tz_target` 形状断言（`^Area/City$` 形态）——文件级路径会把它拼进 path 与
`/etc/timezone`，两条路径共用该前置。

## Alternatives

- **#2315-B 对照 DB 判「有没有装过 Agent」后 FAIL**：否决（见上：安装器不查业务库，
  且 FAIL 仍会破坏——撤除动作已经发生）。
- **#2319-1 恢复逐能力探针**：可行但每次热更新多 N 次 wrapper 调用；能力清单一次调用
  即覆盖全部 ✓（且 issue 方案 2 明确列出了这条路线）。**#2319-3 只收窄 ADR 表述**：否决——
  半态（代码已同步 + 审计记失败 + 文案只有 usage）会留在链上。
- **#2317-3 声明「不支持无 system bus 目标」**：否决——文件级对齐本来就能把这类目标
  对齐好，拒绝它会把 I4 实验容器与精简镜像一起挡在门外。

## Revisit

- **#2315 的「声明态」根因未解**：本单只做到「空声明不破坏」。真正的收敛是让声明有唯一
  权威源（DB 的 Host / site.yaml / onboarding 回写三者之一），否则「带不带清单行为不同」
  这件事仍然存在（只是不再破坏）。属独立议题。
- **#2319 的能力集合是硬编码常量**：新增 wrapper 调用必须同步
  `_REQUIRED_PRIV_SUBCOMMANDS`（守卫测试会在忘记时红 ✓）。若 wrapper 将来引入
  「能力版本号」（如 `capabilities --min-version`），可把集合比对升级为版本比对。
- **#2317 的文件级回退不重启 `systemd-timedated`**：容器内若有该服务在跑，`/etc/localtime`
  变化可能被它覆盖——当前用例（nspawn 容器）无此服务 ✓；若将来出现，需在 rescue 里加
  「停 timedated 或 `systemctl restart systemd-timedated`」分支。
