# 批次复核指引（复核者）

- **状态**：Living v1.2（2026-10-10，按 ADR-0058 v1.4 D11 增补发现分类、收敛规则、每轮一个权威复核与方案归规划者；v1.1 2026-09-29 增补 Owner 选择复核工作面、Project 上下文去锚定与按风险选择隔离强度；v1.0 2026-09-28 随 [ADR-0058](../../adr/ADR-0058-planned-batch-execution.md) Accepted 建立）
- **读者**：批次交付流程中的复核者
- **权威**：职责与闸门以 ADR-0058 D8 / D9 为准；规划做法见 [`batch-planning.md`](batch-planning.md)
- **来源**：批次 B1（[#3463](https://github.com/DUElost/stability-test-platform/issues/3463)）实际使用的两轮复核提示词

## 1. 复核者须满足的条件

- 与实施者处于**不同工作面、不同上下文**；不得是实施该单元的会话。同一会话里换 prompt / 角色不构成独立复核。
- **Reviewer 不绑定具体产品**：由 Owner 按批次 / 复核对象人工选择独立 Web 工作面；具体 Harness / 模型不是治理契约的一部分。
- 若 Reviewer 位于 STP Project 中，项目内历史聊天只可用于背景和资料定位，**不得替代当前 GitHub / `main` / ADR 的独立取证**；历史聊天里的结论不得直接作为“已验证事实”。
- 普通复核可使用同一 STP Project 中的**独立新会话 + 独立取证**；数据丢失、安全、难回退、架构 / 治理实验以及“复核 Planner 本身质量”的场景，优先使用与被复核工作面不同的 Web/Harness，以降低共享上下文带来的锚定。
- 上述隔离强度是工作面选择原则，不新增 Registry 状态、标签或机械门禁；是否需要更强隔离按风险由 Owner 决定。
- 不在 Registry 协调域内，不 declare；复核结论写在 PR 评论里，不改仓库文件。
- 不改实现代码，不改 PR 状态（draft → ready 由 Owner 在看到「通过」后翻转），不操作 auto-merge 或合并。
- 不把方案以外的改进建议作为通过条件；方案以外的发现可以写，但标明「不作为通过条件」。
- 每轮只有一个**权威复核**，由 Owner 指定。其它工作面的意见在权威复核者执行复现之前只是候选，不构成「需修改」；只读源码、未执行的反例必须标「未复现」（ADR-0058 D11 第 4 条）。
- 不为所复核的单元撰写实施方案或派单提示词。路线建议写进复核评论并标「不作为通过条件」，方案修订交规划者（D11 第 5 条）。

## 2. 输入

- 批次方案（批次 issue 正文，以当前版本为准，含版本修订记录与规划者的裁定评论）；
- 被复核 PR 的 diff、改动涉及的源码与测试、CI 结果；
- 若是返修单元：上一轮复核评论。

## 3. 只回答两个问题

**A. 是否符合方案，且没有越界？**逐项核对方案中本单元的修复内容、验收项、版本登记与模板 pin，
以及是否触碰了方案「明确不做」或 scope 以外的文件。

**B. 这次修复漏了什么？**

- **必须列出调用点清单**：该缺陷形态在受影响范围内的全部调用点，每一处标注来源
  （常量 / 已校验 / 已转义 / 未处理）或处置状态。清单写进评论；「未处理」一类必须为空，否则列为遗漏。
- 异常路径：瞬态失败、超时、权限不足、非 UTF-8 输出、空参数。
- 新增的异常 / 失败是否被上游宽泛的 `except` 吞掉，或被调用方的重试语义正确承接。
- 新测试能否区分修复前后（在修复前的代码上应当失败）。
- 白名单类修复是否误拒现有合理取值（对照模板与现有参数）。

**每条遗漏必须归入三类之一**（ADR-0058 D11 第 2 条）：

- **需修改**：落在方案验收清单内的失败，或本轮返修引入的回归。
- **退回规划者**：在验收清单之外、现实中可能误写出来、且现有 required 门禁与测试都拦不住的缺口。附上独立复现与相关 required 测试结果后直接给「退回规划者」；方案修订之前，不交实施者修改。
- **非阻塞**：其余发现，不作为通过条件，可以建议另立 issue。

判定「拦不住」之前，必须在变异副本上运行与该语义相关的全部 required 测试（不只本单元的守卫），把命令和结果写进评论。

**守卫类单元**（checker、门禁、静态分析工具）只按方案的有限红 / 绿清单判定（D11 第 1 条）。找到守卫判错的新输入，不等于需修改：先查它是否在清单内（在则需修改），是否已被行为测试或其它 required 门禁拦住（是则非阻塞）；清单外且都拦不住时，退回规划者。

## 4. 独立负向证据

优先用**可逆变异验证**：临时回退修复点，确认相关测试变红，再恢复，把结果写进评论。至少对每个核心修复点做一次。

变异不适用或风险过高时，写明原因并给出等价证据：

| 对象 | 等价证据 |
|---|---|
| 配置契约 / 模板 | 篡改 fixture 或 pin 后守卫应红 |
| 部署 / 激活步骤 | dry-run，或与旧基线对照 |
| 文档流程 | 事实对账（引用的数字、链接、状态逐条核实） |

## 5. 输出格式（PR 评论）

```text
结论：通过 / 需修改 / 退回规划者
A. 逐项核对：<每项一行，✓ / ✗ + 依据>
B. 调用点清单：<文件:行号 — 来源 / 状态>
   遗漏：<文件:行号、问题、建议修法>（无则写「无」）
         每条附「类别：需修改（清单内 / 本轮回归）、退回规划者（清单外且拦不住的现实缺口）或 非阻塞」与「已有拦截：<门禁或测试名 / 无>」
负向证据：<变异点 → 测试结果；或不适用原因 + 等价证据>
轮次：本单元第 N 轮；上一轮「需修改」项的类别：<…>
```

## 6. 结论之后

- **通过**：在批次 issue 下评论「{单元} 复核通过」并附 PR 评论链接；由 Owner 把 PR 转为 ready。
- **需修改**：交回实施者按评论修改；修改后再复核一次。
- **收敛规则**（ADR-0058 D11 第 3 条）：同一单元连续两轮「需修改」都包含同一类、非回归的新发现时，第三轮不得再给「需修改」，必须给「退回规划者」，并写明需要收窄或改判据的方案节号。规划者修订方案之前，不派新的返修轮次。
- 方案标「合入前复核：否」的单元，合入后的复核发现同样按上述三类分类；非阻塞项不阻塞验收与激活链（D11 第 6 条）。
- **退回规划者**：问题在方案本身（规格缺漏、扫描漏项、判据矛盾）时，在批次 issue 下评论
  「退回：{单元}（复核发现）」，写明方案哪一处需要改。清单外且现有门禁拦不住的现实缺口（D11 第 2 条）属于此类。

## 7. 复核提示词模板

```text
你是批次 Bn 的复核者，负责复核 PR #{PR 号}（单元 {单元}）。规划方案在 GitHub issue #{批次 issue}
（以正文当前版本为准，重点读 §3 {组号} 行、§4 {组号} 验收项、§6 明确不做{、§x 的裁定}）。
{返修单元：开工前先读 PR #{上一轮 PR} 下上一轮的复核评论。}
按 docs/development/ai/batch-review.md 执行，只回答两个问题：

A. 是否符合方案、且没有越界？逐项核对：
   {逐条列出本单元的修复点、版本登记、模板 pin、scope 限制}
B. 这次修复漏了什么？重点检查：
   - 逐个列出 {受影响范围} 内所有 {形态对应的调用点类型}，标注来源 / 状态，写进评论；
   - {本单元特有的异常路径与调用方承接问题}
   - 变异验证：至少对 {核心修复点} 各做一次，结果写进评论。
   - 每条遗漏标注类别（需修改 / 退回规划者 / 非阻塞）与依据；判定「现有门禁与测试拦不住」之前，在变异副本上运行相关 required 测试并写明结果。
{守卫类单元：只按方案 §4 {组号} 的有限红 / 绿清单判定；清单外且现有门禁拦不住的输入给「退回规划者」，其余清单外输入按非阻塞记录。}
{若本单元已连续两轮因同类非回归新发现「需修改」：本轮结论只能是「通过」或「退回规划者」。}

输出：在 PR #{PR 号} 下提交一条评论，格式见 batch-review.md §5。
后续：通过 → 在 #{批次 issue} 下评论「{单元} 复核通过」并附链接（ready 由 Owner 翻转）；
需修改 → 交回实施者；方案问题 → 在 #{批次 issue} 下评论「退回：{单元}（复核发现）」。
禁止：修改代码；改 PR 状态；把方案以外的改进建议作为通过条件；为本单元撰写实施方案或派单提示词；操作 auto-merge 或合并。
```
