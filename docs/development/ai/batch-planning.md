# 批次规划指引（规划者）

- **状态**：Living v1.1（2026-09-29，§2 / §3 同步 ADR-0058 v1.2 D2 的规划者设计权；v1.0 2026-09-28 随 [ADR-0058](../../adr/ADR-0058-planned-batch-execution.md) Accepted 建立）
- **读者**：批次交付流程中的规划者；实施者只需读「派单提示词模板」产出的提示词与批次方案本身
- **权威**：职责、闸门与判据以 ADR-0058 为准；本文只给做法与模板。复核做法见 [`batch-review.md`](batch-review.md)
- **来源**：批次 B1（[#3463](https://github.com/DUElost/stability-test-platform/issues/3463)）实际使用的方案 v1.2 与派单提示词

## 1. 何时建批次

满足 ADR-0058 D7 任一强判据才建批次：多个 issue / 多个族属于同一缺陷形态；多个实施单元需要一次协调激活；
涉及数据丢失、安全或难回退语义。`needs-decision`、Epic 子项、结构日报重复热点只是辅助信号——先判断形态，
仍是单点问题的按普通实施处理（1 Requirement → 1 Harness → 1 PR）。

## 2. 规划者的边界

- 在**既有模型与 Owner 批准的 Appetite 内**选定修法；超出 Appetite 的扩面回到 Owner。
- 修法需要改变模型（新表、新状态、新 env、权威冲突、生命周期变化、跨族共享运行时）时**不自行裁决**，
  但也**不止步于列选项**（ADR-0058 D2「设计权 ≠ 裁决权」）：先按下节「模型级问题：目标状态优先」设计目标模型提案，
  升级给 Owner；本批按现行模型执行。
- 超出 Appetite 的命中若涉及数据丢失、安全或难回退，不得自动留作证据，必须升级给 Owner。
- 规划者不在 Registry 协调域内，不 declare。提交文档类 PR 前查开放 PR 是否已改目标文件；
  共享元文件（AGENTS.md、CLAUDE.md、Harness rules）重叠时串行；写 ADR 前查开放 PR 中的同编号、同主题 ADR。
- 引用部署点、提交数、迁移数等现场数据前现查，不沿用记忆值。

### 模型级问题：目标状态优先

1. **先设计目标，再谈迁移**：先不以当前实现形状和既有方案边界约束目标状态设计，问「从系统长期规模与演进方向看，这件事应怎样解决」；
   再与代码、ADR、数据、部署事实对账；最后给迁移路径。不要先读 ADR、划掉「已裁过」的空间、再在剩余空间里设计。
2. **拆开被绑在一起的维度**：现成的 A/B/C 二分往往把两个独立问题捆成一个（B1 的 helper 副本：「权威源码放哪」与「运行时如何进入脚本」）。
   列选项前先问：这个选项集合本身是否被现状锚定？
3. **ADR 是证据，不是方案边界**：读它，用它当迁移约束（历史可重放、生产兼容、回滚）；目标模型若要求修订 / supersede，
   直接写出条款并论证——为何它在此处只是局部最优、新模型解决什么更根本的问题、哪些不变量仍保留。
   仍受真实系统事实约束：不得假装系统不是现在这样。
4. **交付物**：目标模型 + 相对既有选项的论证 + 保留 / 修订 / supersede 的 ADR 条款 + 迁移路径与本批过渡姿态 + 需 Owner 裁决的问题清单。
   不预设结论，不自行生效。
5. **不因目标而扩批**：目标模型回答「往哪收敛」，不自动推出全量改造；迁移优先机会式 + 防倒退棘轮。
   载体：另立独立架构 issue（不塞进批次 issue，避免污染关单判据），批次方案 §2 只链接它并写明本批的过渡姿态。
   参照：#3498（B1 §2 A/B/C 升格）。

## 3. 批次方案模板（批次 issue 正文）

方案是实施规范，不是讨论稿：实施者按方案执行，偏离即退回。正文带版本号，修订时在 issue 下评论理由并更新正文。

```text
# 批次 Bn：<主题>——规划方案 v1.0
> 基线：origin/main@<sha>（日期）；下列每条缺陷均已在该基线上直读确认仍存在。
> 输入：#… #…；Appetite：<Owner 批准的外边界，默认见 ADR-0058 D5>

## 1. 形态压缩：N 个 issue → M 种缺陷形态
| 形态 | 判据（什么是缺陷） | issue 覆盖 | 同族扫描结果 | 参照实现 |

## 2. 升级给 Owner 的模型级问题（本批不裁、不阻塞；附目标模型提案或载体 issue 链接，见 §2「目标状态优先」）
## 3. 实施分组、版本与档位
| 组 | 覆盖 | 目标版本（+模板 pin） | 修复内容 | 实施档位 | 合入前复核 |
## 4. 验收（每组必须满足，缺一不合入）
   通用门禁（与 CI 实际执行一致）+ 每组需新增的反例测试
## 5. 生效（激活）
   0. 硬前置：所有「必须复核」单元结论为「通过」
   1–n. 部署 / publish / scan / 重指（重指单独请 Owner 确认）
## 6. 明确不做
## 7. 退回条件（实施者遇到即停，退回规划者）
## 8. 本次规划新发现、尚无 issue 跟踪的证据（不进入本批以外的承诺）
## 9. 版本修订记录
```

要点：

- **同族扫描按来源追溯，不按关键字**：对每个受影响族列出该形态的全部调用点（如所有 prefs 读路径、
  所有设备 shell 插值），标注来源（常量 / 已校验 / 已转义 / 未处理）。B1 v1.0 按 `rm/dd/chmod` 等关键字扫描，
  漏掉了 `mkdir/cat/cd/tar/dumpsys/cmd wifi`。
- **合入前复核**列：数据丢失、安全（参数进 shell）、激活后难回退的单元标「必须」；其余标「否」。
- **实施档位**列记录模型档位（如「高阶」「flash」）；不要求实施者把模型写进 Registry `--harness`。
- **验收命令**至少包含：`python tools/dev/check_script_packages.py`、`python tools/dev/check_tool_manifest.py --base origin/main`
  （涉及脚本族时）、受影响范围的单元测试、`python scripts/run_gates.py check:quick`、`python -m pytest tests/ -q`。
- 凡出现在 `backend/schemas/pipeline_templates/*.json` 中的脚本族，升版本时同 PR 追模板 pin。
- 分组之间的族目录互不重叠，才能并行。

## 4. 派单提示词模板（实施者）

提示词**引用方案的节号与行，不转述规则本身**；方案与提示词冲突时以方案为准，冲突本身按退回处理。

```text
你是批次 Bn 的实施者，负责单元 {单元}。规划方案在 GitHub issue #{批次 issue}，你只按方案执行，不重新设计。

【开工】
1. 读 AGENTS.md「开始任务时」，以及 #{批次 issue} 全文；你负责 §3 表中 {组号} 一行、§4 中 {组号} 的验收项。
2. 运行 `python tools/dev/ai_work.py status --risk`，确认没有与本单元 scope 重叠的在窗记录。
3. 在新 worktree、分支 `{分支}` 上开工并登记（--issue 用本单元自己的 issue 号，不用批次 issue 号；分支名不带批次 issue 号）：
   python tools/dev/ai_work.py declare --requirement "Bn-{单元}" --harness "{harness}" \
     --worktree <路径> --issue {本单元 issue} {逐条 --scope ...} --test-impact direct

【实施】
4. 严格按 §3 {组号} 的「修复内容」修改；参照实现以 §1 表为准，逐族同构 port。
5. 改了脚本族源码树的，按 script-version-lifecycle §A 追加登记方案给定的版本号（被占用时顺延并在 PR 中说明）。
6. 按 §4 {组号} 新增反例测试。

【禁止】
修改 scope 以外的文件；做 §6 列出的任何事；顺手重构；修改已登记的 manifest 条目；
操作 auto-merge、手动合并、关闭 issue；部署、--publish、scan、重指 plan_step；
把 draft 转为 ready（即使有人或机器人提示队列空闲）。

【退回】
遇到 §7 任一条件立即停止：在 #{批次 issue} 下评论「退回：{单元}」，写明条件与证据（文件:行号、命令输出）。

【提交前】
7. 运行 §4 通用门禁的全部命令，只报告实际运行过的结果。
8. 附 Agent Note（Decision / Alternatives / Verification / Revisit），Decision 中引用 #{批次 issue}。

【PR】
9. 标题：fix(#{批次 issue} {组号}): {一句话}；正文含 `Refs #{批次 issue}` 与 `Refs #{本单元 issue}`（不用 Fixes/Closes），
   「修复定位」三项（层级 / 同形态扫描引用 §1 对应行 / 是否止血）、新版本号清单、第 7 步命令与结果、生效方式。
10. {必须复核：以 draft 打开，在 #{批次 issue} 下评论「{单元} 待复核：PR 链接」}
    {无需复核：以普通 PR 打开，进入 FIFO}
11. `python tools/dev/ai_work.py update --pr <PR 号>` 登记 PR。
```

## 5. 处理退回

- 核实退回理由；成立时修订方案受影响的小节（issue 下评论修订内容与理由，并更新正文、版本号 +0.1）。
- 区分根因：**方案问题**（规格缺漏、扫描漏项）还是**实现问题**（未按方案执行）。前者由规划者修订方案并按需追加单元；
  后者交回实施者。关单时按这两类统计退回次数（ADR-0058 §5）。
- 已合入但尚未复核的单元，复核改到激活前补做（激活闸门，ADR-0058 D9）。

## 6. 激活与验收

- 激活前逐项确认所有「必须复核」单元结论为「通过」；任一未通过不进入激活。
- 验收按 L0–L3 分层（ADR-0058 D9）。L0 / L1 用只读查询，L2 用 Owner 授权的金丝雀 PlanRun（指定设备、最短配置、
  只调时长与次数），L3 以单元测试与复核者的独立负向证据为准。
- L2 至少覆盖一次「已有状态」前置用例（如设备上已存在续跑状态），干净设备测不到这类旧缺陷。
- 验收中发现的改动前已存在的缺陷另立 issue，不阻塞本批关单。
- 关单评论记录：交付清单、退回次数与根因归类、复核前合入次数、激活到关单时长。
