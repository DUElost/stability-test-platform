# 契约类文档与 SOP 的写作约定

> **最后更新**：2026-10-09
> **决策出处**：[ADR-0059](../adr/ADR-0059-contract-and-sop-writing-conventions.md)（Accepted v1.0）。
> 为什么这样定、备选方案与复议条件见 ADR；本文只写怎么写。

本文的规则句按 §3 书写：只用「必须 / 不得 / 建议 / 可以」，并写出执行者。
本文中的「作者」指写或改文档的人或 Agent，「复核者」指审 PR 的人或 Agent。

## 1. 适用范围

本约定只适用于下列文档中**新写或改动的句子**：

| 类别 | 文档 |
|---|---|
| 契约类 | 根目录与子目录的 `AGENTS.md`；[`ai/execution-contract.md`](./ai/execution-contract.md) 及其附录；ADR 的「决策」节；`docs/design/*-contract.md` |
| SOP 类 | `.claude/skills/*/SKILL.md`；`docs/operations/` 下的流程文档（`incident-*` 事故记录除外）；`docs/` 根目录下的 runbook 与 checklist |

- 本约定不适用于 ADR 的背景与备选节、`docs/reviews/`、`docs/notes/`、`docs/archive/`、代码注释和对话输出。
- 作者不得为满足本约定改写同一文件中未触碰的句子。存量迁移只能另立批次（ADR-0058 流程）。
- 作者不得因本约定改写 `AGENTS.md`「硬不变量」节的原文：它由 S11 锚点逐字固定，强度按节级声明处理（§3.3）。

## 2. 术语

1. 已有推荐名的概念，作者必须只用推荐名。现有对照表：

   | 领域 | 对照表 |
   |---|---|
   | 存储与部署角色（控制面、中心存储、Agent host 等） | [`design/2026-storage-roles-and-aliases.md`](../design/2026-storage-roles-and-aliases.md) |
   | 设备日志链（采集、主机汇总、控制面 merge、dedup 等） | [`design/2026-log-chain-global-semantics.md`](../design/2026-log-chain-global-semantics.md) §4 |
   | 两个 `lifecycle`（Execution 生命周期 / `pipeline_def.lifecycle`） | [`ai/execution-contract.md`](./ai/execution-contract.md) 开头说明 |
   | 界面「任务」与 PlanRun | [`design/05-data-model.md`](../design/05-data-model.md) PlanRun 节 |

   反引号内的代码标识符不受此限。
2. 一个词可能指多个概念，且误读会改变规则的解释或操作的结果时，作者必须加限定语写明指哪一个。
   SOP 的步骤和 skill 的 `description` 一律按「会改变操作结果」处理。误读不改变结果时，作者建议写明。

   | 不写 | 写 |
   |---|---|
   | 任务卡死 | PlanRun 卡死 / SAQ 任务积压 |
   | 定时任务（指操作系统定时器时） | systemd timer / cron |
   | 下线（指主机或设备时） | 退役（ADR-0038 / ADR-0057 定义的状态）或离线（心跳意义上） |

3. 只有出现实际歧义（被误读、复核发现、造成事故），或一个词跨边界使用（用作界面文案、API 或数据库值、
   跨文档契约）时，作者才可以新增对照条目。条目必须写进该概念的 owner 文档，沿用
   「推荐名 | 合法别称 | 不要当成」格式，并把该文档加进第 1 条的表。作者不得新建中心术语表。
4. 对照条目只决定用哪个词，作者不得在对照条目里写定义；含义由 owner 文档的正文定义。
5. 别称在适用范围的文档中已不再出现、且对阅读历史文档也没有帮助时，owner 可以删除该条目。
   作者不得改写 `docs/notes/`、`docs/reviews/`、`docs/archive/` 的原文。
6. 数据库值、API 枚举、审计类型、事件类型、指标标签等机器契约字符串不归本约定管，
   沿用规范值 + 别称表 + 读写守卫（`backend/core/audit.py` 的 `AUDIT_RESOURCE_TYPE_ALIASES` 与
   `backend/tests/test_audit_read_side_alias_guard.py`）。

## 3. 规则句的强度词

| 级别 | 规则句只用 | 含义 | 规则句里不再用 |
|---|---|---|---|
| 要求 | 必须 | 不做即违规 | 须、需要、应、应当、务必 |
| 禁止 | 不得 | 做了即违规 | 禁止、严禁、不要、不用、不应 |
| 推荐 | 建议 | 不照做也合规；偏离会影响契约的解释或执行时，作者必须在同处写明理由 | 推荐、宜 |
| 允许 | 可以 | 做或不做都合规 | 可、允许 |

1. 规则句的结构是「执行者 +（条件）+ 强度词 + 动作」，一句只写一条规则。执行者用固定角色名，
   例如 Owner、规划者、实施者、复核者、Agent、作者。

   | 不写 | 写 |
   |---|---|
   | 实施者不重新设计 | 实施者不得重新设计方案 |
   | 不要直推或手动 Merge | 任何人不得直推 main，也不得手动 Merge |
   | 执行前需要授权 | 执行者必须先确认当前 Requirement 明确授权写入 |

2. 「不能」「不可」「无法」只表示做不到，不表示禁止。「需要」只表示依赖，例如「运行测试需要 PG」。
3. 清单式规则可以在节标题或导语中统一声明强度（例如「以下各条均为要求」），条目内不再重复强度词。
4. SOP 的编号操作步骤按 §4 写成祈使句，步骤里可以省略「执行者 + 必须」，强度由流程的节级声明承载
   （「按顺序执行以下步骤」即要求级）。步骤之外的独立约束、禁止事项和条件性规定按本节第 1 条书写。

## 4. SOP 步骤

1. 一步只写一个动作。只有必须同时完成的动作，才写进同一步。
2. 条件写在动作前面：「如果 X，……」。停止条件单独写成一步。
3. 警告单独成段，放在它保护的步骤之前，写明不得做什么、做了的后果。
4. 用祈使句，以动作开头。执行者不是读者本人时，写出执行者。
5. 会改变状态的步骤后写「预期：」，给出能核对的结果（行数、状态值、输出）。
6. 「确认 X」「检查 X」类步骤必须写出查法：命令、查询语句或页面。作者不知道查法时，必须标出缺口
   并交给该领域 owner 补，不得代编命令。

样板：

```markdown
适用条件：<一句话：什么情况下用本流程>

> 警告：<本流程的总体风险与授权要求>

按顺序执行以下步骤：

1. <动作>（命令或查询）。
   预期：<可核对的结果>
2. 如果 <条件>，停止本流程，改走 <其他流程>。

> 警告：下一步 <只改什么>。不得 <做什么>。<做错的后果>。

3. <动作>。
   预期：<可核对的结果>
```

## 5. 自查与复核

作者提交前、复核者审 PR 时，只核对**本次新写或改动的句子**：

- [ ] 已有推荐名的概念用了推荐名；会改变结果的多义词带了限定语（§2）
- [ ] 规则句只用必须 / 不得 / 建议 / 可以，写出了执行者；「不能」「需要」没有被当作规则用（§3）
- [ ] SOP：一步一个动作，条件在前，警告在被保护的步骤之前，状态变更有「预期：」，检查步骤有查法（§4）
- [ ] 新增的对照条目有实际歧义或跨边界的证据，写在 owner 文档里，没有写定义（§2.3、§2.4）

本约定没有 CI 门禁或自动检查；执行靠作者自查和复核者核对（ADR-0059 D5）。
