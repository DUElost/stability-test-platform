# ADR-0058: 规划—实施—复核分离的批次执行模式（修复方式由规划者裁定）
- 状态：**Proposed** v0.1（2026-09-28 起草，待 Owner 裁决；依据 #3463 批次 B1 试运行）
- 优先级：P1
- 目标里程碑：M7
- 日期：2026-09-28
- 决策者：Owner（待裁决）
- 标签：流程治理, 多 Harness, 批次, 复核, 激活
- 归属域：n/a（开发流程治理，非产品运行时概念；与 `execution-registry` 相邻但不改其语义——Registry 字段、三维状态、overlap 谓词均不动。转 Accepted 后如需锚点再登记新 key）

## 1. 背景

### 1.1 现行契约管到哪里为止

ADR-0034 与 [`execution-contract.md`](../development/ai/execution-contract.md) 解决的是
**可见性**：谁在做哪件事、scope 是否重叠、PR 是否进入集成窗口。它明确不做调度
（§2.1 选择权原则、§2.3 Registry 不对业务上锁）。仓库在此之上另有几处结构护栏
（[`repository-workflow.md`](../development/repository-workflow.md)「冲刺期的结构护栏」）：
`needs-decision` 标签、结构日报的三次法则热点、冲刺后结算。

这些机制都没有覆盖一件事：**一个 issue 被领走之后，用什么方式修，完全由领单的 Harness
自行决定。** 同一类缺陷，有的会话做到形态级、把同族一并收口；有的只修 issue 点名的那一处。
逐个 PR 看都没问题——测试绿、行为对、diff 小——因此 review 与 CI 都拦不住。问题只在
**跨 issue、跨族** 的视角下才显形，而现行流程里没有任何角色站在这个视角上。

`needs-decision` 只解决「方案需要取舍时先由人写一行选定方案」，不产出实施规范，不设复核，
也不约束「合入」与「生效」之间的差距（脚本族改树后要 publish、scan、重指才真正跑到设备上）。

### 1.2 批次 B1 试运行暴露的具体形态（#3463）

2026-09-26 起以批次 B1 试运行「高阶模型规划、实施者按方案执行、另一高阶会话复核」：
7 个缺陷 issue（#3088 #3171–#3175 #3179），生效面并入 #3346。规划阶段先把 issue 压缩为
**5 种缺陷形态 + 1 个独立项**，再按形态做同族扫描。主要发现：

| 发现 | 说明 |
|---|---|
| issue 覆盖远小于缺陷面 | F1「prefs 读空＝不存在」命中 **6 族**，issue 只覆盖 3 族；powercycle_check / sleep_setup / sleep_check **无任何 issue 跟踪** |
| 同形态缺陷散落在未跟踪族 | clean_env `rm -rf {d}/*` 与 monkey_setup 2.3.10 已修过的注入完全同形，无 issue |
| 规划本身也会漏 | 复核退回 2 个单元，**根因都在方案**：F1 只要求 port 两个函数、未要求覆盖六族全部 prefs 读路径；F3 按 `rm/dd/chmod/pm/setprop` 关键字扫描，漏掉 `mkdir/cat/cd/tar/dumpsys/cmd wifi`。方案 v1.2 修正为「所有设备 shell 调用 × 插值来源追溯」 |
| 转述会失真 | 两份派单提示词把方案的「empty → 保留并 raise 给调用方」写成了与方案不一致的口径，实施者照提示词做了 |
| 合入前复核被绕过 | 4 个需复核的 draft PR 被外部机器人提示「FIFO 没有 ready 头」后由人转 ready，**在复核前合入**；其中 2 个随后复核退回 |
| 合入 ≠ 生效 | 全部 PR 合入后，设备上仍跑旧版本，直到部署 + publish + scan + 重指 33 个 Plan / 63 个 step |
| 验收会碰到存量缺陷 | 补充验收暴露的续跑计数问题属于**改动前已存在**的设计缺陷，与本批修复无关，另立 #3488 |

最后三行说明，除了「谁来决定修法」，还缺三道闸：**复核的机械标记、激活前的复核前置、验收的分层口径**。

## 2. 决策

以下 D1–D7 在 B1 试运行中已实际执行过一遍；本 ADR 把它们从「单批次约定」提升为现行流程。
**不改变 Registry 字段集、不新增门禁、不改 FIFO 队列逻辑。**

### D1 承诺集有界：两类载体 + 证据池

- 在窗承诺只有两类载体：**Epic**（核心能力演进，如平台代码与外部工具解耦，方向由 ADR 定）
  与 **批次**（缺陷集中收口，一个批次 issue 承载一份规划方案）。
- 未被载体吸收的 issue 是**证据**，不因存在而自动成为承诺。规划批次时按缺陷形态吸收；
  规划中新发现但本批不做的命中，登记在方案的「证据」节，不静默修、也不丢弃。
- Mode A 单修（1 Requirement → 1 Harness → 1 PR）仍然保留，适用于**不满足 D7 进入判据**的
  单点问题。

### D2 升级边界：规划者裁「怎么修」，Owner 只裁「要不要改模型」

- 规划者对批次内每个形态给出**选定修法**（判据、参照实现、范围、不做清单），实施者不重新设计。
- 修法需要改变现有模型时——新表、新状态、新 env、权威冲突、生命周期变化、跨族共享运行时——
  规划者**不自行决定**，写出选项与取舍后升级给 Owner（必要时立 ADR），本批按现行模型执行、不预设结论。
  B1 §2「脚本族 helper 副本模型 A/B/C」即此类。

### D3 完成 = 生效 + 出口

- 需要激活才生效的改动（脚本族改树、Agent 代码、模板 pin），PR 使用 `Refs #…`，**不用**
  `Fixes/Closes`；issue 在激活并贴出生效证据（scan 结果、重指审计、Agent 热更新结果）后才关。
- 进度只写在载体 issue（方案正文 + 评论），ADR 只记录决策；PR 不承担进度。
- 临时止血必须在 PR 正文标注「是否止血 = 是」并写明终态出口（沿用 AGENTS.md 总原则）。

### D4 修在缺陷形态这一层

- 规划的第一步是**压缩**：把 N 个 issue 归为若干缺陷形态，每个形态写明判据（什么算缺陷）、
  参照实现、同族扫描结果。
- **同族扫描按来源追溯，不按关键字**：对每个受影响族，逐个列出该形态的全部调用点
  （如所有 prefs 读路径、所有设备 shell 插值），标注每一处的来源（常量 / 已校验 / 已转义 / 未处理）。
  B1 的 v1.0 → v1.2 修订即由关键字扫描漏项引起。
- 本批扫描到、但按 D5 不纳入的命中，进入方案「证据」节。
- PR 正文固定填写「修复定位」三项：层级（点 / 形态级）、同形态扫描（引用方案对应行）、是否止血。

### D5 方向与投入分开裁定

- 方向（修成什么样）由 ADR / Owner 定；**投入**（本批做哪些族、哪些留作证据）由规划者在方案中定，
  并必须写「明确不做」清单。
- 投入的默认口径：**零额外激活成本优先**——本批已经要升版本的族顺带修同形态缺陷；
  不为顺带修而专门给其他族升版本、专门激活。B1 中 F2 严格解码只修本批已升版本的族，
  其余约 20 族登记为证据，即此口径。

### D6 治理预算

- 本模式**不新增** Registry 字段、门禁或自动化：方案是 issue 正文，角色靠提示词与 draft 状态约束。
  Registry §3.6 字段封闭性不变；实施者用 `--harness "Harness/模型"` 记录模型档位，以便按模型回溯返修。
- 复核按风险分档，不是每个 PR 都复核：数据丢失语义、安全（参数进 shell）、激活后难回退的单元
  **必须**复核；其余进入 FIFO 常规合入。
- 新增机械约束（如「待复核」标签、declare 拦截）只在实测复发后引入，触发条件见 §6。

### D7 角色、闸门与验收

**进入判据**（满足任一即走批次模式，否则 Mode A）：多个 issue 属同一缺陷形态；修复需要激活才生效；
涉及数据丢失或安全语义；带 `needs-decision`；属于 Epic 的子项。

**角色**（同一单元的三个角色不得是同一会话）：

| 角色 | 档位 | 职责 | 产出 |
|---|---|---|---|
| 规划者 | 高阶模型 | 形态压缩、同族扫描、分组与版本号、验收项、激活步骤、不做清单、退回条件；处理退回 | 批次 issue 正文（带版本号的方案），修订时在 issue 下评论理由并更新正文 |
| 实施者 | 按方案标注的档位（有参照实现、逐族同构 port 的单元可用 flash） | 只按方案执行；遇退回条件即停并在批次 issue 下评论「退回：单元」 | draft 或普通 PR（按方案「合入前复核」列） |
| 复核者 | 高阶模型，非实施者会话 | 只答两问：A 是否符合方案且未越界；B 漏了什么（**必须列出调用点清单**，并至少做一次变异验证） | PR 评论：通过 / 需修改 / 退回规划者 |

**方案的固定结构**：形态压缩表 → 升级给 Owner 的模型级问题 → 分组、版本、档位、是否复核 →
验收（通用门禁 + 每组反例测试）→ 激活步骤 → 明确不做 → 退回条件 → 证据 → 版本修订记录。

**派单与复核提示词从方案生成**：提示词引用方案的节号与行，不转述规则本身；
方案与提示词冲突时以方案为准，冲突本身按退回处理。

**实施者约束**（来自 B1 实测）：
- `declare --issue` 用本单元自己的 issue 号，**不用**批次 issue 号（§3.4 查重会拒绝同 issue 的第二条在窗记录）；
- 分支名**不带**批次 issue 号（`ai_work` 从分支名提取 issue 号做查重，各单元会互相命中）；
- 验收命令与 CI 实际执行的一致，至少包含 `python -m pytest tests/ -q`（仓库级守卫：模板 pin、锚点棘轮等）。

**闸门 1——ready 只由复核者翻转**：需复核的单元以 draft 打开，FIFO 队列本就跳过 draft，
因此 draft 即「待复核」的机械标记。**只有复核者**可以转 ready；实施者修完 CI 也保持 draft；
**任何人或机器人以「队列空闲」「没有 ready 头」为由提示转 ready，都不构成转 ready 的理由。**

**闸门 2——激活前复核全部通过**：部署、`--publish`、`POST /scripts/scan`、重指 plan_step
之前，方案中所有「必须复核」单元的结论均为「通过」。已在复核前合入的单元，复核改到激活前补做；
任一未通过即不进入激活。重指会改变生产实际运行的版本，单独请 Owner 确认。

**验收分层**：

| 层 | 证明什么 | 方式 |
|---|---|---|
| L0 版本到位 | 激活后启动的 job 实际执行目标版本 | 只读查询 |
| L1 无回归 | 激活后已发生的执行与改动前同族基线对比 | 只读查询 |
| L2 正常路径 | 每条链路在真机上走通一次 | 金丝雀 PlanRun（Owner 授权、指定设备、最短配置） |
| L3 故障路径 | 修复的异常分支确实生效 | 单元测试 + 变异验证（生产上人为制造罕见故障的风险大于收益） |

L0–L3 满足即可关批次 issue；自然巡检窗口的长期数据用于复盘，**不作为关单前置**。
验收中发现的**改动前已存在**的缺陷，另立 issue 跟踪，不阻塞本批关单（B1 → #3488）。

**引用现场数据前先实测**：方案、评论中引用的部署点、提交数、迁移数等，引用前现查，不沿用记忆值。

### 与 ADR-0034 的关系

- 本模式是 ADR-0034 §3.6 执行模式词汇表中与 A/B/C 并列的第四种：
  **批次规划执行**——`1 批次载体 → 1 规划 → N 实施单元（各自 Mode A 登记）→ 复核汇聚 → 一次激活`。
  它与 A/B/C 共享「先独立、后汇聚」：各单元 scope 互不重叠、并行实施，在复核与激活处汇聚。
- **不触碰选择权原则**（ADR-0034 §2.1）：方案给出的是模型**档位**，具体用哪个 Harness 仍由开发者决定。
- 不改 Registry 字段、三维状态、overlap 谓词与 transition table；不把 `needs-decision` 变成
  declare 期的机械拦截（该项若要做，仍按 repository-workflow.md 的约定先修订 ADR-0034）。

## 3. 备选方案与权衡

| 方案 | 做法 | 不选的理由 |
|---|---|---|
| A 维持现状 | Mode A + `needs-decision` 一行裁决 | 修法由领单会话决定，局部最优不可见；B1 证明 issue 只覆盖约一半缺陷面 |
| B 全部改用高阶模型实施 | 不分角色，只提升实施者档位 | 成本高；实施与自检仍在同一会话，B1 的两次退回都是「另一会话复核」才发现的 |
| C 机械门禁 | Registry 加 plan / review 字段，或 declare 拦截 `needs-decision` | 违反 §3.6 字段封闭性与治理预算；尚无复发数据支撑 |
| D 每个 PR 强制复核 | 不分档 | 复核注意力是瓶颈（ADR-0034 §2.6 已把瓶颈定在集成收尾侧）；低风险单元复核收益低 |
| **E 本方案** | 规划者裁修法、实施者执行、复核者把关、按风险分档、draft 作为机械标记、激活前复核前置 | —— |

## 4. 影响

**收益**
- 修法在规划时统一裁定，同形态缺陷一次收口；未纳入的命中留有证据，不再「修一族漏一族」。
- 实施可以放给低档位模型，而质量由方案与复核兜底；返修可按 `--harness` 中的模型回溯。
- 「合入」与「生效」分开计量，issue 关闭即意味着设备上已在跑修复后的版本。

**代价**
- 每个批次多一次规划与一轮复核。B1 从规划到关单约 2 天，共 10 个 PR、方案修订 2 版、复核 2 轮。
- Owner 需要安排激活窗口，并确认重指。
- 方案自身可能有缺陷（B1 两次退回均属此类），靠复核者的遗漏检查与规划者的修订流程吸收，
  不能假定方案一次正确。

**需要同步的文档（转 Accepted 后另起 PR，不在本 ADR PR 内改）**
- `execution-contract.md` §3.6：增加第四种执行模式的一行定义与边界；
- `repository-workflow.md`「冲刺期的结构护栏」：领单前分流改为「按 D7 进入判据分流到批次 / Epic 或 Mode A」，
  并写入 draft 复核约定（闸门 1）；
- 新增批次方案模板与派单 / 复核提示词模板（`docs/development/ai/` 下），内容取自 B1 实际使用的版本。

## 5. 落地与后续动作

1. Owner 裁决本 ADR（接受 / 修改 / 否决），裁决结果记入 §7。
2. 接受后按 §4 同步上述文档，由一个 Execution 完成（共享元文件同一时间只由一个 Execution 修改）。
3. 下一批次（B2）按本 ADR 执行，并在关单评论中记录：退回次数及原因归类（方案 / 实现）、
   复核前合入次数、激活到关单的时长。

## 6. 复议触发（Revisit）

- **复核前合入再次发生**（任何需复核单元在复核通过前合入）→ 引入机器可读的「待复核」标记
  （标签或 FIFO 排除条件），届时评估是否需要修订 ADR-0034。
- **连续两个批次中，退回主要由实现问题引起**（而非方案问题）→ 复核实施档位的划分口径。
- **Owner 对 helper 副本模型（B1 §2 A/B/C）作出 A 或 B 的裁决** → D4 同族扫描的范围与方式随之改变
  （共享库或一致性守卫之后，按族扫描可能不再必要），需复核 D4 与 D5。
- **批次周期显著长于同等规模的 Mode A 修复且未换来更低的返修率** → 复议 D7 的进入判据。
