## 1. 背景

### 1.1 现行契约管到哪里为止

ADR-0034 与 [`execution-contract.md`](../development/ai/execution-contract.md) 解决的是
**可见性**：谁在做哪件事、scope 是否重叠、PR 是否进入集成窗口。它明确不做调度
（ADR-0034 §2.1 选择权原则、§2.3 Registry 不对业务上锁）。仓库在此之上另有几处结构护栏
（[`repository-workflow.md`](../development/repository-workflow.md)「冲刺期的结构护栏」）：
`needs-decision` 标签、结构日报的三次法则热点、冲刺后结算。

这些机制都没有覆盖一件事：**一个 issue 被领走之后，用什么方式修，完全由领单的 Harness
自行决定。** 同一类缺陷，有的会话做到形态级、把同族一并收口；有的只修 issue 点名的那一处。
逐个 PR 看都没问题——测试绿、行为对、diff 小——因此 review 与 CI 都拦不住。问题只在
**跨 issue、跨族** 的视角下才显形，而现行流程里没有任何角色站在这个视角上。

`needs-decision` 只解决「方案需要取舍时先由人写一行选定方案」，不产出实施规范，不设复核，
也不约束「合入」与「生效」之间的差距（脚本族改树后要 publish、scan、重指才真正跑到设备上，
见 [`script-versioning.md`](../development/script-versioning.md) 的 `--pending-activation` /
`--plan-step-drift` 对账面）。

### 1.2 批次 B1 试运行暴露的具体形态（#3463）

2026-09-26 起以批次 B1 试运行「规划者出方案、实施者按方案执行、独立会话复核」：
7 个缺陷 issue（#3088 #3171–#3175 #3179），生效面并入 #3346。规划阶段先把 issue 压缩为
**5 种缺陷形态 + 1 个独立项**，再按形态做同族扫描。结项统计：10 个实施 PR、11 个脚本版本激活、
33 个 Plan / 63 个 step 重指、Agent 热更新 48/48；规划者缺陷 5 处，复核拦下 2 个真实漏洞与
1 处规格歧义，流程事故 1 次。主要发现：

| 发现 | 说明 |
|---|---|
| issue 覆盖远小于缺陷面 | F1「prefs 读空＝不存在」命中 **6 族**，issue 只覆盖 3 族；powercycle_check / sleep_setup / sleep_check **无任何 issue 跟踪** |
| 同形态缺陷散落在未跟踪族 | clean_env `rm -rf {d}/*` 与 monkey_setup 2.3.10 已修过的注入完全同形，无 issue |
| 规划本身也会漏 | 复核退回 2 个单元，**根因都在方案**：F1 只要求 port 两个函数、未要求覆盖六族全部 prefs 读路径；F3 按 `rm/dd/chmod/pm/setprop` 关键字扫描，漏掉 `mkdir/cat/cd/tar/dumpsys/cmd wifi`。方案 v1.2 修正为「所有设备 shell 调用 × 插值来源追溯」 |
| 转述会失真 | 两份派单提示词把方案中对读空的处理写成了与方案不一致的口径，实施者照提示词做了 |
| 合入前复核被绕过 | 4 个需复核的 draft PR 被集成观察机器人报告「FIFO 没有 ready 头」后由人转 ready，**在复核前合入**；其中 2 个随后复核退回。激活前补做复核吸收了这次事故 |
| 合入 ≠ 生效 | 全部 PR 合入后，设备上仍跑旧版本，直到部署 + publish + scan + 重指 |
| 验收会碰到存量缺陷 | 补充验收暴露的续跑计数问题属于**改动前已存在**的设计缺陷，与本批修复无关，另立 #3488 |

### 1.3 执行契约的角色假设与实际组织方式已经错位

执行契约写成时，规划、评审、审计都假设发生在**本地 Harness** 中，并通过 Registry 登记：
`execution-contract.md` §3.6 的执行模式词汇表把 Mode B（竞争探索：N 个 Harness 各出独立 Proposal，
汇聚后由人裁决落成 ADR）与 Mode C（并行审计：N 个独立评审、去重汇聚）与 Mode A（生产执行）并列；
[`harness-adapters.md`](../development/ai/harness-adapters.md) 要求「文档 / 评审类会话同样 declare」。
Mode C 曾真实运行（ADR-0038 的 9 份独立评审经 #1557 汇聚；语义归属、覆盖率审计的多份
`docs/reviews/*`）。

B1 起的实际组织方式已不同：规划在云端 Web 工作面进行，复核在另一个云端 Web 工作面进行，
开放 PR 与 FIFO 队列由一个机器人持续观察；只有**实施**仍发生在本地 Harness 的 worktree 中。
Registry（`tools/dev/ai_work.py`）只存在于宿主机本地，云端工作面既无法、也无需登记。
继续把规划与复核写成执行模式，只会留下一条执行不了的登记要求，并让执行契约回答它不该回答的问题
（谁规划、谁评审、谁决定值得做）。ADR-0034 v1.6 已有同类先例：不能独立完成 Execution 周期的工具
定性为「带规则的高级顾问」，不纳入可承接 Requirement 的 Harness 名单。

## 2. 决策

以下 D1–D10 中，D1–D9 的做法已在 B1 实际执行过一遍（v0.2 按评审收窄了边界），D10 是执行层的配套收窄。
**不新增 Registry 字段、不新增门禁、不改 FIFO 队列逻辑。**

### D1 承诺形态：Epic、批次、单点需求；开放 issue 不自动构成开发承诺

- **跨 issue / 跨单元**的计划级承诺只有两类载体：**Epic**（核心能力演进，如平台代码与外部工具解耦，
  方向由 ADR 定）与**批次**（缺陷集中收口，一个批次 issue 承载一份规划方案）。
- 单点、边界清楚且不满足 D7 强判据的问题，直接以原 issue 作为一次实施（1 Requirement → 1 Harness → 1 PR）的
  需求，这是第三种承诺形态。
- 开放 issue 的存在本身**不自动构成**上述任一开发承诺；在被选中之前，它作为问题、需求与证据池保留
  （其中可以是明确的缺陷、风险或外部要求，只是尚未排入当前承诺）。规划批次时按缺陷形态吸收；
  规划中新发现但本批不做的命中，登记在方案的「证据」节，不静默修、也不丢弃。

### D2 决策分层：Owner 定做不做、做多大；规划者定怎么修

| 谁 | 决定什么 |
|---|---|
| Owner | 批次或 Epic 是否值得做、何时做、**Appetite**（外边界，见 D5）；模型级变更；激活窗口与重指确认 |
| 规划者 | 在既有模型与 Appetite 内选定修法：判据、参照实现、范围、分组、版本号、验收、退回条件、不做清单 |
| 实施者 | 按方案执行，不重新设计 |
| 复核者 | 独立核对实施是否符合方案、有无遗漏 |

修法需要改变现有模型时——新表、新状态、新 env、权威冲突、生命周期变化、跨族共享运行时——
规划者**不自行决定**，写出选项与取舍后升级给 Owner（必要时立 ADR），本批按现行模型执行、不预设结论。
B1 §2「脚本族 helper 副本模型 A/B/C」即此类。

### D3 完成 = 生效 + 出口

- 需要激活才生效的改动（脚本族改树、Agent 代码、模板 pin），PR 使用 `Refs #…`，**不用**
  `Fixes/Closes`；issue 在激活并贴出生效证据（scan 结果、重指审计、Agent 热更新结果）后才关。
- 进度只写在载体 issue（方案正文 + 评论），ADR 只记录决策；PR 不承担进度。
- 临时止血必须在 PR 正文标注「是否止血 = 是」并写明终态出口（沿用 AGENTS.md 总原则）。

### D4 修在缺陷形态这一层

- 规划的第一步是**压缩**：把 N 个 issue 归为若干缺陷形态，每个形态写明判据（什么算缺陷）、
  参照实现、同族扫描结果。
- **同族扫描按来源追溯，不按关键字**：对每个受影响族，逐个列出该形态的全部调用点
  （如所有 prefs 读路径、所有设备 shell 插值），标注每一处的来源（常量 / 已校验 / 已转义 / 未处理）。
  B1 的 v1.0 → v1.2 修订即由关键字扫描漏项引起。
- 扫描到、但超出 Appetite 的命中，进入方案「证据」节。
- PR 正文固定填写「修复定位」三项：层级（点 / 形态级）、同形态扫描（引用方案对应行）、是否止血。

### D5 Appetite：Owner 定外边界，规划者在边界内定具体范围

- Owner 批准批次时同时批准其 **Appetite**——这批最多做到多大、愿意付出多少激活成本、什么情况必须停止扩面。
  规划者在 Appetite 内决定具体纳入哪些族、哪些留作证据，并必须写「明确不做」清单。
  超出 Appetite 的扩面，须回到 Owner 重新批准，不由规划者自行扩大。
- 缺陷收口批次的**默认 Appetite**（Owner 未另行指定时适用）：
  本批允许吸收「已经必须升版本的族」中的同形态缺陷；不为顺带修复而单独给其他族新增版本或激活；
  涉及模型级变更则退出本批并升级 Owner。B1 中 F2 严格解码只修本批已升版本的族、
  其余约 20 族登记为证据，即此口径。
- **高风险例外**：超出 Appetite 的命中若本身属于 D7 的数据丢失、安全或难回退语义，
  **不得**仅因「需要额外版本 / 激活」而自动留作证据；规划者须升级 Owner，由 Owner 明确决定
  扩大 Appetite，或接受延期风险并记录在方案中。默认 Appetite 只有裁掉普通命中的权限。

### D6 治理预算

- 本流程**不新增** Registry 字段、门禁或自动化：方案是 issue 正文，职责靠文档、提示词与 draft 状态约束。
- 实施者的模型档位记录在批次方案的分组表（「实施档位」列）与 PR 正文，**不写进 Registry `harness` 字段**——
  该字段按执行契约 §1.2 只记录承接的 Harness。模型档位是批次规划的证据，不是执行登记的元数据；
  若日后确需按档位统计返修率，另行裁决机器可读来源。
- 复核按风险分档，不是每个 PR 都复核：数据丢失语义、安全（参数进 shell）、激活后难回退的单元
  **必须**复核；其余进入 FIFO 常规合入。
- 新增机械约束（如「待复核」标签、FIFO 排除条件）只在实测复发后引入，触发条件见 §6。

### D7 何时走批次：强判据与辅助信号

- **强判据**（满足任一即走批次）：
  - 多个 issue 或多个族属于同一缺陷形态；
  - 多个实施单元需要一次协调激活；
  - 涉及数据丢失、安全或难回退语义，需要独立复核。
- **辅助信号**（提示需要先做形态判断，不自动进入批次）：带 `needs-decision`、属于 Epic 子项、
  结构日报的重复热点。由规划者或 Owner 判断后再决定是否升级为批次；判断后仍是单点问题的，按 D1 单点需求处理。

### D8 职责与工作面

职责按**工作面**划分，而不是按同一 Harness 里的不同提示词划分。规范只约束各职责必须满足的性质；
当前由哪个具体工具承担，写在 [`repository-workflow.md`](../development/repository-workflow.md)，更换工具不改本 ADR。

| 职责 | 必须满足的性质 | 进入 Registry | 权限边界 |
|---|---|---|---|
| 规划者 | 与实施者不同工作面；能读仓库、issue、PR 与生产只读证据 | 否 | 产出批次方案（批次 issue 正文）并处理退回；可提交文档类 PR（ADR、方案、流程文档）；不写实施代码 |
| 实施者 | 属于 Registry 协调域（现阶段即本地 Harness，在宿主机 worktree 中执行） | **是**（ADR-0034 现行语义，无任何改变） | 按方案修改仓库、测试、开 PR；遇退回条件即停 |
| 复核者 | 与实施者**不同工作面、不同上下文**；不得是实施该单元的会话 | 否 | 在 PR 下给出「通过 / 需修改 / 退回规划者」；不改实现，不改 PR 状态 |
| 集成观察者 | 自动化观察开放 PR、FIFO 队列与 CI | 否 | 只观察与报告事实；**无** ready、合入、方案或复核结论的决定权 |
| Owner | 人 | 否 | D2 所列决定；需复核单元的 draft → ready 翻转 |

**规划者**：
- 方案固定结构：形态压缩表 → 升级给 Owner 的模型级问题 → Appetite → 分组、版本、实施档位、是否复核 →
  验收（通用门禁 + 每组反例测试）→ 激活步骤 → 明确不做 → 退回条件 → 证据 → 版本修订记录。
- 派单与复核提示词**从方案生成**：引用方案的节号与行，不转述规则本身；方案与提示词冲突时以方案为准，
  冲突本身按退回处理。
- 提交 ADR 时仍遵守执行契约 §3.5 的纪律 2、3：落笔前查开放 PR 中的同编号、同主题 ADR，
  同一主题不得出现第二份权威 ADR。其他仓库写入遵守 D10-3 的写冲突纪律。

**实施者**（来自 B1 实测）：
- 每个实施单元沿用 ADR-0034 / 执行契约的现行生产实施语义：1 Requirement → 1 Harness → 1 PR，
  Harness 由开发者选择（ADR-0034 §2.1 选择权原则不变）；
- `declare --issue` 用本单元自己的 issue 号，**不用**批次 issue 号（§3.4 查重会拒绝同 issue 的第二条在窗记录）；
- 分支名**不带**批次 issue 号（`ai_work` 从分支名提取 issue 号做查重，各单元会互相命中）；
- 验收命令与 CI 实际执行的一致，至少包含 `python -m pytest tests/ -q`（仓库级守卫：模板 pin、锚点棘轮等）。

**复核者**只回答两问：
- A：是否符合方案、且没有越界；
- B：漏了什么——**必须列出**该形态在受影响范围内的调用点清单，并提供独立的负向证据。
  负向证据优先用可逆的变异验证（临时回退修复点，测试应变红，再恢复）。变异不适用或风险过高时写明原因，
  并给出等价证据：配置契约类篡改 fixture 后守卫应红，部署步骤类做 dry-run 或旧基线对照，文档流程类做事实对账。

**集成观察者**：「队列里没有 ready 的 PR」是集成状态，不是复核状态，
**不构成把任何 draft 转为 ready 的理由**。观察者的报告中不得建议翻转 draft。

### D9 流程约束、激活闸门与验收

**流程约束——待复核单元保持 draft**：需复核的单元以 draft 打开；FIFO 队列本就跳过 draft，
因此 draft 是「待复核」的可见标记。复核者在 PR 下评论「通过」后，**由 Owner 转为 ready**；
实施者修完 CI 也保持 draft。draft 状态本身不是安全边界：复核前合入属于**流程违规，但可恢复**——
复核改到激活前补做。

**激活闸门（安全边界）**：部署、`--publish`、`POST /scripts/scan`、重指 plan_step 之前，
方案中所有「必须复核」单元的结论均为「通过」；任一未通过即不进入激活。**复核前激活不允许发生。**
重指会改变生产实际运行的版本，单独请 Owner 确认。

**验收分层**：

| 层 | 证明什么 | 方式 |
|---|---|---|
| L0 版本到位 | 激活后启动的 job 实际执行目标版本 | 只读查询 |
| L1 无回归 | 激活后已发生的执行与改动前同族基线对比 | 只读查询 |
| L2 正常路径 | 每条链路在真机上走通一次 | 金丝雀 PlanRun（Owner 授权、指定设备、最短配置） |
| L3 故障路径 | 修复的异常分支确实生效 | 单元测试 + 复核者的独立负向证据（生产上人为制造罕见故障的风险大于收益） |

L0–L3 满足即可关批次 issue；自然巡检窗口的长期数据用于复盘，**不作为关单前置**。
验收中发现的**改动前已存在**的缺陷，另立 issue 跟踪，不阻塞本批关单（B1 → #3488）。

**引用现场数据前先实测**：方案、评论中引用的部署点、提交数、迁移数等，引用前现查，不沿用记忆值。

### D10 执行契约收窄：只保留实施执行，Registry 只登记其协调域内的实施者

本 ADR 同时作为对 ADR-0034 / 执行契约的一次裁决（改变现行执行语义，须由 ADR 正式裁决）：

1. **退役执行模式词汇**：`execution-contract.md` §3.6 删除 Mode B（竞争探索）与 Mode C（并行审计）；
   只剩一种执行模型后，「Mode A」的名称也一并取消，§3.6 改为「生产实施是唯一执行模型：
   1 Requirement → 1 Harness → 1 PR」。字段封闭性条款（Registry 是 execution coordination metadata，
   不是 reasoning memory）保留。
2. **Registry 的适用面**：Registry 只登记**属于其协调域的实施 Execution**。当前实现的协调域是
   宿主机上同一克隆的本地 Registry（执行契约 §2.1：Registry root 位于 `git-common-dir` 下、按克隆隔离、
   仅限本地文件系统），因此现阶段等价于「本地 Harness 中的实施者」。划界依据是能否参与该协调域，
   不是进程运行在本机还是云端：日后若有远程实施环境接入同一协调域，按实施者登记，无需修订本 ADR。
   规划者、复核者与集成观察者所在的云端 / Web 工作面不属于该协调域，不 declare。
   `harness-adapters.md`「文档 / 评审类会话同样 declare」收窄为：仅适用于协调域内进行的文档 / 评审类修改。
   （v1.1 落地注：实际落地为「本地 Harness 中修改仓库文档并开 PR 的会话 declare，纯 issue 评论 / PR 评审不登记」，见 §5。
   这比原文「协调域内进行的文档 / 评审类修改」更窄：本地 Harness 中的纯评审会话也不再登记。实际影响很小——
   ADR-0034 §2.6 早已规定无 PR 的评审 / scratch 会话不计入约束；这一收窄随 #3492 提交 Owner 确认。）
3. **协调域外仓库写入的冲突纪律**：协调域外工作面（当前主要是规划者提交的 ADR、方案与流程文档 PR）
   不进入 Registry，其写冲突可见性由 GitHub 开放 PR 承担：
   - 开始修改仓库文件前，必须检查开放 PR 是否已修改目标文件；
   - 共享元文件（AGENTS.md、CLAUDE.md、Harness rules）发生重叠时串行，不并行落笔；
   - 本条只补协调域之外的写入可见性，不把这些工作面重新定义为 Execution。

   由此，协调域内的实施重叠由 Registry + Git 暴露，协调域外的文档重叠由开放 PR + Git 暴露，最终以 Git 为准。
4. **§3.5 的处理**：决策类 Execution 的 `--issue` 纪律（纪律 1）继续适用于协调域内实施者写 ADR 的情形；
   纪律 2、3 同时约束规划者（见 D8）。其「N Harness → N Proposals」表述随 Mode B 退役改为历史说明：
   需要多份独立提案或独立审计时，由规划者 / 复核者工作面组织，汇聚结论仍须落成唯一一份 ADR 或新的需求。
   （v1.1 落地注：§3.5 实际改写为「可见性双通道」——协调域内 Registry + §3.4 查重、协调域外开放 PR 查重，同受纪律 3 约束，
   比「改为历史说明」更进一步，方向与本条一致，见 §5。）
5. **不变的部分**：Registry 字段集、`role` 字段（仍为默认 `implementation` 的无语义元数据，本轮不动）、
   三维状态、overlap 谓词、transition table、§3.4 查重、ADR-0034 §2.1 选择权原则。
6. **历史记录不回改**：已按 Mode C 完成的评审与汇聚（#1557、`docs/reviews/*`、相关 Agent Note）保留原文，作为历史。

### 与 ADR-0034 的关系

ADR-0058 位于 ADR-0034 **上游**：它定义批次交付流程（规划 → 实施单元 → 独立复核 → 激活 → 验收），
其中只有实施单元属于 ADR-0034 管辖的 Execution。批次不是新的执行模式，而是若干次普通实施之上的编排；
ADR-0034 无需知道规划者与复核者的存在。

| 层 | 回答什么 | 权威 |
|---|---|---|
| 交付治理 | 做什么、做多大、怎么修、谁复核、何时激活 | ADR-0058、`repository-workflow.md` |
| 执行协调 | 谁在实施、改哪里、是否撞车、PR 处于什么状态 | ADR-0034、`execution-contract.md` |
| 仓库集成 | 什么进入 `main` | CI、FIFO 队列、集成观察 |

## 3. 备选方案与权衡

| 方案 | 做法 | 不选的理由 |
|---|---|---|
| A 维持现状 | 单点实施 + `needs-decision` 一行裁决 | 修法由领单会话决定，局部最优不可见；B1 证明 issue 只覆盖约一半缺陷面 |
| B 全部改用高阶模型实施 | 不分职责，只提升实施者档位 | 成本高；实施与自检仍在同一会话，B1 的两次退回都是另一工作面复核才发现的 |
| C 机械门禁 | Registry 加 plan / review 字段，或 declare 拦截 `needs-decision` | 违反字段封闭性与治理预算；尚无复发数据支撑 |
| D 每个 PR 强制复核 | 不分档 | 复核注意力是瓶颈（ADR-0034 §2.6 已把瓶颈定在集成收尾侧）；低风险单元复核收益低 |
| E 批次作为执行契约的 Mode D（v0.1 写法） | 在 §3.6 与 A/B/C 并列 | 批次内每个单元本来就是普通实施；新增模式等于改执行契约词汇表，却不带来任何新的登记语义 |
| F 保留 Mode B / C | 规划、评审继续按执行模式在本地 Harness 中登记 | 规划与复核已迁到无法访问本地 Registry 的工作面；保留只会留下执行不了的登记要求 |
| G 本轮同时退役 `role` 字段 | 删除字段 | 字段已无语义，删除要动 schema 与历史记录，当前没有收益；留作复议项（§6） |
| **H 本方案** | Owner 定 Appetite、规划者裁修法、实施者执行、独立工作面复核、draft 作为可见标记、激活前复核为安全边界；执行契约只保留实施执行 | —— |

## 4. 影响

**收益**
- 修法在规划时统一裁定，同形态缺陷一次收口；未纳入的命中留有证据，不再「修一族漏一族」。
- 实施可以放给低档位模型，而质量由方案与独立复核兜底。
- 「合入」与「生效」分开计量，issue 关闭即意味着设备上已在跑修复后的版本。
- 执行契约回到单一职责，去掉一条在云端工作面上执行不了的登记要求。

**代价**
- 每个批次多一次规划与一轮复核。B1 从规划到关单约 2 天，共 10 个 PR、方案修订 2 版、复核 2 轮。
- Owner 需要批准 Appetite、翻转需复核单元的 ready、安排激活窗口并确认重指。
- 方案自身可能有缺陷（B1 两次退回均属此类），靠复核者的遗漏检查与规划者的修订流程吸收，
  不能假定方案一次正确。
- 云端规划者提交的文档类 PR 不在 Registry 中，只靠开放 PR 可见；与本地执行者改同一文件时，
  冲突在 PR 层面暴露与解决。

**需要同步的文档（按原计划在 ADR PR #3489 之外另起 PR 完成：#3490 落地 Accepted 状态与下列同步；实际落地内容以 §5 为准）**
- `execution-contract.md`：§3.6 按 D10-1 改写；§2.1 或 §3.6 写明 D10-2 的协调域划界与 D10-3 的写冲突纪律；§3.5 按 D10-4 改写历史说明；头部版本号递增；

- `repository-workflow.md`：领单前分流改为「按 D7 分流到批次 / Epic 或单点实施」；写入 D9 的 draft 约定、

## 6. 复议触发（Revisit）

- **复核前合入再次发生**（任何需复核单元在复核通过前合入）→ 引入机器可读的「待复核」标记
  （标签或 FIFO 排除条件）。
- **连续两个批次中，退回主要由实现问题引起**（而非方案问题）→ 复核实施档位的划分口径。
- **Owner 对 helper 副本模型（B1 §2 A/B/C）作出 A 或 B 的裁决** → D4 同族扫描的范围与方式随之改变
  （共享库或一致性守卫之后，按族扫描可能不再必要），需复核 D4 与 D5。
- **批次周期显著长于同等规模的单点实施且未换来更低的返修率** → 复议 D7 的判据。
- **协调域外工作面的 PR 与域内实施者在同一文件上反复冲突** → 复议 D10-2 / D10-3（是否需要为域外工作面提供可见性登记）。
- **确认 `role` 字段没有任何消费者** → 复议是否退役该字段。
