# ADR-0039：脚本版本不可变契约收窄——「直至零引用退役」

- 日期：2026-09-13

## 1. 背景

### 1.1 问题定性：不可变契约的代价已经可量化，且收益侧问题从未被回答

`AGENTS.md` 硬不变量规定「已发布 `backend/agent/scripts/<name>/v<version>/` 不可原地修改或删除」，ADR-0020 以「每版本全量副本 + 绝对不可变」实现它。该契约换来了真实价值（§1.3），但代价随版本数线性累积，且**「历史版本还需不需要被重新执行」这个问题自 #735 立项以来没有任何一侧的证据**。

本 ADR 的职责是**回答那个问题并据此裁决契约边界**——不是重新论证膨胀本身（那是 #735 本体：修退役诊断工具 + 退役零引用活跃版本）。

### 1.2 事实基线（2026-09-13，只读实测，`origin/main` = `f268d455`）

**生产库引用分布**（`plan_step` 对 `script` 的 `(name, version)` 冗余引用，非 FK）：

| 指标 | 值 |
|---|---|
| `script` 版本行 | **136** |
| 其中有 `plan_step` 引用 | **45** |
| 零引用（`refs = 0`） | **91** |
| ├ 零引用且 `is_active=true`（**#735 退役候选**） | **60**（21 个工具族，Top：`monkey_setup` 12、`powercycle_check` 6、`mtbf_finish` 5） |
| └ 零引用且已退役（`is_active=false`） | **31** |
| `plan_step` 行 / distinct `(script_name, script_version)` | 152 / **45** |
| `plan_step` 引用「不在 `script` 表」的版本 | **0**（引用闭合） |

**仓内行数占比**（`origin/main:backend/agent/scripts`，仅 `.py`）：

| 分类 | 行数 | 占比 |
|---|---|---|
| 版本目录总行数（148 个目录） | **89,517** | 100% |
| 零引用版本目录（90 个） | **56,394** | **63.0%** |
| ├ 其中「零引用且活跃」（#735 退役动作的覆盖面） | 26,295 | 29.4% |
| 被引用版本目录（必须保留） | 26,878 | 30.0% |
| 无对应 DB 行的目录（该族新增待扫描版本，如 `gpu_check@1.0.8` vs DB 最新 `1.0.6`） | 6,245 | 7.0% |

### 1.3 不可变性买到了什么（先确认代价换来了什么）

- DB 的 `script.content_sha256` 是扫描时磁盘内容的快照，扫描遇 sha 不一致只记 `conflicts`、**不动 DB**——DB 期望值被永久冻结；
- 2026-07-31 事故（`tools/dev/check-script-version-immutability.py` 头注）：一次全仓 `ruff --fix` 原地改写版本目录 → 27 行 script 中 18 行 DB sha 与磁盘永久失配 → 平台仅有的两个 Plan 全部准入 `script_verify_failed`，**派发彻底中断**，且自愈推送修不好（推的是磁盘内容，对不上 DB）；
- 因此全量副本不是懒政，是「历史可复现 + 派发二值安全」的实现方式：版本字节独立、可校验、可 pin（`plan_step.script_sha`，ADR-0023）。

**本 ADR 不削弱上述任何一条**：它收窄的是「保留多久」，不是「可不可改」。删除与改写是两种风险——改写会静默破坏**已有**引用，删除只影响**未来**重新派发。

### 1.4 关键事实：零引用 = 在任何 Plan 中都不存在，不只是「还没跑」

这是本 ADR 与可行性研究之间的**新增证据**（研究 §4 当时登记为「待验证」，本 ADR 已完成该只读统计）：

- `plan_step` 共 152 行、仅覆盖 **45** 个 distinct 版本；`script` 表 136 行中 91 行零引用；
- 逐 JOIN 核验：**零引用版本出现在 `plan_step` 中的数量 = 0**——不是「出现在从未运行的 Plan 里」，而是**根本不出现在任何 Plan 的定义中**（无论该 Plan 是否运行过、是否有 `plan_run` 行）；
- 全库 `plan` 32 行、`plan_run` 258 行；`plan_step` 对 `script` 的引用**完全闭合**（0 条指向表外版本）。

**推论**：零引用版本的「被重新执行」只有一条可能路径——**人工重新编辑某个 Plan 把该版本加回去**。不存在「既有 Plan 将来运行时会用到它」这一情形。这把 §2 的判据从"未知"变成"已知且有界"。

## 2. 决策

### D1（核心）：不可变契约收窄为「直至零引用退役」

将 `AGENTS.md` 硬不变量与 ADR-0020 的绝对不可变，**收窄为两段式**：

1. **只要存在任何 `plan_step` 引用（`refs > 0`），该版本目录绝对不可原地修改、不可删除**——范围、强度与今日完全一致，`check-script-version-immutability.py` 判据不变；
2. **`refs = 0` 且已退役（`is_active = false`）的版本目录，允许物理删除**，溯源由 Git 历史 + 归档承担。

**删除的前置条件（三项同时满足，缺一不可）**：

- `refs = 0`：`plan_step` 对该 `(name, version)` 引用计数为 0（以 `check_unreferenced_script_versions` 的只读输出为判据）；
- `is_active = false`：已退役。**不允许「零引用但活跃」直接删除**——必须先走 #735 的退役动作，让「从可选面移除」与「从仓库删除」分成两个可审计步骤；
- **退役冷却期已满**（D3）。

### D2：删除权不下放给自动流程

物理删除**只允许由人工发起的 PR 执行**，且该 PR 必须：

- 附当次 `check_unreferenced_script_versions` 只读输出（证明 `refs = 0`）；
- 在 PR 描述中列出被删目录清单；
- 不得由任何定时任务、CI job 或 Agent 循环自动产生。

理由：删除是**不可逆**动作（Git 历史可回溯但需要人工介入），而「不可逆 + 自动化」在无人复核时会把一次误判放大成批量损失。可逆的动作（退役 `is_active=false`）才允许自动化。

### D3：退役与删除之间设冷却期，删除粒度按版本而非按族

- **冷却期**：版本置 `is_active=false` 后，**至少一个完整里程碑（M 周期）或 30 天（取长者）** 才可删除。目的是给「退役后发现仍需该版本」留一条**无成本回退**（重新 `is_active=true` 即可，无需恢复 Git 历史）；
- **粒度**：**按单个 `(name, version)` 判定**，不按工具族整体删除。同族内 `refs = 0` 与 `refs > 0` 并存是常态（实测 `monkey_setup` 12 个零引用版本与在用版本并存），按族删除会误删在用版本；
- 冷却期起点以 DB `script` 行的退役时间为准；若该字段不可用，以完成退役动作的 PR 合入时间为准。

### D4：删除后「不可重新派发」是显式接受的代价，且不提供代码级逃生

删除后：

- **历史记录不受影响**：`plan_step.script_sha`、`step_trace`、`job_instance` 等历史事实仍完整，**对历史 run 的溯源成立**；
- **重新派发失效**：若有人把该版本重新加回某个 Plan，准入阶段会因磁盘无该目录而失败（`script_verify_failed` 类），这是**期望行为**（显式失败优于静默降级）；
- **不提供**「删除后仍可重新派发」的旁路（如归档自动还原）。若未来出现真实的重跑需求，应按 D5 走新版本或恢复 Git 历史，而不是给删除动作加隐藏的还原层。

### D5：确有重跑需求时的正解是「发新版本」，不是保留旧副本

若业务上出现「必须用某个历史版本的字节重跑」的真实需求，正解是**按 ADR-0020 发一个新版本**（内容可等同），而不是把该历史版本从删除候选中豁免。这条封闭了「以重跑为由无限保留」的口子。

### D6：本 ADR 不改变 P2/P3 的既有裁决

- **P2（共享基础库）明确不做**：维持可行性研究的裁决——它把不可变性从「每版独立可校验」变成「跨版共享可变面」，与 ADR-0020 立意相反；
- **P3（差量/打包分发）仍归 ADR-0033 §5.4** 的条件落地轨道，不因本 ADR 而改变；
- **`_` 前缀辅助文件不计入 entry sha 的盲区**（`check-script-version-immutability.py` 注释自陈；#888 记「门禁放过旧 `v*` 目录内新增文件」）——本 ADR **不**扩大也不修复该盲区，属独立议题。

### D7：门禁需同 PR 修订，且判据必须与 DB 引用解耦

`check-script-version-immutability.py` 的判据从「所有已发布版本目录禁止变更/删除」改为「**`refs > 0` 的版本目录禁止变更/删除；`refs = 0` 且已退役的目录允许删除**」。

**关键约束**：门禁是 CI 静态检查，**不得**在门禁里连生产库查引用数（违反测试与生产库边界，且会让门禁依赖环境可用性）。因此：

- 门禁判据基于**仓内可静态判定的信号**（版本目录是否存在、是否在允许删除清单中）；
- 「`refs = 0`」的证明责任在 **D2 的人工 PR**（附只读输出），不在门禁；
- 两者通过 PR 描述与评审衔接，不通过门禁自动查询衔接。

## 3. 替代方案与否决理由

| 方案 | 否决理由 |
|---|---|
| **维持绝对不可变（什么都不做）** | 63.0%（56,394 行）的仓内脚本行数是零引用的历史副本，且增速快于治理（#735 立项 09-04 的 101 版本 → 09-13 的 136 版本）。不可变的**收益侧（历史可复现）只对 `refs > 0` 的版本成立**，对零引用版本是无收益的纯成本 |
| **删除零引用但活跃的版本（跳过退役步骤）** | 否——把「从可选面移除」与「从仓库删除」压成一步，失去冷却期与回退路径（D1/D3）。退役是可逆的、可见的中间态，必须先经过它 |
| **按工具族整体删除零引用版本** | 否——同族内零引用与在用版本并存是实测常态（`monkey_setup` 12 个零引用），按族删除会误删在用版本（D3） |
| **删除后保留归档自动还原层** | 否——给不可逆动作加隐藏逆操作，会让「已删除」不再是确定状态，且还原层的正确性无人验证；正解是发新版本（D5） |
| **改走 P2 共享基础库** | 否——维持可行性研究裁决（D6）。它以「跨版共享可变面」换取空间，与 ADR-0020 的独立可校验立意相反 |
| **门禁连生产库查引用数** | 否——违反生产库边界且使门禁依赖环境（D7） |

## 4. 后果

### 4.1 正面

- **直接削减仓内行数**：上限 **63.0%**（56,394 行 / 90 个目录），实际取决于退役动作与冷却期的推进速度；
- **不动执行语义**：删除的是零引用版本，不影响任何在跑的 Plan、任何历史 run 的溯源、任何 `refs > 0` 版本的字节；
- **使 #735 的退役闭环有了终态出口**：退役（可逆）→ 冷却 → 删除（终态），而不是退役后目录永久沉淀。

### 4.2 负面 / 接受的代价

- **删除后不可重新派发**（D4）——显式接受，且不设旁路；
- **需要人工执行删除 PR**（D2）——不做自动化，牺牲速度换可控性；
- **门禁判据与引用证明解耦**（D7）——证明责任落在 PR 评审，存在「人工漏附证据」的流程风险，用 D2 的必需项约束。

### 4.3 落地顺序（依赖关系）

1. **先完成 #735 本体（P0）**：修复 `check_unreferenced_script_versions.py`（已完成，PR #1660）+ 执行退役动作（60 个零引用活跃版本，**对生产库的写操作，须单独走生产变更流程**）；
2. **本 ADR 裁决通过**后，同 PR 修订 `AGENTS.md` 硬不变量与 `check-script-version-immutability.py` 判据（D1/D7）；
3. **冷却期（D3）满后**，由人工 PR 分批删除（D2）。**建议首批只删已退役最久、族内无在用版本的小批**，验证流程后再放量。

**在 1 与 2 完成前，不得执行任何删除。**

## 5. 验证方式

- **本 ADR 立项依据（已完成，只读）**：`script` 136 行 / 零引用 91 / 零引用且活跃 60 / 引用闭合 0 孤儿；`plan_step` 152 行 / distinct 45；行数 89,517 中零引用占 56,394（63.0%）；
- **删除前置校验**：每次删除 PR 必须附当次 `python -m backend.scripts.check_unreferenced_script_versions --json` 输出（D2）；
- **门禁红绿**：`check-script-version-immutability.py` 修订后，须证明「删除 `refs>0` 目录 → 红」与「删除 `refs=0` 且已退役目录 → 绿」双向成立；
- **回归**：`refs > 0` 版本的不可变保护不得因本 ADR 而削弱——沿用 2026-07-31 事故场景做守护测试。

## 6. 复议触发条件

- **真实重跑需求出现**（有人需要某已删除版本的字节）：不撤销本 ADR，按 D5 发新版本；若该需求**反复出现**，则说明 D5 的成本假设不成立 → 重审 D4/D5；
- **删除后发生派发中断事故**（删除动作导致非预期路径失败）：立即停止放量，回退 D1 至绝对不可变并复盘判据；
- **`refs = 0` 不再等于「不在任何 Plan 中」**：若未来引入「Plan 模板引用」「动态脚本解析」等机制，使引用不再完全由 `plan_step` 表达，则 §1.4 的判据失效 → 本 ADR 必须重新裁决（**这是本 ADR 最脆弱的假设**）；
- **退役冷却期（D3）被证明过长或过短**：按实际回退案例数校准。
