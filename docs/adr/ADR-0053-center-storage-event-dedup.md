## 1. 当前事实与问题本质

### 1.1 代码对证（基线 `e9ca6933`，2026-09-25）

1. **当前是筛选上送，不是全量持续上送。**
   `backend/agent/event_uploader.py::_recover_states` 只返回 `UPLOAD_PENDING`；
   普通 LOCAL 入队被拒绝，scan 标记或 HddSpill 的 force 路径才触发上送。
   ADR-0028 D1/D2 同样明确过滤模型。v0.1 将 ADR-0028 描述成「持续上送全部事件」是事实错误，予以撤回。
   重复问题成立，但准确表述是：baseline 每 job 重复采集，**其中被选中或溢出的证据**可能跨 run 重复入中心。
2. **事件行与字节当前耦合在路径上。**
   `backend/models/device_log_event.py::DeviceLogEvent` 有 run/job/serial、state、remote_path、checksum，
   没有独立内容对象引用；`entry_origin` 当前存在 signal extra，不是 DLE 独立列。
   `EventUploader._upload_one` 写 `devices/{run}/{event_id}/{basename}`，原路径校验失败时先删除再复制。
3. **现有目录 checksum 不能直接提升为内容身份。**
   `EventUploader._dir_sha256` 顺序拼接相对路径与文件内容，没有字段长度或结构边界。
   本轮抽取原函数在临时目录复现：`{"a": b"bc"}` 与 `{"ab": b"c"}` 得到相同摘要。
   这是编码歧义，**不是 SHA-256 碰撞**。此外，它没有清单格式版本，不表达空目录，也未显式拒绝软链。
4. **baseline 的一次发现不等于不可变内容。**
   `backend/agent/aee/reconciler.py::_run_baseline_snapshot` 使用 `watcher_baseline:{job_id}`，
   并通过 emit 意图簿维持重试与事件可见性；`processor.py::_run_side_exports_if_needed` 还采集 mobilelog/bugreport。
   同一 db_history 行只定位采集候选，不证明目录已封口，也不证明再次生成的附属信息字节相同。
5. **免拉取会改变 scan 输入。**
   `backend/agent/scan_runner.py::_prepare_scan_root` 从本地 HDD 按 serial/date stamp 建扫描树，
   `aee/scan_scope.py::build_scoped_scan_root` 依赖实际文件。
   只在中心补 DLE/目录链接会使新 job 的本地扫描树缺证据，不能以「看板没变」替代验收。
6. **下游没有统一的 baseline 隔离契约。**
   `plan_run_watcher_summary.py::_aggregate_aee_dashboard_sections` 在来源完整时拆分 baseline/runtime；
   来源不完整则回退合并展示。`dedup_scan.py::run_merge_sync` 合并 scan 报告，
   `device_log_event.py::list_remote_paths_for_extract` 按 run 与可提取状态列举路径，不按来源过滤。
   `dedup_extract.py::run_extract_sync` 还按 basename 分组，仅首个路径被提取（已有回归测试）。
   Jira 适配器 `jira_vendor/stability_jira.py::build_argv` 传递 Excel，不提供 entry_origin 参数；
   **外部厂商工具的最终计数/写入行为本轮未验证，不能声称提单已区分 baseline。**
7. **物理回收不只有 run 主路径。**
   `cron_scheduler.py` 有 run 家族清理、unassigned 清理及 orphan DLE 清理；
   `device_log_event.py::adopt_unassigned_event_dirs` 还会搬移目录。
   因而 v0.1「按 run 是唯一回收路径」不准确。候选复用也不能只查 REMOTE：
   现有 `_REMOTE_STATES` 包括 REMOTE / ARCHIVED / PRUNED，后者表示本地已删，中心仍可提取。

上述为代码与现有测试对证，不代表端到端现场验证。关键验证记录见
[本轮 Agent Note](../notes/architecture/2026-09-25-adr0053-decision-review.md)。

### 1.2 v0.1 历史证据的边界

原稿记录中心盘 916 GB、7 天从 46% 到 88%，owner 删除 134 GB 可再生提取副本；
不同 run 中有大量重复事件目录。它们是起草时记录，**本轮没有重新测量磁盘或读取生产配置**。
按目录名估算重复不可靠；目录名不具跨设备唯一性（#1073）。

L0 抽样 dry-run 原记录：刻意选取 5 个重复密集 run（345/349/379/430/435，共 268 GB），
逐文件 SHA-256 找到 1557 个相同内容组、6442 个待链接文件，可回收 214.1 GB（80%），耗时 37.5 分钟。
这说明字节级重复值得解决，**不证明全量节省率，也不证明整事件包都相同**；全量结果仍未提供。
L0 与磁盘告警（#3272）是历史止血，不决定长期模型。

### 1.3 第一性原理与复利判断

平台需回答四个不同问题：哪个 run 观察到了什么事件、证据是什么、字节在哪里、什么时候允许回收。
事件的业务归属不能由字节存放位置推导；同样，内容相同不代表同一次故障。

长期成本是「唯一证据字节 + 观察引用元数据 + 有界派生工作区」，不应是「run 数 × 历史转储体量」。
因此优先收敛身份与生命周期，而非把跨 run 路径查找做成新的基础设施。
开发期可以一次改正读取边界；不为维持目录布局引入永久双轨，也不借此建设通用分布式存储平台。

## 2. D1–D6 裁决建议

### D1：保留每 run 的观察事实，拆开内容所有权（修订原 D1）

保留 DLE 作为事件观察的权威：不同 run/job 的历史观察独立存在，保留设备、来源、时间与 signal 关联，
不能因同内容而合并崩溃次数。`entry_origin` 必须有可持久化、可查询的明确归属，不能只依赖可丢失的展示标签。

**不再把「每 run 必须拥有一套物理目录」当作不变量。** DLE 引用独立不可变的 evidence manifest；
manifest 引用内容 blob。内容对象不从属于首次上传的 run，删除该 run 不影响其他引用。
已有 local/remote/extract 状态需要与「采集是否完成、证据是否可用、派生物是否生成」分开定义；
首次实现先给出状态映射，不继续让 PRUNED 同时被误解为证据不可用。

目标业务表名保持单数；最小实体职责为 `evidence_blob`（摘要/长度/发布状态）、
`evidence_manifest`（规范清单/摘要）、DLE→manifest 引用，以及上传/读取保活记录。
具体列与迁移由实施设计落定；Redis 不保存这些业务事实。blob/manifest 都不向调用方泄露宿主绝对路径。

### D2：文件内容寻址 + 事件清单；硬链接降为实现优化（替换原 D2）

选择站点内文件系统 CAS：普通文件按 `(sha256, size_bytes)` 校验与寻址，事件由规范化 manifest 组装。
初期一个站点一个对象根，业务调用方只用对象标识与存储接口；不引入对象存储服务、跨站点去重、分块去重或新集群。
物理 blob 可在同一受控存储域跨 serial 复用，业务引用仍独立校验授权；不提供跨权限域的存在性探针。

按文件去重的理由：bugreport/mobilelog 改变时，不应迫使相同的核心转储再存一次。
manifest 必须版本化，固定序列化格式，按规范相对路径排序，并包含条目类型、文件长度、文件摘要及有语义的元数据；
需要保留的空目录显式编码。拒绝重复路径、绝对路径、`..`、软链与特殊文件；不隐式忽略未知条目。
run、job、serial、采集时间等观察元数据放在 DLE/采集记录，避免人为破坏内容复用。
可借鉴 ADR-0051 的规范清单与不可变发布原则，**不照搬发布包的文件排除集**，以免丢证据。

只读消费视图可选择硬链接；可写工作区必须 reflink（底层支持并验证时）或独立复制。
不能通过 chmod 一个硬链接来隔离写入，也不能仅靠代码评审约定保护共享 inode。
最终对象只允许发布者写入，Agent/工具不能原地打开终态对象写入；损坏对象隔离，修复走重新发布流程。

### D3：上送以原子发布和引用提交为中心（替换原 D3）

不采用「按 `(serial, 旧 checksum)` 找某个 run 的副本，失败即复制到另一个 run」作为主模型。
统一协议：**封口采集快照 → 生成清单 → 批量查询缺失 blob → 上传缺失内容到 staging →
中心验证并发布 → 事务绑定 DLE/manifest → 回执确认后才允许本地 prune**。
复用原 EventUploader 的调度、重试与回执链，提取明确存储边界，不另建常驻调度系统。

必须满足以下约束：

- 查存在只是优化提示。并发同 digest 上传通过唯一约束与不覆盖发布收敛；赢家完成校验后，其他写入复用。
- 发布前后都不可把半成品当成可读对象；文件系统持久化先于数据库 AVAILABLE/引用提交。
  NFS 等目标介质的原子性、崩溃持久性须在隔离集成环境实证，不能用本地 rename 成功替代。
- 数据库提交失败可留下暂存孤儿，交回收恢复；不得反过来先宣布 REMOTE 再补字节。
  同一幂等请求重试不能生成重复观察、重复引用或重复节省量。
- 校验失败、清单非法、越权是完整性/契约错误，不得掩盖成普通复制成功。
  缓存未命中、对象不存在可以补传；物化不支持 link/reflink 可以复制，但仍受统一内容与引用协议约束。
- GC 与新引用/正在上传/下载/scan/extract 互斥。持久引用是真源；释放引用与业务事务一致。
  回收采用候选标记、宽限期、最终锁内复核；标为删除中的对象禁止直接新增引用，走等待/重发。
  正在使用的对象有有界保活和崩溃恢复；不能仅靠可漂移的 refcount 或 mtime 删除。

这些是首版条件，不把并发与 GC 正确性留到空间紧张之后再补。

### D4：baseline 复用纳入终态，但以身份与消费链完备为前置（条件接受目标）

baseline 表达「本次开始时已存在的历史证据」，需要新观察记录，不需要重复制造相同字节。
`(serial, aee_type, db_history line)` **只作为候选检索键**。
可跳过核心转储拉取，必须证明：设备与存储代际未重置、源事件身份稳定、采集已封口、
源内容版本未变、已发布证据仍可用，以及所需附件清单完整。
设备端有可靠版本/摘要协议时可使用；否则必须重新读取/校验，不能把 size/mtime 或旧行文本当成强证明。
刷机、重启后的身份复用、目录复用、增长中的转储、历史缺附件均须使不可靠缓存失效。

核心转储与本次采集附属上下文分开建模：历史快照被复用要标注原采集时间；
若业务要求本次 bugreport/mobilelog，则单独采集并形成新 manifest，不能拿旧上下文伪装本次证据。
Agent 本地索引只作可丢弃缓存；跨 host 接管由持久引用支持。

**D4 不能在以下两项之前启用：**

1. scan 能通过 manifest 在当前 run 的本地缓存/受控工作区获得完整输入，并保留平台、serial、工具所需路径语义；
   缓存冷启动、跨 host、对象暂不可达均有恢复/明确失败路径。
   首版可物化后照常 scan；后续只有在工具版本、参数和输入内容都构成缓存键时才复用解析结果。
   本轮不同时建设 scan 结果缓存。
2. 同一观察集对拍 signal、DLE、scan、merge、extract 与提单输入。baseline 可查、可下载、可提取，
   但不作为本轮新发生崩溃进入 runtime 统计；不能沿用历史同名目录去猜来源。
   外部工具不理解来源时，由适配层分离输入或保留伴随映射，不能要求 xls 自然携带不存在的语义。

D4 可在实施顺序上后置，但不得作为无出口的永久延期项。未满足强身份前，保留重新采集路径是正确性要求，
不是线上兼容包袱；也不能承诺所有 baseline 都能做到零 ADB/零磁盘读取。

### D5：提取包是可再生、可写、有限寿命的工作区（强化原 D5）

`jira/` 和工具工作区**不得硬链接不可变证据**。采用 reflink 或复制隔离，按需生成；
不以「一次指纹对比没变化」推定厂商工具以后永不修改。
因此厂商工具是否原地写入不再阻塞架构选择；指纹实验只用来了解工具行为。

提取按 DLE/manifest 身份命名并保留原文件名映射，解决当前 basename 相同只能提取首份的问题；
相同 basename、不同内容都必须可访问，不能静默丢弃或误标 ARCHIVED。
提单成功的外部标识、工具版本、输入清单与结果摘要是长期事实；原始 evidence 与派生工作区分开保留。
工作区的读者/工具执行持有保活，到期且无使用者才回收；失败可重建，不能删正在使用的包。

原始证据 N 天、派生物 M 天的**具体数值**不从单次磁盘压力拍定，归 #3230 G4 的分层保留裁决。
本 ADR 先确定引用/保活/可重建边界；不设置新清理参数、不执行历史删除。

### D6：同时观测逻辑量、物理量、传输量与完整性（接受并扩充原 D6）

必须区分逻辑引用字节、唯一已发布 blob 字节、实际新写入字节、网络传输字节、临时/派生占用；
逻辑去重率与磁盘占用趋势分别展示，不能把硬链接下的目录大小相加当物理占用。
跨 run 共享内容的收益按发布回执的明确口径归因，不能逐 run 相加重复计功；重试不重复记账。

同时记录复用命中/失效原因、ADB 跳过与实际读取量、checksum 失败、staging 孤儿、GC 积压、
不可用引用与 scan/extract 缺口。run 级明细进数据库/日志；Prometheus 使用有界标签，
不把 run_id、serial、digest 放进高基数标签。目标是证据完整前提下的长期增长下降，不追求孤立的命中率。

## 3. 为什么不沿用 v0.1 的终态

- **跨 run 硬链接**：省改调用方的成本，但仍要解决身份、来源选择、源删除竞态、不可变约束、
  basename 冲突和派生物保留。它把这些问题藏在路径关系中。开发阶段选择明确引用模型更可持续。
- **整事件包 CAS**：概念简单，但仅附件发生变化也会重新保存大块相同转储；选择文件 blob + manifest，
  不继续扩展到块级去重。后续若测量证明文件级对象数成为瓶颈，再讨论打包索引。
- **只恢复短保留期/取消 baseline**：前者混淆历史事实与证据寿命，后者失去历史可见性，均不解决根因。
- **DLE 直接引用另一个 run 的路径/使用软链**：源 run 清理会留下悬空引用；CAS 引用的是独立对象，
  生命周期由全部引用决定，两者不同。
- **现在直接引入分布式对象存储**：去重身份与发布协议不依赖它；先在现有文件系统实现最小边界即可。

代价明确：需要新增 manifest/引用模型、发布与 GC 协议，以及修改 scan/extract/download 的读取入口。
收益是同一模型同时承接去重、baseline、按引用回收和派生重建；不会为每个问题再补一份路径索引。

## 4. 实施顺序与验收

### Phase A：构建身份与发布底座（D1/D2/D3/D6）

在隔离环境建立版本化清单、文件 CAS、引用提交、幂等发布、回收协议与有界指标。
上送范围继续按 scan 筛选与溢出策略，不把存放方式的调整顺手变成全量上送政策。
必须证明：编码歧义样本摘要不同；相同文件跨事件只保留一份 blob；附件变化不重传不变核心；
同名异内容隔离；并发上传只产生一个可用对象；回执丢失/进程崩溃可恢复；
校验失败不发布，未确认引用不 prune；删除首次上传 run 不影响其他 run。
“新增 0 字节”仅指重复 payload，不含 DLE/manifest/引用元数据和文件系统开销。

### Phase B：验证并切换全部消费与回收路径（D1/D3/D5）

scan、merge 路径重写、extract、下载、unassigned 归属、run/orphan 回收统一经对象解析边界访问。
先验证 cold-cache、同名异内容、原始/派生生命周期分离、工具修改隔离；
再验证 GC 与新引用/上传/下载/提取交错，以及崩溃后孤儿回收、损坏内容隔离。
备份恢复必须覆盖引用数据库与对象集的一致性，恢复后做引用可达性核验；去重不等于备份。

开发期采用可复现的离线导入/切换，不建设长期兼容双写。
已有数据要保留时，从 DLE 路径读取原件、生成新清单、核验引用闭包后切换；旧 checksum 仅作旧字段记录。
**本轮未获历史数据删除指令，不默认清空数据。** 旧目录回收必须晚于迁移等价性验证；
切换后清除旧的跨 run 查找与按路径所有权回收分支，避免两套事实面并存。

### Phase C：完成 baseline 复用与链路对拍（D4）

在 Phase A/B 完成、设备事件封口/版本能力可证明后，对 MTK/UNISOC 分别覆盖：
重复 run、同 run 多 job、跨 host、刷机/重启、同名异内容、目录增长、缺附件、中心对象缺失、
离线重连、emit 意图重放。无强身份的平台不得伪报复用成功。

验收同时看：runtime 计数不增加、baseline 观察仍完整、scan/merge 的事件集合等价、
提单输入引用正确、下载字节一致、实际 ADB/HDD/网络/中心空间收益分别量化。
这才是 D4 完成；单测绿色或目录存在都不足以证明。

### Phase D：回查并衔接分层保留

按相同观察集比较改前/改后物理增长与处理成本，不用 v0.1 的 80% 定收益承诺。
将 N/M 保留参数、证据到期状态、长期摘要和重建边界交 #3230 G4，保留政策另裁；
ADR-0053 不以“存储永远不会满”作为验收目标。

## 5. 接受门槛、权威文档与剩余实证

本轮已把 D1–D6 的推荐选项明确到可实施条件；**owner 尚未对替代 v0.1 的 CAS 方向作出接受记录**，
因此保持 Proposed。需要确认的是本稿整体终态与依赖顺序，不是再等线上灰度或磁盘压满来证明方向。
架构接受和实施验收分开：owner 接受后即可登记 Accepted，不要求 CAS 先实现；Phase A–D 仍须逐项验收。

接受时在同一文档切片同步 ADR-0025 D4、ADR-0028 的存储/状态约束、
`2026-scan-upload-merge-contract.md`、`2026-storage-roles-and-aliases.md` 和 semantic-ownership 的权威指针；
覆盖的是存储与引用部分，不推翻 DLE 唯一权威或筛选上送语义。
本 Proposed 版本不抢先改写这些已接受契约。

待实证的是实施能力：目标存储发布/持久性、设备端封口与版本协议、厂商工具输入/修改行为、
端到端对拍、全量唯一字节比例、吞吐/对象数量与恢复测试。
它们均未在本轮执行，不能写成“已验证”；其中任一正确性前置缺失时，不启用对应优化。
