## 1. 背景与证据

### 1.1 问题本质

设备日志是稳定性测试的关键产物。设备、Agent host、中心存储三层的存储上限固定，平台的核心价值是让设备日志持续、高效、便捷地流转。

现行链路（ADR-0025 D4、ADR-0028、ADR-0032、[`06-realtime-and-background.md`](../design/06-realtime-and-background.md) §9）由三类触发驱动：
PlanRun 运行中按 `Plan.auto_archive_interval_seconds` 的增量扫描（`auto_archive_sweep`，`is_final=False`）、
PlanRun 终态扫描（`is_final=True`），以及手动触发（`POST /archive`、`POST /{run_id}/dedup/scan` 等）。现行的上传集合有三个来源：

1. MTK：各 Agent 本机扫描与主机汇总后，控制面 `upload_task` 把报表 `Path` 列命中、且处于可标记状态（`DETECTED`、`LOCAL`、`UPLOAD_PENDING`、`UPLOADING`、`UPLOAD_FAILED`）的 DLE 行标为 `UPLOAD_PENDING`。
2. 展锐 UNIVIEW：事件入库即提升为 `UPLOAD_PENDING`（`backend/services/device_log_event.py` `_NO_SCAN_GATE_EVENT_TYPES`）。
3. HddSpill：Agent 本地磁盘压力超过阈值时强制上传，校验回执后删除本地副本（`backend/agent/local_disk_monitor.py`）。

三者都由 EventUploader 写入 `devices/{run}/`。控制面 merge 按平台对各 host 报表做跨 host 去重，与上传并行，不约束上传集合。
extract 把该 run 下 `REMOTE`、`ARCHIVED`、`PRUNED` 且有 `remote_path` 的 DLE 行（`list_remote_paths_for_extract`）复制到 `jira/{run}/`，同 basename 的多个目录只复制第一个（#386），复制成功的行转为 `ARCHIVED`（ADR-0032 D10）。

「现行是先上传后去重」在本 ADR 中只表示：上传集合不受跨 host merge 结果约束；它不表示上传必须先于 merge 完成。
merge 的结果影响下游报表。已经写入 `devices/` 的字节仍保留，extract 又按事件集合复制第二份。问题身份由目录路径、文件名和厂商 xls 文本承载，下游不断从路径反推身份。

## 2. 范围与改进边界

本 ADR 只改四件事：

1. 把代表选择前移到常规原始证据上传之前；
2. 保全全部发生事实；
3. 承接旧 extract 承担的登记与归属职责；
4. 完成新旧分区的日志交付、下载、展示、归档与留存适配。

以下流程继续保留，本 ADR 只规定它们与新链路的接口：采集与 Watcher / Signal、DLE 观察与归属、本机扫描与主机汇总、平台隔离、上传校验 / 回执 / 重试、实时查询与风险看板。

以下不在本 ADR 实施范围内：检索分页与过滤、PRUNED 下载（#3176）等既有单点；旧数据迁移与历史清理；ADR-0053 的内容寻址。（注：v1.2 阶段二仅覆盖 MTK，展锐并入目标链与全平台退出 `CURRENT` 旧链见 v2.0 Proposed 条款，转 Accepted 并随对应批次激活后生效。）

## 3. 身份与用词

| 名词 | 定义 | 权威载体 |
|---|---|---|
| 观察 | Agent 一次采集的登记：event_id、serial、run / job 归属、位置与状态 | `device_log_event`（DLE） |
| 发生 | 同一台设备上的同一次报错 | ADR-0056 D2 `issue_occurrence` |
| 问题 | 按去重规则归在一起的一类发生 | ADR-0056 D2 `issue_signature` |
| 代表 | 「实际 PlanRun × 平台 × 问题 → 某个事件」的选择关系 | 本 ADR 新增的选择记录（D7） |
| 分区 | 实际 PlanRun × 平台 | 本 ADR 新增的分区模式记录（D13） |
| 轮次 | 一次有范围、有截止点的处理批次：周期轮、最后一轮、补充轮 | 本 ADR 新增的轮次记录（D3） |
| 交付物 | 一份有明确范围的材料：分区、软件版本集合、问题与事件、统计快照、缺口 | 本 ADR 新增的交付登记（D9） |
| 主文件夹 | 中心存储上按链根与软件版本组织的物理目录（D9 第 6 条） | 中心存储；只是物理分组 |

1. 一个问题有多次发生；一个事件目录可能承载多个问题；多个问题可以共享同一个代表事件。只上传一份证据，不等于只记一次发生。
2. 任何组件不得把目录名、报表文件名、xls 文本或 DLE ID 直接当作跨轮次的发生身份或问题身份。
   发生身份的构成由实施方案给出。实施方案必须保证：同一次发生无论被周期轮重扫、迟到补报、补充轮、兼容补跑，还是通过溢出副本扫描，都得到同一个发生身份。
3. 问题的跨轮身份由 `issue_signature` 承载。控制面必须把每一轮 merge 的聚类结果映射到已有签名，不得因为某一轮聚类的首行变化而产生新问题。映射规则必须在影子运行中对拍（§9）。

## 4. 不变量

本节对所有实施单元生效。§5 各条与本节冲突时，以本节为准。

- **I1 发生事实幂等累计。**
  - 控制面必须在 S6 把每次发生按发生身份写入数据库。同一次发生被后续轮次重扫、迟到补报、补充轮或兼容补跑再次带入时，控制面不得重复计数。
  - 出现次数按发生身份去重计数，机器数按设备（serial）去重计数。控制面不得逐轮累加报表的 `Count` 或机器数，也不得用某一轮报表的值覆盖累计值。
  - 本地目录被溢出、清理或移走，不得使已确认的发生从数据库中消失或使累计值下降。
- **I2 溢出事件仍在处理集合内。**
  被 HddSpill 移到中心的事件，必须继续参加 S4 扫描、S6 计数和 S7 代表候选，包括在首次扫描前就已溢出的事件。Agent 每轮扫描的输入必须包含本分区在中心已校验的溢出副本；同一次发生经本地与溢出副本两种来源扫描时，控制面必须得到同一发生身份并标注来源（Owner 2026-11-02 裁定，§10.6）。
- **I3 各类完成分开记录。**
  报表覆盖、merge 结果、代表选择、证据完整度、证据发布、交付就绪、保留是不同的状态（§6）。任何组件不得用单一的「完成」或 `ARCHIVED` 表达它们。缺口与失败不得显示为「无问题」。
- **I4 仍需使用的材料受保护。**
  补充轮、上传重试与兼容补跑需要的材料，在这些动作收口前不得被回收。这些材料包括 Agent 本地原件，以及 HddSpill 删除本地后在中心已校验的溢出副本。

## 5. 决策（按流转环节 S1–S11）

本节除 D2 第 4 条、D2 第 5 条未认领前置边界、D3 第 1 条、D10 第 1/2 条及 D13 外，只约束运行模式为「先去重」的分区（D13）。自 §9.2 阶段 A 生效后，D2 第 4 条同时约束所有运行中的 Agent、Agent host 与控制面。D2 第 5 条的未认领前置拦截适用于尚未归属且可能归入「先去重」分区的事件，不得阻断已确定归属历史或「现行」分区的事件。D3 第 1 条适用于尚未定模的候选分区，不得把 D13 第 2 条未登记的历史分区当作新候选。D10 第 1 条适用于已有分区模式记录的实际 PlanRun，包括只登记「现行」模式的运行。D10 第 2 条适用于没有分区模式记录的存量 PlanRun。「现行」分区的日志处理继续按 ADR-0025 D4、ADR-0028、ADR-0032 执行。
每条规则句都写明执行者与强度词（必须 / 不得 / 可以）；只给出定义、范围或取值的句子不带强度词。

### D1 S1 发现、采集、导出

1. Agent 沿用现有 Reconciler / Collector 采集，并必须记录事件来源（runtime 或 baseline）与缺件情况。
2. 「dblog、mobilelog、bugreport 三件齐全」是代表资格（D7），不是事件的定义。Agent 必须照常登记缺件事件，控制面必须照常把它们计入发生（I1）。

### D2 S2 本地缓冲与登记

1. Agent 必须把每个事件登记为 DLE，带 event_id、serial、run / job 归属、本地位置与状态。归属待定的事件必须进入未归属认领（`associate_unassigned_events_to_plan_run`），认领后进入所属分区。
2. DLE 与 Signal 继续供实时查询、风险看板与 PlanRun 页面使用。这条支路不依赖 S5–S10 的任何结果。
3. Agent 本地磁盘超过阈值时，Agent 可以继续用 HddSpill 把事件强制上传到 `devices/{run}/`，并在校验回执后删除本地副本。溢出事件受 I2、I4 约束。
   控制面必须为每个分区维护溢出台账并告警。台账至少记录事件数与字节数。
4. （v2.0 Proposed，#4077；自 v2.0 转 Accepted 并随 §9.2 阶段 A 生效后，同时约束全部运行中 Agent、Agent host 与控制面）：
   - Agent 必须在每次心跳周期消费基于本地 `/proc/self/mountinfo` 的挂载在位判定与后台可读写探针快照。
   - Agent 不得在心跳主循环执行同步非本地文件系统 I/O。
   - 当 `STP_AEE_NFS_ROOT` 未配置、在位缺失、只读、可达性未知或探针过期（`probe_stale=true`）时，Agent 必须将中心存储可写状态记为未就绪，且不得宣称具备 `DEDUP_FIRST` 能力。
   - 控制面在计算 Agent host 常规可调度容量、判定 `DEDUP_FIRST` 准入以及下发扫描或上传轮次前，必须核验目标 Agent host 持有新鲜且未过期的 `STP_AEE_NFS_ROOT` 在位可写正证（`probe_stale` 不得为 `true`）。
   - 当上述在位可写正证缺失、无效或过期（含 `probe_stale=true`）时，控制面不得将相应作业或轮次派发至该 Agent host。
   - Agent 在向中心存储写入任何数据前（含第一笔报表或伴随文件复制、分片或空回执登记、HddSpill 溢出上传、事件上传或代表证据写入），必须确认 `STP_AEE_NFS_ROOT` 当前在位可写且非过期。
   - 写前可写校验失败时，Agent 必须阻断本次中心存储写入。
   - 写前可写校验失败时，Agent 必须递增对应失败指标。
   - 写前可写校验失败时，Agent 必须继续本地采集。
   - 写前可写校验失败时，Agent 不得删除本地原件（I4）。
   - 写前可写校验失败时，Agent 不得将 `DEDUP_FIRST` 分区改写回 `CURRENT`。
5. （v2.0 Proposed，#4104 方案乙）：
   - 当展锐分区处于 `DEDUP_FIRST` 模式时，控制面在全部事件入库与认领路径（单条上报、批量上报、状态重放与 `associate_unassigned_events_to_plan_run`）均不得将常规事件置为 `UPLOAD_PENDING`。
   - 对可能归入 `DEDUP_FIRST` 分区但归属或运行模式尚待认领的事件，控制面与 Agent 均必须以同一归属与定模决策路径核验归属，不得在定模完成前先行置为 `UPLOAD_PENDING` 或按 `CURRENT` 补传。
   - 当展锐分区处于 `DEDUP_FIRST` 模式时，Agent 必须将常规事件保留为 `LOCAL`（含本地补传队列拦截），仅在 S7 选中为代表或触发第 3 条 HddSpill 时才可以上传至中心存储。
   - 对于展锐 `DEDUP_FIRST` 分区，Agent 的 `UnisocUniviewReconciler` 必须作为 S1 发现与采集阶段唯一的设备 ADB 日志采集者。
   - 在作业启动后、开始本次测试执行前，Agent 必须冻结设备缓冲基线快照。
   - 对设备坏钟（如复位到 `1970-01-01`）场景，Agent 必须以「相对基线新增或变更的不可篡改采集水线」与绑定串号判定 `实际 PlanRun` 归属，不得把前序基线目录按首见时间误归入当前作业。
   - 对无法确定归属的事件，Agent 必须按待认领或未归属缺口登记。
   - Agent 必须在采集每次发生时落盘为发生唯一不可变本地目录，并随发生固化全部 D9 第 6 条命名输入（或已计算的规范主文件夹名）。
   - Agent 必须按 D1 第 2 条与 I1 照常登记缺件事件并标注缺件（不得过滤缺件发生）。
   - 控制面必须按 D1 第 2 条与 I1 照常将缺件事件计入发生。
   - Agent 不得因类型目录同名（例如同一设备多次 `Assert.109000001`）原地覆盖既有本地原件。
   - Agent 必须在每个 `(实际 PlanRun, 平台, Agent host)` 记录真实的采集成功、失败或未完成事实，供 S4/S5 区分正常零事件与采集失败。
   - 控制面不得仅因作业进入终态就视同采集已完成。
   - 在展锐 `DEDUP_FIRST` 分区的 S4 扫描阶段，Agent 不得调用 ADB 命令再次抓取设备日志。
   - Agent 必须在 S4 按 `实际 PlanRun × 平台 × Agent host` 冻结本轮本地不可变发生目录集合。
   - Agent 必须在 S4 将本分区在中心已校验的 I2 溢出副本快照回接进本轮扫描输入。
   - Agent 不得跨不同发生拼凑三件证据。
   - 控制面不得跨不同发生拼凑三件证据。

### D3 S3 分区模式固定与轮次调度

1. 控制面必须在尚未定模的候选分区第一个受运行模式影响的动作（含所有事件入库、批量创建、状态重放、未归属认领与上送标记）之前，按 `实际 PlanRun × 平台` 写入运行模式（D13）。控制面不得因 Agent host 暂时缺挂载或能力回退把已固化的 `DEDUP_FIRST` 分区改写回 `CURRENT`，也不得把 D13 第 2 条未登记的历史分区重写为新模式。（v2.0 Proposed 补全前置边界）
2. 控制面必须为每一轮写入轮次记录：轮次号、种类（周期轮 / 最后一轮 / 补充轮）、期望集、输入截止点、状态（待执行 / 执行中 / 已关闭）。
3. 周期轮：控制面必须在分区运行中按扫描周期触发，默认 6 小时，可配置（Owner 已裁定）。周期轮入队失败时，控制面可以由下一个周期轮替代。
   扫描周期是本 ADR 新增的独立参数。实施者不得复用 `Plan.auto_archive_interval_seconds`，ADR-0060 D3-1 对该字段（未设表示不自动归档）的约定不变。
4. 最后一轮：控制面必须在 PlanRun 进入终态（`SUCCESS`、`PARTIAL_SUCCESS`、`FAILED`）后触发。
5. 补充轮：最后一轮关闭后，若有属于本分区的报表到达，控制面必须触发补充轮。补充轮的期望集是分区有效覆盖（D9 第 4 条）中仍缺失的 (host, 平台)。
6. 最后一轮与补充轮不得被后续周期替代。控制面必须持久化这两类轮次；入队失败或执行中断时，调度器必须在每个检查周期重新入队，直到该轮关闭。
7. 扫描周期、报表等待期、本地保留期 N 是三个独立参数，实施方案不得互相推导。
8. 报表等待期默认 2 小时，可配置（Owner 2026-11-02 裁定）。控制面必须在期望集报表全部到达或等待期届满时关闭本轮。实施者配置等待期时，必须使其短于扫描周期。

### D4 S4 本机扫描、主机汇总、报表上送

1. Agent 必须按轮次执行本机扫描与主机汇总（MTK 为 `start_log_scan -m 0` 加 `-dedup_org`）。扫描输入为本分区的本地事件，加上 I2 规定的溢出事件。
2. Agent 上送的每份报表必须绑定 PlanRun、host、平台与轮次。
3. Agent 必须随报表上送伴随映射：主机汇总前原始报表（`*_org.xls`）的每一行都要映射到对应的 event_id 与发生身份。映射必须覆盖全部发生，不得只映射代表。
4. 主机报表与控制面 merge 报表的 xls 内部格式不变（D12 第 3 条）。伴随映射放在报表之外。
5. Agent 必须在报表上送回执后回收本轮扫描临时目录（staging）。
6. 扫描工具失败或上送失败时，控制面必须在 S5 把该 (host, 平台) 记为缺失，并由下一轮或补充轮恢复。
7. 扫描工具必须在每份报表旁输出成员关系文件（契约 `stp.scan_membership` 1.x），给出每行的分支（相似度去重 / 单例 / 过滤）、组归属、代表标记，以及工具版本、规则版本和解析库版本。Agent 必须随报表上送该文件。成员关系文件缺失或不可用时，控制面必须把该报表计为降级覆盖，不得自行比较签名作为替代。
8. 工具维护者必须为每个正式发布版本打上对应平台仓库的不可变 tag（MTK 为 `start-log-scan/vX.Y.Z`，展锐新增 tag 规则见第 9 条）并附带有效 `release.json`。工具维护者不得原地修改已发布版本。Agent 与控制面仅在扫描工具已按正式版本 tag 发布且 `release.json` 校验通过时才可以运行该工具；当版本 tag 缺失或 `release.json` 缺失、损坏或校验失败时，Agent 与控制面均不得运行该工具。部署者在部署任何平台工具新版本前必须取得 Owner 同意。
9. （v2.0 Proposed，#3884 / #3830 / #3766 / #4104）：
   - 工具维护者必须通过不可变版本 tag `scan-result-gt/vX.Y.Z` 加有效 `release.json` 发布展锐扫描工具（`Scan-Result-GT`），且不得原地修改已发布版本。
   - Agent 与控制面仅在 `Scan-Result-GT` 已按 `scan-result-gt/vX.Y.Z` 发布且 `release.json` 校验通过时才可以运行该工具，不得运行未发布或清单校验失败的版本。
   - Agent 必须在 S4 仅向 `Scan-Result-GT` 提供按 `实际 PlanRun × 平台 × Agent host` 冻结的本地不可变输入快照及已回接 I2 溢出副本。
   - `Scan-Result-GT` 必须纯离线扫描上述冻结快照。
   - `Scan-Result-GT` 必须在单次扫描完成后正常退出，不得依赖超时强杀。
   - `Scan-Result-GT` 不得遍历或读取未列入当前实际 PlanRun 的 Agent host 其他设备。
   - 当冻结快照存在事件时，`Scan-Result-GT` 必须输出格式不变（D12 第 3 条）的 `*_org.xls`、符合 `stp.scan_membership` 1.x 契约的成员关系文件，以及确定性映射回本地 `DLE`、`occurrence_key`、随发生固化的 D9 第 6 条命名输入或已计算的规范主文件夹名、以及三件源材料状态（`dblog`/`mobilelog`/`bugreport`）的原始行伴随映射。
   - 当个别事件的命名输入与规范主文件夹名均缺失时，Agent 与控制面仍必须按 I1 照常登记发生并保留报表行，只在 S8/S9 登记可解释的发布缺口；Agent 与控制面均不得因此丢弃报表行或重查已换版设备。
   - 只有当同一 `(实际 PlanRun, 平台, Agent host)` 同时满足以下三项条件时，Agent 才可以向控制面登记 `platform=unisoc` 的显式有效空回执（计入 S5 覆盖 `EMPTY`）：（1）`UnisocUniviewReconciler` 的本轮采集过程确认无异常（如 ADB `ls` 非零返回、权限或断连未知等未完成采集不得记为空）；（2）本分区全部中心已校验 `I2` 溢出副本已无误回接并纳入输入清单；（3）`Scan-Result-GT` 正常退出并产出机器可读零结果证明。
   - 上述任一前提缺失、未知、失败或分片/空回执登记失败时，控制面必须将该 `(Agent host, 平台)` 记为 `MISSING`。
   - 当同轮报表、伴随映射、成员关系文件与分片登记全部取得控制面确认回执后，或者当同轮显式空回执取得控制面确认回执后，Agent 必须回收本轮可重建的 `.stp-scan` 临时工作目录。
   - 对失败或无回执的 `.stp-scan` 临时目录，Agent 必须在超过有界排查重试窗口后仅清理可重建的扫描副本，不得解除或提前删除受 I4 保护的本地缓冲原件。

### D5 S5 报表接收与覆盖判定

1. 控制面必须按 ADR-0032 B1 的 `scan_completeness`，从 PlanRun 设备表派生每轮的期望集（host, 平台）。
2. 控制面必须为期望集里的每一项记录覆盖状态：收到、空回执、缺失、迟到。没有事件的 host 必须上送空报表或等价的空回执；空回执算覆盖，缺失不算。
3. 等待期满或期望集全部覆盖时，控制面必须结束等待，把收到与空回执的报表作为本轮有效输入。
4. 迟到报表（属于本分区，但晚于所属轮次的输入截止点）必须作为下一轮或补充轮的输入，不得冒充本轮输入（#3720）。
5. S5 只判定输入覆盖，不宣布交付完成。

### D6 S6 跨 host merge 与发生入库

1. 控制面必须按分区对本轮有效输入执行 merge，把结果写入数据库：问题 ↔ 发生 ↔ 事件映射，以及每个问题的出现次数与机器数（I1）。
   - 判断两次发生是否属于同一问题时，控制面必须按平台调用对应受版本管理的扫描工具匹配入口（MTK 调用 `start_log_scan -match_issues`；展锐 `DEDUP_FIRST` 分区按 v2.0 Proposed 接入受版本管理的 `Scan-Result-GT` 跨机匹配入口 `stp.issue_match_request` / `stp.issue_match_result`），并以该工具返回结果作为唯一问题归并依据。
   - 当上述匹配入口不可用、工具/规则版本不兼容或返回错误时，控制面必须按第 3 条记录 merge 失败并保留恢复出口，不得回落到单机聚类 ID、报表 `Count` 或控制面自实现签名比较规则。
   - 控制面必须维护跨轮、跨主机的问题身份、发生身份与覆盖记账。
2. 本轮有效输入为空（期望集全部缺失）时，控制面不得执行「零问题」merge，本轮 merge 结果记为「无输入」。
3. merge 失败时，控制面必须独立记录失败，本轮不产生选择；重跑同一轮必须幂等。
4. 本条修订 ADR-0053 D7 规则 3。控制面必须在同一实际 PlanRun 内完成签名级归并和累计计数。
5. ADR-0053 D7 规则 1、2、4、5 对既有下游消费继续有效。

### D7 S7 选择代表事件

1. 选择记录的范围是「实际 PlanRun × 平台 × 问题」。同一问题在同一分区内只能有一个代表。
2. 选择状态（待选 / 已选）与证据完整度（齐全 / 不全）是两个独立字段。
3. 控制面必须在选择时已知的发生中，选最早出现、且 dblog、mobilelog、bugreport 三件齐全的那个事件作代表。三件必须出自同一个事件，即同一台设备的同一次报错。控制面不得用不同设备的同一问题，或同一设备不同时间点的同一问题，拼凑出三件齐全。
4. 没有齐全事件时，控制面必须让该问题保持「待选」，在后续轮次再选。最后一轮或其后的补充轮仍没有齐全事件时，控制面必须选最早出现的事件，并把该问题同时记为「已选」与「证据不全」。
5. 同一问题再次出现时，控制面必须更新发生记录，不得改选，不得要求补传证据。
6. 控制面写入选择后不得改选，S8 上传失败也不例外。

### D8 S8 证据传输、校验、回执

1. 控制面必须把选择结果回传给持有代表源材料的 Agent。
2. Agent 必须只上传被选中的代表事件。代表的源可以是 Agent 本地原件，也可以是中心已校验的溢出副本；溢出副本作源时，控制面或 Agent 可以在中心侧完成复制，不得要求设备重新导出。
   - （v2.0 Proposed）对于展锐 `DEDUP_FIRST` 分区，Agent 与控制面必须仅从 D2 第 5 条受保护的不可变本地目录或中心已校验溢出副本读取代表源。
   - （v2.0 Proposed）Agent 必须在采集时随发生固化 D9 第 6 条所需全量命名输入（或已计算的规范主文件夹名）与发生身份映射。
   - （v2.0 Proposed）Agent 与控制面不得因仅有中心溢出副本而重新向已换版设备查询版本属性或导出代表证据。
3. 上传、校验与回执沿用 EventUploader 现有链路。上传失败时，Agent 必须重试同一选择，不得新增代表。
4. Agent 在中心校验回执前不得删除源（#1083，I4）。
5. 一个事件目录被多个问题选为代表时，Agent 只能上传一次。
6. 除 D2 第 3 条的 HddSpill 外，Agent 不得在选择结果回传前，把事件证据上传到中心存储。主机报表、伴随映射、统计导出不受此限。

### D9 S9 交付发布与登记

1. S9 有两个动作：登记交付物版本、判定交付状态。
   - 控制面可以在分区任何时候登记交付物版本，供查看与下载；登记本身不表示就绪。
   - 控制面必须按第 5 条判定每个交付物版本的交付状态。
   - 判定的输入来自四处：S5 覆盖结果、S6 统计、S7 选择、S8 回执。控制面不得把「全部代表已有回执」作为判定的唯一入口。
2. 交付物版本必须记录以下内容：
   - 范围：实际 PlanRun、平台、软件版本集合；
   - 依据的轮次集合（最后一轮及已关闭的补充轮）与据此得到的有效覆盖；
   - 收录的问题与事件；
   - 统计快照版本；
   - 未完成项：仍在传输或等待回执的代表；
   - 缺口：有效覆盖中缺失的 (host, 平台)、证据不全的问题、上传终态失败的代表；
   - 对应的主文件夹集合。
3. 代表的证据发布状态（§6）分三种：
   - 已校验：已收到中心校验回执；
   - 重试中：尚未收到校验回执，仍在重试；
   - 失败：重试达到实施方案规定的上限后的终态。
   控制面不得把「失败」以外的代表记为缺口；「重试中」的代表同样不得记为缺口。
4. 分区有效覆盖：对期望集里的每个 (host, 平台)，只要最后一轮或任一已关闭的补充轮收到了它的报表或空回执，控制面就必须把它记为已覆盖。
   - 控制面不得因计算有效覆盖而改写各轮次自身的覆盖记录（D5 第 4 条）。
   - 每个交付物版本按其依据的轮次集合计算有效覆盖。补充轮关闭且 merge 成功后，控制面必须重新计算有效覆盖，并按第 5 条判定新版本。
5. 控制面必须按以下顺序判定交付状态，取第一个成立的结果：
   1. 分区最后一轮尚未关闭，或依据轮次中最近一次 merge 的结果是失败或无输入：**未就绪**。
   2. 有效覆盖为空（期望集全部缺失）：**未就绪**。控制面不得把它包装成零问题的成功结果。
   3. 有任何代表处于「重试中」：**未就绪**。控制面不得因 merge 成功而提前宣布就绪。
   4. 有效覆盖完整，且没有证据不全的问题、没有「失败」的代表：**就绪**。没有问题时，这是有效的空交付物。
   5. 其余情况：**就绪但有缺口**。控制面必须在交付物中列出全部缺口。
6. Agent 必须把代表证据写入以下目录结构：

   ```text
   {证据区根}/
   └── {主PlanRun编号}_{项目名}_{软件版本缩写}_{测试开始时间戳}_{MonkeyAEEinfo|MonkeyYloginfo}/   # 按平台与软件版本区分
       └── {SN}/
           └── {唯一事件目录名}/        # MTK 形如 {时间戳}_db.{XX}；展锐含时间戳/实例唯一前缀
   ```

   - （v2.0 Proposed，#4103）Agent 在展锐 S8 上传代表证据时，必须写入经 D2 第 5 条固化的 `{唯一事件目录名}`。
   - （v2.0 Proposed）Agent 必须在代表上传回执载荷中绑定当前 `DLE` 与交付范围。
   - （v2.0 Proposed）Agent 不得使用同设备后续同名发生覆盖既有目的目录。
   - （v2.0 Proposed）Agent 在 S8 重试上传同一发生时，必须幂等写入同一目的目录。
   - （v2.0 Proposed）当随发生固化的 D9 第 6 条命名输入完整（或已存规范主文件夹名）时，控制面与 Agent 必须按上述规范主文件夹路径发布。
   - （v2.0 Proposed）当个别发生缺失关键命名输入导致无法构造规范主文件夹名时，控制面必须在 S9 登记可解释的发布缺口，不得误并分区或静默跳过。
   - （v2.0 Proposed）控制面只有在收到中心校验回执并更新交付登记后，才可以在 S9 将对应事件转为 `ARCHIVED`。

   - 证据区根是中心存储下新增的顶层目录，与 `devices/`、`jira/` 并列，名称由实施方案确定并登记到 `storage_families`。
   - 主 PlanRun 是链根（`plan_run.root_plan_run_id`），没有链时是 PlanRun 本身。
   - 同一 PlanRun 内软件版本不一致时，每个软件版本一个主文件夹（Owner 已裁定）。
   - 实施者必须按离线工具 [stability_Offline-MonkeyTestTool](https://github.com/DUElost/automation-toolkit/tree/main/python-tools/stability_Offline-MonkeyTestTool) 的 `_get_aee_log_folder_name` 规则生成 `{项目名}_{软件版本缩写}_{测试开始时间戳}`。该规则从 `ro.product.name`、`ro.build.display.id`、`ro.build.version.incremental`、`ro.build.version.release` 推导。
   - 实施者必须把命名规则实现为按项目可扩展、带版本的规则，新增项目时只能增加规则，不得改已有规则。
7. 主文件夹只是物理分组。任何组件不得用主文件夹推断交付范围，交付范围以 D9 第 2 条的登记为准。
8. 控制面必须为每个交付物版本生成统计导出文件，作为数据库的副本供人工查看和下载。统计导出文件不在原始证据的校验范围内。
9. 事件只有在已通过校验、且已登记进所属交付物后，控制面才可以把它转为 `ARCHIVED`。控制面不得因交付物声明了缺口而把缺口对应的事件归档。
10. 缺口补齐（补传成功、补充轮关闭）后，控制面必须登记新的交付物版本，并保留旧版本的登记。

### D10 S10 既有报表消费的分区边界

1. 对已有分区模式记录的运行，控制面必须把既有按 PlanRun 产物取报表的入口限定在可确认归属的「现行」分区。控制面必须按实际 PlanRun 和平台确认报表归属。
2. 对没有分区模式记录的存量运行，控制面必须沿用既有产物读取规则。
3. 控制面必须以 D9 登记的交付物范围提供「先去重」分区的证据、统计和缺口。
4. 日志消费者为处理交付证据而创建可写工作区时，必须使用可隔离写入的 reflink 或独立副本。

### D11 S11 留存、回收与恢复保护

S11 是独立的控制环，不是某一步的后继。

| 对象 | 保留条件 | 状态 |
|---|---|---|
| Agent 本地原件（未选中事件） | 分区最后一轮关闭后再保留 N 天；控制面不得因补充轮重新计算 N；I4 保护期间不得回收 | 起算点已定（§10.6）；N 的值待 Agent 本地缓冲测量后裁定 |
| 扫描临时目录（staging） | 报表（或显式空回执）上送确认后回收；失败/无回执可重建 `.stp-scan` 副本超有界重试窗口后仅清可重建缓存（v2.0 Proposed） | 沿用现行并补失败回收例外 |
| 主机报表、merge 报表 | 沿用现行 run 级保留 | 沿用现行 |
| 溢出副本（`devices/{run}/`） | I4 保护期间不得回收；之后按现行 run 级保留 | 已定 |
| 主文件夹与代表证据 | 按整条链清理；清理前必须单独取得 Owner 确认 | 已定 |
| 发生、问题、选择、交付登记 | 长期记录，不随文件回收删除 | 已定 |

1. 在 N 由 Owner 裁定之前，Agent 不得因本 ADR 新增本地缓冲原件的删除路径；D4 第 9 条规定的 `.stp-scan` 失败临时目录有界回收仅适用于可重建的扫描工作副本，Agent 不得借此清理受 I4 保护的本地事件原件。
2. 控制面必须记录分区最后一轮的关闭时间，作为所有 host 共同的 N 天起算点。Agent 收到关闭通知之前不得回收；离线的 Agent 重新上线后必须按同一起算点计算。
3. 任何组件不得按单个 PlanRun 删除主文件夹或其中的事件目录。

### D12 平台范围、旧数据与报表格式

1. （v2.0 Proposed 条件性修订——自展锐并入批次按 §9 阶段 C 激活后取代原「只覆盖 MTK」限制；激活前维持 v1.2 口径）：本 ADR 的契约在控制面与 Agent 具备双平台能力并完成对应批次激活后，同时覆盖 MTK（主文件夹后缀 `…_MonkeyAEEinfo`）与展锐（主文件夹后缀 `…_MonkeyYloginfo`）分区；未接入平台继续沿用现行链路并按 D13 共存，控制面不得将「v2.0 已合入」或「具备静态能力」等同于已启用。
2. 旧数据不迁移。运行模式为「现行」的分区继续留在 `devices/` 与 `jira/`。Owner 必须按 [v1.1 D12 第 2 条的既有条件](https://github.com/DUElost/stability-test-platform/blob/73144bf9d8b578a99b9762958d0120e4d5e0d8ab/docs/adr/ADR-0062-device-log-dedup-before-upload.md#L280) 确认旧日志归档与删除。Owner 必须在删除前按实际 PlanRun 单独确认。
3. 实施者不得改变主机报表与控制面 merge 报表的 xls 内部格式。需要新增工具参数时，实施者必须先提出并取得 Owner 同意。

### D13 新旧分区并存（②-1，Owner 已定方向）

1. 运行模式的单位是实际 PlanRun × 平台。链根只用于中心存储的物理分组，不决定模式。
2. 控制面按 D3 第 1 条写入模式后，不得改写。没有模式记录的存量分区，一律按「现行」解释；控制面不得因开关的当前值回读而改写它们。
3. （v2.0 Proposed 条件性修订）在展锐并入批次完成 §9 阶段 C 激活前，控制面只可以对 MTK 分区开启「先去重」且不得对展锐分区开启「先去重」；在展锐并入批次激活后，控制面与 Agent 可以对 MTK 与展锐双平台分区按 D3 第 1 条开启「先去重」。当同一 PlanRun 中一侧分区走「先去重」且另一侧分区走「现行」时，控制面与 Agent 对代表选择、事件上传、归档完成判据、手动操作入口与失败展示都必须按分区隔离，不得将一侧失败或就绪扩展为另一侧状态。
4. 现行手动 extract 是 run 级接口。对混平台 PlanRun，控制面必须只对「现行」分区执行 extract，不得对整个 run 一律返回 409，也不得把「先去重」分区的 DLE 纳入 extract 输入。只有「先去重」分区的请求，控制面才可以返回 409。
5. 关闭开关只阻止之后的分区进入「先去重」。关闭开关后，控制面与 Agent 必须继续支持已有新格式数据的回执、读取、下载与回收。
6. 新旧并存是过渡状态，退出条件写在 §9 阶段 D（原 v1.2 阶段三）。实施者不得把两套业务事实作为永久设计叠加。
   - （v2.0 Proposed）旧链退出前，实施者不得为现行 `CURRENT` 链路的 `extract_task` 新增过渡性超时补丁。
   - （v2.0 Proposed）控制面与 Agent 必须先完成 §9 阶段 B 的 MTK 全量切量、阶段 C 的展锐并入 `DEDUP_FIRST`，并满足阶段 D 的全部旧链入口冻结与真实写入者排空门槛。
   - （v2.0 Proposed）上述门槛全部满足并经 Owner 批准后，控制面才可以下线当前受支持 MTK 与展锐分区的现行 `extract_task` 与自动扫描/上送主链路。

### D14 交付物取代重复 extract（②-2，Owner 已定方向）

1. 控制面不得对「先去重」分区执行 extract。该分区的交付物是 D9 登记的交付物，内容包括已校验的代表证据、统计导出与缺口。
2. 控制面必须以 D9 登记的交付物作为「先去重」分区的日志交付出口。控制面必须沿用「现行」分区的既有交付出口。
3. 本条修订 ADR-0032 D10 的 `ARCHIVED` 含义：事件已登记进所属交付物，且对应证据已通过校验。「现行」分区由 extract 写入，「先去重」分区由 S9 写入。
   区分依据是分区的运行模式，不是平台。`ARCHIVED` 不表示报表覆盖完整、三件齐全或全部问题处理成功。
4. 实施者必须在阶段二启用前验证 D16 所列日志消费者和 D10 的分区边界。

### D15 FAILED 与受控兼容补跑（②-3，Owner 已定方向）

1. PlanRun 为 `FAILED` 时，控制面必须照常执行最后一轮、代表上传与交付发布，以保存事故证据。本条修订 ADR-0028 D2 与 ADR-0032 D7 中「FAILED 自动跳过 merge」的规定；该修订只适用于「先去重」分区。
2. 控制面必须对 `FAILED` 分区提供已登记交付物的查看和下载。
3. 扫描、merge、上传失败属于日志处理失败，按 D4–D9 各自的出口恢复。控制面不得因 PlanRun 已失败而停止恢复，也不得因此宣布交付完成。
4. 关闭开关、代码回滚、受控兼容补跑是三个不同的动作。关闭开关本身不是数据回退。
5. 受控兼容补跑由 Owner 对单个「先去重」分区发起，对该分区额外生成一份现行格式的产物。实施方案必须给出：
   - 源材料：Agent 本地原件，或中心已校验副本；
   - 覆盖范围；
   - 独立的结果登记；
   - 幂等：重复执行必须保留累计发生数（I1）与原交付物的登记。
6. 兼容补跑不得通过把 DLE 回写为 `LOCAL` 来驱动。
7. 补跑只能覆盖仍在保留期内的本地子集时，结果登记必须列出缺失清单与非全量声明。

## 6. 状态拆分

| 状态 | 单位 | 取值 | 写入环节 |
|---|---|---|---|
| 报表覆盖 | 轮次 × (host, 平台) | 收到 / 空回执 / 缺失 / 迟到 | S5 |

实施方案不必为每项新建状态机。界面和判据不得用一个 `ARCHIVED` 或 `FAILED` 包办上述状态。

## 8. 放弃的备选

| 备选 | 结论 | 理由 |
|---|---|---|
| 保持先上传后去重，实施 ADR-0053 内容寻址 | 否决 | Run 1096 最多省 19%，本 ADR 的顺序调整省 96.6%（待影子运行复测） |
| 只做主机汇总就上传 | 否决 | 6.4% 对 3.4%，且跨 host 的同一问题仍会重复上传 |

## 9. 迁移与激活（按 ADR-0058 批次推进）

### 9.1 v1.2 已 Accepted 基线（批次 B8：MTK）

1. 前置：#3829（字节台账）与 #3831（项目名、版本来源）先按单点修复。ADR-0056 D2 的 `issue_signature` / `issue_occurrence` 是 Accepted 设计、尚未实施，B8 的实施单元必须包含其落地或等价载体。
2. 阶段一（影子运行）：控制面按 D3 执行 S5–S7 与 S9 的登记，只写数据库，不改变上传。实施者必须用真实 PlanRun 对拍以下各项：
   - 问题数、跨轮问题映射、发生映射；
   - 出现次数与机器数（I1）；
   - 代表三件齐全率、应上传字节；
   - 交付物范围。

1. ADR-0025 D4 归档-1 原定中心只接收三类内容：汇总报告、报告中 db 对应的事件目录、溢出事件目录。设计原意是按需上送。

## 11. 走查场景（1–13 归 B8 阶段一；14–19 归 v2.0 Proposed 阶段 A/C/D 分阶段验收）

1. 同一设备在两轮各新增一次同一问题：次数 2、机器数 1；重复提交第二轮报表，结果不变。
2. 一个事件承载两个问题：保留两条问题映射，证据目录只上传一次。
3. 一个问题三件不齐：先待选；最后一轮选同一事件并标证据不全，不跨事件拼凑。
4. 首次扫描前发生 HddSpill：该事件仍可被扫描、计数、选为代表；之后本地清理不使累计次数下降。
5. host 正常空回执、host 离线无回执、merge 失败：三者得到不同且可解释的结果。
6. 最后一轮部分关闭后报表迟到：补充轮启动，所需材料受保护；N 天到期后无法恢复的部分列为缺口。
7. 同一 run 中 MTK 走新链、展锐走旧链：手动 extract 只作用于旧分区，两种交付都能定位；一侧失败不伪装成另一侧失败。
8. 链上两个 run、多个软件版本：共享父目录不串交付范围；处理子 run 不误删链上其他证据。
9. 代表已选但上传回执失败、Agent 重启：仍重试同一代表，发布不假绿，源材料未被误删。
10. 已 `ARCHIVED` 或 `PRUNED` 的代表做兼容补跑：不靠回写 `LOCAL` 驱动；记录兼容报表的源与覆盖，重复补跑后累计发生数和原交付登记一致。
11. PlanRun `FAILED`：最终扫描轮、代表发布和交付恢复继续。已登记交付物可查看和下载，同一运行的现行分区仍按各自模式处理。
12. 零问题且期望集全部明确回执：形成有效空交付物；全体无回执不得包装成零问题。
13. 同一 run 中 MTK 走新链、展锐走旧链：既有按 PlanRun 产物取报表的消费入口只能选择可确认属于展锐现行分区的报表。没有模式记录的存量运行沿用既有规则。
14. （v2.0 Proposed，阶段 A 验收）`STP_AEE_NFS_ROOT` 挂载脱落、只读或探针 `probe_stale=true`：心跳可写判定与准入拒收旧探针正证（Agent 仍正常上报心跳与续约租约，不停止心跳或本地采集），写前守卫立即阻断首笔中心存储写入（含报表/伴随文件复制、分片登记、溢出与代表上传），不沿用陈旧缓存放行，保留本地原件且不回退 `CURRENT`；恢复可写且获新鲜探针正证后恢复放行。
15. （v2.0 Proposed，阶段 C 激活前验收）展锐真实设备有效零事件 vs 采集/回接/扫描异常（拆开 S5、S6 与 S9 判定）：
    - **S5 `(Agent host, 平台)`**：仅采集确认完成 + `I2` 溢出完整回接 + 工具零结果证明三项同时成立时记 `EMPTY`；若 ADB `ls` 失败/断连或回接/扫描失败或缺证明，记为 `MISSING`（不得将未知/失败记空）。
    - **S6 轮次归并**：全部期望 `(host, 平台)` 为 `MISSING` 时，本轮 merge 记 `NO_INPUT`（不得包装为零问题）；存在 `EMPTY` 覆盖时进入有效零问题/问题归并。
    - **S9 交付状态**：按共同前置 → 阶段分支的顺序判定（不因处于影子期跳过前置校验）：
      1. 无论影子运行期还是已激活 `DEDUP_FIRST` 分区，只要最后一轮未关闭、依据轮次最近一次 merge 未成功（失败或 `NO_INPUT`）、或有效覆盖为空（全 `MISSING`），控制面必须判定 **`NOT_READY`**。
      2. 上述共同前置均通过后，若尚处于阶段 C 激活前影子运行期（S8 不适用），控制面必须判定 **`SCOPE_ONLY`**（不发布交付证据）。
      3. 上述共同前置均通过后，若处于已激活 `DEDUP_FIRST` 分区，控制面必须按 D9 第 5 条继续判定：存在「重试中」代表时判 **`NOT_READY`**；有效覆盖完整且无证据不全问题、无「失败」代表时判 **`READY`**（无问题时为有效空交付物）；满足 D9 第 5 条其余前提的其余情况（含 `EMPTY` + 部分 `MISSING` 缺口或存在证据不全/失败代表缺口）判 **`READY_WITH_GAPS`** 并列出全部缺口。
16. （v2.0 Proposed，阶段 C 激活前验收）展锐坏钟基线隔离与同设备同名异次发生：前序作业遗留目录停留在基线内时，即使新作业设备挂钟复位为 `1970-01-01` 也不串入当前作业；同一设备多次发生同名异常（如多个 `Assert.109000001`）本地不可变目录与 S8 `{证据区根}/…_MonkeyYloginfo/{SN}/{唯一事件目录名}/` 互不覆盖，重试幂等且不覆盖既有发生。
17. （v2.0 Proposed，阶段 C 激活前验收）展锐首次扫描前发生 HddSpill 溢出（含设备后续换版重刷）：中心已校验溢出副本回接参加 S4 扫描与 S6/S7 选代表，同一发生本地/溢出身份一致、通过随发生固化的命名输入或规范主文件夹名独立复现规范主文件夹且累计不重复也不漏记；若命名输入均缺失则仍计 I1 发生并在 S9 记发布缺口，不丢行也不重查已换版设备。
18. （v2.0 Proposed，阶段 C 激活前隔离演练 + 激活后生产验收）双向混合与双新链 S9：`MTK 现行 + 展锐先去重` 各自隔离失败、手动 `extract` 仅对 `CURRENT` 分区放行；阶段 C 激活后双平台同为 `DEDUP_FIRST` 时真实通过 S9 发布（非影子 `SCOPE_ONLY`），D13.2 历史未定模分区保持旧语义不变。
19. （v2.0 Proposed，阶段 D 验收）阶段 D 统一入写冻结与真实写入者排空：在进入最终排空前同时封住新增 `CURRENT`、`cron_scheduler`、`plan_run_finalization`/`plan_run_abort` 延迟旧链触发及非 D15 手动 `extract`/手动 `scan`/`merge` 入口；不仅在 `saq_tasks`/衍生重试未收口或「SAQ 协程已终态取消但同步写入仍持锁」时不误判排空，而且在观测为空后再次尝试手动 `scan`/`merge`/`extract` 或迟到终态副作用时均被屏障拦截、不得重启任何旧写；全部收口且真实写入者退出/隔离后才下线旧 `extract` 主入口，D15 受控兼容补跑与历史只读查询仍可正常执行。

## 12. 复议触发

- 影子运行中，问题数、跨轮问题映射、发生映射或累计统计与现行 merge 不一致。
- Agent 本地缓冲测量显示 D11 的保留期无法放下单个 PlanRun 的全部事件。
- HddSpill 溢出字节在单个 PlanRun 内超过代表证据字节。
- 展锐合入时，主机汇总工具的报表形态无法满足 D4。
