## 1. 背景与证据

### 1.1 问题本质

设备日志是稳定性测试的关键产物。设备、Agent host、中心存储三层的存储上限固定，平台的核心价值是让设备日志持续、高效、便捷地流转。

现行链路（ADR-0025 D4、ADR-0028、ADR-0032、[`06-realtime-and-background.md`](../design/06-realtime-and-background.md) §9）由三类触发驱动：
PlanRun 运行中按 `Plan.auto_archive_interval_seconds` 的增量扫描（`auto_archive_sweep`，`is_final=False`）、
PlanRun 终态扫描（`is_final=True`），以及手动触发（`POST /archive`、`POST /{run_id}/dedup/scan` 等）。现行的上传集合有三个来源：

1. MTK：各 Agent 本机扫描与主机汇总后，控制面 `upload_task` 把报表 `Path` 列命中、且处于可标记状态（`DETECTED`、`LOCAL`、`UPLOAD_PENDING`、`UPLOADING`、`UPLOAD_FAILED`）的 DLE 行标为 `UPLOAD_PENDING`。
2. 展锐 UNIVIEW：事件入库即提升为 `UPLOAD_PENDING`（`backend/services/device_log_event.py` `_NO_SCAN_GATE_EVENT_TYPES`）。
3. HddSpill：Agent 本地磁盘压力超过阈值时强制上传，校验回执后删除本地副本（`backend/agent/local_disk_monitor.py`）。

三者都由 EventUploader 写入 `devices/{run}/`。控制面 merge 按平台对各 host 报表做跨 host 去重，与上传并行，不约束上传集合。
extract 把该 run 下 `REMOTE`、`ARCHIVED`、`PRUNED` 且有 `remote_path` 的 DLE 行（`list_remote_paths_for_extract`）复制到 `jira/{run}/`，同 basename 的多个目录只复制第一个（#386），复制成功的行转为 `ARCHIVED`（ADR-0032 D10）。

「现行是先上传后去重」在本 ADR 中只表示：上传集合不受跨 host merge 结果约束；它不表示上传必须先于 merge 完成。
merge 的结果只影响提单清单，不影响已经写入 `devices/` 的字节；extract 又按事件集合复制第二份。问题身份由目录路径、文件名和厂商 xls 文本承载，下游不断从路径反推身份。

## 2. 范围与改进边界

本 ADR 只改四件事：

1. 把代表选择前移到常规原始证据上传之前；
2. 保全全部发生事实；
3. 承接旧 extract 承担的登记与归属职责；
4. 完成新旧分区的消费适配。

以下流程继续保留，本 ADR 只规定它们与新链路的接口：采集与 Watcher / Signal、DLE 观察与归属、本机扫描与主机汇总、平台隔离、上传校验 / 回执 / 重试、实时查询与风险看板、人工提单门禁。

以下不在本 ADR 实施范围内：检索分页与过滤、PRUNED 下载（#3176）等既有单点；展锐目标链；旧数据迁移与历史清理；ADR-0053 的内容寻址。

## 3. 身份与用词

| 名词 | 定义 | 权威载体 |
|---|---|---|
| 观察 | Agent 一次采集的登记：event_id、serial、run / job 归属、位置与状态 | `device_log_event`（DLE） |
| 发生 | 同一台设备上的同一次报错 | ADR-0056 D2 `issue_occurrence` |
| 问题 | 按去重规则归在一起的一类发生 | ADR-0056 D2 `issue_signature` |
| 代表 | 「实际 PlanRun × 平台 × 问题 → 某个事件」的选择关系 | 本 ADR 新增的选择记录（D7） |
| 分区 | 实际 PlanRun × 平台 | 本 ADR 新增的分区模式记录（D13） |
| 轮次 | 一次有范围、有截止点的处理批次：周期轮、最后一轮、补充轮 | 本 ADR 新增的轮次记录（D3） |
| 交付物 | 一份有明确范围的材料：分区、软件版本集合、问题与事件、统计快照、缺口 | 本 ADR 新增的交付登记（D9） |
| 主文件夹 | 中心存储上按链根与软件版本组织的物理目录（D9 第 6 条） | 中心存储；只是物理分组 |

1. 一个问题有多次发生；一个事件目录可能承载多个问题；多个问题可以共享同一个代表事件。只上传一份证据，不等于只记一次发生。
2. 任何组件不得把目录名、报表文件名、xls 文本或 DLE ID 直接当作跨轮次的发生身份或问题身份。
   发生身份的构成由实施方案给出。实施方案必须保证：同一次发生无论被周期轮重扫、迟到补报、补充轮、兼容补跑，还是通过溢出副本扫描，都得到同一个发生身份。
3. 问题的跨轮身份由 `issue_signature` 承载。控制面必须把每一轮 merge 的聚类结果映射到已有签名，不得因为某一轮聚类的首行变化而产生新问题。映射规则必须在影子运行中对拍（§9）。

## 4. 不变量

本节对所有实施单元生效。§5 各条与本节冲突时，以本节为准。

- **I1 发生事实幂等累计。**
  - 控制面必须在 S6 把每次发生按发生身份写入数据库。同一次发生被后续轮次重扫、迟到补报、补充轮或兼容补跑再次带入时，控制面不得重复计数。
  - 出现次数按发生身份去重计数，机器数按设备（serial）去重计数。控制面不得逐轮累加报表的 `Count` 或机器数，也不得用某一轮报表的值覆盖累计值。
  - 本地目录被溢出、清理或移走，不得使已确认的发生从数据库中消失或使累计值下降。
- **I2 溢出事件仍在处理集合内。**
  被 HddSpill 移到中心的事件，必须继续参加 S4 扫描、S6 计数和 S7 代表候选，包括在首次扫描前就已溢出的事件。Agent 每轮扫描的输入必须包含本分区在中心已校验的溢出副本；同一次发生经本地与溢出副本两种来源扫描时，控制面必须得到同一发生身份并标注来源（Owner 2026-11-02 裁定，§10.6）。
- **I3 各类完成分开记录。**
  报表覆盖、merge 结果、代表选择、证据完整度、证据发布、交付就绪、Jira 执行、保留是不同的状态（§6）。任何组件不得用单一的「完成」或 `ARCHIVED` 表达它们。缺口与失败不得显示为「无问题」。
- **I4 仍需使用的材料受保护。**
  补充轮、上传重试与兼容补跑需要的材料，在这些动作收口前不得被回收。这些材料包括 Agent 本地原件，以及 HddSpill 删除本地后在中心已校验的溢出副本。

## 5. 决策（按流转环节 S1–S11）

本节各条只约束运行模式为「先去重」的分区（D13）。运行模式为「现行」的分区继续按 ADR-0025 D4、ADR-0028、ADR-0032 执行。
每条规则句都写明执行者与强度词（必须 / 不得 / 可以）；只给出定义、范围或取值的句子不带强度词。

### D1 S1 发现、采集、导出

1. Agent 沿用现有 Reconciler / Collector 采集，并必须记录事件来源（runtime 或 baseline）与缺件情况。
2. 「dblog、mobilelog、bugreport 三件齐全」是代表资格（D7），不是事件的定义。Agent 必须照常登记缺件事件，控制面必须照常把它们计入发生（I1）。

### D2 S2 本地缓冲与登记

1. Agent 必须把每个事件登记为 DLE，带 event_id、serial、run / job 归属、本地位置与状态。归属待定的事件必须进入未归属认领（`associate_unassigned_events_to_plan_run`），认领后进入所属分区。
2. DLE 与 Signal 继续供实时查询、风险看板与 PlanRun 页面使用。这条支路不依赖 S5–S10 的任何结果。
3. Agent 本地磁盘超过阈值时，Agent 可以继续用 HddSpill 把事件强制上传到 `devices/{run}/`，并在校验回执后删除本地副本。溢出事件受 I2、I4 约束。
   控制面必须为每个分区维护溢出台账并告警。台账至少记录事件数与字节数。

### D3 S3 分区模式固定与轮次调度

1. 控制面必须在分区第一个受运行模式影响的动作之前写入运行模式（D13）。
2. 控制面必须为每一轮写入轮次记录：轮次号、种类（周期轮 / 最后一轮 / 补充轮）、期望集、输入截止点、状态（待执行 / 执行中 / 已关闭）。
3. 周期轮：控制面必须在分区运行中按扫描周期触发，默认 6 小时，可配置（Owner 已裁定）。周期轮入队失败时，控制面可以由下一个周期轮替代。
   扫描周期是本 ADR 新增的独立参数。实施者不得复用 `Plan.auto_archive_interval_seconds`，ADR-0060 D3-1 对该字段（未设表示不自动归档）的约定不变。
4. 最后一轮：控制面必须在 PlanRun 进入终态（`SUCCESS`、`PARTIAL_SUCCESS`、`FAILED`）后触发。
5. 补充轮：最后一轮关闭后，若有属于本分区的报表到达，控制面必须触发补充轮。补充轮的期望集是分区有效覆盖（D9 第 4 条）中仍缺失的 (host, 平台)。
6. 最后一轮与补充轮不得被后续周期替代。控制面必须持久化这两类轮次；入队失败或执行中断时，调度器必须在每个检查周期重新入队，直到该轮关闭。
7. 扫描周期、报表等待期、本地保留期 N 是三个独立参数，实施方案不得互相推导。
8. 报表等待期默认 2 小时，可配置（Owner 2026-11-02 裁定）。控制面必须在期望集报表全部到达或等待期届满时关闭本轮；等待期必须短于扫描周期。

### D4 S4 本机扫描、主机汇总、报表上送

1. Agent 必须按轮次执行本机扫描与主机汇总（MTK 为 `start_log_scan -m 0` 加 `-dedup_org`）。扫描输入为本分区的本地事件，加上 I2 规定的溢出事件。
2. Agent 上送的每份报表必须绑定 PlanRun、host、平台与轮次。
3. Agent 必须随报表上送伴随映射：主机汇总前原始报表（`*_org.xls`）的每一行都要映射到对应的 event_id 与发生身份。映射必须覆盖全部发生，不得只映射代表。
4. 主机报表与控制面 merge 报表的 xls 内部格式不变（D12 第 3 条）。伴随映射放在报表之外。
5. Agent 必须在报表上送回执后回收本轮扫描临时目录（staging）。
6. 扫描工具失败或上送失败时，控制面必须在 S5 把该 (host, 平台) 记为缺失，并由下一轮或补充轮恢复。

### D5 S5 报表接收与覆盖判定

1. 控制面必须按 ADR-0032 B1 的 `scan_completeness`，从 PlanRun 设备表派生每轮的期望集（host, 平台）。
2. 控制面必须为期望集里的每一项记录覆盖状态：收到、空回执、缺失、迟到。没有事件的 host 必须上送空报表或等价的空回执；空回执算覆盖，缺失不算。
3. 等待期满或期望集全部覆盖时，控制面必须结束等待，把收到与空回执的报表作为本轮有效输入。
4. 迟到报表（属于本分区，但晚于所属轮次的输入截止点）必须作为下一轮或补充轮的输入，不得冒充本轮输入（#3720）。
5. S5 只判定输入覆盖，不宣布交付完成。

### D6 S6 跨 host merge 与发生入库

1. 控制面必须按分区对本轮有效输入执行 merge，把结果写入数据库：问题 ↔ 发生 ↔ 事件映射，以及每个问题的出现次数与机器数（I1）。
2. 本轮有效输入为空（期望集全部缺失）时，控制面不得执行「零问题」merge，本轮 merge 结果记为「无输入」。
3. merge 失败时，控制面必须独立记录失败，本轮不产生选择；重跑同一轮必须幂等。
4. 本条修订 ADR-0053 D7 规则 3：同一 PlanRun 内的签名级去重与累计计数由 STP 负责。跨 PlanRun 是否并入既有 JIRA 单，仍归提单工具与 JIRA。
5. ADR-0053 D7 规则 1、2、4、5（同一发生跨 run 不重复提单、baseline 默认不进提单输入、身份无法证明时 fail-open、是否已提单只查长期记录）继续有效。

### D7 S7 选择代表事件

1. 选择记录的范围是「实际 PlanRun × 平台 × 问题」。同一问题在同一分区内只能有一个代表。
2. 选择状态（待选 / 已选）与证据完整度（齐全 / 不全）是两个独立字段。
3. 控制面必须在选择时已知的发生中，选最早出现、且 dblog、mobilelog、bugreport 三件齐全的那个事件作代表。三件必须出自同一个事件，即同一台设备的同一次报错。控制面不得用不同设备的同一问题，或同一设备不同时间点的同一问题，拼凑出三件齐全。
4. 没有齐全事件时，控制面必须让该问题保持「待选」，在后续轮次再选。最后一轮或其后的补充轮仍没有齐全事件时，控制面必须选最早出现的事件，并把该问题同时记为「已选」与「证据不全」。
5. 同一问题再次出现时，控制面必须更新发生记录，不得改选，不得要求补传证据。
6. 控制面写入选择后不得改选，S8 上传失败也不例外。

### D8 S8 证据传输、校验、回执

1. 控制面必须把选择结果回传给持有代表源材料的 Agent。
2. Agent 必须只上传被选中的代表事件。代表的源可以是 Agent 本地原件，也可以是中心已校验的溢出副本；溢出副本作源时，控制面或 Agent 可以在中心侧完成复制，不得要求设备重新导出。
3. 上传、校验与回执沿用 EventUploader 现有链路。上传失败时，Agent 必须重试同一选择，不得新增代表。
4. Agent 在中心校验回执前不得删除源（#1083，I4）。
5. 一个事件目录被多个问题选为代表时，Agent 只能上传一次。
6. 除 D2 第 3 条的 HddSpill 外，Agent 不得在选择结果回传前，把事件证据上传到中心存储。主机报表、伴随映射、统计导出不受此限。

### D9 S9 交付发布与登记

1. S9 有两个动作：登记交付物版本、判定交付状态。
   - 控制面可以在分区任何时候登记交付物版本，供查看与下载；登记本身不表示就绪。
   - 控制面必须按第 5 条判定每个交付物版本的交付状态。
   - 判定的输入来自四处：S5 覆盖结果、S6 统计、S7 选择、S8 回执。控制面不得把「全部代表已有回执」作为判定的唯一入口。
2. 交付物版本必须记录以下内容：
   - 范围：实际 PlanRun、平台、软件版本集合；
   - 依据的轮次集合（最后一轮及已关闭的补充轮）与据此得到的有效覆盖；
   - 收录的问题与事件；
   - 统计快照版本；
   - 未完成项：仍在传输或等待回执的代表；
   - 缺口：有效覆盖中缺失的 (host, 平台)、证据不全的问题、上传终态失败的代表；
   - 对应的主文件夹集合。
3. 代表的证据发布状态（§6）分三种：
   - 已校验：已收到中心校验回执；
   - 重试中：尚未收到校验回执，仍在重试；
   - 失败：重试达到实施方案规定的上限后的终态。
   控制面只能把「失败」的代表记为缺口，不得把「重试中」的代表记为缺口。
4. 分区有效覆盖：对期望集里的每个 (host, 平台)，只要最后一轮或任一已关闭的补充轮收到了它的报表或空回执，控制面就必须把它记为已覆盖。
   - 控制面不得因计算有效覆盖而改写各轮次自身的覆盖记录（D5 第 4 条）。
   - 每个交付物版本按其依据的轮次集合计算有效覆盖。补充轮关闭且 merge 成功后，控制面必须重新计算有效覆盖，并按第 5 条判定新版本。
5. 控制面必须按以下顺序判定交付状态，取第一个成立的结果：
   1. 分区最后一轮尚未关闭，或依据轮次中最近一次 merge 的结果是失败或无输入：**未就绪**。
   2. 有效覆盖为空（期望集全部缺失）：**未就绪**。控制面不得把它包装成零问题的成功结果。
   3. 有任何代表处于「重试中」：**未就绪**。控制面不得因 merge 成功而提前宣布就绪。
   4. 有效覆盖完整，且没有证据不全的问题、没有「失败」的代表：**就绪**。没有问题时，这是有效的空交付物。
   5. 其余情况：**就绪但有缺口**。控制面必须在交付物中列出全部缺口。
6. Agent 必须把代表证据写入以下目录结构：

   ```text
   {证据区根}/
   └── {主PlanRun编号}_{项目名}_{软件版本缩写}_{测试开始时间戳}_MonkeyAEEinfo/   # 每个软件版本一个
       └── {SN}/
           └── {事件目录名}/        # 设备上的原名，形如 {时间戳}_db.{XX}
   ```

   - 证据区根是中心存储下新增的顶层目录，与 `devices/`、`jira/` 并列，名称由实施方案确定并登记到 `storage_families`。
   - 主 PlanRun 是链根（`plan_run.root_plan_run_id`），没有链时是 PlanRun 本身。
   - 同一 PlanRun 内软件版本不一致时，每个软件版本一个主文件夹（Owner 已裁定）。
   - 实施者必须按离线工具 [stability_Offline-MonkeyTestTool](https://github.com/DUElost/automation-toolkit/tree/main/python-tools/stability_Offline-MonkeyTestTool) 的 `_get_aee_log_folder_name` 规则生成 `{项目名}_{软件版本缩写}_{测试开始时间戳}`。该规则从 `ro.product.name`、`ro.build.display.id`、`ro.build.version.incremental`、`ro.build.version.release` 推导。
   - 实施者必须把命名规则实现为按项目可扩展、带版本的规则，新增项目时只能增加规则，不得改已有规则。
7. 主文件夹只是物理分组。任何组件不得用主文件夹推断交付范围，交付范围以 D9 第 2 条的登记为准。
8. 控制面必须为每个交付物版本生成统计导出文件，作为数据库的副本供提单与人工查看。统计导出文件不在原始证据的校验范围内。
9. 事件只有在已通过校验、且已登记进所属交付物后，控制面才可以把它转为 `ARCHIVED`。控制面不得因交付物声明了缺口而把缺口对应的事件归档。
10. 缺口补齐（补传成功、补充轮关闭）后，控制面必须登记新的交付物版本，并保留旧版本的登记。

### D10 S10 提单消费与结果记录

1. 10a 生成清单：控制面可以按 ADR-0012 的策略，针对一个交付物版本生成提单清单。`FAILED` PlanRun 的分区不得自动生成清单或自动发起 JiraRun。
2. 10b 人工复核与建单：人通过厂商工具建单。提单工具必须读取交付物登记的范围，不得扫描整个链根推断归属。提单工具不得在主文件夹内原地写入；需要工作区时，必须复制到独立的可写工作区（沿用 ADR-0053 D5 的隔离原则）。
3. 10c 回写结果：控制面必须在启动提单工具之前登记 JiraRun（沿用 `backend/api/routes/dedup.py` 的先落库后启动顺序，#1084）。工具结束后，控制面必须回写 JiraRun 的执行结果，以及 issue key 与发生的关联。
4. JiraRun「已收口」只表示执行结束，成功与失败必须分别判断。JiraRun 是对交付物的一次消费记录，不是交付就绪的前置条件。

### D11 S11 留存、回收与恢复保护

S11 是独立的控制环，不是某一步的后继。

| 对象 | 保留条件 | 状态 |
|---|---|---|
| Agent 本地原件（未选中事件） | 分区最后一轮关闭后再保留 N 天；补充轮不重新计算 N；I4 保护期间不得回收 | 起算点已定（§10.6）；N 的值待 Agent 本地缓冲测量后裁定 |
| 扫描临时目录（staging） | 报表上送回执后回收 | 沿用现行 |
| 主机报表、merge 报表 | 沿用现行 run 级保留 | 沿用现行 |
| 溢出副本（`devices/{run}/`） | I4 保护期间不得回收；之后按现行 run 级保留 | 已定 |
| 主文件夹与代表证据 | 按整条链清理；清理前必须单独取得 Owner 确认 | 已定 |
| 发生、问题、选择、交付登记 | 长期记录，不随文件回收删除 | 已定 |

1. 在 N 由 Owner 裁定之前，Agent 不得因本 ADR 新增本地删除路径。
2. 控制面必须记录分区最后一轮的关闭时间，作为所有 host 共同的 N 天起算点。Agent 收到关闭通知之前不得回收；离线的 Agent 重新上线后按同一起算点计算。
3. 任何组件不得按单个 PlanRun 删除主文件夹或其中的事件目录。

### D12 平台范围、旧数据与报表格式

1. 本 ADR 只覆盖 MTK。展锐分区沿用现行链路，主文件夹名预留为 `…_MonkeyYloginfo`，由后续批次合入。
2. 旧数据不迁移。运行模式为「现行」的分区继续留在 `devices/` 与 `jira/`。确认已提单后按 run 归档或删除，删除前必须单独取得 Owner 确认。
3. 实施者不得改变主机报表与控制面 merge 报表的 xls 内部格式。需要新增工具参数时，实施者必须先提出并取得 Owner 同意。提单工具一侧做兼容（Owner 已裁定）。

### D13 新旧分区并存（②-1，Owner 已定方向）

1. 运行模式的单位是实际 PlanRun × 平台。链根只用于中心存储的物理分组，不决定模式。
2. 控制面按 D3 第 1 条写入模式后，不得改写。没有模式记录的存量分区，一律按「现行」解释；控制面不得因开关的当前值回读而改写它们。
3. 只有 MTK 分区可以使用「先去重」。同一 PlanRun 的 MTK 分区走新链、展锐分区走旧链时，选择、上传、完成判据、手动操作与失败展示都必须按分区限定。
4. 现行手动 extract 是 run 级接口。对混平台 PlanRun，控制面必须只对「现行」分区执行 extract，不得对整个 run 一律返回 409，也不得把「先去重」分区的 DLE 纳入 extract 输入。只有「先去重」分区的请求，控制面才可以返回 409。
5. 关闭开关只阻止之后的分区进入「先去重」。关闭开关后，控制面与 Agent 必须继续支持已有新格式数据的回执、读取、下载与回收。
6. 新旧并存是过渡状态，退出条件写在 §9 阶段三。实施者不得把两套业务事实作为永久设计叠加。

### D14 交付物取代重复 extract（②-2，Owner 已定方向）

1. 控制面不得对「先去重」分区执行 extract。该分区的交付物是 D9 登记的交付物，内容包括已校验的代表证据、统计导出与缺口。
2. 本条修订 ADR-0012 的交付出口：「先去重」分区的唯一交付路径是 D9 交付物 + JiraRun；「现行」分区的交付出口不变。
3. 本条修订 ADR-0032 D10 的 `ARCHIVED` 含义：事件已登记进所属交付物，且对应证据已通过校验。「现行」分区由 extract 写入，「先去重」分区由 S9 写入。
   区分依据是分区的运行模式，不是平台。`ARCHIVED` 不表示报表覆盖完整、三件齐全、全部问题处理成功或已经建单。
4. 提单适配属于 D16 的消费方就绪。实施者必须在任何分区写入新格式数据之前完成提单适配，不得放到之后补做。

### D15 FAILED 与受控兼容补跑（②-3，Owner 已定方向）

1. PlanRun 为 `FAILED` 时，控制面必须照常执行最后一轮、代表上传与交付发布，以保存事故证据。本条修订 ADR-0028 D2 与 ADR-0032 D7 中「FAILED 自动跳过 merge」的规定；该修订只适用于「先去重」分区。
2. `FAILED` 分区不得自动生成提单清单，也不得自动发起 JiraRun；人工查看、下载以及明确触发的清单与建单保留。
3. 扫描、merge、上传失败属于日志处理失败，按 D4–D9 各自的出口恢复。控制面不得因 PlanRun 已失败而停止恢复，也不得因此宣布交付完成。
4. 关闭开关、代码回滚、受控兼容补跑是三个不同的动作。关闭开关本身不是数据回退。
5. 受控兼容补跑由 Owner 对单个「先去重」分区发起，对该分区额外生成一份现行格式的产物。实施方案必须给出：
   - 源材料：Agent 本地原件，或中心已校验副本；
   - 覆盖范围；
   - 独立的结果登记；
   - 幂等：不重复计数（I1）、不重复建单、不覆盖新交付物的权威。
6. 兼容补跑不得通过把 DLE 回写为 `LOCAL` 来驱动。
7. 补跑只能覆盖仍在保留期内的本地子集时，结果登记必须列出缺失清单与非全量声明。

### D16 消费方就绪

1. 阶段二打开任何分区的「先去重」开关之前，实施者必须让下表所列消费方全部能处理「先去重」分区，并在阶段一用影子数据验证。

   | 消费方 | 「先去重」分区下的行为 |
   |---|---|
   | `backend/core/artifact_paths.py`（`resolve_device_event_remote_path` 只认 `devices/`） | 增加证据区根的校验路径，`devices/` 规则不变 |
   | DLE 回执白名单（`backend/services/agent_device_log_events.py`） | 接受证据区根下的 `remote_path` |
   | DLE 下载、产物下载（`device_log_event_download.py`、`plan_run_artifact_download.py`） | 能从证据区根下载；交付物可下载 |
   | extract、手动 extract 接口、`extract_bundle` | 按 D13 第 4 条只作用于「现行」分区 |
   | JiraRun 与提单工具 | 读取交付物登记范围（D10） |
   | `auto_archive_sweep` 归档完成判据（现为 merge + extract） | 「先去重」分区改为交付状态为「就绪」或「就绪但有缺口」（D9 第 5 条） |
   | 前端 `PlanRunDetailPage`、`DedupReportCard`、`LogEventsCard` | 按分区显示运行模式、轮次覆盖、问题清单、交付物与缺口 |
   | `storage_families` 与清理任务 | 登记证据区根；按 D11 以链为清理单位，遵守 I4 |
   | 未归属事件认领 | 认领后进入所属分区的期望集 |
   | `measure_center_storage` | 统计证据区根 |
   | HddSpill（`local_disk_monitor.py`） | 按 D2 第 3 条与 I2 |
   | 报表 Path 重写与按 basename 查 DLE（`backend/services/dedup_scan.py` 的主机 Path → `devices/` 映射与发布时重写） | 改为使用 D4 第 3 条的伴随映射；不得沿用路径重写推断身份或落点 |
   | 手动 merge 接口（`backend/api/routes/dedup.py` 的 merge 路由） | 遵守分区模式、轮次与幂等（D3、D6） |
   | 上传汇总、状态查询与类型（`device_log_event.py` 的汇总、`saq_tasks.py` 的上传汇总写入、`dedup.py` 的状态路由、`api/schemas/dedup.py`、`frontend/src/utils/api/types.ts`） | 按分区返回 §6 的状态 |
   | PlanRun 能力目录（`backend/services/plan_run_catalog.py`） | 按分区模式给出可用操作 |

2. 上表是现有清单的分组，不证明调用点已经穷尽。实施者必须沿生产方到消费方核对全部调用点，发现遗漏时在 PR 中登记，并在打开开关前处理完毕。

## 6. 状态拆分

| 状态 | 单位 | 取值 | 写入环节 |
|---|---|---|---|
| 报表覆盖 | 轮次 × (host, 平台) | 收到 / 空回执 / 缺失 / 迟到 | S5 |
| merge 结果 | 轮次 | 成功 / 失败 / 无输入 | S6 |
| 代表选择 | 分区 × 问题 | 待选 / 已选 | S7 |
| 证据完整度 | 分区 × 问题 | 齐全 / 不全 | S7 |
| 证据发布 | 代表事件 | 已校验 / 重试中 / 失败 | S8 |
| 交付就绪 | 交付物版本 | 就绪 / 就绪但有缺口 / 未就绪 | S9 |
| Jira 执行 | JiraRun | 沿用现有状态；收口后分别判断成功与失败 | S10 |
| 保留 | Agent 本地原件、溢出副本 | 保护中 / 可回收 / 已回收 | S11 |

实施方案不必为每项新建状态机。界面和判据不得用一个 `ARCHIVED` 或 `FAILED` 包办上述状态。

## 8. 放弃的备选

| 备选 | 结论 | 理由 |
|---|---|---|
| 保持先上传后去重，实施 ADR-0053 内容寻址 | 否决 | Run 1096 最多省 19%，本 ADR 的顺序调整省 96.6%（待影子运行复测） |
| 只做主机汇总就上传 | 否决 | 6.4% 对 3.4%，且跨 host 的同一问题仍会重复上传 |

第 3 项的沿革（Owner 2026-11-02 补充，规划者对证）：

1. ADR-0025 D4 归档-1 原定中心只接收三类内容：汇总报告、报告中 db 对应的事件目录、溢出事件目录。设计原意是按需上送。
2. 实施中「按需」的单位落在事件上。主机报表列出本机全部 db 事件，`upload_task` 按报表 `Path` 标记上传，上送集合因此接近全量。Run 1096 中心收到 803 个事件目录、110.72 GB；每个问题只传一份代表时只需 25 个目录、3.80 GB（§1.2）。

## 11. 走查场景（阶段一验收）

1. 同一设备在两轮各新增一次同一问题：次数 2、机器数 1；重复提交第二轮报表，结果不变。
2. 一个事件承载两个问题：保留两条问题映射，证据目录只上传一次。
3. 一个问题三件不齐：先待选；最后一轮选同一事件并标证据不全，不跨事件拼凑。
4. 首次扫描前发生 HddSpill：该事件仍可被扫描、计数、选为代表；之后本地清理不使累计次数下降。
5. host 正常空回执、host 离线无回执、merge 失败：三者得到不同且可解释的结果。
6. 最后一轮部分关闭后报表迟到：补充轮启动，所需材料受保护；N 天到期后无法恢复的部分列为缺口。
7. 同一 run 中 MTK 走新链、展锐走旧链：手动 extract 只作用于旧分区，两种交付都能定位；一侧失败不伪装成另一侧失败。
8. 链上两个 run、多个软件版本：共享父目录不串交付范围；处理子 run 不误删链上其他证据。
9. 代表已选但上传回执失败、Agent 重启：仍重试同一代表，发布不假绿，源材料未被误删。
10. 已 `ARCHIVED` 或 `PRUNED` 的代表做兼容补跑：不靠回写 `LOCAL` 驱动；新旧交付都有明确记录，不重复计数、不重复提单。
11. PlanRun `FAILED`：证据处理继续，自动 JiraRun 被拦住，人工路径可用。
12. 零问题且期望集全部明确回执：形成有效空交付物；全体无回执不得包装成零问题。

## 12. 复议触发

- 影子运行中，问题数、跨轮问题映射、发生映射或累计统计与现行 merge 不一致。
- Agent 本地缓冲测量显示 D11 的保留期无法放下单个 PlanRun 的全部事件。
- HddSpill 溢出字节在单个 PlanRun 内超过代表证据字节。
- 展锐合入时，主机汇总工具的报表形态无法满足 D4。
