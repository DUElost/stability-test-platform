## 1. 产品定义与范围

已确认的架构方向为：**同一套平台产品，在多个机房内网形成独立运行的站点，使用统一交付物和运维流程**。
新增城市应主要增加站点配置，而不是复制一条代码分支、修改源码中的地址，或克隆城市 A 的业务数据库。

已明确：每地有自己的控制平面、日志服务器、Host 主机和 Devices；需要便利地从零安装与持续运维。
2026-09-14 用户确认独立站点架构，并接受各站点按现有入口与账号体系开设作为基线，同时要求比较更便捷的管理方式。
同日用户进一步确认：暂不考虑 SSO，接受轻量导航、统一交付运维及只读运维总览；这些能力纳入分期交付，不再作为待选建议。
同日补充平台基线：各节点均为 Linux、CPU 架构一致，发行版可能为 Debian 13 或 Ubuntu；实际 CPU 架构标识与 Ubuntu 版本仍未确定，不将“同架构”解释为系统包/venv/二进制可直接通用。
尚未明确：站点之间是否互通、是否完全离线、维护停机窗口，以及总览的连通、采集与访问控制细节。
只读总览不作为开设新站点的前置条件；SSO 和跨站点写操作不纳入当前范围。

三个能力必须分开评审：

| 能力 | 解决的问题 | 本需求建议位置 |
|------|------------|----------------|
| 多站点交付 | B、C 能独立安装、执行测试、维护升级 | 首期主体 |
| 单站点多控制面实例 | 一个机房内部的容量、可用性、滚动发布 | 复用 ADR-0027，按实际需求开启；不是增加城市的前置条件 |
| 跨站点管理 | 统一导航、只读运维总览 | 已确认，按阶段交付；账号与授权仍在各站点，SSO/跨站点写操作不在当前范围 |

“从零”首期建议以**已安装受支持操作系统的空白服务器**为起点，包含平台及依赖安装、存储接入、Agent 上线和首个专项验证。
操作系统装机、BIOS、交换机和设备物理接线需有准备清单，但是否自动化裸机装机另行确认。

## 3. 建议拓扑与边界

```text
统一发布产物 / 安装介质（可通过内网镜像或离线转运分发）
        │                    │                    │
        ▼                    ▼                    ▼
     城市 A 站点           城市 B 站点           城市 C 站点
     控制面 + UI           控制面 + UI           控制面 + UI
     本地 PostgreSQL       本地 PostgreSQL       本地 PostgreSQL
     本地 Redis            本地 Redis            本地 Redis
     本地中心存储          本地中心存储          本地中心存储
     Host → Devices        Host → Devices        Host → Devices
```

- 一个站点是一组角色，不是一台服务器；首个标准拓扑覆盖独立控制服务器、日志服务器及多台 Agent Host。
- PostgreSQL 在各站点分别承载业务事实；不跨城市共用数据库、Redis 队列、设备租约或 NFS/CIFS 挂载。
- 测试调度、设备控制、日志第一落点和归档均在本机房。跨城链路或发布服务不可用，不应成为本地执行的依赖。
- “日志服务器”沿用现有中心存储角色；不把全量原始运行日志改为跨城实时集中上传，保留 Agent SSD/HDD 与中心存储分层。
- 发布服务不是运行控制面；各站点可以在经过验证的版本兼容范围内分别选择升级时间，不要求 A、B、C 同时更新。
- 已确认建设轻量站点目录及只读运维总览，展示获授权的版本、健康、备份时间与异常摘要，标注数据时间和离线状态；它不是业务事实源，也不能绕过站点授权。SSO、跨站点写操作和业务数据同步不纳入当前范围。

引入稳定的部署级 `site_id` 和显示名称作为建议设计：标识不依赖 IP、安装路径或城市显示名。
本地 Host/Device/Job 的现有身份语义保持不变；未来汇总可使用 `(site_id, local_id)` 区分，不为此给所有业务表预加区域列。
该元数据及对外接口的具体落点由后续 ADR/设计确认，当前不存在相应运行时配置承诺。

### 3.1 独立运行不等于只能分散管理

**已确认组合：独立站点 + 本地账号 + 轻量导航 + 统一交付/运维规程 + 分期建设的只读总览。**
账号沿用站点本地用户名/密码、管理员用户管理及本地 Cookie 会话。
统一导航和总览不要求统一登录；SSO 当前明确不做，不预建相关接口或改动账号模型。

| 层级 | 解决什么 | 成本与前提 | 已确认安排 |
|------|----------|------------|------|
| L0：独立入口与账号 | 各城市自行开设、授权、使用 | 最少新增能力；跨站点人员需分别授予/回收权限 | 已可接受的首期基线 |
| L1：站点目录/快捷导航 | 找入口、识别目标站点、找到负责人和运维文档 | 可复用现有内网页或受控书签；只保存允许展示的站点信息，不存密码/token；用户须能到达目标内网 | 已接受，随 P1 交付；不强制新建后台服务 |
| L2：只读运维总览 | 一处查看版本、健康、备份时间与异常摘要 | 需要被授权的数据通道、逐站点最小权限和数据时效标记；会新增运维责任 | 已接受，在 P4 交付；不阻塞 P1/P2 的独立站点闭环 |

导航无需等待总览，优先复用既有工具。只读总览虽然较后交付，仍是本需求的已确认范围，不能在完成独立安装后被遗漏。
SSO 不安排选型、集成或验收；未来仅在用户重新提出需求时另行评审。统一管理不意味着业务数据集中或自动获得其他站点权限。

管理层边界：

- 导航只跳转，各站点照常登录；不通过 URL 传凭据、不共享 JWT 密钥、不扩大 Cookie Domain。优先用不同站点主机名；同一主机的不同端口不能作为 Cookie 隔离。
- 导航不能替代授权 VPN/堡垒机等连通方案；站点完全隔离时保留本地入口，版本/健康可通过获准的脱敏离线报告盘点，不伪装实时总览。
- 只读总览应显示采集时间、过期/未知/不可达状态；使用逐站点最小权限，不复用 Agent 共享密钥或超级管理员凭据，不复制完整业务库与原始日志。
- 统一运维首先是同一发布物、预检/升级/恢复规程和逐站点执行记录，而不是“一个按钮无条件升级全部城市”。当前不建设中央写操作，各站点维护仍须站点授权、升级门禁、灰度、维护窗口和审计。
- 人员离职或权限变动必须逐站点核销；同名用户不等于同一身份，不能假定修改 A 的账号会同步其他站点。
- 总览自身的访问控制与站点摘要读取授权必须明确，不能依赖共享管理员账号或鉴权失败时放行；只读权限不能扩张为任务下发、升级或账号修改权限。

## 4. 功能需求（分期交付）

### R1. 一份站点配置，运行时沿用现有契约

- 统一描述站点标识、访问域名、安全 profile、角色部署目标、部署根、存储角色、时区/时间同步、发布版本和依赖来源。
- 推荐以受校验的站点配置文件作为安装输入，渲染已有环境文件和服务模板，而不是增加第二套运行时配置系统。
- 将通用发布物、站点非敏感配置、秘密材料和运行数据分离；真实地址清单及秘密不打入通用包或仓库样例。
- 新站点生成自己的凭据、会话签名材料和管理员引导信息；不得复制 A 的 `.env`、Agent 状态目录或整库来实现“快速安装”。
- 配置更新先显示脱敏差异；重复安装/升级不得重建有效密钥、改写主机身份，或覆盖经过允许的本地磁盘差异。
- 初次接入配置不替代数据库中的 Host/Device 业务事实。业务模板若需复用，只允许明确的定义导入，不携带运行历史和身份绑定。

### R2. 可追溯、可离线转运的发布交付物

- 同一产品发布覆盖经验证的 OS/CPU 组合；已知各节点架构相同，但 Debian/Ubuntu 系统包、Python ABI 与本地工具仍需分发行版/版本验证和打包。首期冻结实际需要的有限支持矩阵，不承诺任意发行版，也不直接跨发行版复制 venv。
- 覆盖后端、前端静态产物、Agent、pipeline schema、已发布脚本、迁移、安装工具，以及依赖锁定信息。
- 发布清单记录产品版本、已合入 `main` 的来源 revision、内容校验信息、数据库 schema 目标、Agent 协议兼容范围和工具依赖；前端产物与 Nginx root 对齐。
- 安装端能验证发布来源和完整性；离线交付不能成为绕过现有部署源守卫的途径。包及校验元数据的信任来源须在设计中明确。
- 运行期不依赖 GitHub、npm 或公共 pip 源；离线安装路径需预备系统包/Python 依赖，不能只把源码压缩后称为离线包。
- 第三方工具、驱动、固件和许可逐项声明“可随包分发/需现场预置/不可离线使用”；沿用 [ADR-0033](../adr/ADR-0033-tool-kit-ecosystem-integration.md)，不顺带重建所有外部工具的包管理。

### R3. 可预检、幂等、可诊断的安装入口

以一个运维入口组织已有工具，提供预检、安装、状态和诊断操作；名称与实现形式待设计，不表示仓库已有这些统一命令。

1. **预检**：OS/架构、权限、端口、DNS/时间、必要包、磁盘与目录、存储分享身份、API/SSH 可达性；区分必需依赖与可选集成。
2. **准备**：创建受限服务账号及目录、验证秘密、渲染模板；对已有安装先识别身份与数据，不直接初始化覆盖。
3. **控制面**：明确目标数据库后迁移/初始化最小数据，安装前端及反代，完成管理员安全引导；失败不得展示整体成功。
4. **存储**：配置或接入已声明的分享，校验挂载身份和权限；挂载丢失不能静默退化成写本机同名目录。不得自动格式化已有数据盘。
5. **Agent**：复用已有安装/注册与版本校验，验证本地 ADB 和设备发现；保持 `HOST_ID`、`API_URL`、本地路径等受保护配置语义。
6. **验收**：检查登录/CSRF、WebSocket、调度与 Agent 心跳、脚本目录一致性、存储读写及一条受控专项链路，输出逐项结果与修复建议。

失败后能定位到站点/角色/阶段并安全重试。重复执行不重复注册主机、重置管理员或破坏数据。
通过 `/health` 或 systemd 显示 active，只能作为部分证据，不能代替安装验收。

### R4. 站点内安全更新与可判定回退

- 记录当前版本、目标版本、配置/schema 兼容性及允许的组件混跑组合；不默认任意两个版本都能互通。
- 复用现有 Host 升级门禁和灰度批次：活跃任务默认拒绝/跳过升级，不自动 abort；不得绕过刷机等关键操作的安全条件。
- 遵循现有“Agent 支持先就绪，再提高最低协议门禁”的顺序；不兼容变化需要兼容过渡版本或明确维护方案，不能靠强制跳过校验。
- 文件下发不等于新进程生效；包含 schema 的更新按现有契约重启 Agent，并核对心跳 revision、脚本/schema 一致性及恢复状态。
- 控制面更新明确维护窗口、停止新调度、活跃任务处置与恢复验收；首期不承诺零停机，也不能推断控制面停机后 Agent 可无限离线续跑。
- 更新前验证备份与目标发布物；迁移失败不得继续启动不匹配版本。保留可恢复的旧产物及配置，失败停止扩大批次。
- 区分“应用回退”和“数据恢复”：旧应用能否读取新 schema 必须有证据，不把切换旧代码或 `alembic downgrade` 当作通用回滚保证。

### R5. 备份、重建与运维交接

- 备份范围包含数据库、站点配置、发布版本记录、受保护的秘密恢复材料以及必要的中心存储文件；按现有日志分层另列 Agent 本地数据的恢复/保留边界。
- 明确数据库与文件备份的一致性窗口，备份副本不能仅留在被保护的同一台服务器/同一块盘；访问控制、保留和加密策略随部署交付。
- 用空白隔离环境恢复并验证关键业务读取、文件引用及可恢复能力，不能只验证压缩包存在或 SQL 导入退出码。
- 灾难恢复保留原站点身份；创建 B 这样的新站点必须生成新身份。恢复副本不得与原站点同时连接同一批真机。
- 恢复后的租约、Agent LocalDB/outbox 和运行中任务要按[执行协议](../design/07-execution-protocol.md)与[数据库维护流程](../operations/control-plane-db-maintenance.md)核对，禁止盲目重放硬件操作。
- 提供版本/依赖/容量/备份时间的运维摘要及默认脱敏的诊断导出；不自动收集 token、连接串、私钥或完整主机清单。

### R6. 站点安全与外部集成

- 默认推荐 HTTPS；`production` 与 `internal` 均保留受限 SameSite、CSRF 等要求。internal 无 TLS 的 Secure 豁免仅按 [ADR-0024](../adr/ADR-0024-browser-session-security-hardening.md)现有边界使用，不能推广成“内网不需要安全”。
- 凭据按站点隔离、最小授权；管理页面与运维操作明确显示目标站点，避免管理员在相似界面操作错站点。
- 在方案评审中核对 [ADR-0035 §6](../adr/ADR-0035-agent-host-identity.md#6-升级触发条件trigger)：若新网段/运维团队使受信管理域失效，或要求主机级审计归属，按既有裁决启动主机独立凭据实施，不能借“多站点复制”延后。
- 各站点分别声明 JIRA、通知、AI 等外部依赖是否启用及其可达性；跨城断网/公网断网时，本地核心测试不依赖它们，相关外部操作应清晰降级或失败，不能声称离线时仍可完成外部提单。

### R7. 轻量导航与只读运维总览

- 导航提供获准展示的站点名称、入口、负责人及运维文档；直接进入本站现有登录页，目标站点标识清楚，导航故障不影响原地址访问。
- 总览仅展示已授权的版本、健康、备份时间及异常摘要，每条摘要带站点身份、采集时间与时效状态；断链不能把历史健康值当作当前健康。
- 明确总览访问者权限、各站点摘要授权与数据最小化；不复制用户密码、完整业务库或原始日志，不增加跨站点写操作。
- 采集方式及服务部署位置依网络与安全设计确定，不能假定站点互通；该技术设计待完成，不改变“总览已纳入范围、站点不依赖总览运行”的边界。

## 5. 必须保留的原有优点与不变量

- 不改变 Plan → PlanRun → Job 的业务主链；保留 Pipeline 顶层 `lifecycle`、`script:<name>`、设备租约/fencing、Watcher、去重与归档契约。
- ASGI 仍采用既有 `socketio.ASGIApp(sio_server, fastapi_app)` 入口；Redis 仍只承担队列与瞬时通信。
- 不修改已发布脚本版本及其 `default_params`；发布物完整携带需要支持的版本，不借打包进行原地改写或退役。
- 不把城市 B 的安装建立在城市 A 的持续在线之上；不要求 A 先搬机、迁库或切换存储。
- 保持单站点默认简单、小规模可运维；统一入口不能成为唯一运行依赖，站点不可达时必须保留独立维护路径。
- 不承诺跨城容灾自动接管真机或统一强一致数据库；单站点 HA、跨站点调度和全文集中日志检索不因本需求自动进入首期。

## 6. 开发分期与出口

| 阶段 | 交付范围 | 进入下一阶段的证据 |
|------|----------|--------------------|
| P0：范围与裁决 | ADR-0041 v1.1 已确认独立站点、本地账号及非 SSO 管理范围；继续确认网络/OS/存储支持矩阵、安全触发、维护窗口、恢复目标及总览访问控制 | 范围确认不等于 P0 完成；剩余输入及 A 安装/升级/恢复基线仍待确认/记录 |
| P1：新站点最小闭环 | 站点配置校验、固定版本交付包、依赖准备、控制面/存储/Agent 安装与验收，交付可复用既有内网页的轻量导航 | 隔离的 B 等价环境从空白 OS 跑通首个专项；无源码地址改动、无 A 数据/凭据复制；导航通过 MS-13 |
| P2：可持续运维 | 版本兼容检查、灰度升级、失败停止、应用回退条件、备份恢复与诊断 | 两个真实发布版本的升级演练及故障注入；独立环境恢复通过；完成运维交接 |
| P3：推广与兼容收口 | B 小规模试点，再用同一发布物和另一份配置部署 C；评估 A 接入统一运维 | B/C 独立运行证据；A 保留功能回归通过，接入失败可保持原运行方式，不长期维护城市分支 |
| P4：只读运维总览 | 交付站点版本、健康、备份时间及异常摘要总览；与本地账号及站点授权边界对齐，不引入 SSO/跨站点写操作 | 经确认的采集与访问控制设计落地，MS-14/MS-15 通过；故障不影响站点独立使用 |

P1 不能作为“已完成多站点产品化”的终点，P2 的维护与恢复能力是本需求的必要部分。
当前进度仅为 P1/I1：显式站点配置的安全读取、脱敏校验与合成测试已落地；发行版适配、发布计划、远端安装、导航及真机验收仍待实施。MS-01–MS-15 不因 I1 单元测试通过而标为通过。
P4 只读总览也已被用户接受为交付范围；允许分阶段验收，但不能把“后续阶段”重新解释为未获批准或可默认不做。
如果 A 暂时沿用现有安装流程，这只是推广过渡：出口为 P2 验证完成且 A 维护窗口获批后，经兼容接入统一交付；不得形成长期专属分支。
安装/更新耗时、人工干预次数、RPO/RTO 先实测并与用户冻结目标，不在未知机器和网络条件下承诺固定分钟数。

建议实现分片围绕依赖关系展开：发布产物与元数据 → 配置/预检 → 角色安装 → 生命周期运维 → 验收与操作文档。
优先复用 `deploy/control-plane/`、`tools/prepare_env.py`、`tools/ansible/`、现有 Agent 更新服务和备份脚本；具体改动文件在各实施单检查代码后确定。

## 7. 验收标准（全部待实施验证）

| ID | 场景 | 通过标准 |
|----|------|----------|
| MS-01 | 全新安装 | 受支持 OS 的空白控制服务器、日志服务器、Agent Host 完成安装；非原作者按交付指南接入受控设备并完成主链，不改源码 |
| MS-02 | 同包复用 | 同一发布物用于 B、C，只更换站点输入；版本可识别，没有 A 的数据库记录、秘密或机器状态泄入 |
| MS-03 | 断网隔离 | 断开站点间/发布源链路但保留站点 LAN，本地已安装核心能力正常；外部集成状态诚实，站点间故障不串扰 |
| MS-04 | 幂等与失败前置 | 重跑安装不重置身份/密钥/数据；无效配置、缺包、校验失败或错误挂载目标在破坏性步骤前失败 |
| MS-05 | 受限网络交付 | 按约定网络 profile，仅靠已声明的介质/镜像和预置依赖安装；完全离线是否必选在 P0 冻结，不暗中访问公网下载 |
| MS-06 | 完整主链 | 登录/CSRF、SocketIO、Plan/claim、设备租约、脚本门禁、Watcher、日志/scan/upload/merge 在隔离环境通过；可选外部提单使用专用测试目标 |
| MS-07 | 安全灰度 | 活跃 Job 不被默认升级中断；新旧允许组合可执行；更新失败停止扩批，实际进程版本与上报一致 |
| MS-08 | 迁移与回退 | 空库及受支持旧 schema 的迁移在隔离数据库验证；失败不启动错误组合；可回退/须恢复的边界有实测证据 |
| MS-09 | 灾难恢复 | 在与真机隔离的环境恢复数据库/配置/必要文件；验证引用与任务恢复处置，记录数据损失窗口与耗时 |
| MS-10 | 安全与可辨识 | 无默认弱口令/明文秘密输出、SSH 不关闭主机校验；站点凭据隔离；管理员明确识别目标站点 |
| MS-11 | A 的兼容性 | 现有单站点部署不因新站点功能被迫变更；既有主链、性能/长跑稳定性和日志分层按基线回归 |
| MS-12 | 运维可移交 | 非原开发者能完成版本查看、预检、一次升级及恢复演练；报告阶段结果而非只报告命令成功 |
| MS-13 | 轻量导航（P1） | 站点与入口可辨识、跳转不传凭据；导航不可用时各站点原地址仍可独立登录使用 |
| MS-14 | 只读总览（P4） | 版本/健康/备份/异常摘要带站点及采集时间；断链后显示过期/未知，不误报当前健康；总览故障不影响本地核心能力 |
| MS-15 | 总览权限隔离（P4） | 未授权者不能读取站点摘要，跨站点角色不因同名账号而继承；摘要读取凭据不能下发任务、升级或修改账号；不依赖 SSO |

自动化验证使用一次性 VM/容器、独立数据库/端口/目录和合成配置；不得读取生产 env 或真实主机清单来组装测试环境。
安装、迁移、恢复与故障注入均禁止在现有生产宿主/业务库上试跑。
既有单元测试只能验证已有工具的局部契约，不代表 MS-01 至 MS-15 已通过。

## 8. 需要用户确认的输入

1. **管理落地条件**：导航、统一运维和只读总览已确认；现有内网页可否复用、谁能访问总览、允许展示哪些站点摘要，以及总览部署/采集的授权边界？SSO 不再列为待选问题。
2. **网络边界**：站点是否互通、能否访问公司镜像/公网，是否要求完全离线安装；JIRA 等服务在哪里、由谁授权？
3. **标准硬件环境**：Linux、同 CPU 架构、Debian 13/Ubuntu 已确认；仍需实际架构标识、Ubuntu 版本、逐角色发行版、Host/Device 规模与日志容量，以及日志服务器使用受管 Linux 分享还是既有分享、是否需要自动裸机装机。
4. **连续性目标**：可接受维护窗口、长跑作业如何避让，以及 RPO/RTO；是否真的要求站点内零停机？
5. **运营信任与复用**：各城市是否同一运维/权限边界，是否有主机级审计要求；脚本之外哪些业务定义必须复用，哪些数据禁止跨站点？

本 PRD 用于收敛需求和拆实施单；已确认边界以 ADR-0041 v1.1 为准，剩余交付输入及管理技术设计仍待评审，不据此直接改写现行身份或执行协议。
